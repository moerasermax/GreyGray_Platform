## 我發現但沒做的事

1. **單一品項取消端點沒有做真環境端對端，只有單元測試層級**。
   `POST /v1/orders/{orderId}/lines/{lineId}/cancel` 要跑真環境得先有 `ordering.order_line`，
   而回應投影 `ToAdminOrderAsync` 會用 `catalog.GetSkusAsync` 去查 SKU——開發環境
   `catalog.sku` 是 0 筆，補一筆 SKU 就得連 product／category 一起補。兩處守衛的程式碼
   一字不差、刪法相同，改寫後的測試打的正是這個端點（`CancelOrderLineAsync`），
   所以我判斷不值得為了投影那一段去汙染開發環境的目錄資料。**要更硬的證據就得先補目錄種子資料**，
   那超出這一包的所有權（`ops/seed/` 是 BE-26 的）。

2. **E3 仍然是這條路上唯一的阻塞，而且它現在的症狀是「500，不是 422」**。
   目前跑在 5001 的 admin Host 對 `/v1/orders/{orderId}/cancel` 會在**端點參數 DI 解析**
   就丟 `缺少綠界設定 'Payment:ECPay:MerchantId'`（`ModuleRegistration.cs:140`），
   連端點本體都進不去。也就是說**在真憑證投遞之前，後台這個按鈕仍然是壞的**，
   只是壞的理由從「BE-30 的守衛」換成了「E3 缺設定」。進度表如果要把
   「已付款訂單取消不了」標成解決，這一句要寫清楚，否則下一個人會再繞一次同樣的路。
   我沒有把綠界測試代號寫進 `D:\GreyGray\secrets`（那是 BE-25 建好的投遞管道，不歸我），
   只在那個暫時行程的環境變數裡用過。

3. **`docs/11-M1a補漏派工書.md:95` 還記著 `payment.original-refund-not-configured` 這個
   已經不存在的 error code**。那是歷史派工書，照 CLAUDE.md 的分類屬「歷史脈絡」，
   我沒有去改。要不要在 `docs/05-API契約.md` 或 ADR 補一句「這個 code 已在第十四波移除」，
   是整合者的判斷。契約文件本身沒有列過這個 code（grep 過），所以**不算契約變更**。

4. **手動打這組 admin 端點有兩個會絆人的地方，值得寫進 runbook**（FE-12 重跑時會遇到）：
   ① 路徑上的 id 是 `Guid.TryParseExact(raw, "N")`——**不能帶連字號**，帶了會回
   `404 ordering.order-not-found`，看起來像「查無此單」，其實是格式沒對；
   ② 登入發的 `gg_admin_session` cookie 帶 `secure`，所以 .NET／curl 走 http 時
   cookie container 不會自動送，得手動塞 `Cookie:` header，否則會拿到 `401 auth.unauthorized`。
   兩個都不是 bug，但都會讓人誤判。

5. **閘門的坑：`ACTIVE.md` 的生效區塊只要被圍欄包住，整個閘門就靜默退回整合者模式**
   （見 §0）。`gg_active_packages` 回空時，`claim-package.sh` 只印一句 note 就放棄綁定，
   而 `audit-dispatch.sh` 與 `selftest.sh` 在「零個生效包」時本來就會直接跳過——
   也就是**沒有任何一支檢查會說話**。這正是 CLAUDE.md 講的「查了零個對象跟查過都沒事長得一樣」
   那個家族的新成員：`ACTIVE.md` 有 `package:` 字樣但被圍欄吃掉時，值得印一句
   ⚠ 而不是安靜地當成整合者模式。閘門檔只有 Leader 能改，所以我只回報，沒有動手。
