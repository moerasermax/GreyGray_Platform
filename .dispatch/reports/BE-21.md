## 我發現但沒做的事

**1. 帳務相關的既有 bug（`Ordering.Core`，不在 BE-21 allow，沒有動）——建議優先處理**

`src/Modules/Ordering/GreyGray.Modules.Ordering.Core/Order.cs:206`，`CapturePayment` 裡：

```csharp
PaidAmountMinor = amount.AmountMinor;
PaidCurrency = amount.Currency;
RefundedCurrency = amount.Currency;   // ← 這一行
LastPaymentFailureCode = null;
```

每一筆訂單完成付款時，`RefundedCurrency` 就被設成非 null（`RefundedAmountMinor` 仍是 0，
根本還沒有任何退款）。`db/migrations/0006_m1a_core.sql` 的
`orders_refunded_consistent` check constraint 規定「金額 0 就必須幣別 NULL，否則两者都要有值」，
所以這一行會讓**任何一筆完成付款的訂單**，在真正套用 migration 的資料庫上寫入時
直接炸 `23514`（check constraint violation）。

**怎麼發現的**：本包 §4 的端對端測試一開始用 `db/migrations` 的原始 SQL 建 schema
（比照 `GoodsReceivedInventoryTests.cs` 的做法），第一次 `CapturePayment` 之後
`SaveChangesAsync` 就直接丟 `Npgsql.PostgresException: 23514 orders_refunded_consistent`。
用 `Include Error Detail=true` 印出失敗列逐欄位比對後確認：`refunded_amount_minor=0`
但 `refunded_currency='TWD'`。

**為什麼現有測試都沒抓到**：目前所有會呼叫 `CapturePayment` 的 Ordering Postgres
整合測試（`OrderingOutboxIntegrationTests.cs`、`M1b3SeamsPostgresTests.cs` 等）都用
`dbContext.Database.EnsureCreatedAsync()` 建 schema——那是照 EF model
（`OrderingDbContext.OnModelCreating`）產生 DDL，而 `orders_currency_consistent`／
`orders_paid_consistent`／`orders_refunded_consistent` 這三條 check constraint
**只存在於 migration 的原始 SQL，EF model 裡沒有對應的 `HasCheckConstraint`**。
所以從來沒有一個 Ordering 整合測試是在「真的套過 migration」的資料庫上完成過付款。

**衝擊面**：BE-22 一旦把本機環境接上真的 migration（`ops/invoke-migrations.ps1` 套
`0001`～`0014`），FE-12 對真後端跑第一個「結帳付款」流程大概率就會在這裡炸掉——
這是 D 階段第一步就會踩到的坑，不是邊角案例。

**沒有動它的原因**：`Ordering.Core` 不在 BE-21 的 `allow`（`docs/19` 明講
「不必改 Ordering.Core……而且 Core 不在你的 allow」），閘門也會擋下對它的寫入。
這是單行、看起來像複製貼上打錯的 bug，但改不改、怎麼改屬於下一包或整合者判斷，
不是我能單方面決定的範圍。

**為了讓本包自己的端對端測試能跑**：改用 `dbContext.Database.EnsureCreatedAsync()`
（比照其他既有 Ordering 整合測試的作法）而不是套 `db/migrations` 的原始 SQL，
理由與取捨寫在 `OrderingGoodsReceivedHandlerTests.cs` 頂端的 `<remarks>`。
這代表本包的端對端測試驗證了「DI 接線 ＋ 冪等 ＋ outbox」，但**沒有**驗證
「在真正套過 migration 的 schema 上」——因為現在還做不到（訂單付款這一步就會先炸）。
