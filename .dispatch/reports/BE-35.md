## 逐條自驗

### 必做 1　`BffHttp` 加兩階段多載

✅ `src/Platform/Http/BffHttp.cs` 新增

```csharp
public static async Task<IResult> ExecuteIdempotentAsync<TState, TResponse>(
    HttpContext context,
    IIdempotencyStore idempotency,
    string scope,
    object? request,
    Func<CancellationToken, Task<Result<TState>>> work,
    Func<TState, CancellationToken, Task<TResponse>> render,
    int successStatus,
    CancellationToken cancellationToken)
```

四條語意逐條對應到程式碼：

| 語意 | 實作 |
|---|---|
| ① `work` 回 `IsFailure` → `AbandonAsync` ＋ `Problem` | `work` 包在自己的 `try` 裡，`IsFailure` 分支 abandon 後回 `Problem(outcome.Error)`；`work` 丟例外也照舊 abandon 再往上丟 |
| ② `work` 成功 → 絕不 Abandon | `work` 的 `try/catch` 到取得 `state` 就結束。**「② 過了這一行，副作用已經產生」之後的程式碼裡沒有任何一個 `AbandonAsync`**（`grep` 得到的三個 `AbandonAsync` 全在 ① 那一段） |
| ③ `render` 回 `TResponse` 而不是 `Result<TResponse>` | 簽章即證明。**「組回應失敗」在型別上表達不出來**——`ToOrderAsync`／`ToAdminOrderAsync` 想回 `Result` 就編不過 |
| ④ `render` 丟例外 → 仍 `CompleteAsync` 再往上丟 | `catch (Exception)` → `LogCritical` → `CompleteDegradedAsync`（存退化回應）→ `throw`。`CompleteDegradedAsync` 自己失敗時只記 `LogCritical`，**不覆蓋正在往上丟的原始例外** |

兩個設計決定，寫在這裡供複驗：

1. **退化回應是 JSON `null`（`DegradedRenderSnapshot`），不是 `{}`。**
   `render` 炸掉時不存在正確的回應可以存，而「存什麼」會被之後同一把 key 的重送拿到。
   `{}` 會被前端當成一個所有欄位都缺席的正常物件而靜默錯下去；`null` 會立刻炸開。
   兩害相權取「不會被誤認為正確」的那個。**這條路本身不該發生**（`render` 依設計是全函數），
   它是 defensive backstop。
2. **最後那個 `CompleteAsync` 自己失敗時不接手。**
   冪等鍵留在 `IN_FLIGHT`：lease 未過期的重送拿到 409，過期後才會重跑。
   那一邊是安全的——`Abandon` 才會讓已經產生的副作用被重做一次。

**非泛型多載（現在在 `BffHttp.cs:302`，原 `:181`）沒有動。**
這一波五個端點的回應都有 body（`OrderResponse`／`AdminOrderResponse`，201／200），
沒有任何一個走 204 無內容那條路，所以沒有呼叫點需要改用它。
`git diff --numstat` 的 `0` deletions 也證實它一行都沒被改。
（**它有同一個缺陷**：`IsFailure` 與 `catch` 都無條件 `AbandonAsync`。目前 33 個呼叫點沒有一個
用它，所以今天沒有實害；見「我發現但沒做的事」①。）

### ① 非泛型多載（`BffHttp.cs:302`）有同一個缺陷，但今天沒有實害

`ExecuteIdempotentAsync(..., Func<CancellationToken, Task<Result>> action, ...)`（204 那個）
的 `IsFailure` 與 `catch` 一樣是無條件 `AbandonAsync`。派工書必做 1 說「這一波沒有呼叫點要改用它
就不要動，但要在報告裡說明」——**現況是 33 個呼叫點沒有任何一個在用它**
（`grep` 全部命中泛型版），所以它今天是死碼等級的風險。
**沒有動它。** 但如果之後有人寫一個「回 204、而且副作用 commit 之後還有步驟」的端點，
它會是下一個 #22。建議：等真的有第一個呼叫點時，比照這一波加一個
`work`／`onCommitted` 兩階段的 204 版本，而不是現在先加一個沒人用的多載。

### ③ `ToAdminOrderAsync` 原本有一個會丟例外的洞，順手補掉了

改成 `TryGetValue`，找不到就走同一套退化值並 `LogError`。
這在「改成不會失敗的版本」的字面範圍內，但它是一個**獨立於 #22 的既有缺陷**，
