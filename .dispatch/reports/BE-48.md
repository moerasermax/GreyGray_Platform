## 逐條自驗

派工書 §5「可能寫錯的地方」逐條：

### ① `ExecuteIdempotentAsync` 的重放：換 cookie 要放哪一層

**照派工書給的第二個選項做：放在方法回傳之前，以回應是否成功決定。**

查證過 `src/Platform/Http/BffHttp.cs:249-256`：兩階段多載在 `identity.CachedResponse is not null`
時**直接 `return Results.Text(...)`，根本不會進 `work`**。所以換車若寫在 `work` 裡，
同一把 Idempotency-Key 重放就換不到車。改成：

```csharp
if (result is IStatusCodeHttpResult { StatusCode: StatusCodes.Status201Created })
{
    SetCartCookie(context.Response, CartId.New());
}
```

201 是這個端點唯一的成功狀態（`successStatus`）；失敗走 `BffHttp.Problem`（4xx），
`EarlyResult`（缺 key／同鍵進行中）也不是 201，所以「真的成功之後才換」成立。
重放時再換一次也無害——換到的一樣是一台全新的空車。

測試 `Successful_checkout_retires_the_cart_cookie` 的第二段就是打這一條：同一把 `key-1`
送第二次，`Ordering.CreateCalls` 仍是 1（確定走的是快取那條路），而回應仍帶新 `gg_cart`。

### ② `SetCartCookie` 的選項要跟 `ClearCartCookie` 一致

沒有新增任何 cookie 寫法，兩處都是呼叫既有的 `SetCartCookie`，選項自然一致。
測試仍然明文斷言 `path=/`／`secure`／`samesite=lax`／`httponly` 四項
（`Successful_checkout_retires_the_cart_cookie`），照 #36 那支的做法。

### ③ `CartView` 加欄位會影響所有建構點

用 `init` 屬性 `public bool IsCompleted { get; init; }`，**建構式參數一個都沒動**。
全專案 `new CartView` 只有 `CheckoutApplicationService.cs:570` 一處，其餘呼叫端零改動；
建置 0 警告 0 錯誤可證。

### ④ 必做 C-1 要讓服務端真的帶值

`ToView`（`CheckoutApplicationService.cs:561`）是 `CartView` 的**唯一組裝點**
（`GetCartAsync`／`AddLineAsync`／`UpdateLineAsync`／`RemoveLineAsync` 四條路都回它），
所以只在那裡填 `IsCompleted = cart.IsCompleted` 就每條路都涵蓋。
`EmptyCart` 走的是空車，預設 `false`，正確。

專門有一支測試釘死這件事，正是為了不重演 #43 那種「型別有了沒人填」：
`Cart_view_reports_completion_so_the_host_can_see_it` —— 結案**前**讀回來 `IsCompleted`
是 `false`、結案**後**讀回來是 `true`，而且服務層仍然回 `IsSuccess`（語意刻意不動）。

### ⑤ `ReleaseByKeyAsync` 可能有兩個呼叫端

查過了。`ReleaseByKeyAsync`（internal）只有一個呼叫端：
`OrderingEventHandlers.cs:36` 的 `OrderCancelledInventoryHandler`。
`ReleaseAsync(ReservationId)`（public，在 `IStockReservation` 上）沒有任何生產程式碼呼叫，
只有 `ShipmentDispatchInventoryTests.Dispatch_after_release_fails_loudly` 用它做前置。

**兩者共用同一段 private `ReleaseAsync`，所以照派工書改在 service 裡，兩邊都受惠。**

有沒有呼叫端「期待已出庫時失敗」？沒有。唯一的呼叫端 `OrderCancelledInventoryHandler`
拿到失敗就 `throw`，那正是 #46 卡住的成因。
反向確認：`ConsumeAsync` 對**已釋放**的保留仍然 fail-closed
（`inventory.reservation-already-released`），BE-47 那條測試沒被動到，仍然綠。

## 我發現但沒做的事

1. **`services.AddLogging()` 被加進 `AddInventoryModule`——派工書沒提到，這是我自己的判斷。**
   必做 D 要求「留一行 log」，但**全專案沒有任何 `*.Infra` 模組注入過 `ILogger`**
   （`grep -rn ILogger src/Modules/*/*.Infra/` 零命中），`StockReservationService` 本來也沒有。
   而 `tests/GreyGray.M1a.Inventory.Tests` 那四個手搭的 `ServiceProvider` 都沒有 `AddLogging()`，
   直接 `GetRequiredService<ILogger<T>>()` 會讓它們在 DI 就炸。
   選了「在 `AddInventoryModule` 裡冪等地 `services.AddLogging()`」而不是「改四個測試」——
   後者會讓下一個新增 Inventory 測試的人踩同一顆雷。
   **這是這一包唯一一處派工書沒明講的判斷，請 Leader 覆核。**
   替代方案是拿掉 log 只留守衛；那樣「已出庫所以不釋放」就完全沒有可觀測痕跡，
   跟這個 repo 一貫的「不准靜默退化」相反，所以沒選。

2. **「取消已出貨的訂單」本身該不該被允許，這一包沒碰**（派工書 §2 明列）。
   現在的行為是：訂單可以被取消，庫存那一段安靜跳過。但**貨已經在客人手上**，
   帳面上這張單就變成「已取消卻已交運」——退款、退貨入庫、銷貨成本迴轉都沒有人做。
   #46 只是讓事件不再卡住，**沒有讓這個業務狀態變得正確**。

3. **正式機那則 `attempts=9` 的 outbox 訊息我沒有也不能處理**（沒有連線）。
   這一包部署之後重放它會是 no-op（reservation 狀態已是 2 → 安靜成功）。
   如果它在部署前就已經進死信，需要 Leader 手動重放一次才會結案。

4. **`GetCartAsync` 換車後會再查一次資料庫，一定回空車。**
   刻意維持跟 #36 那條 `cart-not-found` 路徑一模一樣的形狀（換 cookie → 再查一次），
   沒有為了省一次 round trip 自己組空車——兩條路走同一段程式碼比較不會漂移。

5. **前端（FE-29／#45）不會知道「你手上的 cart id 換了」。**
   `gg_cart` 是 `HttpOnly`，前端讀不到，所以換車對它是透明的；但若前端在記憶體裡快取了
   購物車內容或徽章數字，仍要靠 `GET /v1/cart` 回來的空車才會歸零。
   `CartResponse` 刻意沒有加欄位（派工書 §1 C-3），這是對的，只是記一筆讓 Leader 對照 FE-29。

6. **`GetCartAsync` 只在「已結案」與「not-found」兩種情況換車，其他失敗照舊回錯誤。**
   例如服務層若回別的錯誤碼，行為不變。這是刻意的：換車是一種資料丟棄，
   只在已經確定那台車不能用時才做。
