# BE-32 自驗報告

修好 cursor 分頁 `Where` 子句的排序翻譯失敗——跟 BE-29 修過的 `OrderBy`/`ThenBy` 同一種手法
（`.Value.CompareTo` 拆開強型別 ID 繞過 EF Core 值轉換器）、同一個根因，只是出現在 `Where`

`<=`／`>=` 四個運算子，`Where` 子句改成直接比較整個強型別 ID。BE-29 留下的兩條 `[Skip]`
迴歸測試拿掉標記後真的轉綠。

## 我發現但沒做的事

### ① 全新發現：`Order.cs:567 BuildOrderNumber` 只取 GUID v7 的前 7 個 hex 字元，並發時序相近的訂單會撞號

**現象**：連續（甚至間隔 3～30 秒）對真實 dev host 送出多筆 checkout，第二筆之後
穩定 500，`storefront.out.log` 顯示：

```
Npgsql.PostgresException (0x80004005): 23505: duplicate key value violates unique constraint "ux_orders_tenant_number"
DETAIL: Key (tenant_id, order_number)=(00000000-0000-0000-0000-000000000001, GG26083101A0579) already exists.
```

**根因**：

```csharp
// src/Modules/Ordering/GreyGray.Modules.Ordering.Core/Order.cs:567
private static string BuildOrderNumber(OrderId id, DateTimeOffset placedAt) =>
    $"GG{placedAt.UtcDateTime:yyMMdd}{id.Value:N}"[..15].ToUpperInvariant();
```

`id.Value:N` 是 32 字元的 hex（無破折號），`[..15]` 只留「GG」＋ 6 碼日期 ＋ **前 7 碼**
hex。`OrderId` 用 `Guid.CreateVersion7()` 產生，v7 GUID 的前 48 bit 是毫秒時戳、
big-endian 排列，所以字串最前面幾碼直接對應時戳的高位元。**只取前 7 碼**代表只取
時戳的高 28 bit（`timestamp >> 20`），這個值大約每 **2^20 毫秒（≈17.5 分鐘）**
才會變一次——**同一個 17.5 分鐘視窗內，不管建立幾筆訂單，前 7 碼幾乎必然相同**，
撞上 `ux_orders_tenant_number`（`tenant_id, order_number` 唯一鍵）就 500。

**實測**：本波驗證時連續／間隔重試超過 20 次、跨度超過 10 分鐘，全部撞同一個
`order_number`（`GG26083101A0579`）；直到真實時間又往後推進了一段才拿到下一筆
不同的 `order_number`（`GG26083101A057A`）。

**影響評估**：這不是我這一波動到的檔案（`Order.cs` 不在 BE-32 的 `allow:` 清單內，
也完全不是同一類問題——這是 `OrderNumber` 生成邏輯，不是 EF Core 查詢翻譯），**沒有動手修**。
但這是一個**真實的生產風險**：任何兩張訂單只要在同一個 ~17.5 分鐘視窗內建立
（例如促銷活動流量高峰、或單純巧合），第二張就會建單失敗、整個 checkout 500。
建議下一波派工修：把 `[..15]` 的截斷範圍加大（例如改取完整 32 碼 hex 的更多位數，
或改成不依賴 GUID 前綴、改用遞增序號／完整雜湊），並補一條「同一視窗內連續建兩張
訂單」的迴歸測試。

### ② 觀察到但沒有深入查證：checkout 對客戶端回 500，訂單卻已經真的寫進資料庫

在追查①的過程中，有一筆訂單（`GG26083101A057A`，`placedAt` 11:42:15）**確實存在於
資料庫裡**，但我逐一檢視當時送出的每一筆 checkout 請求的 HTTP 回應紀錄，**沒有任何
一筆在那個時間點顯示 201**——換句話說，這筆訂單很可能是在某次被我記錄成 500 的
checkout 呼叫裡，**訂單那次 `SaveChangesAsync` 已經 commit，但同一個請求後續某個
步驟又丟例外，讓整個 HTTP 回應變成 500**，導致客戶端（我）以為失敗、資料庫其實
已經有一筆「幽靈訂單」。

**我沒有深入查證這個現象的根因**（可能是購物車清空、事件發佈、或其他後續步驟跟
訂單建立沒有包在同一個交易範圍內），原因是：(a) 這牽涉到 checkout 端對端流程與
交易邊界設計，遠超出 BE-32 的範圍（`OrderingRepository.cs`／`OrderingContracts.cs`
的 cursor 比較運算子）；(b) 我不確定這是否單純是①號 bug 的另一種表現形式
（例如：訂單真的建立成功，但緊接著的某個動作因為某種暫時性原因失敗，剛好又跟
①同時發生，讓我誤以為兩者相關）。**這裡誠實記錄「觀察到的現象」，不是確診的結論**，
留給下一次有資源深入查證的人判斷是否為真正獨立的 bug（如果是，代表 checkout 有
「回應失敗但訂單已建立」的風險，客戶可能重複付款或看不到自己已經下的單）。

### ③ 為完成活體驗證，臨時給 storefront process 塞了假的 ECPay 測試憑證，沒有寫進任何檔案

storefront host 時額外加了三個 process 層級環境變數

### ④ 出貨清單（`GET /v1/shipments`）沒有做活體 HTTP 測試——經使用者裁決的範圍決策

`POST /v1/shipments`（`FulfillmentApplicationService.CreateAsync`）要求引用的訂單
狀態必須是 `ReadyToShip`（`FulfillmentApplicationService.cs:33`）。要讓一筆訂單
走到那個狀態，需要：付款 webhook（`POST /v1/webhooks/ecpay`，需要正確簽章）→
（Preorder 商品）現場採購流程標記買到 → 開團結算 → 訂單狀態機推進到
`ReadyToShip`。這整條路徑跟 BE-32 要修的 `Where` 子句排序翻譯問題完全無關，
只是「建測試資料」的成本。另外檢查發現：**目前開發環境所有 Stock 模式商品的
可用庫存都是 0**（`GET /v1/products/{id}` 回 `"available":0`），M1a／M1b 也沒有
公開的補貨端點（`POST /v1/lots` 是 M2 里程碑），所以繞道用現貨模式走捷徑
（`PaidAwaitingClose → ReadyToShip`）也不可行。

跟使用者討論後（回合中選項 (a)），**決定不花費遠超過 BE-32 本身修法規模的成本
去建構一整條訂單生命週期只為了活體測 `/v1/shipments`**，改為信賴已經轉綠的
`FulfillmentAdminListSortPostgresTests`——**這條自動化測試套用的是跟訂單側
一模一樣的嚴謹度**：用 testcontainers 起真實 Postgres、seed 三筆 `CreatedAt`
完全相同的出貨單逼出 tie-break、改之前先紅（貼出 `could not be translated`
例外）、改之後轉綠且斷言的是**順序**而非只斷言不丟例外，套用的又是跟
`OrderingRepository.cs:123` 完全同一個運算子重載修法（`ShipmentId` 加的四個
運算子逐字比照 `OrderId`）。**這不是遺漏，是本波明確的範圍裁決**，理由與决策
過程完整記錄在對話紀錄裡。
