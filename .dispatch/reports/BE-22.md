## 我發現但沒做的事

1. **`install-dev-environment.ps1` 第一版沒有判斷「migrations 已經套過就跳過」，
   無條件重放全部 14 份——這踩到 `db/migrations/0003_channel_seams.sql` 一個
   既有的、跟 BE-22 無關的非冪等 bug，已經修好我自己腳本的部分，但 SQL 檔本身沒動。**
   細節：`0003_channel_seams.sql` 對 `ledger.account` 的 seed row 是
   `INSERT ... ON CONFLICT (tenant_id, code) DO NOTHING`；但
   `0005_m1a_payment_ledger.sql` 後來替 `ledger.account` 加了一個 **`NOT NULL`
   且沒有預設值**的 `id` 欄位。PostgreSQL 檢查 `NOT NULL` 是在建構候選列的時候，
   早於 `ON CONFLICT` 判斷衝突，所以「已存在就跳過」這個保護在欄位加了之後
   **擋不住**：對一個已經跑過全套 migrations 的資料庫重放 `0003`，會在建構列時
   就先因為 `id` 是 NULL 噴 `ERROR: null value in column "id"`，不會走到
   `ON CONFLICT` 被吞掉。整份檔案包在 `BEGIN...COMMIT`，失敗會整份 rollback，
   沒有留下半套髒狀態（我有重新查過 `iam.customer`／`ledger.account` 的列數
   確認沒有掉資料）。這條路徑正常的整合測試不會踩到——`ops/test.ps1` 用
   Testcontainers 每次都是全新容器，永遠不會「對已經跑過 migrations 的資料庫
   重放 migrations」；只有像我這種「重跑同一個持久化本機環境」的情境才會踩到。
   **`db/migrations/0003_channel_seams.sql` 不在 BE-22 的 allow（`ops/**`）裡，
   我沒有動它**，只在自己的 `install-dev-environment.ps1` 裡加了「已經有完整
   `migrations-applied.json` 就整批跳過」繞開，讓本機環境腳本本身可以安全重跑。
   這個 SQL 檔案的問題需要另外派工修（例如把 seed INSERT 挪到 `0003` 更早，
   或讓 `0005` 加欄位時一併處理舊 seed row 的回填）。

2. **PostgreSQL 本體沒有照派工書字面描述「當一般背景行程」跑，改用 Docker 容器
   （`postgres:17-alpine`），這是這一波最大的偏離，寫清楚判斷過程：**
   實測 `postgres.exe` 用官方 ZIP binaries 解壓、`initdb` 完全正常（跟
   docs/14 §8.4 的既有結論一致：「`initdb` 本身不會拒絕管理員身分執行」），
   但**啟動 server 本體**時直接被 PostgreSQL 自己內建的安全檢查擋下：
   ```
   Execution of PostgreSQL by a user with administrative permissions is
   not permitted. The server must be started under an unprivileged
   user ID to prevent possible system security compromises.
   ```
   這不是設定或環境問題，是 Windows 上 `postgres.exe` 寫死的 `IsUserAnAdmin()`
   檢查，只要目前使用者屬於 Administrators 群組就會被拒絕——而這個 session
   本來就是用 Administrator 身分跑的（`whoami`／`IsInRole(Administrator)` 都是
   `True`）。正式機用 `GreyGraySvc` 這種專屬非管理員帳號繞過，但派工書 §5 BE-22
   的必做清單完全沒有要求開發機建立專屬 Windows 帳號、改 ACL、停用 Windows
   Update、排除 Defender、裝 cloudflared／prod-monitor——那些是
   `install-environment.ps1` 給「正式機」的 ceremony；為了繞一個 OS 層級的權限
   檢查就去新建 Windows 帳號、動使用者自己這台開發機的安全設定，代價比問題本身大，
   也不是這一包被交付的範圍。**改用 Docker 執行 PostgreSQL 本體**：容器裡是
   `postgres` 這個 Linux 使用者，跟 Windows 側是不是 Administrator 完全無關；
   Docker Desktop 本來就已經裝著、且這個 repo 的整合測試（`Testcontainers.PostgreSql`）
   本來就是用同一顆 `postgres:17-alpine` 映像，不是我這一波新引入的依賴。
   官方 ZIP binaries 繼續解壓，只是改當 **`psql`／`pg_isready` 客戶端工具**用，
   `ops/invoke-migrations.ps1` 完全沒有改——它本來就只認 host/port，不管背後
   是不是容器。data／WAL 用 bind mount 掛回 `D:\GreyGray\PostgreSQL\data`，
   實際位元組留在 D 槽，滿足「裝在 `D:\GreyGray`」的要求；`pg_wal` 仍在
   `data\pg_wal` 底下同一顆磁碟，跟 docs/14 §8.3「不強制獨立 junction」的既有
   結論一致。**這個判斷我認為是對的，但畢竟偏離了派工書字面的做法，請整合者
   確認可以接受**；如果不能接受，備案是：另外建一個非管理員的本機帳號專門跑
   `postgres.exe`（等於是把 `install-environment.ps1` 的服務帳號那段搬一份輕量版
   過來），我沒有先斬後奏做這件事，因為那牽涉到在使用者自己的機器上新增
   Windows 帳號，屬於需要先講清楚的動作。
