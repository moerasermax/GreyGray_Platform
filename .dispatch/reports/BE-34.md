共用同一個 `IPricingQuotation` 與同一個 `ICatalogQuery` 實例（跟正式環境 DI 一致），
但**各自持有獨立的 `FakeUnitOfWork`**——「兩段各自 commit」正是這個問題的核心，
共用一個工作單元會把它整個掩蓋掉。測試替身只有四個：`ISessionStore`、`IIdempotencyStore`、
`ICatalogQuery`、以及包住 `FakePricing` 的 `GatedPricing`。**冪等語意沒有任何一條是我自己寫的**：
`checkout.cart-already-completed`、`ReplayCompletedEvent`、`GetByCheckoutAsync` 比對
`CheckoutIdempotencyKey`，全部是真實 Core 程式碼在跑。

可信度的折扣有三處，如實列出：
- **持久層是記憶體 repository**（`FakeCartRepository`／`FakeOrderRepository`，`TestDoubles.cs` 既有），
  不是 Postgres。所以「唯一鍵衝突」「交易隔離」這一層的行為沒有被測到；但這一波要釘的是
  **控制流與冪等判斷**，那一層完全在 Core 裡，與持久層無關。
- **`FakeUnitOfWork.SaveChangesAsync` 只是計數**，不是真的 commit。「已 commit」在測試裡的
  意義是「該模組已經走完它的寫入路徑並且不會被後續步驟回捲」——這正是問題所在，因為
  **本來就沒有任何東西會回捲它**（三步驟根本不在同一個交易裡）。
- **`InspectableIdempotencyStore` 是記憶體版**，但語意逐條比照
  `IdempotencyStore.TryBeginAsync` 的 SQL：`ABANDONED` ＋ 相同 `request_hash` → `Proceed`，
  `COMPLETED` → 回快取，hash 不同 → `KeyReusedWithDifferentPayload`。差別只在它留得住
  最後狀態讓測試看得到（`AdminCancelLineEndpointTests` 那一份 `Abandon` 時直接把 entry 刪掉，
  看不出「被 abandon 過」）。

#### 情境 1：第一次 checkout，`ICatalogQuery.GetSkuAsync` 回 failure

觸發方式：用裝飾器包住真的 `ICheckoutApplication`，在 `CompleteAsync` **成功回傳之後**
才把共用的 catalog 切成失敗。這樣第 ①② 步照常跑完（`Order.Place` 與事件發佈都不碰 catalog），
第 ③ 步 `ToOrderAsync` 必定回 `ordering.catalog-snapshot-unavailable`。
catalog 仍然是同一個實例，時序卻是確定的。

| 觀察項 | 實際結果 |
|---|---|
| 回應狀態碼 | **422**（`BffHttp.StatusFor` 對這個 code 落在預設分支）——**不是 201** |
| 回應內容 | 含 `ordering.catalog-snapshot-unavailable` |
| 訂單有沒有真的建立 | **有**，`ListCustomerAsync` 查到 **1** 張 |
| 事件 | `OrderPlaced` × 1、`PaymentRequested` × 1 **都已經發出去** |
| 冪等鍵最後狀態 | **`Abandoned`** |

**(A′) 幽靈訂單成立，而且比原本記載的更嚴重一點：`PaymentRequested` 也已經送出。**
這正好解釋 BE-32 報告「我發現但沒做的事②」看到的那張 `GG26083101A057A`。

#### 情境 2：同一把 key ＋ 同一個 CartId 重試（catalog 恢復）★

| 觀察項 | 實際結果 |
|---|---|
| 回應是不是 201 | **是，201** |
| **訂單總數是 1 還是 2** | **1** ★ |
| 回的是不是第一次那張 | **是**，`OrderId` 相同，回應 body 含同一個 `OrderNumber` |
| 冪等鍵最後狀態 | `Completed` |

**★ 這一條把文件的說法推翻了。** 機制與 Leader 的靜態推論完全一致：BFF 的 key 被 abandon
只是讓業務邏輯重跑一次，而業務邏輯本身可重入——`CheckoutApplicationService.CompleteAsync`
看到 `cart.IsCompleted` 且 `CheckoutIdempotencyKey` 相同就 `ReplayCompletedEvent()` 重播同一個
`CheckoutCompleted`；`OrderingApplicationService.CreateFromCheckoutAsync` 用
`GetByCheckoutAsync(TenantId, CartId)` 找到既有訂單、比對 `CheckoutIdempotencyKey` 相同就
直接回那一張。**「客人重複下單／重複付款」站不住。**

#### 必做 3／(B)：第 ② 步失敗

觸發方式：讓 `IPricingQuotation.GetSnapshotAsync` 回 failure。**這是刻意挑的真實失敗原因**——
Ordering 建單時要回頭跟 Pricing 拿凍結好的報價快照，那是一次跨模組讀取，而
`CompleteAsync` 用的是 `QuoteAsync`／`FreezeAsync`，兩者互不影響，所以能只讓第 ② 步壞掉。

| 觀察項 | 實際結果 |
|---|---|
| 回應 | **404** ＋ `pricing.snapshot-not-found`（`StatusFor` 對 `not-found` 回 404） |
| 購物車是不是已經 `IsCompleted` | **是**——再呼叫 `AddLineAsync` 回 `checkout.cart-already-completed` |
| 訂單有沒有建立 | **沒有**，0 張 |
| 冪等鍵最後狀態 | **`Abandoned`** |
| **同一把 key 重試會不會自動復原** | **會**。修好第 ② 步的失敗原因後用同一把 key 重試 → **201**、訂單 **1** 張、冪等鍵 `Completed` |

所以 (B) 的形狀是：**暫時性失敗 → 同一把 key 重試就復原；永久性失敗 → 購物車永久卡在
「已結案卻沒有訂單」**。

**但 (B) 還有一條 Leader 的靜態分析與交接書都沒提到的自癒路徑**，見「我發現但沒做的事」②：
`CheckoutCompleted` 是**跟購物車結案同一個交易**寫進 outbox 的，Worker 的
`OutboxDispatchWorker` 會把它派給 `CheckoutCompletedHandler`，那支 handler 呼叫的正是
`ordering.CreateFromCheckoutAsync`。**也就是說 (B) 在正式環境會由 outbox 非同步補建訂單**，
最多重試 10 次、指數退避。這把 (B) 的嚴重性從「訂單遺失」降成「客人當下看到錯誤，訂單稍後才出現」。

#### ★ 重複風險：找到 **1 個**——`POST /v1/shipments`

**33 個全部審過，落在「★重複風險」的只有 `M1bFulfillmentEndpoints.cs:72`（`POST /v1/shipments`）。**

- **什麼副作用會做第二次**：`fulfillment.shipment` 多一列、`fulfillment.shipment_order`
  多 N 列，同一批訂單同時掛在**兩張**出貨單底下。
- **為什麼它跟其他「建立型」端點不同**：`POST /categories`／`POST /products`／`POST /campaigns`
  ／`POST /me/addresses` 建出重複資料的後果是「後台多一筆看得到、刪得掉的草稿」；
  **出貨單不是**——重複的那一張會被撿貨、被 `dispatch`（寫入 `carrier_cost` 物流成本），
  同一批貨可能出兩次、物流成本重複入帳。這是這一類裡唯一會**直接賠錢**的。
- **重試場景長什麼樣**：`CreateAsync` 已經 `SaveChangesAsync` 之後，**在
  `ExecuteIdempotentAsync` 自己的收尾階段**發生錯誤——`JsonSerializer.Serialize(result.Value)`
  丟例外，或 `idempotency.CompleteAsync` 丟例外（`IdempotencyStore.cs` 在
  `affected != 1` 時明確 `throw new InvalidOperationException("冪等 lease 已過期，
  或在完成前已被其他請求接手。")`，資料庫連線在這個瞬間斷掉也一樣）。
  `catch { AbandonAsync(...); throw; }` 於是把冪等保護解除並回 500；
  前端／店員看到 500 之後**用同一把 key 重送**（這正是 `Idempotency-Key` 存在的意義），
  `TryBeginAsync` 對 `ABANDONED` ＋ 相同 hash 回 `Proceed` → **第二張出貨單**。
- **觸發條件比 checkout 窄**：checkout 走的是**業務失敗**（`Result.Failure`）這條每天都會走的路；
  `POST /v1/shipments` 要的是「commit 成功之後、冪等鍵寫回之前」的基礎設施故障。
  **但後果比 checkout 嚴重**，因為 checkout 那邊有兩層模組冪等接住，這邊一層都沒有。
- **這一波沒有動它**（必做 5 明文「只讀不改」）。

**A5／A7／A10／S5（`POST /categories`、`POST /products`、`POST /campaigns`、
`POST /me/addresses`）落在同一個形狀但影響較小**：底層一樣沒有冪等、一樣沒有自然鍵唯一約束，

### 明確回答第 8 項

> `00-進度總表.md`「現在卡在哪」#22 與 `04-交接書.md` 第四節寫的
> 「(A) 客戶端拿同一把 `Idempotency-Key` 重試 → 會被當成全新請求 → **建出第二張訂單**」

**這句話是錯的。** 可執行的測試（情境 2，用真的 `CheckoutApplicationService` ＋ 真的
`OrderingApplicationService`）證實：同一把 key ＋ 同一個 CartId 重試 → **HTTP 201**、
**訂單總數維持 1**、回的是**第一次那張訂單**（`OrderId` 相同）、冪等鍵最後是 `Completed`。

「被當成全新請求」這半句是對的（`TryBeginAsync` 對 `ABANDONED` ＋ 相同 request hash 確實回
`Proceed`），**錯的是後半句的推論**——重跑業務邏輯不等於重做副作用，因為業務邏輯本身可重入：

- Checkout：`cart.IsCompleted` 且 `CheckoutIdempotencyKey` 相同 → `ReplayCompletedEvent()`
  重播**同一個** `CheckoutCompleted`（`EventId` 都一樣）
- Ordering：`GetByCheckoutAsync(TenantId, CartId)` 找到既有訂單且 `CheckoutIdempotencyKey`
  相同 → 直接回那一張

**所以「客人重複下單／重複付款」這個嚴重性描述是誇大的，兩份文件都要改。**
實際成立的是三條較輕的不一致：(A′) 幽靈訂單（客人看到錯誤但訂單與 `PaymentRequested` 都已產生）、
(A″) 換一把 key 就走進死路（訂單完好但這條路回不了 201）、(B) 購物車結案卻沒有訂單
（同一把 key 重試會自癒，outbox 也會非同步補建）。

### 必做 6：修法選項分析（**只分析，沒有實作**）

#### 選項 1　讓 `action` 能回報「副作用已產生，不要 abandon」

- **做法**：`ExecuteIdempotentAsync` 的 `action` 除了 `Result<T>` 之外，多一個管道讓呼叫端標記
  「這次雖然失敗，但副作用已經 commit」。實作上可以加一個 `Func<..., Task<(Result<T>, bool SideEffectCommitted)>>`
  的多載，或傳一個 `IdempotencyScope` 物件讓 lambda 呼叫 `scope.MarkCommitted()`。
  標記過就走 `CompleteAsync`（存退化的回應）而不是 `AbandonAsync`。
- **影響範圍**：`BffHttp.cs` 泛型版與非泛型版**都要改**（`:160-164`、`:174-178`、`:206`、`:215`）；
  33 個呼叫點裡只有需要的那幾個改用新多載，其餘維持舊多載 → **相容**。
  ECPay webhook 那份手寫的也要同步。
- **代價**：`BffHttp` 的介面變複雜；「什麼時候該標記」變成每個呼叫點的判斷，**判斷錯了沒有東西會說話**
  ——這正是這個 repo 一再踩到的失敗模式。
- **契約／資料庫**：都不動。
- **解掉哪幾條**：(A′) ✅、(A″) ✅（第一次就 201，不會走到換 key）、★ `POST /v1/shipments` ✅
  （用同一個機制在 commit 後標記）。**解不掉 (B)** ——(B) 的副作用（購物車結案）本來就是
  「已 commit 卻該回捲」，標記只會讓客人拿到一個「成功但沒有訂單」的更糟回應。

#### 選項 2　把回應組裝移出「會 abandon」的範圍

- **做法**：`CompleteCheckoutAsync` 的 lambda 只做 ①②，成功就回一個**最小的**成功值
  （例如 `OrderView`／`OrderId`）讓冪等鍵 `Complete` 掉；第 ③ 步 `ToOrderAsync` 移到
  `ExecuteIdempotentAsync` **之外**，組不出完整回應就回退化版本（缺商品名稱等欄位）。
- **影響範圍**：只動 `M1aEndpoints.cs` 的 checkout 這一段（本包剛抽出來的那個方法），
  `BffHttp.cs` 一行不動。同款形狀的 S12／A3／A4／A20 要各自照做。
- **代價**：冪等鍵快取的是最小值而不是最終回應，**重送時的回應會與第一次不同**
  （第一次可能是完整版、重送是從快取還原的最小版，或反過來）——這違反冪等的直覺，
  要嘛統一都存退化版，要嘛把 `ToOrderAsync` 的結果也塞進快取。
- **契約／資料庫**：**可能動到契約**——退化回應的 `lines[].name` 等欄位要能是 `null`，
  而 `docs/05-API契約.md` 已凍結。要嘛改契約（要提案），要嘛保證退化回應仍符合現有 schema。
- **解掉哪幾條**：(A′) ✅、(A″) ✅。**解不掉 (B)**，**解不掉 ★**（`POST /v1/shipments` 的
  問題不在回應組裝，在 `CompleteAsync` 本身可能失敗）。

#### 選項 3　第 ③ 步不准讓整個請求失敗（最小改動）

- **做法**：`ToOrderAsync` 讀不到 SKU 就填 fallback（例如用 `SkuId` 當顯示名），
  不回 `Result.Failure`。`ordering.catalog-snapshot-unavailable` 這個錯誤碼從此不再出現在 checkout。
- **影響範圍**：`M1aEndpoints.cs` 一個私有方法。**改動最小**。
- **代價**：把「讀不到 catalog」這件事**藏起來**——客人看到一張品名怪怪的訂單，
  而不是一個明確的錯誤。要配一條可觀測性（log／metric），否則故障變靜默。
- **契約／資料庫**：不動（欄位仍有值，只是值變成 fallback）。
- **解掉哪幾條**：(A′) ✅（就 checkout 這一條）、(A″) ✅。
  **解不掉 (B)**、**解不掉 ★**、**解不掉 S12／A3／A4／A20 那四個同款幽靈**
  （它們的第 ③ 步是 `ToOrderAsync`／`ToAdminOrderAsync`，還讀 customers／payments，
  要一個一個比照處理）。

#### 選項 4　只在「確定沒有副作用」的失敗上 abandon

- **做法**：不由呼叫端標記，而是**改變預設**——`ExecuteIdempotentAsync` 預設**不** abandon，
  失敗時把錯誤回應也 `CompleteAsync` 進去（同一把 key 重送會拿到同一個錯誤）；
  只有明確標記為「可安全重試」的錯誤（驗證失敗、`request.*` 那一類）才 abandon。
- **影響範圍**：`BffHttp.cs`，**33 個呼叫點的語意全部改變**。
- **代價**：**很大而且危險**。今天的行為是「失敗了就讓客人能重試」，改成預設不能重試之後，
  第 ①② 步真的因為暫時性原因失敗（DB 短暫斷線）的請求會被**永久釘死**成錯誤，
  客人必須換一把 key——而換 key 在 checkout 這條路上正是 (A″) 的死路。
  等於用一個新的、更常見的故障換掉一個罕見的故障。
- **契約／資料庫**：不動。
- **解掉哪幾條**：(A′) 的「冪等保護被解除」那一半 ✅、★ ✅。
  **(A′) 的「客人拿到錯誤」那一半解不掉**（反而變成永久的）、**(B) 解不掉**、**(A″) 惡化**。
  **我不建議這一個**，列出來是因為它是最直覺的「反過來做」，值得先寫清楚為什麼不行。

#### 選項 5　補償／outbox ＋ saga（最完整也最貴）

- **做法**：checkout 三步驟改成一條 saga：① 購物車結案寫入 ＋ `CheckoutCompleted` 進 outbox
  （**這一段今天已經存在**）；② 由 outbox handler 建單（**今天也已經存在**）；
  BFF 只負責啟動並輪詢／回 `202 Accepted` ＋ 一個查詢位置。第 ② 步永久失敗時，
  補償把購物車退回可編輯。
- **影響範圍**：checkout 端點的**回應語意**（201 → 202 ＋ 輪詢）、前端結帳流程、
  `docs/05-API契約.md`、可能要一張 saga 狀態表。
- **代價**：最大。前端要改，契約要改，測試要重寫。
- **契約／資料庫**：**都要動**。
- **解掉哪幾條**：(A′) ✅、(A″) ✅、(B) ✅（唯一真正解掉 (B) 的選項）、★ ⚠️
  （要對 `POST /v1/shipments` 另外處理，saga 化 checkout 不會順便修好出貨單）。

### ② (B) 路徑在正式環境還有一條 outbox 自癒路徑——交接書與派工書都沒提到

`CheckoutApplicationService.CompleteAsync` 在 `unitOfWork.SaveChangesAsync` **之前**
就 `eventPublisher.PublishAsync(completed, ...)`，而 Checkout 模組註冊的是
`OutboxEventPublisher<CheckoutDbContext>`——**`CheckoutCompleted` 是跟購物車結案同一個交易
寫進 `platform.outbox_message` 的**。

Ordering 模組註冊了
`AddIdempotentIntegrationEventHandler<CheckoutCompleted, CheckoutCompletedHandler, OrderingDbContext>()`
（`Ordering.Infra/ModuleRegistration.cs:100-104`），而 `CheckoutCompletedHandler.HandleAsync`
呼叫的正是 `ordering.CreateFromCheckoutAsync`。Worker Host（`Worker/Program.cs:56、65-66`）
同時掛了 `OutboxDispatchWorker` 與 Checkout／Ordering 兩個模組。

**所以 (B)「購物車結案了但沒有訂單」在正式環境會由 outbox 非同步補建訂單**，
`OutboxDispatcher` 是 at-least-once ＋ 指數退避、最多 10 次才進死信。
`ICheckoutApplication.CompleteAsync` 的 XML doc 其實早就寫了這個設計意圖：
「BFF 可將回傳事件同步交給 Ordering 建單；outbox 的非同步重送會由 Ordering 冪等吸收」。

**為什麼沒有測它**：要證實這條路徑需要真實 Postgres ＋ 真的跑起來的 Worker ＋ 等待
outbox 派送週期，那是端對端測試的範疇，遠超過本包「查證 checkout 三步驟控制流」的範圍，
而且會把一組 0.6 秒跑完的確定性測試變成需要容器與計時的不穩定測試。
`OrderingOutboxIntegrationTests.cs` 已經在測 outbox 本身，但沒有涵蓋
「checkout 同步路徑失敗 → outbox 補建」這條組合。

**這件事直接影響 (B) 的嚴重性評級**，Leader 更新 `00-進度總表.md` #22 時應該一併寫進去。
**但請先確認它在正式環境真的會動**——如果 Worker 沒跑、或 outbox 派送被關掉，這條保險就不存在。

### ③ `POST /v1/orders/{orderId}/cancel`（Storefront）與 Admin 三個退款端點是**同款幽靈，之前沒人提過**

必做 5 的表格裡是 S12／A3／A4／A20。它們跟 checkout 是**一模一樣的形狀**：
狀態改變 ＋ 退款事件（`OrderCancelled`／`RefundRequested`）已經 commit 並送出，
之後才 `ToOrderAsync`／`ToAdminOrderAsync` 讀 catalog／customers／payments 組回應——
那一步會回 `Result.Failure`，於是整個請求變成錯誤、冪等鍵被 abandon。

**比 checkout 更麻煩的地方**：checkout 重試會自癒（情境 2 已證實），
**這四個不會**——底層是狀態機守衛，訂單已經 `Cancelled`、品項已經 `Unavailable`，
重試只會拿到另一個錯誤（`ordering.cannot-self-cancel-after-payment` 之類）。
所以「客人／店員按了取消，畫面顯示失敗，但退款其實已經送出去了，而且再按也沒用」是可能的。

**沒有動它們**（必做 5 明文只讀不改，而且它們不在本包 `allow:` 內）。
