## 我發現但沒做的事

1. **「ReadOnly 角色 → 403」這條測試沒有寫。** 403 是
   `.AddEndpointFilter(new StaffRoleFilter(StaffRole.Operator))` 在**路由層**產生的：
   `StaffRoleFilter` 從 `HttpContext.RequestServices` 取 `ISessionStore`／`IStaffDirectory`／`IStaffRolePolicy`，
   而直接呼叫 `CreateSkuAsync` 完全繞過 filter。要真的驗到它，得跑完整的 admin 路由管線
   （`MapM1aAdminEndpoints()` 會建出全部 35 條路由，`RequestDelegateFactory` 在建 endpoint 時就要能
   從 `IServiceProviderIsService` 判斷每一個介面參數是不是 DI 參數，否則會被當成 request body 而炸）——
   等於要為所有 admin 端點的相依介面各造一個假物件。全 repo 目前沒有這套基礎
   （`grep -rn "Status403Forbidden\|StaffRoleFilter" tests/` 零命中，沒有 `WebApplicationFactory`），
   派工書 §1 必做 3 也寫「若根本沒有 HTTP 層測試基礎設施就回報，不要硬造一套」。
   **端點確實掛了 `StaffRoleFilter(StaffRole.Operator)`（與同段其他 Operator 端點逐字相同），
   但那一行目前沒有任何自動化測試釘住**——Leader 的活體驗收（§4 第 3 點的 ReadOnly 403）是唯一的把關。
   如果要補，建議另開一包做「admin 路由管線測試基礎」，一次把 20 幾條 Operator/Owner/Accountant
   端點的角色守衛全部釘起來，比為這一條硬造划算。
2. **「之後 `GET /v1/products/{id}` 的 skus 有它」是用 catalog port 驗的，不是打 HTTP。**
   `GET /v1/products/{productId}` 是 inline lambda，同樣碰不到；測試改成建完之後
   `catalog.GetProductAsync` 讀得回那個 SKU（Host 的 GET 就是包這一層 ＋ `ToAdminProductsAsync`）。
   真正的端對端仍要靠 Leader 的活體驗收。
3. **`AdminSkuRequest` 從 `private` 變 `internal`。** 這是把處理邏輯抽成具名方法的必要條件
   （CS0051），不是額外的擴權：它仍是 `internal static class M1aEndpoints` 的巢狀型別，
   只有同組件與 `InternalsVisibleTo` 的測試組件看得到，跟既有的 `CancelOrderInput` 同級。
4. **`docs/05` 那張 Admin 表沒有總數欄位**，所以「若那張表有『合計 N 條』的數字一起改」不適用；
   `check-openapi` 的里程碑數字（29 → 30）是工具自己數出來的，不是文件裡的常數。
5. **契約新增了 `404`／`422` 兩個 response，但 milestone 模式的 gate 不會驗 response 集合**
   （`CompareMilestoneCoverage` 只比對 method+path，程式碼裡明寫「本模式未執行完整 schema 語意比對」）。
   也就是說 403/404/422 的宣告目前沒有任何機械檢查釘住，只有 `self-test` 的完整比對模式（用的是自己的
   小樣本檔）在示範那套比對還活著。這不是這一包造成的，既有 34 條 admin operation 都一樣。
