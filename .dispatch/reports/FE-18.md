## 我發現但沒做的事

**★★ 這一波要解的症狀，這個修法（`experimental.trustHostHeader: true`）沒有解掉。**
派工書 §0 對「這個 flag 是真的、會生效」的查證是對的（Next 確實有讀這個欄位、
也確實不在官方型別裡），但**它在目前這套正式機部署拓樸下不會被走到**，原因有兩層，
都是這一輪動手才查到、派工書原本的診斷沒有涵蓋的：

**第一層——build 階段就已經被強制蓋掉。**
`next/dist/build/index.js` 產生 `required-server-files.json`（standalone
server 開機時讀的那份 manifest）時，寫死：

```js
experimental: {
  ...config.experimental,
  trustHostHeader: _ciinfo.hasNextSupport,   // 不是 config.experimental.trustHostHeader
  ...
}
```

`_ciinfo.hasNextSupport` 只有跑在 Vercel／Next 官方託管平台才是 `true`；
自架（ADR-003，native process + NSSM）一律是 `false`。所以不管
`next.config.ts` 裡寫什麼，`required-server-files.json` 裡的
`trustHostHeader` 一律被覆寫成 `false`——這一輪重新 build 之後直接
`grep required-server-files.json` 印出來的就是 `"trustHostHeader":false`，
即使 `next.config.ts` 裡明明寫的是 `true`。

**第二層——就算第一層沒發生，`next-server.js` 也不會走到 `trustHostHeader` 那個分支。**
真正決定 middleware 裡 `request.url` origin 的是
`next-server.js` 的 `attachRequestMeta()`：

```js
const initUrl = this.fetchHostname && this.port
  ? `${protocol}://${this.fetchHostname}:${this.port}${req.url}`   // ← 這一支
  : this.nextConfig.experimental.trustHostHeader
    ? `https://${req.headers.host || 'localhost'}${req.url}`       // trustHostHeader 只在這裡起作用
    : req.url;
```

三元運算式**先**檢查 `this.fetchHostname && this.port`——只要兩者皆真就直接用
`HOSTNAME:PORT` 組 URL，**連 `trustHostHeader` 都不會被讀到**。而 standalone
`server.js` 的固定邏輯是 `const hostname = process.env.HOSTNAME || '0.0.0.0'`，
只要吃到 `HOSTNAME` 環境變數就是真值，直接傳進 `startServer({ hostname, port, ... })`。
`ops/deploy.ps1:215` `:222` 固定設 `HOSTNAME=127.0.0.1`——所以正式機的部署方式
本身就保證 `this.fetchHostname && this.port` 恆真，`trustHostHeader` 這個分支
在目前的部署拓樸下**永遠不會被 evaluate**，無論它的值是什麼。

**這不是猜測，是端對端驗證出來的**：把 `experimental.trustHostHeader: true` 寫進
`next.config.ts`、`pnpm typecheck`／`pnpm build` 都過，用 `HOSTNAME=127.0.0.1 PORT=5098`
啟動一份跑得起來的 server（見上方「指令與輸出」§4），送兩個不同的 spoofed
`Host` header，`Location` 都還是 `http://localhost:5098/login`——跟修好前的症狀
一模一樣。

**沒有做的事：** 沒有自己動手改成別的修法。這一包的檔案所有權只有
`frontend/apps/admin/next.config.ts`，而上面兩層根因都不是「這個檔案該填什麼值」
能解的——第一層要嘛想辦法讓 build 過程不要覆寫（`hasNextSupport` 判斷寫死在
`next` 套件內部，不是 config 能關的開關），第二層要嘛不要讓 `HOSTNAME` 傳給
`startServer`（但拿掉 `HOSTNAME` 意味著監聽位址會退回 `0.0.0.0`，牽動的是
`ops/deploy.ps1` 的部署設定與可能的安全考量，不在這一包範圍，也不是我能單方面
決定的取捨）。這已經不是「調參數」層級的修法，需要重新設計——例如自己在
middleware 裡讀 `x-forwarded-host`／cloudflared 送來的 header 手動組 origin，
不依賴 Next 的 `trustHostHeader` 機制；或是評估 `ops/deploy.ps1` 拿掉
`HOSTNAME` 改監聽 `0.0.0.0` 是否可接受。這兩個方向都需要 Leader／整合者
決定範圍與取捨，不是我能自己在這一包裡定案的。

`next.config.ts` 裡的改動維持（照派工書必做 1 做了、型別過了），但我把註解
改寫成如實記錄「這個 flag 對目前拓樸沒效果，見自驗報告」，不再寫「這個修法對得上
目前的部署拓樸」這種已經被推翻的結論，避免下一個人看到程式碼以為問題已經解決。

**次要發現**：派工書 §5 必做 1 的範例寫 `as NextConfig['experimental']`，在這個
repo 的 `tsconfig`（`exactOptionalPropertyTypes: true`）下會被 `tsc` 擋下來
（`TS2375`：`ExperimentalConfig | undefined` 不能指派給不接受 `undefined` 的目標）。
改成 `as NonNullable<NextConfig['experimental']>` 才過。這只是型別斷言寫法的
落差，不影響上面的核心結論。
