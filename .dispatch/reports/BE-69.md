## 逐條自驗

### §1 實作項目

1. Core 新增 sealed `OrderingCheckoutAlreadyPlacedException`，形狀比照既有 Ordering concurrency 例外。
2. `OrderingDbContext.SaveChangesAsync` 只在 PostgreSQL `23505` 且 constraint 精確為 `ux_orders_tenant_checkout_cart` 或 `ux_orders_checkout_event` 時，先 `ChangeTracker.Clear()` 再轉成新例外；原有 `DbUpdateConcurrencyException` 分支未改。其他 constraint 的 23505 實測仍是原 `DbUpdateException`。
3. `CreateFromCheckoutAsync` 接住新例外後按 tenant＋cart 重讀；原有冪等分支與競態重讀共用 `ResolveExistingCheckout`：同鍵回既有 `OrderView`，異鍵回 `ordering.checkout-already-processed`；重讀為 null 時用 `throw;` 重拋原例外。
4. 未改 timer／outbox／SaveChanges 順序，未加 lock，未改 Host、Platform、包裝器或 `IOrderingApplication` 方法清單。
5. Host 輸家孤兒 timer 實測存在；以該不存在的 OrderId 直接呼叫 `PaymentDueTimeoutHandler` 不丟例外，贏家狀態仍 `AwaitingPayment`，沒有 `OrderCancelled`。

### §3 R1～R6、B1

- R1：真 PostgreSQL；repository 包裝讓輸家第一次 `GetByCheckoutAsync` 查真庫得到 null，之後另一 DbContext 先建贏家。Host 無交易路徑回 Success 且 Id 等於贏家；該 cart 只有 1 張單；`OrderPlaced`／`PaymentRequested` 各 1；兩筆 payment-due timer 中一筆為孤兒，觸發後 no-op。
- R2：相同 cart／event、不同 idempotency key 的確定性相撞回 Failure `ordering.checkout-already-processed`，不丟例外，訂單仍 1 張。
- R3：真 `IdempotentIntegrationEventHandler<CheckoutCompleted, CheckoutCompletedHandler, OrderingDbContext>`；交易內唯一違反經 savepoint 回滾後可重讀贏家，handler 不丟例外並 commit；`processed_message` 1、訂單 1、兩種 outbox 各 1；同 EventId 再送一次仍不增生。這證明本環境交易內重讀做得到，沒有修改包裝器。
- R4：先建相同 EventId、不同 CartId 的人造資料形狀，實際撞 `ux_orders_checkout_event` 並翻成新例外；按 loser cart 重讀為 null，因此重拋；資料庫仍 1 張單。另有 predicate 單元案例釘住兩個允許的 constraint。
- R5：相同 idempotency key、不同 cart／event 實際撞 `ux_orders_tenant_checkout_key`，保留原 `DbUpdateException`；predicate 對其他 23505 與 23514 都回 false。
- R6：暫移 Application catch 後 R1、R3 同時轉紅，`2/2 failed`；還原後專屬 `9/9` 綠。
- B1 建置與全套：Release `0 warning / 0 error`；13 支 exe `606 → 615`、0 failed；OpenAPI storefront `34/34`、admin `30/30`。
- B1 既有斷言修改：`0` 條。舊斷言 `N/A` → 新斷言 `N/A` → 依據：本包只新增 `OrderingCheckoutRacePostgresTests.cs`，沒有修改任何既有測試檔或既有斷言。
