## 逐條自驗

### 派工書 §1.1：Payment.Contracts 只驗不寫入口

1. 新增公開 `IEcpayCallbackVerifier.Verify(IReadOnlyDictionary<string,string>)`，回傳 `Result<EcpayCallbackEnvelope>`；envelope 只含已驗證的 `MerchantTradeNo`、`TradeNo`、`RtnCode`。
2. `PaymentApplicationService` 同時實作既有 command/query 與 verifier；建構子未變。公開 Verify 與既有 `HandleEcpayCallbackAsync` 共用同一個私有驗證流程，所以服務層原有驗簽沒有移除。
3. 驗證流程仍使用正式 `EcpayGateway.VerifyCallback`，並檢查 `MerchantID`、必要欄位、整數格式；Verify 本身不存取 repository／unit of work／publisher。
4. `AddPaymentModule` 將 verifier 解析到同一個 scoped `PaymentApplicationService`；未加入 `InternalsVisibleTo`。

### 派工書 §1.2：端點先驗簽、再去重

1. `MapPost` 的 verifier、payment command、idempotency store 都標示 `[FromServices]`；端點先讀 form，再呼叫抽出的 `HandleEcpayWebhookAsync`。
2. 驗簽／欄位驗證失敗立即回既有 Problem，尚未呼叫任何 idempotency API。
3. 驗證成功後才建立 scope `webhook:ecpay:payment-result`、key `{MerchantTradeNo}:{TradeNo}:{RtnCode}`。
4. request hash 的 canonical input 只含上述三個已驗欄位；不含 `CheckMacValue` 或其他可變但無關欄位。
5. AlreadyCompleted、InFlight、不同 payload、服務失敗 Abandon、例外 Abandon 後重拋與成功 Complete／`1|OK` 的原有分支語意均保留；`IIdempotencyStore` 未變。

### 派工書 §1.3：過渡期只收信用卡

`CreateCheckoutFields` 使用命名常數輸出 `ChoosePayment=Credit`，沒有 `IgnorePayment` 或 `CreditInstallment`。註解明載 ADR-044 過渡限制以及 BE-66 未來不能只改回 `ALL`；綠界官方測試向量中的 `ALL` 未修改。

### 派工書 §3.1：D1、W1～W10

W1～W10 的正常通知均由 `EcpaySimulatorCore.Sign` 以 Payment module 設定的 MerchantId／HashKey／HashIV 產生正式簽章；沒有固定回 true／false 的假驗簽器。端點測試的 verifier 全由 `services.AddPaymentModule(configuration)` 後從 scope 解析。

| 編號 | 做了什麼 | 實際輸出／斷言 |
|---|---|---|
| D1 | 同一 scope 解析 `IEcpayCallbackVerifier` 與 `IPaymentCommand` | 兩者 `ShouldBeSameAs`，證明有 DI 註冊且為同一 scoped service |
| W1 | 先送未重簽的竄改 `TradeAmt`，再送正式簽章原通知 | 前者 422 `payment.invalid-signature`；後者 200 `1\|OK`；服務恰好 1 次、TryBegin 恰好 1 次 |
| W2 | 只送未重簽的竄改通知 | 422；entry count=0、TryBegin calls=0、服務 calls=0；刻意注入 TryBegin 後測試紅燈顯示 1 筆，還原後綠 |
| W3 | 同一正式通知送兩次 | 兩次 200 `1\|OK`；服務 1 次；列為 Completed，第二次走 AlreadyCompleted |
| W4 | 刪 MerchantTradeNo、刪 TradeNo 後正式重簽；另以錯 MerchantID 正式重簽 | 三個子案例皆 422 `payment.invalid-callback`；entry count=0、TryBegin=0、服務=0 |
| W5 | 送正式通知並檢查儲存 identity | scope=`webhook:ecpay:payment-result`；key=`MerchantTradeNo:TradeNo:RtnCode` |
| W6 | 以另一個 hash 在舊 scope 建立後 Abandon，再送正式簽章通知 | 200 `1\|OK`；服務 1 次；新 scope 列 Completed，證明舊 poisoned row 不阻擋 |
| W7 | 假 command 回 `payment.stale-callback`，同正式通知送兩次 | 兩次 422；服務 2 次；每次失敗均 Abandon，可重新認領 |
| W8 | 假 command 丟 `InvalidOperationException("boom")` | 例外原樣重拋；對應冪等列已 Abandoned |
| W9 | 同 MerchantTradeNo／TradeNo 分別正式簽 `RtnCode=失敗` 與 `RtnCode=1` | 兩次均 200；服務 2 次；儲存存在兩把不同 key |

### 派工書 §3.3：邊界六類

- 重複與併發：W3 重送、W7 失敗後重試、W9 同交易先失敗後成功、W10 無關欄位重送、V4 Captured 重放；新舊版本不會同時跑是派工書既定部署條件。
- 上下限：本包沒有新增數值範圍、數量或時間上限；RtnCode／TradeAmt 的非法整數格式由 V2 覆蓋，故其餘不適用。
- 非法狀態轉移：本包不新增 Payment 狀態轉移；V4 覆蓋 Captured 重放不二次發事件。
- 權限／偽造：W1、W2、W4、W6 證明偽造或欄位不合法的通知不寫冪等、不呼叫服務，也不阻擋後續真通知。
- 事件重放：V4 證明同 TradeNo 的成功通知不發第二次 `PaymentCaptured`；W3/W10 證明端點重放不二次呼叫服務。
- 部分失敗：W7 覆蓋可預期失敗後 Abandon／重試；W8 覆蓋例外時先 Abandon 再往外拋。
