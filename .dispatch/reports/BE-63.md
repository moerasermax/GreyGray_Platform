- 取號通知新增 `POST /v1/webhooks/ecpay/payment-info`；流程順序、事件 key、canonical hash、五種冪等結果與付款結果通知相同，只換成 `webhook:ecpay:payment-info` 與 `IEcpayPaymentInfoHandler.HandleEcpayPaymentInfoAsync`。
- P1：偽造簽章回 422，`TryBegin=0`、冪等列 0、handler 0。
- P2：成功把原始欄位同一實例交給 handler，以三欄複合 key／payment-info scope 完成，snapshot 與純文字回應皆為 `1|OK`。
- P3：`AlreadyCompleted` 回 `1|OK`、`InFlight` 回 409、payload mismatch 回指定 Problem；三者 handler／Complete／Abandon 均零呼叫。
- P4：handler 回 `payment.concurrent-update` 時先 Abandon 並回 409；handler 例外時用 `CancellationToken.None` Abandon 後原樣拋出。
- P5：付款結果與取號通知用相同 key 依兩種先後順序執行，兩邊各處理一次，scope 互不阻擋。
- P6：既有 W1～W10、D1 斷言沒有刪改；Checkout/Ordering 全包 161、failed 0。
- 訂單詳情只有 `OrderStatus.AwaitingPayment` 呼叫 `IPaymentInstructionsQuery`；O1 驗證七個 instructions 欄位完整投影。
- O2：PaidAwaitingClose、ClosedAwaitingDeparture、Cancelled、Completed 均回 `paymentInstructions: null` 且 query 0 呼叫；故意移除狀態 gate 時四案確實轉紅。
- O4：以「付款失敗後已無有效取號」與「上一組取號已過期」兩個命名案例驗證 query success/null 會回 null。
- O5：AwaitingPayment 查詢失敗回 Problem 422 與原錯誤碼，不偽裝成 null。

### §3 驗收矩陣與邊界六類

- 重複與併發：P3 覆蓋 AlreadyCompleted／InFlight／key mismatch，P5 覆蓋跨 scope 同 key；P4 覆蓋 concurrent-update。
- 上下限：本包沒有數值範圍輸入；事件 key 與 hash 形狀固定沿用付款結果路由，故不另造無關上下限案例。
- 非法狀態轉移：O2 對四種非 AwaitingPayment 狀態驗證不查取號資訊；以 red injection 證明 guard 有效。
- 權限／驗證：P1 覆蓋 webhook 簽章失敗且不建立冪等列；訂單詳情沿用既有 customer session 與 customer order query。
- 事件重放：P3 AlreadyCompleted 與 P5 同事件跨 scope 覆蓋重送邊界。
- 部分失敗：P4 覆蓋 handler 回 Result failure 與丟例外，皆先 Abandon；例外路徑不沿用已取消的 request token。
