**情境①　沒有任何 forwarded header、`Host: 127.0.0.1:5098`（模擬 dev 直連）**

```
$ curl -s -D - -o /dev/null "http://127.0.0.1:5098/orders" -H "Host: 127.0.0.1:5098"
HTTP/1.1 307 Temporary Redirect
location: /login?from=%2Forders
```

`Location` 沒有跟 spoofed host 走、也沒有跑掉——`resolveOrigin()` 在這個
情境下 `forwardedHost` 就是 `127.0.0.1:5098`，等於 `request.nextUrl.origin`
本身，Next 對「目標 origin 與目前請求 origin 相同」的重導向會序列化成相對
路徑（`/login?...` 而非帶完整 origin），這是 Next 自己在 `NextResponse.redirect`
序列化 `Location` header 時的正常行為，不是這次改動引入的問題——相對路徑
在 HTTP 語意上等同「同一個 origin 下的 `/login`」，瀏覽器與 curl `-L` 都會
正確導到 `127.0.0.1:5098/login`，跟改之前「沒有反代時導去正確位置」的行為
一致，沒有壞掉。

**情境②　`-H "Host: admin.greygray.tw"`（模擬反代保留原始 Host）**

```
$ curl -s -D - -o /dev/null "http://127.0.0.1:5098/orders" -H "Host: admin.greygray.tw"
HTTP/1.1 307 Temporary Redirect
location: http://admin.greygray.tw/login?from=%2Forders
```

`Location` 是 `admin.greygray.tw`，**不再是 `localhost`**——症狀解掉了。

**情境③　`-H "Host: 127.0.0.1:5098" -H "X-Forwarded-Host: admin.greygray.tw" -H "X-Forwarded-Proto: https"`（模擬反代改寫 Host、原始網域放 X-Forwarded-Host）**

## 我發現但沒做的事

**情境①的 `Location` 是相對路徑而非絕對 URL，跟派工書描述的「應該用
`127.0.0.1:<port>` 這個 origin」字面上不完全一樣，但驗證下來是 Next 自己的
正常序列化行為，不是這次改動的問題。** `resolveOrigin()` 在沒有 forwarded
header 時退回 `request.nextUrl.origin`，這個值本身就是 `http://127.0.0.1:5098`；
但 `NextResponse.redirect(new URL('/login', 'http://127.0.0.1:5098'))` 在目標
origin 與目前請求的 origin 相同時，Next 會把 `Location` header 序列化成相對
路徑（`/login?from=...`）而不是帶完整 origin 的絕對 URL——這是 Next 內部對
「同源重導向」的最佳化，瀏覽器與遵守 HTTP 語意的 client 都會正確處理。
情境②③的目標 origin（`admin.greygray.tw`）跟目前請求的 origin（`127.0.0.1:5098`）
不同，所以那兩個情境的 `Location` 仍是完整絕對 URL，符合派工書逐字描述。
沒有進一步查證這個「同源時序列化成相對路徑」的行為是 Next 15.5.24 一直都有、
還是這一波才出現——因為不管哪一種，都不影響這一包要解的症狀（spoofed Host
情境下 `Location` 不再是 `localhost`），也沒有被派工書列為必做項目，記在這裡
供下一個人參考，不影響交付判斷。

其餘沒有發現偏離派工書預期的地方。
