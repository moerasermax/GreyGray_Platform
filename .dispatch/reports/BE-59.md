# BE-59 自驗報告

本包是查證包，只新增 characterization test 與本報告，未修改 `src/`、`docs/`、`ops/`、模擬器或既有測試檔。

- Evidence：Release solution build 兩次皆為 0 warning／0 error；付款測試執行檔由 66 增至 78，前後皆 0 failed、1 skipped；C0～C10 共新增 12 個案例。
- Confidence：服務層現況與 webhook 冪等風險為高；綠界一般協定為高（官方文件）；測試特店 `3002607` 當下開通方式與「是否只能模擬付款」為低，明列尚待確認。
- 尚待確認：需登入綠界測試後台或由綠界技術支援確認 `3002607` 的實際付款頁選項、非即時付款在 stage 是否存在非模擬的入帳途徑，以及未傳 `PaymentInfoURL` 時是否保證不送任何 server-side 取號通知。

## 查證結論

### 1. 綠界協定

#### 1.1 `ChoosePayment=ALL` 與測試特店 3002607

- **已觀察**：官方說 `ALL` 不是固定清單，而是「依特店開通的付款方式」顯示選擇頁；可被 `IgnorePayment` 隱藏的類別目前列有 Credit、ApplePay、WebATM、ATM、CVS、BARCODE、TWQR、BNPL、WeiXin、DigitalPayment。官方也提醒付款方式會持續增加／調整，建議串接時固定指定方式。來源：[全方位金流付款](https://developers.ecpay.com.tw/2864/)。
- **尚待確認**：官方公開頁沒有列出測試特店 `3002607` 在本次查證日期實際開通的完整清單，所以不能把上述「可能類別」寫成付款頁「實際會全部出現」。應登入 [測試特店管理後台](https://vendor-stage.ecpay.com.tw/) 建一筆 `ChoosePayment=ALL` 訂單實看，或向綠界技術支援確認；測試帳號來源：[測試介接資訊](https://developers.ecpay.com.tw/2856/)。

#### 1.2 ATM／CVS／BARCODE 取號結果

- **已觀察**：官方定義取號結果以 Server POST 送至 `PaymentInfoURL`，不是付款完成用的 `ReturnURL`。ATM 取號成功 `RtnCode=2`；CVS／BARCODE 取號成功 `RtnCode=10100073`。共同欄位含 `MerchantID`、`MerchantTradeNo`、`TradeNo`、`TradeAmt`、`PaymentType`、`TradeDate`、`CheckMacValue`；ATM 另有 `BankCode`、`vAccount`、`ExpireDate(yyyy/MM/dd)`；CVS 有 `PaymentNo`、`ExpireDate(yyyy/MM/dd HH:mm:ss)` 且三段 `Barcode*` 空白；BARCODE 則有三段 `Barcode1/2/3`、`PaymentNo` 空白。來源：[ATM/CVS/BARCODE 取號結果通知](https://developers.ecpay.com.tw/2881/)。
- **已觀察**：ATM、CVS、BARCODE 各頁只承諾「若有設定 `PaymentInfoURL`」才會背景回傳取號資訊；未設時頁面停在綠界顯示繳費資訊，`ClientBackURL` 若有設定則提供返回商店按鈕。來源：[ATM 虛擬帳號付款](https://developers.ecpay.com.tw/2872/)、[CVS 超商代碼付款](https://developers.ecpay.com.tw/2874/)、[BARCODE 超商條碼付款](https://developers.ecpay.com.tw/2876/)、[全方位金流付款](https://developers.ecpay.com.tw/2864/)。
- **推論**：現行 AioCheckOut 沒有 `PaymentInfoURL` 或 `ClientRedirectURL`，因此正常協定路徑不會把取號結果送到 GreyGray webhook；客人只能在綠界頁看到帳號／代碼，再靠 `ClientBackURL` 返回。官方沒有寫出「未設時絕不 fallback 到 ReturnURL」這句排他保證，故 stage 實測仍列為待確認，不能把 fallback 當事實。

#### 1.3 繳費完成通知與延遲

- **已觀察**：付款完成以 Server POST 送 `ReturnURL`，成功 `RtnCode=1`，欄位包含 `PaymentDate`（付款時間，台北牆上時間字串）、`TradeDate`、`TradeNo`、`TradeAmt`、`PaymentType`、`PaymentTypeChargeFee`、`SimulatePaid` 與簽章。來源：[付款結果通知](https://developers.ecpay.com.tw/2878/)、[全方位金流付款](https://developers.ecpay.com.tw/2864/)。
- **已觀察**：若商店未正確回 `1|OK`，綠界官方說會每隔 5～15 分鐘重送、當天共四次；BARCODE 因超商端作業時間，可能在消費者付款後兩天才通知。來源：[付款結果通知](https://developers.ecpay.com.tw/2878/)、[站內付 ReturnURL](https://developers.ecpay.com.tw/9232/)。
- **尚待確認**：官方未對 ATM／CVS 的「首次通知時間減 PaymentDate」承諾上限；因此不能證明一定小於 20 分鐘。現行 20 分鐘 age gate 對 BARCODE 官方明載的兩天延遲顯然不相容，對 ATM／CVS 則是未受官方 SLA 支持的風險。

#### 1.4 測試商店的 ATM／CVS／BARCODE 付款完成

- **已觀察**：官方測試介接頁指示可在廠商後台對 ATM 訂單按「模擬付款」，且此種通知帶 `SimulatePaid=1`；付款通知文件也定義 `SimulatePaid=1` 就是由廠商後台模擬付款按鈕送出、不是客人真實付款。來源：[測試介接資訊](https://developers.ecpay.com.tw/2856/)、[付款結果通知](https://developers.ecpay.com.tw/2878/)。
- **已觀察**：現行設定 `AllowSimulatedPaid=false`；C9 實測 `SimulatePaid=1` 回 `payment.simulated-callback-rejected`，Payment 維持 Pending、不發事件。因此「後台模擬付款」確實走不到收款。
- **尚待確認**：官方頁只說 ATM／CVS／BARCODE「可」由後台模擬，沒有排他地寫「測試商店只能如此完成付款」；CVS／BARCODE 是否也一律只能模擬、以及 stage 是否存在銀行／超商測試入帳通道，需在後台各建一筆訂單或向綠界確認。不能據現有官方文字寫成已證實的「只能」。

#### 1.5 預設繳費期限

- **已觀察**：ATM `ExpireDate` 預設 3 天，可設 1～60 天；來源：[ATM 虛擬帳號付款](https://developers.ecpay.com.tw/2872/)。
- **已觀察**：CVS `StoreExpireDate` 預設 10080 分鐘（7 天），最多 43200 分鐘（30 天）；來源：[CVS 超商代碼付款](https://developers.ecpay.com.tw/2874/)。
- **已觀察**：BARCODE `StoreExpireDate` 預設 7 天，可設 1～30 天；來源：[BARCODE 超商條碼付款](https://developers.ecpay.com.tw/2876/)。
- **已觀察**：GreyGray 沒送 `ExpireDate`／`StoreExpireDate`，所以使用供應商預設；Payment 自己的 `ExpiresAt=30 分鐘` 只是「是否沿用同一付款 attempt」的應用層期限，和綠界 3／7 天繳費期限不是同一件事。

#### 1.6 同一個 MerchantTradeNo 重送 AioCheckOut

- **已觀察**：官方規格要求 `MerchantTradeNo` 必須唯一、不可重複使用；來源：[全方位金流付款](https://developers.ecpay.com.tw/2864/)。
- **尚待確認**：官方公開頁沒有承諾重送相同 `MerchantTradeNo` 時會顯示舊訂單、拒絕、或回哪個錯誤碼；所以不能把任一精確行為寫成事實。應以 stage 實送相同單號兩次並保留兩次 HTTP／頁面回應，或向綠界技術支援確認。現行 C10 在 30 分鐘內會重送同一組 AioCheckOut 欄位與同一 `MerchantTradeNo`，因此這不是純理論問題。

### 2. 現行程式在各通知下的行為

下表的 Payment／事件為新增 C0～C10 實測；訂單影響由 `PaymentCapturedHandler`／`PaymentFailedHandler` 與 `Order` 現行程式碼推得。付款失敗只寫 `LastPaymentFailureCode`，訂單仍 `AwaitingPayment`；該欄位不在 `OrderView`。付款成功後，純現貨訂單到 `ReadyToShip`，含預購則到 `PaidAwaitingClose`。前台付款結果頁輪詢約 19 秒後，未收款一律只看到「尚未確認付款／重新前往付款」；`PaymentDueAt` 永遠 null，期限文案不會出現。

| 通知／操作 | Payment 現況 | 事件 | 訂單現況 | 前台現況 |
|---|---|---|---|---|
| C0 正常 `RtnCode=1, SimulatePaid=0` | Captured | `PaymentCaptured` | ReadyToShip 或 PaidAwaitingClose | 輪詢後可看到已付款 |
| C1 ATM 取號 `RtnCode=2`（若送進服務） | Failed，FailureCode `2` | `PaymentFailed` | AwaitingPayment，只記 failure code | 仍顯示尚未確認付款 |
| C2 CVS/BARCODE 取號 `RtnCode=10100073`（若送進服務） | Failed，FailureCode `10100073` | `PaymentFailed` | 同上 | 同上 |
| C3 已由 C1 設 Failed，再送同單號付款完成 | `Capture` 丟 `InvalidOperationException`，仍 Failed | 無新增事件 | AwaitingPayment | 永遠不會顯示已付款 |
| C4 31 分鐘後重新發動 | 舊筆 Failed（Expire）、新筆 Pending、新單號 | 無事件 | AwaitingPayment | 得到新付款導轉；看不到舊筆已失效原因 |
| C5 C4 後舊單號付款完成 | `Capture` 丟例外 | 無事件 | AwaitingPayment | 錢可能已收，訂單仍未付款 |

### 3. 四條推論

#### (a) 取號通知、Failed 與同鍵不同 payload

- **已觀察**：C1／C2 證明取號通知若進 `PaymentApplicationService`，所有非 1 的 `RtnCode` 都把 Payment 設成 Failed 並發 `PaymentFailed`。C3 證明「服務層已處理取號，再直接處理付款完成」會由 `Capture` 丟 `付款狀態 Failed 不可轉為 Captured`。
- **已觀察**：真 webhook 在 commit `7096a27` 第 1072～1079 行用整份表單 hash 與 `MerchantTradeNo` 先 `TryBeginAsync`，第 1098 行才呼叫服務層；同鍵不同 hash 在 `IdempotencyStore.cs:131-134` 永遠回 `KeyReusedWithDifferentPayload`。因此取號通知若真的先走同一 webhook 且完成，付款通知會在端點先被 `payment.callback-payload-mismatch` 擋下，碰不到 C3 的 `Capture`。
- **推翻一部分表述**：若取號通知「完全沒進應用」，Payment 仍是 Pending，後續有效付款通知會像 C0 一樣成功 Capture，不會丟 C3 例外。C3 的必要前提是「取號已讓服務層把 Payment 設 Failed，但付款完成沒有被端點冪等先擋」；例如繞過端點直接呼叫服務，或未來清除／分離了冪等鍵。
- **推論**：官方正常協定送取號到 `PaymentInfoURL`，現況根本沒提供該欄位，所以「取號必定打目前 ReturnURL webhook」不成立；是否有未文件化 fallback 尚待 stage 實測。條件成立時，最終確實是錢收了但訂單不會變已付款。

#### (b) 30 分鐘後重開新單、舊代碼付款

- **已觀察**：C4、C5、C7 證實。31 分鐘後同 `OrderId` 會把舊 Payment Expire 成 Failed、不發事件，建立新 Payment／新 `MerchantTradeNo`；舊單號後來送 `RtnCode=1` 由 `Capture` 丟例外，送 `RtnCode=2` 由 `Fail` 丟例外。
- **推論**：實際 HTTP 是否先被端點冪等擋，取決於舊單號先前是否已有 webhook idempotency row；沒有時會進服務層並出現上述例外。結果都不會讓 Ordering 收到 `PaymentCaptured`。

#### (c) ATM 入帳通知晚於 PaymentDate 20 分鐘

- **已觀察**：C6 的兩個獨立情境證實：19 分鐘成功收款；21 分鐘回 `payment.stale-callback` 且仍 Pending。時間字串依正式碼以台北牆上時間組出，避免時區組錯。
- **推論**：被拒後的同內容重送只會增加 `clock.UtcNow - PaymentDate`，不能自行恢復；若第一次失敗已由 webhook `AbandonAsync`，相同 hash 可重入但仍持續 stale。官方沒有給 ATM 首次通知低於 20 分鐘的 SLA，BARCODE 甚至明載可晚兩天。

#### (d) 偽造 POST 先佔用冪等鍵

- **已觀察**：`7096a27:M1aEndpoints.cs:1064-1079` 在驗簽前只要求 `MerchantTradeNo`，即建立／接手冪等列；偽造表單進服務層後驗簽失敗，端點在第 1101 行 Abandon。`IdempotencyStore.cs:81-83` 只允許「相同 hash 且 Abandoned／過期」重新認領；第 131～134 行對不同 hash 永遠回 `KeyReusedWithDifferentPayload`。`AbandonAsync` 第 207～214 行只改狀態、不刪資料；全 repo 沒有清除 `platform.idempotency_key` 的工作。
- **推論（高信心）**：攻擊者只要取得瀏覽器表單中的 `MerchantTradeNo`，可先送任意偽造 payload；真正綠界通知因 hash 不同永久被擋。嚴重度建議 **High**：這不是直接竊款，但可造成已入帳款項無法驅動訂單與出貨，且是遠端、低成本、可針對單筆訂單重複利用的完整性／可用性問題。
- **修法方向**：在任何 idempotency 寫入前先驗證綠界 CheckMacValue 與 MerchantID；取號與付款完成若共用入口，也要先辨認已驗簽的事件類型，再用不同 scope／穩定事件鍵。另需一次性處理既有 poisoned rows，否則只改順序不會讓已被佔用的單號恢復。此項即使採 A 只收信用卡也必須在開張前修。

### 4. `PaymentDueAt` 是刻意保留還是漏做

- **已觀察**：`PaymentDueAt` 只出現在 `Order` 宣告、EF mapping、snapshot／view mapping 與 API response；`rg -n "PaymentDueAt" src` 找不到任何賦值。現有 saga timer 只有鑑賞期；沒有 ATM／超商期限 ADR 或「刻意保留」紀錄。
- **推論（高信心）**：這是漏做，不是可證明的刻意保留。Payment 的 30 分鐘 `ExpiresAt` 不能代替訂單的 3／7 天繳費期限。
- **不修的影響**：前台永遠不顯示繳費期限；訂單不會因逾期未付自動取消；客人拿舊帳號／代碼付款時可能撞 C5／C7；未重新發動的 Pending 即使過三天仍可被 C8 收款；庫存／團務也無法依可見且一致的 due time 收斂。

### 5. 修法選項與建議

#### A. 開張先只收信用卡

- 將 `src/Modules/Payment/GreyGray.Modules.Payment.Infra/EcpayGateway.cs:42` 的 `ChoosePayment = "ALL"` 改為 `"Credit"`；API 形狀可不變。
- 前台付款文案、FAQ、條款與客服說明需明確改為「僅信用卡」，移除 ATM／超商代碼／條碼及繳費期限暗示。
- 之後可再開，但不能只把字串改回 ALL；需先完成 B 的狀態、取號資訊、期限、冪等與模擬器支援。
- 成本粗估：後端限制＋前台文案各 1 包；安全問題 (d) 另 1 包且不可省。

#### B. 正式支援非即時付款

- Payment：送 `PaymentInfoURL`；新增「已取號待繳費」狀態與取號資訊（ATM bank/account、CVS code、BARCODE 三段碼、provider expiry）；migration、查詢契約與事件一起補。
- Host／安全：取號 endpoint 與付款結果 endpoint 分離，或至少在驗簽後依事件類型分 scope。建議 scope 如 `webhook:ecpay:payment-info` 與 `webhook:ecpay:payment-result`；key 至少含 `MerchantTradeNo + event kind`，付款結果可再納入 `TradeNo`。絕不能再用同一 `MerchantTradeNo`／同一 scope 讓取號與付款互斥，也不能在驗簽前寫鍵。
- Ordering：收到 provider expiry 後設定 `PaymentDueAt`；補逾期未付 saga／排程、取消與已付款競態規則。需明確決定「訂單期限」取綠界期限、業務期限，或兩者較早者。
- Storefront／契約／前端：凍結的新欄位呈現帳號／代碼／條碼與到期時間；付款結果頁不能只輪詢 19 秒後叫客人重付。
- 模擬器與測試：支援 ATM/CVS/BARCODE 取號、`PaymentInfoURL`、後續付款與 `SimulatePaid`；補兩類 webhook 重放、先後顛倒、到期與部分失敗測試。
- 粗估 **5～6 包**：安全／webhook 基礎、Payment 狀態與 migration、Ordering due+saga、Host+契約、模擬器+整合測試、前端；若凍結契約要先修訂，契約應由 Leader 先做。

#### C. 建議的分期做法

- **建議**：開張前先做 A，加上獨立且優先的 (d) 驗簽順序修補；把 B 排到取得正式綠界資格、確認產品確實需要現金型付款後再做。
- 理由（開張前風險 × 實作成本）：目前 B 不只是顯示一個代碼，而是跨 Payment、Ordering、契約、前端、模擬器與 saga 的完整產品能力；硬開 ALL 會同時暴露模擬付款拒絕、20 分鐘 stale、30 分鐘 attempt 與 3／7 天 provider 期限衝突、`PaymentDueAt` 缺失及 webhook 冪等問題。A 的行為限制成本小、可立即消除未實作付款方式的收款風險；(d) 則連信用卡也受影響，必須另修，不能被 A 掩蓋。
