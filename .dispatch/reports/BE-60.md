## 逐條自驗

1. **只改 `0023` trigger 函式**：把「同租戶存在 `parent_id = NEW.id`」檢查移到查詢上層之前，因此即使 `NEW.parent_id` 對應的上層尚未出現在同一語句的可見列中，仍會拒絕已經有子分類的 `NEW`。函式外的欄位、外鍵、CHECK、索引、trigger 建立、owner 斷言與重放內容零改動。推論確認：三層鏈 G→C→R 的孫→子→根列序由 C 的既有子分類檢查擋下；根→子→孫列序由 G 查到 C 已有上層擋下。Evidence：M9 兩種列序均斷言 `23514/category_two_level`，完整 Migrations 25/25。Confidence：高；尚待確認：無。
2. **M9**：同一條 multi-row INSERT 同時驗「孫、子、根」與「根、子、孫」兩種列序，兩者都要求 `23514` 與 constraint `category_two_level`。舊 trigger 先紅（第一種列序未拋例外），新 trigger targeted 與完整套件皆綠。
3. **S15**：採真交易競態，不使用純函式或攔截器。競態交易先把預定父分類改成子分類但暫不提交；服務層在 Read Committed 下先看見舊根分類並通過應用層檢查，SaveChanges 進 trigger 後實際等待同租戶 advisory lock；測試觀察到一把未授予 advisory lock 才提交競態交易。服務最後回 failure Result，`Error.Code == "catalog.category-depth-exceeded"`，沒有例外逸出。TEMP 副本拿掉服務層 catch 後，同一測試確實因 `CatalogPersistenceConflictException → DbUpdateException → PostgresException 23514` 變紅。Evidence：S15 targeted 1/1、負向 0/1、完整 IdentityCatalog 42/42。Confidence：高；尚待確認：無。
4. **BE-58 報告**：只把 §3.4 那一句改為「S13 驗對照表、S14 驗應用層先擋；資料庫路徑由 BE-60 的 S15 補上」，其他內容未改。
