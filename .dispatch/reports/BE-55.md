## 我發現但沒做的事

1. **★ 比派工書寫的更嚴重的 hardcode 清單缺口，Leader 複驗後追加成 #58 交給本包一併修**：
   `ops/install-dev-environment.ps1` 的 `$migrationFiles` 只列到 `0017`、
   `ops/verify-environment.ps1` 的 `$expectedCount` 也寫死 `17`，`0018`／`0019`／`0020` 從來沒補進去
   （Leader 起 dev 環境時被迫手動補套三支才發現）。已把 `0018`～`0022`（含 BE-54 的 `0021`）全部
   補進 `install-dev-environment.ps1`，`verify-environment.ps1` 的 `$expectedCount` 改成 22
   並更正兩處訊息字串。**另外自己多抓到一處 Leader 也沒列的**：`install-dev-environment.ps1`
   收尾的 `Write-Host "PASS 本機開發環境整備完成：...migrations 0001~0017。"`，同樣的問題（列死不會隨現況更新），
   已一併改成 0022。**這三個檔都已跑過 `install-dev-environment.ps1` 實測**，`PASS migrations：22 份已套用`。

2. **既有 Shared.Kernel 的 JSON converter 臭蟲，第一次被本包的型別撞到**：
   `GuidIdJsonConverterFactory.CanConvert`（`src/Shared.Kernel/Json/GuidIdJsonConverter.cs`，不在
   BE-55 的 allow 裡）用「有沒有一個型別為 `Guid` 的 `Value` 屬性 + 吃 `Guid` 的建構式」判斷
   「這是不是一個 `XxxId`」；`Nullable<Guid>`（也就是裸 `Guid?`）恰好也符合這兩個條件（`Nullable<T>.Value`
   剛好回傳 `T`），於是被誤判成 `XxxId`，嘗試 `GuidIdJsonConverter<Guid?>`——但 `Nullable<T>` 不滿足
   `where TId : struct` 的泛型限制，序列化與反序列化都會丟 `TypeLoadException`。全 repo 目前沒有
   任何一個 Contracts 型別用過裸 `Guid?`（都用 `XxxId?`），所以這個坑一直沒被踩到。**沒有修
   Shared.Kernel 本體**（不在 allow 裡，而且是全域性的行為變更，影響範圍要 Leader 判斷），
   改在自己的 `TicketOrderId(Guid Value)` wrapper 型別繞過——JSON 線上格式完全不變（一樣是無連字號
   32 碼字串），符合「定義自己要的最小投影，不吃對方完整狀態機」的既有慣例。**建議另開一個小工作包
   修 `GuidIdJsonConverterFactory.CanConvert`，讓它明確排除 `Nullable<>` 本身**——這個臭蟲之後任何一個
   模組只要在契約裡用裸 `Guid?`（例如某個可選的外部識別碼）就會踩到，而且錯誤訊息（`TypeLoadException`）
   完全看不出跟「用了 `Guid?`」有關，很難排查。

3. **`ReadOnly` 不能結案、`Operator` 可以的角色守衛，沒有走 route pipeline 測試**：這個 repo 目前
   沒有 route pipeline 測試基礎——比照既有慣例（例如 BE-44 的 admin `ReadOnly 403` 也是「子代理明講
   沒有路由管線測試基礎，留給活體」），`StaffRoleFilter` 是全 Admin Host 共用、已經在生產環境跑的
   既有機制，本包只新增了「哪個 `StaffRole` 掛在哪條路由」這件事。已經用真 dev Host 驗證了
   `StaffRoleFilter` 確實掛上路由（未登入回 401），但**沒有用種子帳號（`readonly.seed@greygray.dev`／
   `operator.seed@greygray.dev`）實際登入比較 403 vs 200**——找不到這兩個帳號的明文密碼
   （`ops/seed-dev-staff.ps1` 只在第一次建立時印出密碼，之後重跑只會回報「已存在，略過」，
   而這次不是我建立的帳號）。業務邏輯本身（結案／重複結案 409）已經在 `AdminSupportEndpointTests`
   用直接呼叫 handler 的方式測過。

4. **`CustomerNotificationFlowTests.cs` 的 `WorkerModuleSchemas` 刻意沒有補 `customer_service`**：
   這個測試只套用 `0001`～`0004` 這四份 migration（不含 `0022`），如果照抄 hardcode 表格第 4 列
   把 `customer_service` 加進 `WorkerModuleSchemas`，`ConfigureRolePasswordsAsync` 會對一個不存在的
   role 下 `ALTER ROLE ... PASSWORD`，直接讓這條 E2E 紅掉。而且 Worker 從來不需要這個連線字串

   沒有掛 `AddCustomerServiceModule`）。已在 `WorkerCompositionTests.cs` 加註解說明這是刻意不掛，
   `CustomerNotificationFlowTests.cs` 維持零改動。

5. **沒有測「同一 Idempotency-Key 重送」的完整 replay 語意**：`BffHttp.ExecuteIdempotentAsync` 本身
   是既有、已經被其他端點測過的機制，本包沒有另外驗證「第二次帶同一把 key 打會拿到快取回應」這條路徑
   （只驗了正常建立與各種驗證失敗）。

6. **防灌用滾動視窗，不是嚴格整點視窗**：`TryConsumeRateLimitAsync` 每次成功寫入都把 TTL 重設回
