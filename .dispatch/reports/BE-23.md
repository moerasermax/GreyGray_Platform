## 逐條自驗

### 必做 1　刪掉 `Order.cs:206`（`RefundedCurrency = amount.Currency;`）　✅

**只刪了那一行，前面兩行原封不動。** diff 是 `1 deletion(+0 insertions)`，見上面第 7 節。
`PaidAmountMinor = amount.AmountMinor;` 與 `PaidCurrency = amount.Currency;` 兩行都還在，
第 6 節的 `sed -n '196,213p'` 就是證據。

**對外行為有沒有變？沒有。** 唯一讀 `RefundedCurrency` 的投影是 `Order.cs:140-141`：

```csharp
RefundedAmountMinor,
RefundedCurrency ?? GrandTotal.Currency);
```

刪掉那一行之後，剛付完款的訂單 `RefundedCurrency` 是 `null`，投影走 `?? GrandTotal.Currency`；
刪掉之前是 `amount.Currency`。而 `CapturePayment` 前面已經擋掉 `amount != GrandTotal`
（197 行），所以 `amount.Currency` 恆等於 `GrandTotal.Currency`——
**兩者算出來是同一個 `Money(0, TWD)`，對 Contracts 的消費端零差異。**
這也解釋了為什麼 172 條測試沒有一條變紅：在應用層看不出來，只有資料庫的約束看得出來。

### 必做 2　把三條 check constraint 補進 `ConfigureOrder`　✅

補了 `orders_currency_consistent`、`orders_paid_consistent`、`orders_refunded_consistent`
三條，位置擺在各自對應的 `ck_orders_*_non_negative` 旁邊，順序與 `0006` 一致。

逐字比對（左＝`db/migrations/0006_m1a_core.sql:598-615`，右＝我寫進 EF model 的字串，
C# 的字串串接與換行不影響 SQL 語意）：

| constraint | `0006` 的定義 | EF model | 一致？ |
|---|---|---|---|
| `orders_currency_consistent` | `goods_total_currency = shipping_fee_currency AND goods_total_currency = grand_total_currency AND goods_total_currency IN ('TWD','JPY','USD','KRW','EUR','HKD','CNY','THB','GBP','SGD')` | 同左 | ✅ |
| `orders_paid_consistent` | `(paid_amount_minor IS NULL AND paid_currency IS NULL) OR (paid_amount_minor IS NOT NULL AND paid_currency IS NOT NULL AND paid_amount_minor >= 0 AND paid_currency = grand_total_currency)` | 同左 | ✅ |
| `orders_refunded_consistent` | `(refunded_amount_minor = 0 AND refunded_currency IS NULL) OR (refunded_amount_minor > 0 AND refunded_currency IS NOT NULL AND refunded_currency = grand_total_currency)` | 同左 | ✅ |

欄位名用的是資料庫的 snake_case（`refunded_amount_minor`），不是 C# 屬性名。

**這一條有沒有真的生效，不是用看的。** 新測試的第一段就直接查 `pg_constraint`：

```csharp
foreach (var constraint in new[]
         { "orders_currency_consistent", "orders_paid_consistent", "orders_refunded_consistent" })
{
    (await ConstraintExistsAsync(connectionString, constraint, cancellationToken))
        .ShouldBeTrue($"EF model 沒有宣告 {constraint}，EnsureCreatedAsync 的 schema 就守不住它。");
}
```

三條都要在 `EnsureCreatedAsync()` 建出來的 schema 裡查得到，否則測試自己先紅。
沒有這一段的話，往後有人不小心把 `HasCheckConstraint` 刪掉，測試會安靜地繼續全綠——
那正是這次要修的病。

**★ 派工書問的那件事：其餘幾條我沒有補。**
`orders_id_not_empty`／`orders_status_known`／`orders_shipping_policy_known`／
`orders_delivery_method_known`／`orders_quote_explain_array` 維持現狀，照 §5 的指示不多做。
理由跟派工書寫的一樣：那幾條是列舉範圍檢查，C# 的 `enum` 與 `OrderId` 已經在型別層擋住，
風險不同等級；而且多補一條就多一份「EF 與 migration 要同步維護」的負擔。
我評估後**同意不補**，沒有不聲不響多做。（但發現了另一組漂移，見下面「我發現但沒做的事」。）

## 我發現但沒做的事

### 1. ★ `ck_orders_totals_non_negative` 在 EF model 與 `0006` 不一致（同一家族的漂移）

不是我補的那三條，是**本來就在 EF model 裡的那一條**少了一半：

```
0006_m1a_core.sql:593-597
  goods_total_amount_minor >= 0
  AND shipping_fee_amount_minor >= 0
  AND grand_total_amount_minor >= 0
  AND grand_total_amount_minor = goods_total_amount_minor + shipping_fee_amount_minor   ← EF 沒有

OrderingDbContext.cs（現況）
  goods_total_amount_minor >= 0 AND shipping_fee_amount_minor >= 0
  AND grand_total_amount_minor >= 0
```

少掉的正是**唯一有業務意義的那一段**（總額必須等於商品加運費）。三個非負判斷 EF 都有，
但「總額對不對」EF 完全沒守。這跟這次的 bug 是同一個家族：
`EnsureCreatedAsync()` 建的測試資料庫守得比正式機鬆，所以任何把總額算錯的改動，
在測試裡不會被擋，上了正式機才炸。

**沒動的理由**：§5 只列了三條 `orders_*` 要補，這一條不在清單裡，而且它不是「補上缺的
constraint」，是**改動既有 constraint 的內容**——如果現在有任何測試資料剛好違反那個等式，
會有更大範圍的紅字。這需要整合者決定要不要納入這一波。改法很小：把那一段字串補回去即可。

### 2. `order_line_refund_consistent` 同樣只存在於 migration，EF model 沒有

`order_line_id_not_empty`／`order_line_mode_known`／`order_line_status_known`／

（`Order.cs:626-627`，缺貨補償），那裡兩個欄位是成對設的。所以是「目前恰好沒踩到」，
不是「有東西在守」——跟 `CapturePayment` 修之前的狀況一模一樣，只差運氣。

**沒動的理由**：`order_line` 的約束完全不在派工書 §5 的範圍裡，我不想在一個「修 bug」的
