## 逐條自驗

派工書 `docs/33-前端第十九波派工書.md` §5「可能寫錯的地方」逐條對應：

1. **`limit: 100` 只拿第一頁**：兩個新的 `useEffect`（`shipments/page.tsx` 第 92-106 行、
   `orders/page.tsx` 第 68-83 行）都在註解寫明是刻意取捨。
   - A（出貨單→訂單編號）：`orderIds` 本身是每張出貨單自己的欄位，不受 `listOrders`
     分頁影響，所以個別查不到就退回 `orderId.slice(0, 8)`（`ShipmentOrderLinksCell.tsx`），
     不會出現騙人的總數。
   - B（訂單→出貨進度）：`listShipments` 分頁會直接影響張數對不對，所以額外帶了
     `truncated` 旗標（`page.nextCursor != null`），有下一頁時文案自動附註「（可能不完整）」
     （`orders/_lib/shipmentProgress.ts`），不假裝張數是總數——`shipmentProgress.test.ts`
     最後一組測試釘住這件事。
2. **一張出貨單可以掛好幾張訂單**：`ShipmentOrderLinksCell` 對 `orderIds` 陣列逐一 map；
   `shipmentProgressText` 透過既有的 `shipmentsOfOrder`（`orderIds.includes`）比對，
   `shipmentProgress.test.ts`「一張出貨單掛多張訂單」那組測試兩個訂單 id 各自算一次確認互不干擾。
3. **狀態值用 enum 字串不要用數字**：兩個新檔都用 `S['ShipmentStatus']`／`S['OrderStatus']`
   字面值比對（`'Delivered'`、`'Cancelled'` 等），沒有出現數字轉換。
4. **兩張列表頁都是 client component**：新的兩個 `useEffect` 各自獨立、依賴陣列都是 `[]`
   （各自只抓一次），跟原本抓主要清單的 effect（依賴 `status`／`reloadKey` 或
   `debouncedQ`／`status`／`campaignId`／`reloadKey`）並排、互不覆寫，也不會在每次
   render 重打——沒有把新 effect 的依賴掛到會頻繁變動的 state 上。主要清單一樣先出
   `loading` 骨架，不等這兩個新 fetch。
5. **`orders/page.tsx` 跨資料夾 import `shipments/_lib/`**：`typecheck` 全綠，沒有 lint／
   路徑規則報錯；而且這個模式在 `orders/[orderId]/page.tsx`（FE-29，import
   `../../shipments/_lib/api`、`../../shipments/_lib/orderShipments`）已經先例，
   這次 `orders/page.tsx`（層級少一層，`../shipments/_lib/api`）與
   `orders/_lib/shipmentProgress.ts`（`../../shipments/_lib/orderShipments`）沿用同一寫法，
   沒有撞到需要停下來問的狀況。

派工書 §1 必做 C 的五項邊界：

1. 0 張／全部簽收／部分簽收／建了沒交運——判斷本身已由 `orderShipments.test.ts`
   （FE-29）釘住，這裡在 `shipmentProgress.test.ts` 補呈現層那一半的四種文案
   （「未建立」「全部已簽收」「3 張 · 還差 2 張簽收」「1 張 · 還差 1 張簽收」）。
2. 一張出貨單掛多張訂單：`shipmentProgress.test.ts`「★ 一張出貨單掛多張訂單」、
   `shipmentOrderLinksCell.test.tsx`「★ 一張出貨單掛多張訂單」兩邊都測了。
3. 訂單 map 查不到退回 `id.slice(0,8)`：`shipmentOrderLinksCell.test.tsx`
   「★ map 查不到就退回前 8 碼 id」，另外補了「合併出貨時其中一張查不到編號」
   那組確認不會互相拖累。
4. `Cancelled` 文案：`shipmentProgress.test.ts`／`shipmentProgressCell.test.tsx`
   都有「★ 已取消不顯示誤導的出貨進度」，且刻意用「底下掛著已簽收的出貨單」
   的樣本，確認不是因為沒有出貨單資料才恰好過。
5. 出貨單清單讀取失敗時兩張頁面都還能渲染其他欄位：
   - A：`ordersLoadFailed` 只影響「訂單」欄本身（退回原本「N 張」文字），
     不影響同一列其他欄位——這是 `DataTable` 逐欄 `renderCell` 的既有機制，
     沒有任何 early return 會整列消失；`shipmentOrderLinksCell.test.tsx`
     「★ 訂單清單整個讀取失敗」測的是這一格自己退化。
   - B：`shipments === null`（`shipmentsFailed` 為 true 時傳入）時
     `shipmentProgressCell.test.tsx`「★ 出貨單清單讀取失敗時仍然畫得出這一格」
     確認這一欄照樣渲染文字而不是拋例外；同理其他欄位不受影響。
   - 兩個新 `useEffect` 都各自 `catch`／第二個 `.then` 回呼處理失敗，
     不會拋到元件外面讓整頁 `ErrorState` 蓋掉主要清單。
