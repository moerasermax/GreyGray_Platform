## 我發現但沒做的事

### ①（第二輪已解，仍留下更大的一個觀察）派工書 §0.3 的前提不成立：`!` 拿不掉，因為請求型別是手寫的、不是 codegen 產的（**必做 A 卡在這裡**）

派工書假設「重生型別後這個 `!` 就是多餘的」。實際上 `checkout/page.tsx` 的 `CheckoutInput`
來自 `Parameters<typeof api.checkout>[1]`，而 `api.checkout` 的第二個參數型別是
`packages/api-client/src/endpoints/storefront.ts` 第 47-53 行**手寫**的 `CheckoutRequest`——
它是契約的一份人工複本，跟 `types.storefront.ts` 沒有型別上的連結，`pnpm api:generate` 不會動到它。

要的修改只有一行（第 49 行）：

```diff
-  readonly shippingPolicy: S['ShippingPolicy'];
+  readonly shippingPolicy?: S['ShippingPolicy'] | null;
```

改完之後 `checkout/page.tsx` 第 193 行的 `!` 才拿得掉。**我沒有改**，因為：
`packages/api-client/src/endpoints/storefront.ts` 不在 FE-26 的 `allow` 裡，
而且派工書 §2 明寫「不要動 `packages/api-client/src/` 手寫的部分」。
照 §6 的規矩停下來回報，不自己換做法（沒有加 cast、沒有在頁面裡另外宣告一個型別繞過去）。

**這不影響使用者現在的旅程**：`!` 只存在於編譯期，執行期送出去的值本來就是 `null`，
而後端 BE-41 之後接受 `null`。#37 已經被後端修掉了，這一項純粹是型別衛生。

**但它是一個真的洞**，而且比這一行大：`CheckoutRequest`、`AddCartLineRequest`、`QuoteCartRequest`……
整組請求型別都是手寫的複本。**契約改了，這裡不會自動跟上，也沒有任何東西會說話**——
這一次是「型別比契約嚴」（頂多多一個 `!`），下一次可能是「型別比契約鬆」，
那就會像 #37 一樣一路送到後端才炸。建議下一波（範圍給對的包）把這些請求型別改成
從 `paths[...]['post']['requestBody']['content']['application/json']` 推導，
手寫的只留 query／回傳的便利別名。這件事我只提，沒做。

### ②（第二輪已解）必做 C 在真瀏覽器裡還不會生效：呼叫端 `StorefrontTabBar.tsx` 不在 `allow` 裡

`activeTabHref` 現在收得下 `?next=`，但唯一的呼叫端是
`apps/storefront/app/_components/StorefrontTabBar.tsx` 第 41 行：

```tsx
const pathname = usePathname();       // ← Next.js 的 usePathname() 不含查詢字串
const active = activeTabHref(pathname);
```

`usePathname()` 拿不到 `?next=`，所以畫面上的行為不會變（`/login?next=/checkout` 仍然亮「我的」），
§4-4 的第三件事現在驗不過。需要的修改也只有幾行（第二個參數是選填的，介面向下相容）：

```diff
-import { usePathname } from 'next/navigation';
+import { usePathname, useSearchParams } from 'next/navigation';
...
   const pathname = usePathname();
+  const searchParams = useSearchParams();
...
-  const active = activeTabHref(pathname);
+  const active = activeTabHref(pathname, searchParams.toString());
```

`_components/` 不在 FE-26 的 `allow` 裡（§3 的所有權表只給了 `_lib/tabs.ts` 與它的測試），所以我沒改。
⚠ 一併提醒 Leader：`useSearchParams()` 在 Next.js App Router 會把用它的元件推進 CSR bailout，
`StorefrontTabBar` 是**根 layout** 上的元件，改之前值得先確認要不要用 `<Suspense>` 包住，
否則整站的靜態產生可能受影響——這正是「不要自己順手改」的那種決定。

### ③ `me/page.tsx` 原本沒有測試目錄，我新開了一個

§3 寫「`(account)/me/page.tsx` 與其測試」，但那一頁沒有測試、這個 workspace 也沒有 jsdom／
`@testing-library`（照 `tabs.ts` 開頭的說明，而且刻意不加相依）。
所以我照這個 repo 既有的做法把「順序與分支」抽成純函式 `(account)/me/logout.ts` 再測，
新目錄 `(account)/me/__tests__/`。兩個路徑都在 `allow:` 的 `(account)/me/` 底下。
元件本身的行為沒有變（成功導向首頁、失敗顯示同一句 `LOGOUT_FAILED_MESSAGE`、
`loggingOut` 的收放時機一模一樣）。

### ④ 草稿只在「按了送出才知道要登入」這條路上有用

存草稿的時機是 `handleSubmit` 收到 401。如果使用者是自己先去點「我的」→ 被丟到登入頁 →
登入完回到 `/checkout`，那條路上沒有經過 `handleSubmit`，也就沒有草稿。
這符合派工書的字面（「結帳頁 401 導向登入前」），我沒有擴大範圍去攔別的離開路徑
（例如 `beforeunload` 或每次改欄位就存）——每次改欄位就存會讓 `sessionStorage` 一直被寫，
而且會把「使用者自己清空的欄位」也存起來，那是另一個決定，不是我該自己做的。

### ⑤ `?next=` 的分頁判斷刻意不遞迴

`/login?next=%2Flogin%3Fnext%3D%2Fcheckout` 這種套娃只解一層：目的地是 `/login`，
落在「我的」底下 → 亮「我的」。不追進去是刻意的——遞迴解 `next` 等於讓一個外來字串
決定要跑幾圈。有測試涵蓋一般情形，這種病態輸入的結果是「亮我的」，不會出事。
