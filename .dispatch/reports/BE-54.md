## 逐條自驗

派工書的驗證要求在 §3（九條）。逐條對應：

### 1. #56 回歸：宅配下單後**修改地址簿**，舊訂單讀出來的收件人**不變**

`OrderRecipientSnapshotTests.Editing_the_address_book_does_not_change_an_existing_order` — **通過**。
地址簿 `王大明/0911222333` → 下單 → 改成 `李小華/0988777666` → 重讀訂單仍是 `王大明/0911222333`。
另外把前台回應也驗了：同一份 JSON 裡訂單層是 `"recipientName":"王大明"`、`shippingAddress` 區塊是
`"recipientName":"李小華"`（那一段契約本來就是即時回查）。**兩個值不一樣**正是「沒有從地址簿取」的證據。

### 2. #56 回歸：宅配下單後**刪除地址**，舊訂單的收件人**還在**

`Deleting_the_address_keeps_the_frozen_recipient` — **通過**。
`FakeCustomerDirectory.AddressExists = false` 之後，回應是 `"shippingAddress":null`（契約允許），
但 `"recipientName":"王大明"`／`"recipientPhone":"0911222333"` 照樣在。

### 3／4. 超商取貨缺姓名／缺手機 → 422 `checkout.recipient-required`（不是 500）

`Convenience_store_requires_the_recipient`（Theory 四組：缺姓名、缺手機、姓名全空白、手機全空白）
— **通過**，四組都回 `422` ＋ body 含 `checkout.recipient-required`，且訂單數為 0。
實作走 `Result.Failure`（`CheckoutApplicationService.ValidateDeliveryAsync` 的超商分支），不是丟例外。

### 5. 姓名或手機超長 → 擋下

`Overlong_recipient_is_rejected_as_a_business_failure` — **通過**。51 字姓名回
`checkout.recipient-name-too-long`、21 字手機回 `checkout.recipient-phone-too-long`，都是 422、都沒建單。
⚠ 這兩個錯誤碼是新的、**不在凍結契約的 422 清單裡**——理由與既有 `checkout.buyer-note-too-long`
一樣（那個碼也在程式裡、也不在契約清單裡）。詳見「我發現但沒做的事」第 1 條。

### 6. 事件重放：outbox 重送 `CheckoutCompleted` 後，訂單上的快照值不變

`Replayed_checkout_event_still_carries_the_frozen_recipient` — **通過**。
下單後先把地址簿改掉，再用同一把 key 進 `CompleteAsync`（＝`Cart.ReplayCompletedEvent()` 那條路），
重放出來的事件仍是 `王大明/0911222333`；把它再餵給 `Ordering.CreateFromCheckoutAsync`，
訂單 id 不變、快照不變、訂單數仍是 1。
**這條就是派工書 ★② 的哨兵**：`Cart.Complete` 的 `Completed*` 那一段漏了的話，這裡會是 null。

### 7. 冪等：同一把 `Idempotency-Key`、換掉收件人 → 422 `platform.idempotency-key-reused`

`Same_idempotency_key_with_a_different_recipient_is_rejected` — **通過**。
第一次 201、第二次（只換 `recipientName`）422 ＋ `platform.idempotency-key-reused`，
訂單只有一張且收件人是第一次那個。指紋加在
`CompleteCheckoutFingerprint`（`src/Hosts/GreyGray.Api.Storefront/M1aEndpoints.cs`）。

### 8. outbox 清理四條

`OutboxRetentionTests` 四個 Fact — **通過**：

- `Only_processed_and_expired_messages_are_deleted`：一次把四種列都放進去，只刪掉「已投遞且過期」那一列；
  未過期、**死信**、未投遞三列都還在。死信那一列刻意給了一個**過期的 `processed_at`**——
  只靠「`processed_at` 非 null」判斷的話會把它掃掉，而那正是派工書 ★⑤ 要擋的。
  再掃一次回 0，不會多動別的列。
- `Deletion_is_limited_to_the_batch_size`：5 筆、batch=2 → 2／2／1。
- `Retention_days_come_from_configuration`：同一筆 10 天前的訊息，保存 30 天不刪、保存 7 天刪掉

- `Non_positive_retention_days_are_rejected`：`FromDays(0)`／`FromDays(-1)` 丟
  `ArgumentOutOfRangeException`（組態寫錯要當場炸，不能安靜地變成「永不清理」）。

`Program.cs` 的開機驗證也點名 `OutboxRetentionSweeper`（組態錯誤要讓 Worker 開不起來）。

## 我發現但沒做的事

1. **兩個新錯誤碼不在凍結契約的 422 清單裡**：`checkout.recipient-name-too-long`、
   `checkout.recipient-phone-too-long`。契約只給了 `checkout.recipient-required`，
   但「缺值」與「超長」是兩件事，用同一個碼會讓前端沒辦法給對的訊息。
   我照既有慣例辦——`checkout.buyer-note-too-long` 也在程式裡、也不在契約的 422 清單與 `docs/05` 裡——
   **但沒有去改契約**（不在 allow，而且那是 Leader 的判斷）。
   Leader 要決定的是：(a) 維持現狀（清單本來就不是窮舉），或 (b) 補進兩份 OpenAPI 的 422 描述，
   或 (c) 要我改成共用 `checkout.recipient-required`。前端 FE-34 若要為超長顯示專屬訊息，就需要 (b)。

2. **舊地址簿資料的姓名或手機可能是空的**（派工書 §5 列為「停下來回報」的情況）。
   我查了：`ShippingAddressInput` 的 `recipientName`／`phoneNumber` 在契約上是 required，
   `Identity` 那邊也是必填欄位，所以**理論上不會有空值**。我的實作採取不讓結帳失敗的做法：
   空白就 `NormalizeOptional` 成 `null` 存進快照（而不是丟錯或擋下下單）。
   理由：真有髒資料時，擋下結帳會讓客人完全買不了東西，而快照是 null 只是後台看不到、可以補。
   **這是我自己的取捨，不是派工書指定的**——Leader 若希望改成「空值就擋下並要客人先補地址」，請說。

3. **`AdminOrderResponse` 仍然沒有 `ShippingAddressId`**。派工書 §0.1 把它列為現況的洞之一
   （「連 `ShippingAddressId` 都沒有」），但 §1.5 只要求加 `recipientName`／`recipientPhone`，
   契約（`openapi.admin.yaml` 的 `AdminOrder`）也只加了那兩個。所以我**沒有**加 `shippingAddressId`。
   後台現在看得到收件人姓名電話與超商門市，但宅配的**地址**仍然看不到——出貨要寄宅配的話這還不夠。
   這需要改契約，是 Leader 的決定。

4. **`platform.outbox_message` 沒有針對 `processed_at` 的索引**。清理用的是
   `WHERE processed_at IS NOT NULL AND processed_at < cutoff AND dead_lettered = false ... LIMIT n`，
   現有三個索引（`ix_outbox_pending` 只涵蓋未投遞、`ix_outbox_aggregate`、`ix_outbox_dead_letter`）
   都幫不上，表大了之後這是一次 seq scan。**我沒有加索引**：那要改 migration 的既有表定義或再開一支，
   而且要不要加得看正式機的實際資料量（每小時掃一次、`LIMIT 500`，現階段的量跑得動）。
   留給 Leader 判斷是否值得在下一波補。

5. **BE-55 的中間狀態讓「整包建置」與 `ops\test.ps1` 跑不完整**（見「指令與輸出」①②）。
   我沒有碰它的任何檔案，也沒有把它的失敗算成本包的綠燈。
   **Leader 驗收時請在 BE-55 收工後重跑一次整包 `ops\test.ps1`**——那一次才是真正的總驗收，
   我這邊只能證明「我這三個測試專案各自全綠，唯一的紅字堆疊指向 BE-55 的新組件」。

6. **沒有跑真環境的 HTTP 旅程**。dev 的三個 Host 是用 Release 跑著的舊版本（開工前就在跑），
   本包的改動沒有部署上去，所以「真的送一次 `POST /v1/cart/checkout` 帶 `recipientName`」
   沒有做過。派工書沒有要求，但這是自驗的邊界，先講清楚：
   上面所有 422／201 都是直接呼叫 `M1aEndpoints.CompleteCheckoutAsync` 得到的，
