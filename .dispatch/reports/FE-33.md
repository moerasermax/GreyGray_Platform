## 我發現但沒做的事

1. **`createCvsMapSession` 實際上仍會帶 `Idempotency-Key` header。** `packages/api-client/src/http.ts` 對所有 POST 自動補一把（`options.idempotencyKey ?? newIdempotencyKey()`），端點層關不掉。契約沒有要求冪等鍵，後端理應忽略這個 header；如果 BE-53 的端點會因為多一個 header 出事，要回來看。`http.ts` 不在 allow，沒動。
2. **mock 模式在瀏覽器裡的地圖流程沒有驗證、很可能走不通。** mock 沒有假地圖可以選，開票回的 `action` 我設成 `/checkout?cvsSelection=<票>`（表單 POST 回結帳頁、帶票）。但 Next 的 page 路由接不接表單 POST 我不確定；付款那條是另外做了 `app/mock-cashier/route.ts` 來接，而那個目錄不在 allow。這一包的 vitest smoke 都是 Node 端 MSW、不經過導覽，所以測不到這個。**真實流程要靠 BE-53 的模擬器假地圖驗**；如果 mock 瀏覽器模式也要能走，得另外給一個 route handler 的授權。
3. **`sessionStorage` 拿不到（私密瀏覽、配額滿）時，從地圖回來表單是空的**——既有草稿機制的限制，派工書明寫這一包不處理。補充一個細節：此時回程網址上的票仍會被讀到並顯示門市（票從網址來，不靠草稿），但配送方式、留言會不見。
4. **沒有草稿但回程帶票**（例如 storage 存不起來）：照派工書「只有票」，配送方式來自 `cart.quote`（伺服器記得上一次詢價）。如果連 `cart.quote` 都沒有，配送方式是「尚未選擇」，門市區塊要等客人自己選回超商取貨才看得到（票與門市其實已經讀好了）。沒有自作主張把配送方式設成超商取貨——那是猜。
5. **「只清選店票」寫草稿時，是從 storage 讀回來再清**，不是從 state 組。理由寫在頁面註解：這支會在進頁 effect 的閉包裡被叫到，那時 state 還是初始值，照 state 存會把剛合併好的草稿蓋成空的。代價：如果客人進頁後又打了留言、然後才撞到 422，storage 裡的留言是舊的——但畫面上的留言（state）不受影響，下一次前往地圖或 401 存草稿時會用 state 蓋回去。
6. **mock 的選店票結帳後沒有作廢**（真後端是一次性）。刻意沒做：冪等重送同一個 payload 會撞到「已用過」，mock 沒必要模擬到那麼細。
7. **`cvsMapFormFields` 用 `Object.entries`**，JS 物件的「整數樣式」鍵會被排到前面——跟付款頁同樣的做法，綠界欄位名都不是數字，實務上沒影響，但「順序不變」嚴格說只對非數字鍵成立。
8. 稽核 ⑪ 列的 7 個候選（`_lib/tabs.ts`、`login/page.tsx`、付款頁、`priceDisplay.test.tsx`、`package.json`、`pageShell.test.ts`）都是派工書裡「照抄範本」或「不准動」的參考用途，我沒有改它們。
