## 逐條自驗

### 派工書 §1

1. Storefront 訂單詳情注入 `IClock`；只透過同檔唯一的 `private static bool IsPaymentOverdue(OrderView order, DateTimeOffset now)` 判定：`AwaitingPayment && PaymentDueAt 有值 && now >= due.AddSeconds(1)`。逾期時不查取號，`paymentInstructions` 為 `null`。
2. 付款 route 保留 lambda 包法並綁定 `IClock` 後 `await InitiateCustomerPaymentAsync(...)`；原付款邏輯抽成 `internal static Task<IResult>`。執行順序由測試確認為：已取消先回 409；逾期回 422、code `ordering.payment-overdue`、訊息「繳費期限已過，正在等待確認付款，不能再付款。」；兩者都不呼叫 `payments.InitiateAsync`。
3. Storefront 詳情把 `CancelledAt`、`CancellationSource` 從 `OrderView` 原樣帶出；共用結帳 `ToOrderAsync` 與取消回應的 `PaymentOverdue` 都維持 `false`。`ToOrderAsync` 簽章未改。
4. Admin 訂單回應帶出 `PaymentDueAt` 與 `CancellationSource`；`ToAdminOrderAsync` 簽章未改。
5. 所有新增 Host 測試使用 `FakeClock`。既有 PaymentInstructionsHostTests 的 O1～O5 斷言未修改，只在兩個呼叫點補入 `new FakeClock(Now)`。

### 派工書 §3 H1～H6

- H1：同一期限測 `due` 為未逾期、`due + 1 秒` 為逾期；`PaymentDueAt = null`、Paid、Cancelled 即使時間已過也不逾期。
- H2：逾期詳情回 `paymentOverdue = true`、`paymentInstructions = null`，且取號 query 次數為 0；未逾期維持既有查詢路徑。
- H3：Customer、Staff、System 三種 `CancellationSource` 都逐一驗 JSON 值；有效訂單驗 `cancelledAt/cancellationSource = null`，舊取消資料驗 `cancelledAt` 有值而 source 可為 null。
- H4：逾期自助取消仍回 200、source 為 Customer、`paymentOverdue = false`；共用結帳輸出也驗 `paymentOverdue = false` 且取消欄位為 null。
- H5：逾期付款驗 422、精確 code/message、付款呼叫 0；同一 idempotency key 重試仍為 422，證明 422 未被快取。已取消且逾期時驗 409 優先；PaidAwaitingClose/ReadyToShip 過期仍會進付款服務；`due` 當下仍可付款。
- H6：Admin mapper 驗 `paymentDueAt`、`cancellationSource` 的屬性值及 JSON 名稱／值。

### docs/45 邊界六類

- 重複與併發：同一 idempotency key 在逾期 422 後重試，兩次都為 422 且付款呼叫 0，覆蓋重複請求；本包沒有新增共享可變狀態或併發寫入，既有付款 idempotency 機制不變。
- 上下限：覆蓋期限當下、期限加一秒、期限缺值；符合 ADR-044 的一秒緩衝邊界。
- 非法狀態轉移：覆蓋已取消優先 409、逾期待付款 422，以及 PaidAwaitingClose/ReadyToShip 不被期限誤擋。
- 權限：本包不更動授權政策；所有 Customer 端點案例沿用既有 customer session，Admin mapper 不新增端點或角色。
- 事件重放：不適用；本包只調整 Host DTO 映射與付款前置檢查，沒有發布、訂閱或重放事件。
- 部分失敗：逾期待付款代表計時器尚未完成取消的時間窗；詳情不再呼叫取號 query，付款也在外部付款呼叫前停止，因此取號／付款服務失敗不會遮蔽逾期結果。
