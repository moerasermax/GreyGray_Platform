## 逐條自驗

### 必做 1　migration `0017_inventory_lot_wholesale_idempotency.sql`（新檔）✅

逐項照 `0016` 的形狀：`\set ON_ERROR_STOP on`、`BEGIN;`、`SET ROLE greygray_owner;`、
`ADD COLUMN IF NOT EXISTS ... varchar(255)`、**過濾式**唯一索引
`ux_lot_tenant_creation_key (tenant_id, creation_idempotency_key)
WHERE creation_idempotency_key IS NOT NULL`、`COMMENT ON COLUMN`、`RESET ROLE;`、
owner 檢查 `DO $$`（schema 清單換成 `inventory`／`platform`）、`COMMIT;`。

`COMMENT` 明講這**不是**「同一個 SKU 只能進一次貨」，而且補了一句 0016 沒有的情境：
NULL 也可能代表「這一列不是走 `POST /v1/lots` 建的」（帶回入庫走 `GoodsReceived`，
冪等由 `platform.processed_message` 保證）。

**沒有**動 `from_campaign_id` 的 nullability，**沒有**碰 `quantity_available`。
證據：上面「指令與輸出 §6」的真 DB 輸出，以及
`WholesaleReceiptPostgresTests.Migration_0017_creates_an_enforcing_filtered_unique_index`
——它斷言 `indexdef` 含 `WHERE (creation_idempotency_key IS NOT NULL)`、
兩列沒有鍵的資料可以共存、同一把鍵第二次插入噴 `23505`。

### 必做 2　`LotAggregate` 加批發進貨的工廠方法 ✅

- 新工廠 `CreateFromWholesale(id, tenantId, skuId, quantity, unitCost, batchCode,
  creationIdempotencyKey, receivedAt)`。
- 守衛：冪等鍵 1..255（`platform.idempotency-key-required`）、`quantity <= 0`
  （`inventory.invalid-wholesale-quantity`）、成本為負或幣別未知
  （`inventory.invalid-wholesale-unit-cost`）、`batchCode` 超過 64 字元
  （`inventory.invalid-batch-code`）。全部回 `Result` 業務失敗，不是例外。
  最後一條是我加的：`batch_code` 是 `varchar(64)`，超長是可預期的使用者輸入，
  讓它一路走到資料庫才變成例外違反六條鐵則第 5 條。
- `Source = LotSource.LocalWholesale`、`FromCampaignId = null`、`BatchCode` 由呼叫端給。
- 新增 `CreationIdempotencyKey` 屬性與 EF 映射
  （`creation_idempotency_key`，`HasMaxLength(255)`，加上逐字對齊 0017 的過濾式唯一索引宣告）。
- `ReceivedAt` 由應用服務用 `IClock` 取（`clock.UtcNow`），聚合只收參數——
  跟 `CreateFromGoodsReceived` 一致。測試 `first.Value.ReceivedAt.ShouldBe(Now)`
  用的是 stub clock，直接證明沒有偷用 `DateTimeOffset.UtcNow`。
- **私有建構式的 `Guid fromCampaignId` 改成 `Guid?`**（派工書說「怎麼讓它接受 null 由你決定」）。
  選這個而不是多載：多載要複製整段賦值，兩份會漂移。
  `CreateFromGoodsReceived` 仍然傳 `fromCampaignId.Value`，**行為一個字都沒變**，
  由既有測試 `GoodsReceived_creates_lot_and_is_idempotent`（斷言
  `lot.FromCampaignId == campaignId.Value`）守著。

另外加了 `ToContract()`：成本／來源／入庫時間缺任何一項就丟 `InvalidOperationException`。
理由寫在 XML doc——`lot_receipt_fields_consistent` 保證這四欄要嘛全有要嘛全無，
全無的列只可能來自 0010 之前，程式裡沒有任何路徑建得出來，所以那是「不該發生」，
要吵出來而不是安靜編一個 0 元成本（六條鐵則第 5 條）。

### 必做 3　Inventory 的應用服務：模組層冪等 ✅

- `Inventory.Contracts` 新增：`WholesaleReceipt`、`AdminLotListRequest`、`LotPage`、

| 打錯 `skuId` | 擋得住 | **會建出孤兒批號** |
| SKU 在重試之間被刪 | **重播永遠回不了原批號**（#22 A″ 死路），唯一出路是換新鍵，而換新鍵正好繞過模組冪等、建出第二個批號 | 重播照常回原批號 |

`InventoryApplicationService.SameReceipt` 的 XML doc 裡。
「同一把鍵送了不同數量」在 HTTP 那一層已經被 `IIdempotencyStore` 的 payload 比對擋成 422。
