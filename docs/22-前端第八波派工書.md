## 0. 這一波要解的問題：FE-18 的修法對目前的部署拓樸沒有效果，改用另一個做法

**背景**：第七波 FE-18 依照第七波派工書的診斷，把
`experimental.trustHostHeader: true` 加進 `apps/admin/next.config.ts`。
FE-18 **完整照做，而且額外做了 Leader 當時做不到的即時驗證**（Leader 撞到
Windows/pnpm standalone symlink 的 `EPERM` 崩潰，FE-18 改用 `next start`
成功繞過，走的是同一段 `next-server.js` runtime 邏輯）——結果發現**這個修法
沒有解掉症狀**：spoofed `Host` header 送進去，`Location` 還是
`http://localhost:<port>/login`，跟修好前一模一樣。

FE-18 往下追查 Next.js 15.5.24 原始碼，找到兩層原因（**你不需要重查，
直接看結論，完整推導在 `.dispatch/reports/FE-18.md`**）：

1. **build 階段就被蓋掉**：`next/dist/build/index.js` 產生
   `.next/required-server-files.json`（build 產物，改動前不存在，`next build`
   之後才會出現）時寫死
   `trustHostHeader: _ciinfo.hasNextSupport`（不是讀 `config.experimental`
   裡的值）。`_ciinfo.hasNextSupport` 只有跑在 Vercel 才是 `true`，自架
   （ADR-003）一律 `false`。不管 `apps/admin/next.config.ts` 裡寫什麼，
   最終烘進 standalone 產物的值都是 `false`。
2. **就算沒有第 1 層（`.next/required-server-files.json` 那一步），也走不到 `trustHostHeader` 那個分支**：
   `next-server.js` 的 `attachRequestMeta()` 判斷式是
   `this.fetchHostname && this.port ? 用 HOSTNAME:PORT 組 URL : (trustHostHeader ? 用 Host header : 原樣)`——
   **先**檢查 `fetchHostname && port`，兩者皆真就直接用 `HOSTNAME:PORT`，
   `trustHostHeader` 根本不會被讀到。standalone `server.js` 的
   `hostname = process.env.HOSTNAME || '0.0.0.0'` 只要吃到環境變數就是真值，
   而 `ops/deploy.ps1:215` `:222` 固定設 `HOSTNAME=127.0.0.1`——所以正式機
   部署拓樸下這個分支**永遠不會被評估**，無論 `trustHostHeader` 是什麼。

**改用另一個做法**：不依賴 Next.js 這個內部機制，**middleware 自己讀
反向代理送來的 header 手動組 origin**。這是任何框架在反向代理後面都通用的
做法（不是 Next.js 特有的權宜之計），優點是完全不受上面兩層 Next.js 內部
邏輯影響，也不需要動 `ops/deploy.ps1` 的 `HOSTNAME` 設定（那個設定讓
listener 只聽 loopback，`ops/deploy.ps1:222` 註解寫明「不要把 BFF listener
暴露到 LAN」，是有意的安全考量，這一波不去動它）。

**關鍵依據（FE-18 的即時驗證已經證實）**：FE-12（第九波）與 FE-18（第七波）
都測過 `X-Forwarded-Proto: https` **會**被 Next 正確反映在 `nextUrl.protocol`
上（壞掉的只有 host 那一段，protocol 那一段本來就是對的）——所以這一波的
修法**只需要覆寫 host，不需要覆寫 protocol**，用 `request.nextUrl.protocol`
（已經正確）拼上從 header 讀到的 host 即可，範圍比重寫整個 origin 邏輯更小、
更不容易引入新問題。

## 5. 工作包

### FE-19　middleware 改讀反向代理 header 手動組 origin，取代失敗的 trustHostHeader　🔴

**相依**：無　**獨佔**：見 §3

#### 必做 1　`apps/admin/next.config.ts` 拿掉 `experimental.trustHostHeader`

移除 FE-18 加的那一段（`experimental: { trustHostHeader: true } as
NonNullable<NextConfig['experimental']>` 那幾行與它的註解），恢復成這一波
之前完全沒有 `experimental` 區塊的樣子。**這是清理，不是保留「以防萬一」**——
它已經證實沒有效果，留著只會讓下一個人誤以為這裡解決過問題。

#### 必做 2　`apps/admin/middleware.ts` 改用反向代理 header 組 origin

在既有的 `isPublicPath` 函式附近，新增一個函式（形狀示意，變數命名與寫法
你自己判斷，但邏輯要對）：

```typescript
/**
 * standalone server.js 固定帶 HOSTNAME 環境變數，導致 Next 內部一律用
 * HOSTNAME:PORT 組 request.url 的 origin，完全不理會實際的反向代理 Host
 * header（即使開了 experimental.trustHostHeader 也一樣，見 docs/22 §0）。
 * 正式機用 cloudflared 反代，這裡改成自己讀 x-forwarded-host／host header
 * 手動組 origin，不依賴 Next 那套機制。
 *
 * protocol 不受同一個問題影響（X-Forwarded-Proto 已經被 Next 正確反映在
 * nextUrl.protocol 上，FE-18／FE-12 都驗證過），所以只覆寫 host 這一段。
 */
function resolveOrigin(request: NextRequest): string {
  const forwardedHost = request.headers.get('x-forwarded-host') ?? request.headers.get('host');
  if (!forwardedHost) {
    return request.nextUrl.origin;
  }
  return `${request.nextUrl.protocol}//${forwardedHost}`;
}
```

把 `middleware()` 函式裡建立 `loginUrl` 的那一行從
`new URL('/login', request.url)` 改成 `new URL('/login', resolveOrigin(request))`。
其他邏輯（`isPublicPath`、cookie 檢查、`searchParams.set('from', ...)`）
不用動。

**為什麼優先讀 `x-forwarded-host` 再退回 `host`**：如果反向代理有明確設定
「轉發時保留原始 Host」，`host` header 本身送到 origin 時就已經是正確的公開
網域；但有些反向代理設定會改寫 `Host` header 本身（送真正要連的內部位址），
改用 `X-Forwarded-Host` 攜帶原始網域。這一波還沒設定 cloudflared（E2 未
動工），不確定最終會是哪一種，兩個都讀、優先信 `X-Forwarded-Host`，涵蓋
兩種可能，不用等 E2 決定了才能寫這段程式碼。

**自驗（寫進 `.dispatch/reports/FE-19.md`）**

1. `pnpm typecheck` 全過
2. `pnpm build` exit 0（admin 與 storefront 都跑）
3. `git diff --name-only` —— 只有 `frontend/apps/admin/next.config.ts` 與
   `frontend/apps/admin/middleware.ts`
4. **即時驗證（這一包的核心）**：沿用 FE-18 已經驗證過的方式（用完整
   `node_modules` 跑 `next start`，`HOSTNAME=127.0.0.1 PORT=<你選的埠>`），
   送這幾個請求：
   - 不帶任何 forwarded header、`Host: 127.0.0.1:<port>`（模擬 dev 直連）：
     `Location` 應該用 `127.0.0.1:<port>` 這個 origin，行為跟改之前一致
     （不能讓沒有反代的情境壞掉）
   - `-H "Host: admin.greygray.tw"`（模擬反代保留原始 Host）：`Location`
     應該是 `http://admin.greygray.tw/login?from=...`，**不再是
     `localhost`**
   - `-H "Host: 127.0.0.1:<port>" -H "X-Forwarded-Host: admin.greygray.tw"
     -H "X-Forwarded-Proto: https"`（模擬反代改寫 Host、原始網域放
     X-Forwarded-Host）：`Location` 應該是
     `https://admin.greygray.tw/login?from=...`
   三種情境都要貼出實際的 `curl` 指令與 `Location` header 內容，不是推測
5. **dev 環境親自跑一次**：`pnpm dev:admin`，瀏覽器或 curl 打一個未登入的
   受保護頁面，確認導向 `/login` 正常（沒有反代時的行為不能被這次改動影響）
