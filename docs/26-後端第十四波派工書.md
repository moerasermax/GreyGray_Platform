## 0. 這一波要解的兩個問題

**都是 Leader 這一輪重新驗證 D 階段時，第一次真的用瀏覽器＋真後端跑完整登入

### 0.1　BE-29：三個 admin 列表端點對真資料庫全部 500

啟動 `D:\GreyGray` 三個 Host、用種子帳號登入後台，點開三個清單頁：

| 頁面 | 端點 | 結果 |
|---|---|---|
| 訂單列表 | `GET /v1/orders?limit=20` | **500** |
| 出貨列表 | `GET /v1/shipments?limit=20` | **500** |
| 現場採購清單（有資料時） | `GET /v1/campaigns/{campaignId}/purchase-items` | 高度懷疑同一個成因（見 0.1.3），這一輪沒有真的團資料可以端到端重現，但程式碼是同一個模式 |

`admin.out.log` 的例外都是同一個形狀：

```
System.InvalidOperationException: The LINQ expression 'DbSet<Order>()
    .Where(o => o.TenantId == @tenantId)
    .OrderByDescending(o => o.PlacedAt)
    .ThenByDescending(o => o.Id.Value)' could not be translated. ...
```

（`shipments` 的例外一字不差同一個訊息，只是 `DbSet<Shipment>()` 與
`s.Id.Value`。）

#### 0.1.1　根因

`OrderByDescending(...).ThenByDescending(x => x.Id.Value)`——**用 `.Value`
拆開強型別 ID（`OrderId`／`ShipmentId`／`PurchaseItemId` 這種 wrapper）
再排序，EF Core 的值轉換器（value converter）在 `ThenBy` 這個位置不知道怎麼翻譯
成 SQL。** 只要直接對強型別 ID 本身排序（`ThenByDescending(x => x.Id)`，
不要 `.Id.Value`），值轉換器就能正常處理整個屬性的轉換——這正是
`CampaignRepository.cs:56`（`.ThenByDescending(campaign => campaign.Id)`）與
`LedgerQuery.cs:134`（`.ThenByDescending(entry => entry.Id)`）已經在用、
而且跑得通的寫法。

**壞掉的三處，一模一樣的手誤：**

| 檔案 | 行 | 現在的寫法 |
|---|---|---|
| `src/Modules/Ordering/GreyGray.Modules.Ordering.Infra/OrderingRepository.cs` | 128 | `.ThenByDescending(order => order.Id.Value)` |
| `src/Modules/Fulfillment/GreyGray.Modules.Fulfillment.Infra/FulfillmentRepository.cs` | 67 | `.ThenByDescending(shipment => shipment.Id.Value)` |
| `src/Modules/Procurement/GreyGray.Modules.Procurement.Infra/ProcurementRepository.cs` | 36 | `.ThenBy(item => item.Id.Value)` |

**為什麼 172～176 條既有測試完全沒抓到**：這三個方法（`ListAdminAsync`／
`GetCampaignListAsync`）在既有測試裡只被 fake in-memory repository 頂替過
（`GreyGray.M1a.CheckoutOrdering.Tests/TestDoubles.cs`、
`GreyGray.M1b.Procurement.Tests/ProcurementTests.cs` 裡的 `FakeOrderQuery`／
`FakePurchaseItemRepository` 之類），從來沒有一條測試讓真正的 EF repository
對著真 Postgres（或 testcontainers）跑過這個查詢。`ProcurementCompensationPostgresTests.cs`
與 `M1b3SeamsPostgresTests.cs` 這種對 Postgres 跑的測試存在，但沒有一條剛好
呼叫到 `GetCampaignListAsync`。這是測試覆蓋的真實缺口，不是巧合。

#### 0.1.2　`ProcurementRepository.cs:36` 這一處為什麼「高度懷疑但沒有實測到」

`GET /v1/campaigns/{campaignId}/purchase-items` 在呼叫這條查詢之前，
先用 `ICampaignQuery` 查一次 campaign 是否存在——這一輪的開發環境資料庫裡
沒有任何 `campaign.campaign` 列（`GET /v1/campaigns?limit=5` 回空陣列），
所以每次呼叫都在查詢執行前就先撞到 `procurement.campaign-not-found` 404，
根本沒機會執行到 `.ThenBy(item => item.Id.Value)` 那一行。**但程式碼形狀
與另外兩個已經實測壞掉的一模一樣，值轉換器層級的翻譯失敗跟資料存不存在
無關**——這是靜態比對出的高信度判斷，不是臆測，你的驗收要用真資料親自證實。

### 0.2　BE-30：兩處過期的守衛讓「已付款訂單原路退款」整條路徑完全打不到

**master 進度表的「現在卡在哪」把這一項標成 ✅ BE-17 已解決——那句話只對了
一半。** BE-17／BE-18 確實把「呼叫綠界真退刷 API」「儲值金退款擋到 M3」這兩件
事在 `OrderingApplicationService` 這一層做完、測完了（`OrderingApplicationService.cs:29-30`
的註解自己寫著：「**整條退款流程已經實作完成**，缺的只有客人主動加值入口與
到期規則」）。**但沒有人拿掉 admin HTTP 端點那一層更早、更舊的守衛**——那個
守衛寫在 M1a-6（`e1a30a3`，BE-17／BE-18 都沒碰過這個檔案），比 BE-17 早了
好幾波，當時綠界退刷 API 真的還沒做，是合理的 fail-closed。**現在它變成一個
沒人記得要拆的路障，把已經蓋好的路整條擋住。**

`src/Hosts/GreyGray.Api.Admin/M1aEndpoints.cs` 兩處一模一樣：

```csharp
if (input.RefundTo == RefundDestination.OriginalPaymentMethod &&
    existing.Value.PaidAmount is { IsZero: false })
{
    return Result<AdminOrderResponse>.Failure(
        "payment.original-refund-not-configured",
        "綠界原路退款尚未完成 provider API 設定，訂單未取消；可改選退款至儲值金。");
}
```

- `:204-210`（`POST /v1/orders/{orderId}/cancel`，整張訂單取消）
- `:290-296`（`POST /v1/orders/{orderId}/lines/{lineId}/cancel`，單一品項取消）

**兩處都在呼叫 `ordering.CancelAdminAsync`／`ordering.CancelLineAsync` 之前**，
只要訂單有付款金額、退款去向選原路退款，就直接回 422，**根本不會呼叫到
application service**，BE-17 蓋好的綠界退款路徑完全沒有機會被觸發。

**這不是臆測，有一條既有測試明確鎖死這個行為**：
`tests/GreyGray.M1a.CheckoutOrdering.Tests/AdminCancelLineEndpointTests.cs:66-87`
建一筆已付款訂單，用 `RefundDestination.OriginalPaymentMethod` 呼叫取消，
斷言回應是 `422` 且 `body` 包含 `"payment.original-refund-not-configured"`，
**還額外斷言 `ordering.CancelLineCalls.ShouldBe(0)`**——這條測試存在的目的
就是證明「不應該呼叫到 application service」，跟 BE-17／BE-18 蓋好的東西
互相矛盾。**176 條測試全過的原因是這條測試本身就在幫這個過期行為背書**，
不是巧合，是這條測試也要跟著這一包一起更新。

**影響範圍**：後台「取消整張訂單」「取消單一品項」選「原路退款」，只要訂單
已經付款，現在點下去必定 422，**唯一能選的是儲值金，而儲值金又被
`GuardStoredValueRefund` 擋到 M3**——實務上等於**已付款訂單現在完全取消不了**，
跟「現在卡在哪 #1」原本要解決的症狀一模一樣，只是換了一層擋。
