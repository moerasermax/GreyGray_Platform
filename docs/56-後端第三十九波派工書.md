## 0. 事實（Leader 2026-09-19 自己讀過原始碼查證）

### 0.1 這個缺陷怎麼來的

第四十波 BE-55 做客服工單時，`Ticket` 需要一個**可選的**訂單識別碼。
它第一次寫成裸的 `Guid?`——**全 repo 至今沒有任何契約型別用過裸 `Guid?`**（都用 `XxxId?`），
於是踩到一個一直存在、但從來沒被觸發的臭蟲：序列化與反序列化都丟 `TypeLoadException`。

BE-55 沒有改 `Shared.Kernel`（不在它的 allow，而且是全域行為變更），
改用自己的 `TicketOrderId(Guid Value)` wrapper 繞過，並建議另開包修根因。**這一包就是。**

### 0.2 根因（`src/Shared.Kernel/Json/GuidIdJsonConverter.cs` 第 28-41 行）

`CanConvert` 用「是 value type ＋ 非 primitive ＋ 非 enum ＋ 有 public 的 `Value` 屬性且型別是 `Guid`
＋ 有吃 `Guid` 的建構式」判斷「這是不是一個 `XxxId`」。

**`Nullable<Guid>`（也就是 `Guid?`）把這五個條件全部滿足**：

- `Nullable<T>` 是 value type、不是 primitive、不是 enum
- **`Nullable<Guid>.Value` 的回傳型別剛好就是 `Guid`**
- **`Nullable<Guid>` 有 `Nullable(Guid value)` 這個建構式**

於是 `CreateConverter` 會去 `MakeGenericType(typeof(Guid?))`，
但 `GuidIdJsonConverter<TId>` 的限制是 `where TId : struct`，
而 **C# 規格明文把 `Nullable<T>` 排除在 `struct` 限制之外**——執行期直接 `TypeLoadException`。

⚠ **錯誤訊息完全看不出跟「用了 `Guid?`」有關**，下一個踩到的人會查很久。

## 1. 要做的事

### 1.1 修 `CanConvert`

在 `CanConvert` 開頭明確排除 `Nullable<>`：

```csharp
if (Nullable.GetUnderlyingType(typeToConvert) is not null)
{
    return false;
}
```

⚠ **要寫一段註解說明為什麼**——不寫的話，後人看到「排除 Nullable」會以為是多餘的防禦。
註解要講清楚「`Nullable<Guid>` 剛好滿足下面每一個條件，而 `where TId : struct` 不接受它」。

⚠ **不要改其餘四個條件**，也不要改 `CreateConverter`、`GuidIdJsonConverter<TId>` 本體。
`XxxId?`（例如 `OrderId?`）走的是 `System.Text.Json` 內建的 `NullableConverter`，
把底層型別交給我們的 converter，那條路**本來就是對的、不能動**。

### 1.2 測試（`tests/GreyGray.Contracts.Tests/`）

在 `WireFormatTests.cs`（已經有 `GuidIdJsonConverter` 的測試）或同目錄新檔加：

1. **先紅後綠的迴歸測試**：一個含裸 `Guid?` 屬性的型別，序列化與反序列化都不丟例外，
   而且 wire 格式是 `"..."`／`null`（不是物件）。
   ⚠ **修之前這條一定要真的紅**（丟 `TypeLoadException`），修完才綠——
   請在報告裡寫出「修之前跑到的實際錯誤訊息」
2. `XxxId?`（可為 null 的強型別 ID）**行為不變**：null 寫成 `null`、有值寫成無連字號 32 碼字串
3. 非 null 的 `XxxId` 行為不變

### 1.3 順手確認（不要改）

`src/Modules/CustomerService/` 裡 BE-55 為了繞過而加的 `TicketOrderId` wrapper，
**這一包不要拿掉**。理由：它已經在生產路徑上、JSON 線上格式與 `Guid?` 相同，
拿掉是另一個決定（要改契約型別、要重跑那包的測試），不在這一包。
**在報告裡寫一句「TicketOrderId 現在可以改回 Guid? 了，但本包沒有改」** 就好。
