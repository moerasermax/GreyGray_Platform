## 1. 修法：**已經定死，不要重新設計**

BE-34 列了五個選項，Leader 看完證據後**沒有直接選其中任何一個**，
理由與最終決定如下——**你不需要重新評估，照做即可**：

**為什麼不選 BE-34 的選項 1（讓 lambda 標記「副作用已產生」）**：它把
「該不該標記」變成每個呼叫點的人為判斷，**判斷錯了沒有任何東西會說話**。
BE-34 自己就寫了這正是這個 repo 一再踩到的失敗模式。

**為什麼不選選項 3（只讓 `ToOrderAsync` 不失敗）**：只治 checkout 一處，
S12／A3／A4／A20 要各自比照，而且把「catalog 讀不到」變成靜默故障。

### 定案：把 `action` 拆成「做事」與「組回應」兩段，讓**結構**保證正確性

在 `BffHttp` 增加一個**新的多載**（舊多載一律不動，33 個呼叫點裡只有這一波要改的那幾個改用新多載）：

```csharp
public static async Task<IResult> ExecuteIdempotentAsync<TState, TResponse>(
    HttpContext context,
    IIdempotencyStore idempotency,
    string scope,
    object? request,
    Func<CancellationToken, Task<Result<TState>>> work,      // 會失敗；失敗時 abandon 是安全的
    Func<TState, CancellationToken, Task<TResponse>> render, // 組回應；不准讓整個請求失敗
    int successStatus,
    CancellationToken cancellationToken)
```

語意：

1. `work` 回 `IsFailure` → **照舊 `AbandonAsync` ＋ 回 Problem**（這是對的：
   失敗發生在還沒 commit、或 commit 了但底層可重入，重試是安全的）
2. `work` 成功 → **副作用已經產生，從這一刻起絕對不准 `Abandon`**
3. `render` 負責把 `TState` 變成回應。**它的回傳型別不是 `Result<T>`，是 `T`**
   ——型別系統直接讓「組回應失敗」這件事表達不出來，不需要任何人為標記
4. `render` 若真的丟例外 → 仍要 `CompleteAsync`（存下退化回應）**再**往上丟，
   **不准 `Abandon`**

**這個設計的重點是第 3 點**：不是靠人記得標記，而是靠型別讓錯誤的寫法編不過。

### 各端點怎麼落地

- **`work`** ＝ 原本 lambda 裡到「取得領域物件」為止的那幾步
  （checkout 是 ①`CompleteAsync` ②`CreateFromCheckoutAsync`，回 `OrderView`）
- **`render`** ＝ 原本的 `ToOrderAsync`／`ToAdminOrderAsync`，**改成不會失敗的版本**：
  讀不到 SKU／customer／payment 就填退化值

**退化值的硬性要求**：

1. **不准改契約。** `docs/05-API契約.md` 已凍結。退化回應必須仍然符合現有 schema
   ——欄位該有值就要有值，不准塞 `null` 到不可為 null 的欄位。
   例如商品名稱讀不到時用 SkuId 的字串形式當顯示名，不要留空。
2. **不准靜默。** 每一次退化都要留下可觀測的痕跡（用這個 repo 既有的 log 機制，
   照 `CLAUDE.md` 的慣例）。「把故障藏起來」是 BE-34 對選項 3 的主要批評，
   不要在這裡重蹈覆轍。

### 同步 ECPay webhook 的手寫版

`src/Hosts/GreyGray.Api.Storefront/M1aEndpoints.cs:777` 起的
`POST /v1/webhooks/ecpay` 複製了一模一樣的 `IsFailure → Abandon`／`catch → Abandon`
形狀。BE-34 把它分類為**安全**（`HandleEcpayCallbackAsync` 自己有冪等），
**所以這一波不改它的行為**，但要**加一行註解**指向這一波的新多載，
