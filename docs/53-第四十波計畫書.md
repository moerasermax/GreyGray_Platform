## 盤點結果（2026-09-19，Fable ＋ Gemini 跨家盤點，Leader 逐條複驗過三個關鍵點）

### 跟先前記載不符、要更正的三件事

1. **結帳端點是 `POST /v1/cart/checkout`**，不是 `/v1/checkout`。
2. **宅配的收件人姓名與手機早就在收**——存在 Identity 地址簿，AES-256-GCM 加密
   （`IdentityDbContext.cs:125-126`、`IdentityDataProtector.cs:33-74`）。
   缺的不是「沒有欄位」，是**訂單沒有凍結快照**，而且**後台完全沒輸出**。
3. 「後台只看得到遮罩」是錯的描述。後台訂單詳情的 `CustomerContactMasked` **永遠寫死 `null`**
   （`src/Hosts/GreyGray.Api.Admin/M1aEndpoints.cs:1170`，Leader 複驗過）——後台不是看到遮罩，是**什麼都看不到**。

### 順帶挖出來、本波要一起修的缺陷

**#56　宅配收件資訊沒有凍結快照，舊訂單會跟著地址簿變動。**
訂單只存 `ShippingAddressId`，前台訂單詳情是**即時**回查地址簿
（`src/Hosts/GreyGray.Api.Storefront/M1aEndpoints.cs:1482-1507`，Leader 複驗過）。
於是：

- 客人事後修改地址 → `IdentityServices.cs:304-333` 是原地 `Update`，**舊訂單的收件資訊跟著變**
- 客人事後刪除地址 → `IdentityServices.cs:346` 是實體刪除，**舊訂單的 `shippingAddress` 直接變 null**

這跟 ADR-038 對超商門市所做的「凍結進訂單」是同一個問題的兩半，門市補了、宅配沒補。

**#57　`platform.outbox_message` 永不清理，個資會永久留存。**（Leader 2026-09-19 自查）
`OutboxDispatcher.cs:89` 投遞成功後只寫 `message.ProcessedAt = clock.UtcNow`，
全 `src/Platform/Outbox/` **沒有任何 `Remove`／`Delete`／`Purge`／保存期限**。
已投遞的訊息連同 payload 永遠留在表裡。

這不是本波帶進來的（`buyerNote` 客人留言早就在 payload 裡），但**本波會顯著加重**：
收件人真實姓名與手機會跟著 `CheckoutCompleted` 進去，而且永遠不會消失。

**處置**：本波在 BE-54 順手補一道「已投遞且超過保存期限的 outbox 訊息刪除」，
天數做成組態（比照 ADR-025 鑑賞期天數的做法）。
⚠ **`IsDeadLettered` 的訊息不刪**——那是還沒處理完的問題，刪掉就查不出來了。

### 契約層的既存矛盾（本波必須解掉）

`docs/api/openapi.admin.yaml:1380-1384` 已凍結的文字寫著：

> 遮罩後的聯絡方式。**要看明文必須另外呼叫並填寫存取理由**，每一次讀取都會寫進 audit。

**那個「另外呼叫」的端點程式裡不存在**，而且使用者現在拍板不遮罩。這段描述要正式修訂。

### 稽核現況（影響 ADR-039 怎麼寫）

`IAuditWriter` 介面在 `src/Platform.Abstractions/Audit/IAuditWriter.cs:41-62`，
但**沒有任何實作類別、三個 Host 都沒註冊、`db/migrations` 裡連 `audit.` 資料表都沒有**。
Identity 的 `CustomerDirectoryService.GetContactAsync` 因此一律回 `audit.writer-unavailable`
（而且它在 `src` 裡沒有任何呼叫者）。

**BE-50（`docs/49-後端第三十四波派工書.md`，「讓稽核真的會寫」）確實還沒生效**，migration 序號已被往後推三次。

## 要寫的 ADR

### ADR-039　訂單收件人資訊：凍結快照、後台全員明文、不加解鎖閘門

- **決定**：收件人姓名與手機在下單時凍結進訂單（宅配從地址簿抄、超商由客人填）；
  後台**所有員工**看得到明文，不遮罩、不要求填存取理由。
- **理由**：出貨是全體營運工作，遮罩＋解鎖會讓每次出貨多一道摩擦而換不到實際保護
  （後台帳號本來就能看到訂單全貌）。使用者 2026-09-19 拍板。
- **取捨與失效條件（一定要寫進 ADR）**：
  - 快照**存明文**，不加密。理由：後台全員可見，加密只擋得住直接讀資料庫的人；
    而同一份資料會隨 `CheckoutCompleted` 進到 `platform.outbox_message` 的 payload，
    只加密 `orders` 而不加密 outbox 是自欺。
  - **失效條件**：一旦後台開始有「外部合作夥伴帳號」或員工數量成長到看不住，這個決定要重審。
  - Identity 地址簿**維持加密**不動（它的存取路徑不一樣）。
- **否決**：① 只給出貨角色看＋每次寫稽核（使用者明確不要）；
  ② 加密快照（見上，擋不住真正的洩漏路徑，卻讓後台查詢變複雜）；
  ③ 不做快照、繼續即時查地址簿（#56 就是這樣來的）。

### ADR-040　客服工單自建模組，不接 AI、不開 GitHub issue

- **決定**：新開 `Support` 模組，工單留在站內、後台自己的列表看；
  前台小幫手走引導式選單，不接 AI。
- **理由**：客人的姓名與訂單內容不該離開自己的系統（GitHub issue 是公開或需外部帳號、
  還要把 token 放正式機）；引導式選單不會亂承諾退款，也不花 API 費用。使用者 2026-09-19 拍板。
- **否決**：GitHub issue、寄 Email 給客服信箱（沒有列表可追蹤處理狀態）、接 AI 自動回答。

   （`Storefront/Logistics/CvsLogisticsEndpoints.cs:350-365`，`SetAsync` 帶 TTL、`GetAsync` 取回）。
   **Garnet 掛掉時 fail-open（放行）並記 error log**——理由：客服留言不是安全邊界，
   KV 掛掉時寧可收到灌水，也不要讓真客人問不了問題；何況 session 也靠 Garnet，
   它掛掉時整站登入已經先壞了（見記憶：pid 檔還在但行程不見 → 登入 500）。
   覆驗改回答：**這個 fail-open 的判斷有沒有反例**。
3. ~~**新模組的 schema／role／連線字串**投遞路徑~~ **已結案**：Gemini 覆驗指出漏了 hardcode 清單，
   Leader 複驗後擴充成**五處**，見 BE-55 第 7 項的表。
4. ~~**冪等指紋加欄位**~~ **已結案**（Gemini 覆驗，證據 `src/Platform/Http/BffHttp.cs:412-414`）：
   指紋序列化後算 SHA256 比對。加了新欄位之後，**同一把 `Idempotency-Key` 換掉收件人會回 422
   `platform.idempotency-key-reused`**，而現況是直接回快取的舊回應、把新收件人靜靜吞掉。
   **這個行為改變是我們要的**——它剛好補掉一個「換了收件人卻不會被察覺」的洞。
   實作者要為這個新行為補一條測試。
5. ~~**`Support` 算業務模組還是支撐模組**~~ **已由 Leader 自查定案**：
   架構測試的 `SupportModules` 語意是「**不被任何業務模組依賴——它們只訂閱事件**」
   （`ModuleBoundaryTests.cs:22-33` 的註解原文）。客服工單模組**要被兩個 Host 直接呼叫、不是只訂閱事件**，
   所以**不進** `SupportModules`，只進 `Modules` 清單。

   ⚠ **因此模組不要叫 `Support`**——那個名字會跟「支撐模組（`SupportModules`）」語意撞在一起，
   以後每個讀架構測試的人都要重新判斷一次。**改名為 `CustomerService`**，schema 用 `customer_service`。
   （本計畫書其餘各處提到的 `Support` 一律以此為準。）
