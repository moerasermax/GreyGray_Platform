## 2. 必做

### 2.1 先解掉契約缺口（見 §4），不要先寫程式

`AdminOrderLine` 沒有 `refundedAmount`。不先處理的話，後端會做出一筆
**後台畫面顯示不出來的退款**——`docs/06` FE-8 明確要求
「缺貨退款的 line 要看得出來：`status = Unavailable` ＋ `refundedAmount`」。

### 2.2 應用層

`IOrderingApplication` 加：

```csharp
Task<Result<AdminOrderResponse>> CancelLineAsync(
    OrderId orderId,
    OrderLineId lineId,
    string reason,
    RefundDestination refundTo,
    CancellationToken cancellationToken);
```

回傳型別跟 `CancelAdminAsync` 一致——契約的 `200` 回的是 `AdminOrder`，不是 204。

### 2.3 領域

- 該 line 轉成 §4.2 決定的狀態，算出 `refundedAmount`
- **其餘 line 續行，訂單不整張作廢。** 這是這條端點存在的全部理由，
  也是客人最怕的事（`docs/06` FE-8：「客人最怕的是以為整張單沒了」）
- 訂單層的金額要跟著調整；**不要在前端算，也不要讓兩個地方各算一次**
- 金額一律 `Money`，時間一律經 `IClock`（六條鐵則 1、2）

### 2.4 Ledger

開部分退款分錄。**分錄是對既有事實的記錄**——先有退款這件事，才有分錄，
順序不要顛倒。借貸必須平（前端驗收會實際加總畫面上的兩欄比對）。

### 2.5 發布 `OrderLineCancelled`

欄位早就定好了，現在是死的：

```
EventId, OccurredAt, TenantId, OrderId, LineId, Reason, RefundAmount, RefundTo
```

走各模組自己 DbContext 的 outbox（ADR-016），不要繞過。

### 2.6 端點

`src/Hosts/GreyGray.Api.Admin/M1aEndpoints.cs`，照**整張單取消**的既有形狀做
（同檔案 line 175 起，那是這一條的對照組）：

- `x-required-role: Operator`
- `BffHttp.ExecuteIdempotentAsync` ＋ `Scope(context, $"orders:{orderId}:lines:{lineId}:cancel")`
- **沿用整張單取消的 `OriginalPaymentMethod` 擋門**——
  已付款且選原路退回時回
  `payment.original-refund-not-configured`「綠界原路退款尚未完成 provider API 設定」。
  不要因為這是新端點就默默讓它通過，那會變成一筆記了帳卻沒真的退的錢
- request body：`{ reason (maxLength 200), refundTo }`，照契約
- 找不到 order／line 回 `ordering.order-not-found` 系列，不要丟例外

## 4. 已確認的契約缺口（動手前要先決定）

### 4.1 `AdminOrderLine` 沒有 `refundedAmount`

實測：`openapi.storefront.yaml` 的 `OrderLine` **有** `refundedAmount`（line 1250），
`openapi.admin.yaml` 的 `AdminOrderLine` **一次都沒出現**。
但 `docs/06` FE-8 要求後台要看得出退了多少。

兩條路，選一條並凍結：

1. **`AdminOrderLine` 補 `refundedAmount`**（與 Storefront 對稱）。
   契約是凍結的，走 `docs/05` 的流程提出——這是**新增可空欄位**，
   不是破壞性變更，前端 codegen 重跑後既有型別不受影響
2. 明確決定後台不顯示退款金額，只看 `status`。
   那要回頭改 `docs/06` FE-8 的要求，並讓前端拿掉對應顯示

**建議走 1。** 對帳的人看到一個 line 變成缺貨卻不知道退了多少，
下一步一定是去翻分錄——那正是這個欄位要省掉的事。

**決定（2026-08-29）**：採第 1 條。`AdminOrderLine` 新增可空 `refundedAmount`，
與 Storefront 對稱；既有欄位、required 集合與 enum 均不改。

### 4.2 該 line 應該轉成哪個狀態

`OrderLineStatus` 同時有：

- `Unavailable = 3`，XML doc 寫「現場缺貨。該 line 取消並退款，**其餘 line 續行，訂單不整張作廢**」
- `Cancelled = 9`

那段 XML doc 描述的正是這條端點的行為。但端點的 summary 是「取消單一品項並退款」，
兩者語意重疊。要先決定並寫進 `docs/02-事件與狀態機.md`：

- 「現場缺貨」與「營運手動取消單品」是同一件事還是兩件事？
- 如果是兩件事，`reason` 不足以區分，狀態要能區分

不決定就實作的話，前端的 `StatusPill` 與時間軸會出現兩種語意混用的值。

**決定（2026-08-29）**：這條 endpoint 的 frozen description 明寫「現場缺貨時用」，
因此轉 `Unavailable`；`Cancelled` 保留給整單取消時的 line，或未來另行定義的
非缺貨單品取消。兩者不靠 `reason` 猜測。
