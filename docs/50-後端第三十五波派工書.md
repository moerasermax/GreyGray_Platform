### 0.2 `db/migrations/0001_schemas_and_roles.sql`——15 個 schema、15 個對應 login role，兩者都不設密碼

逐行重新核對（第一版把陣列位置說反了，這裡是修正後的版本）：

- **第 71-76 行**：對這 15 個名字**逐一** `CREATE SCHEMA IF NOT EXISTS ... AUTHORIZATION greygray_owner`，並且逐一建立同名的

  **所以正確的說法是：15 個 schema、15 個對應的 login role（含 `greygray_platform`），外加 2 個 NOLOGIN 共用角色，一共 17 個角色。**
- **第 108-111 行**是另一個、只有 14 個元素（不含 `platform`）的陣列，但它的用途不是建 schema，是讓那 14 個模組的 role
  額外拿到 `platform` schema 的讀寫權限（因為 outbox／idempotency 表在 `platform`，見第 101-104 行的註解）。
  **這個陣列跟「要 DROP 哪些 schema」無關，不要把它算進 15 個 schema 的推導裡**（第一版犯的錯就是這裡）。
- **密碼**：第 76 行 `CREATE ROLE %I LOGIN NOBYPASSRLS IN ROLE greygray_app` **沒有 `PASSWORD` 子句**——0001 建出來的 15 個
  login role 建立當下是**沒有密碼的**，連不進去。正式機能連是因為 `ops/deploy.ps1:168-203` 另外用 `ALTER ROLE ... PASSWORD`
  對其中**實際被 13 個模組使用**的 role 設密碼、寫進 `secrets\module-role.password`。
  **結論不變（reset 腳本不能碰任何 ROLE），但理由要更正**：不是「migration 設了初始密碼、DROP 會弄丟它」，
  而是「migration 完全不管密碼，密碼是 `deploy.ps1` 事後另外管理的獨立狀態，reset 腳本沒有能力、也沒有必要去重建它，

**CASCADE 的範圍警告（外部覆驗抓到，原始版本沒提）**：`DROP SCHEMA <name> CASCADE` 會連同該 schema 底下**所有**物件
（表、view、function、sequence……）一起砍掉，**也會砍掉其他 schema 裡任何依賴這些物件的東西**（例如有人手動在 `public`
建了一個依賴 `inventory.lot` 的 view，即使 `public` 不在這 15 個名字裡，那個 view 照樣會被連坐刪除，這是 PostgreSQL
`DROP ... CASCADE` 的標準行為，不是這支腳本的邊角案例）。**這一包假設「這 15 個 schema 以外沒有東西依賴它們」，
如果你在查證過程中發現有例外（例如 `public` schema 裡有東西），停下來回報，不要自己決定要不要一併處理。**

### 0.4 這是一支會清光正式資料庫的腳本，計畫書明文要求「刻意的確認」

`docs/46-D3開張資料基準與還原演練計畫書.md` §3.1：「必須有一道刻意的確認（不能手滑就把正式庫清掉）」。
現有專案裡沒有這種「輸入資料庫名稱回顯確認」的既有模式可抄，你要自己做：
呼叫端必須另外傳一個 `-ConfirmDatabaseName` 參數，值要**逐字元**（區分大小寫，`-ceq`）等於 `-DatabaseName`，
不相等就 `throw`，而且**在丟這個例外之前不能連線資料庫、不能執行任何 DROP**。

**額外防呆（外部覆驗提醒）**：`-DatabaseName` 這個字串最終會被當成 psql 的 `--dbname` 參數值，而 psql 的 `--dbname`
接受**連線字串（conninfo）格式**，也就是說如果有人（或未來某支呼叫腳本）不小心把一長串 `host=... dbname=... user=...`
當成 `-DatabaseName` 傳進來，`-ConfirmDatabaseName` 只要逐字元照抄那一長串也會「通過確認」，但實際連線目標可能被
conninfo 字串裡的 `host=`／`port=` 覆寫成別的機器。**這一包要多加一道檢查**：`-DatabaseName` 與 `-ConfirmDatabaseName`
都不准包含 `=`、空白、或換行字元，違反就直接 `throw`（訊息講清楚「這裡只接受單純的資料庫名稱，不接受連線字串」）。

## 1. 必做

### 必做 A　新增共用的 migration 清單掃描邏輯：`ops/lib/Migrations.ps1`

新增一個小的共用檔（比照 `ops/lib/` 現有的 `Process.ps1`、`Deployment.ps1` 那種 dot-source 函式庫模式），
提供一個函式，例如：

```powershell
function Get-SortedMigrationFiles {
    param([Parameter(Mandatory)][string]$RepoRoot)
    $migrationRoot = Join-Path $RepoRoot 'db\migrations'
    Get-ChildItem -LiteralPath $migrationRoot -Filter '*.sql' -File
        | Where-Object { $_.Name -match '^\d{4}_[A-Za-z0-9_-]+\.sql$' }
        | Sort-Object Name
        | ForEach-Object { $_.FullName }
}
```

**不合法檔名（不符合 `^\d{4}_[A-Za-z0-9_-]+\.sql$`）要被過濾掉還是要噴錯，由你判斷並在報告裡說明理由**
（兩種都說得通：過濾掉比較寬容但可能悄悄漏掉打錯字的檔案；噴錯比較安全但如果資料夾裡本來就有非 migration 用途的
`.sql` 檔會擋住整支腳本——**先掃一次 `db/migrations/` 底下有沒有非四位數開頭的 `.sql` 檔，看到什麼再決定**）。

`ops/reset-database.ps1`（必做 B）與 `ops/install-dev-environment.ps1`（必做 E）都改用這個函式取得清單，
不要各自維護一份。

### 必做 B　新增 `ops/reset-database.ps1`

參數（比照 `ops/invoke-migrations.ps1` 的命名習慣）：

[Parameter(Mandatory)][string]$ConfirmDatabaseName      # 必須逐字元等於 $DatabaseName，見 §0.4

行為順序（每一步都要，順序不能換——§0.3／§0.4 已經解釋過為什麼順序重要）：

   **第 1、2 步都不能連線資料庫。**
3. 組出要 `DROP` 的 15 個 schema 清單（§0.2 那份，寫死在腳本裡當常數陣列，不要用 `information_schema` 動態撈——

4. 用 `ops/lib/Migrations.ps1` 的 `Get-SortedMigrationFiles` 取得完整、排序過的 migration 清單。
5. **在做任何 DROP 之前**，把第 4 步拿到的每個檔案路徑丟給 `invoke-migrations.ps1` 會做的那個檔名／路徑驗證邏輯先跑一遍

   當作預檢），確保清單裡沒有壞檔案。**這一步失敗要直接 `throw`，此時資料庫還沒被動過。**

      （這是 `0018_inventory_reservation_consumed.sql:32-33` 實際加的欄位，Leader 已經讀過那份 migration 逐行確認，
      不用你重新猜表名或欄位名）。
    - 兩個都成立才印「✓ 重建完成」；缺一個就 `throw`。
11. 印出總結：套用了幾支 migration、**最後一支的檔名**、耗時（`Get-Date` 前後差即可）。
12. **提醒訊息**：印一行提醒「若 dev 環境的 `state/migrations-applied.json`（`ops/install-dev-environment.ps1` 用的）
    記錄的是舊清單，這支腳本執行後那個檔案不會自動更新，下次跑 `install-dev-environment.ps1` 前記得刪掉它」
    （§0.1 那個脫節風險，用印訊息的方式提醒操作者，不要試圖自動同步兩支腳本的狀態——那是耦合，不是這一包的範圍）。

### 必做 C　`ops/self-test.ps1` 新增檢查（純邏輯／靜態檢查，不連資料庫）

`ops/self-test.ps1` 檔頭本來就宣告「不碰 DB」（見該檔開頭幾行的自我宣告），**這一包不打破這個既有邊界**——
真的連資料庫的驗證走必做 D（手動實測，不進 self-test.ps1、不進 CI）。這裡只加靜態/邏輯層級的檢查，至少 4 項：

1. `-ConfirmDatabaseName` 與 `-DatabaseName` 不一致 → `throw`，而且傳一個明知連不到的假 host/port 進去，
   斷言丟出的是「確認不符」那句話而不是連線逾時或其他錯誤，證明順序是確認先於連線。
2. `-DatabaseName` 或 `-ConfirmDatabaseName` 含 `=`／空白 → `throw`，且同樣不連線（§0.4 額外防呆）。
3. `-ValidateOnly`：印出的 migration 清單，跟 `Get-SortedMigrationFiles` 現場算出來的清單逐一比對（不是寫死期望值 18 支——
   下次加 0019 這條測試不能變成需要手動改期望值），同一次呼叫也要確認沒有連線資料庫。
4. 15 個 schema 名稱的常數陣列與 `db/migrations/0001_schemas_and_roles.sql` 第 65-69 行那個陣列逐一比對相等
   （防止以後有人改了 0001 的 schema 清單卻忘了同步這支腳本）。

### 必做 D　手動實測協定（不是自動化測試，是必做的一次性真實驗證，結果寫進報告）

**外部覆驗抓到的關鍵缺口**：只驗證「兩次執行都成功、schema／欄位都在」證明不了資料真的被清掉——
就算漏掉 DROP 那一步、只是單純重放 migrations，這些斷言照樣會過。**這一步要多驗一件事：舊資料真的消失了。**

這一步**不放進 `ops/self-test.ps1`、不放進 CI**——本機 dev 環境的 Postgres 是 Docker 容器
（`ops/install-dev-environment.ps1:163-201`，`postgres:17-alpine`），有沒有可用的 `psql.exe`／CI 有沒有裝 PostgreSQL
用戶端都不是這一包能保證的環境前提，**勉強塞進自動化測試只會做出一條在別人機器上莫名其妙紅掉的測試**。
改成：你在自己的開發環境**手動**執行一次，把完整終端機輸出貼進報告，格式如下：

1. 確認 `psql.exe` 可用：dev 環境已知路徑是 `D:\GreyGray\PostgreSQL\bin\psql.exe`（`ops/install-dev-environment.ps1:356`
   附近同樣這樣組路徑），如果你的環境不是 `D:\GreyGray`，用你自己環境對應的路徑。
2. 準備一顆**專用的、可以整顆作廢**的測試資料庫（不是 dev 環境平常在用的那顆 `postgres` 資料庫），例如另外
   `CREATE DATABASE greygray_reset_selftest`（用 `postgres` 這個 superuser 帳號建，密碼在
   `secrets\postgres-superuser.password`，跟 `install-dev-environment.ps1` 建立方式一致）。
3. 對這顆測試資料庫跑一次 `ops\reset-database.ps1 -ValidateOnly`，貼出完整輸出（15 個 schema、18 支 migration 清單、
   目標資料庫三項都要看得到）。
4. 跑一次真的（不加 `-ValidateOnly`），確認：全新資料庫（原本沒有這 15 個 schema 之一）也能一次跑完；
   結尾印出「套用了 18 支、最後一支是 0018」。
5. **插入一筆識別用的資料**（例如 `INSERT INTO inventory.reservation (...) VALUES (...)`，隨便一筆能通過現有 constraint
   的合法資料，或更簡單：`CREATE TABLE inventory._reset_marker (id int); INSERT INTO inventory._reset_marker VALUES (1);`——
   這張表不在任何 migration 裡，純粹是這次手動驗證用的標記物）。
6. **再跑一次** `ops\reset-database.ps1`（不加 `-ValidateOnly`），成功結束後，查 `inventory._reset_marker` 這張表
   **應該已經不存在**（`SELECT to_regclass('inventory._reset_marker')` 應該回 `NULL`）——**這一步才是真正證明「DROP 真的執行了，
   不是單純重放 migrations」的關鍵**，貼出這個查詢與結果。
7. 用完把這顆測試資料庫整顆 `DROP DATABASE greygray_reset_selftest` 清掉，不要留著。

### 必做 E　修 `ops/install-dev-environment.ps1` 現有的漏 0018 缺陷（§0.6）

把第 46-55 行那段寫死的陣列，改成呼叫必做 A 新增的 `Get-SortedMigrationFiles`（dot-source `ops/lib/Migrations.ps1`）。
**這一步只換取得清單的方式，不改這段之後的邏輯**（`$migrationsStateFile` 比對、`invoke-migrations.ps1` 呼叫方式都不動）。
改完之後這支腳本會自動吃到 `0018`，也會自動吃到未來新增的 migration，**同一種缺陷不會再發生第三次**。

## 5. 可能寫錯的地方（撞到就停下來問，不要自己換做法）

- **`-ConfirmDatabaseName` 用 `-eq` 而不是 `-ceq`**：PowerShell 的 `-eq` 對字串預設不分大小寫，會讓「打錯大小寫」這種最常見的
  手滑被誤判為「確認相符」，整道防線形同虛設。**一定要用 `-ceq`。**
- **在 DROP 之前沒有先驗證過全部檔名格式**（§0.3 的順序風險）：如果 `invoke-migrations.ps1` 是在套用到一半才發現某個檔案不合法，
  資料庫會被留在「schema 已清空、migration 沒套完」的狀態，比原本更糟。
- **必做 D 只驗證「兩次執行都成功、schema／欄位存在」，沒有驗證資料真的被清掉**——這是外部覆驗抓到的核心缺口，
  一定要有「插標記 → 重建 → 標記消失」這一步，用假連線或只驗證指令組出來的樣子等於這一包最重要的保證沒被驗證到。
- **把必做 D 的手動實測誤放進 `ops/self-test.ps1` 或 CI**——那兩層現在都沒有可用的 Postgres 前提，會做出一條環境依賴的假測試。
- **`DROP SCHEMA` 忘記用雙引號包 schema 名稱**——照抄 `invoke-migrations.ps1` 與 `0001` migration 一律用 `%I`／引號的習慣。
- **驗證版本那一步猜表名而不是照 §1 必做 B 第 10 步給的精確欄位斷言寫**——這一版已經把 `information_schema.columns` 的精確條件
  列出來了，不要自己重新猜。
- **忘記 CASCADE 的影響範圍不只這 15 個 schema 本身**（§0.2 那段警告）——如果查證過程中發現 `public` 或其他 schema 有東西
  依賴這 15 個 schema 裡的物件，停下來回報，不要自己決定要不要處理。
- **`ops/` 腳本要能在 PowerShell 5.1 跑**（正式機只有 5.1；`RandomNumberGenerator::Fill` 那類 .NET 5+ 限定 API 09-03 真的撞過）。
- **`Get-SortedMigrationFiles` 判斷不合法檔名時選擇「噴錯」還是「過濾」要先掃一次現況再決定**（§1 必做 A 已經講過），
  不要沒看現況就套用某一種假設。
