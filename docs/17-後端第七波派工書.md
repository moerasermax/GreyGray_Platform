## 0. 這一波在哪裡

**M1b 的收尾。** 第六波把出貨、缺貨補償、帶回入庫都做出來了，
但整合驗收發現三個「接起來才看得到」的洞，加上進度表裡積很久的四件，
2026-08-30 一次拍板成 **ADR-024 ～ 028 ＋ ADR-019 更正**。這一波就是把那些決定落地。

**做完這一波，M1b 才真的走得完一條路：**

```
開團 → 下單 → 付款 → 截團 → 採購 → （缺貨補償／漲價詢問）
→ 帶回入庫 → 訂單自動轉待出貨 → 建出貨單 → 交運 → 簽收
→ 鑑賞期 7 天 → Completed → 帳務對得起來
```

粗體的兩段是這一波補的：**帶回後自動轉待出貨**（第六波接線斷了）與**鑑賞期後轉完成**（根本沒做）。

**進度的形狀**：C 實作 32/36，但 **D 整合與測試 0/7、E 上線 0/7**。
程式寫完不等於能上線——這句話從第五波寫到現在還是真的。

## 5. 工作包

### BE-17　綠界原路退款 API（ADR-024 前半）

**相依**：無（程式可以先做完）　**獨佔**：`src/Modules/Payment/**`

**為什麼這一包存在**：這是**現在最擋 M1b 的一件**。
已付款訂單的取消退款目前走不通——`Payment/OrderingEventHandlers.cs:43` 對
`OriginalPaymentMethod` 直接 `throw NotSupportedException`：

> 「綠界原路退款尚未具備凍結的 provider API 與必要設定；**不得把退款要求標成成功**」

**那個 `throw` 是對的，不要只是把它拿掉。** 拿掉而沒有真的退款，
系統會把「錢已退」記進 Ledger 而客人根本沒收到錢——那比現在的失敗嚴重得多。
**要做的是讓它真的能退，然後才把 throw 換成真實結果。**

**地基已經在了**：`EcpayGateway.cs` 有 CheckMacValue 的產生與驗證、
`Payment:ECPay:{MerchantId,HashKey,HashIV}` 的組態讀取。這一包是**擴充它**。

**必做**

1. `EcpayGateway` 加上退款能力（綠界的信用卡退刷／關帳 API），
   沿用既有的 CheckMacValue 與組態，**不要另外寫一套簽章**。
2. `RefundRequestedHandler` 對 `OriginalPaymentMethod` 改成**實際呼叫綠界**，
   依綠界的回應決定成功或失敗。**失敗要回 `Result` 的業務失敗，不要 throw。**
3. **冪等**：同一筆 `RefundRequested` 重送不可以重複退款。
   用既有的消費端冪等機制（`processed_message`）＋ Payment 自己的
   `refunded_amount_minor` 累計上限雙重把關。
4. **部分退款要能累計**：`Payment` 已經持久化 `refunded_amount_minor`，
   多次 line refund 累加後不得超過原付款——這條既有邏輯不要改壞。
5. 失敗的退款要留下可查的軌跡（綠界回什麼、什麼時候），客服會問。

**⚠️ E3 的狀態要講清楚**

正式商店代號與金鑰（E3）**老闆還在辦**。這一包：

- 用**綠界測試環境**的憑證做到能實際發動一次退款並拿到回應
- 自驗要貼出**真的呼叫過測試環境**的證據，不是只有單元測試
- **不可以宣稱「可上線」**——正式憑證到位前那句話不成立。
  交付說明要明寫「已對測試環境驗證，正式憑證未到位」

如果綠界測試環境不支援退款，**停下來回報**，不要用 mock 假裝驗過。

**自驗（逐條貼出實際指令與實際輸出）**

1. `dotnet build .\GreyGray.slnx` 0 error 0 warning
2. `.\ops\test.ps1` 全綠，說明新增幾條
3. `git diff --name-only` —— 只有你擁有的路徑
4. `grep -rn "decimal \|double " src/Modules/Payment/` 應為 0 筆
5. **對綠界測試環境實際發一次退款**的請求與回應（金鑰遮蔽）
6. 冪等測試：同一筆 `RefundRequested` 送兩次，只退一次
7. 累計上限測試：多次部分退款加總不得超過原付款

### BE-18　Ordering：M1b 只開原路 ＋ 鑑賞期 Saga Timer

**相依**：無　**獨佔**：**`src/Modules/Ordering/**`（整個模組）** · `db/migrations/0013_`

**這一包有兩件事，都在 Ordering。**

#### 第一件：`StoredValue` 在 M1b 回可預期的業務失敗（ADR-024 後半）

ADR-023 決定二說得很清楚，但**整個 repo 沒有任何地方實作**——
前端只擋在 UI，API 層仍然收得下 `StoredValue`，收了之後 Payment 會**真的**把錢記進儲值金。

要在 `OrderingApplicationService` 的取消退款路徑（`CancelAdminAsync`／`CancelLineAsync`）
加上守衛：

- 收到 `StoredValue` → 回 `Result` 的**業務失敗**（不是例外），
  錯誤訊息要說清楚「**儲值金退款要到 M3 才開放**」
- **不得默認任何一種去向**——沒指定就是錯誤，不要偷偷代選
- M3 要開的時候只需要拿掉這個守衛，所以**用組態旗標或明確的常數**，
  不要把「M1b」這個字散在程式各處

#### 第二件：鑑賞期 Saga Timer（ADR-025）

凍結契約明寫：**送達不等於完成**，訂單要等鑑賞期屆滿才轉 `Completed`。
現在沒有這個 Timer，訂單永遠停在 `Delivered`，**D2 端對端流程走不完**。

- 訂閱 BE-14 發的 `fulfillment.ShipmentDelivered.v1`，簽收時排一個 saga timer
- **鑑賞期 7 天**（ADR-025），**做成組態不要寫死**——之後要調不用改程式
- Timer 屆滿 → 訂單轉 `Completed`
- 用 `ISagaTimerScheduler<OrderingDbContext>`（泛型版），
  **讓 timer 與業務資料在同一次 `SaveChanges`**。
  不要用 platform 那個全域 scheduler——那會讓 timer 與訂單狀態分屬兩個交易
- **`ShipmentDelivered` 的 handler 與 saga scheduler 都註冊在
  `Ordering.Infra/ModuleRegistration.cs`**（比照 `Procurement.Infra/ModuleRegistration.cs:67`）。
  那個檔是你的，**不必動 Worker**——Worker 只掛通用的 dispatcher
- `0013_` 加鑑賞期到期時間的欄位（如果你的設計需要）

**做法要點**

- 訂單如果在鑑賞期內被取消，timer 屆滿時**不可以**把它拉回 `Completed`——
  狀態機要擋，而且要有測試。
- 一張訂單可能對應**多個出貨單**（N:M，BE-14 做的）。
  **全部簽收之後才起算鑑賞期**，不是第一個簽收就起算。這條容易做錯。
- 孤兒 timer（訂單已不存在或狀態不對）要安靜 no-op，不要 throw。

**自驗（逐條貼出實際指令與實際輸出）**

1. build 0/0；`ops/test.ps1` 全綠，說明新增幾條
2. `git diff --name-only` —— 只有你擁有的路徑（＋預先授權例外 2）
3. `grep -rn "decimal \|double " src/Modules/Ordering/` 應為 0 筆
4. `grep -rn "DateTimeOffset.UtcNow" src/Modules/Ordering/` 應為 0 筆
5. **`StoredValue` 被拒絕**的測試輸出（要看得到錯誤碼與訊息）
6. **鑑賞期**：簽收 → timer 排入 → 撥快時鐘 → 訂單轉 `Completed` 的完整測試
7. **多出貨單**：兩張出貨單，只簽收一張時**不**起算鑑賞期的測試
8. `0013_` 連續執行兩次（可重跑性）

### BE-19　契約與事件形狀異動

**相依**：無　**獨佔**：`docs/api/**` · `Procurement/**` · `Campaign/**`　**（完全不碰 Ordering）**

**三個契約異動，一起做因為它們共用同一次 codegen。**

> **接線不在這一包。** 第一版把它放這裡，但接線要改 `Ordering.Infra` 的註冊檔，
> 而那是 BE-18 的。改成獨立的 **BE-21**，等你和 BE-18 都落地再做。

#### ① `GoodsReceived.v1` 加 `OrderLineId`

第六波驗收發現：「帶回入庫後訂單自動轉待出貨」**這條線是斷的**。

- `GoodsReceived` 只帶 `CampaignId`＋`SkuId`＋`Quantity`＋`UnitCost`＋`Source`
- `IOrderingGoodsReceipt.RecordGoodsReceivedAsync(OrderLineId, ...)`
  **已經存在、已經實作、已經 DI 註冊**，但全 repo 沒有任何呼叫點

事件是**一個採購品項發一則**（`MarkReceivedAsync` 裡對單一 `item`），
而 `PurchaseItem` 本來就帶 `OrderLineId`、也是用它去重。**值就在手上，只是沒放進去。**

> **這是改 v1 的 wire shape**，一般情況下 ADR-018 不允許。
> 但 `GoodsReceived.v1` 是第六波才新增的、**從來沒上過正式機**，
> 現在改沒有相容性成本，之後才改就要發 v2。老闆已拍板改 v1。

#### ② 新增 `GET /v1/shipments/{id}`

契約只有列表、建立、`dispatch`、`deliver` 四條，**沒有單筆查詢**。
FE-13 的出貨單詳情頁只能撈 `limit:100` 的列表再在前端過濾——
出貨單超過 100 張之後點詳情會白頁，**而且不會報錯**。

這是**新增 operation 不是改既有形狀**，相容性風險低。

#### ③ `AdminCampaignInput` 加漲價詢問逾時欄位（ADR-027）

現在是 2 小時的技術預設值。改成每團可設——日本藥妝店與精品店的節奏不一樣。
`AdminCampaignInput` 在 `docs/api/openapi.admin.yaml:1158`，
