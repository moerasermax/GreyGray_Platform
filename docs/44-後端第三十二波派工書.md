### 0.2 #44 的根因：全站只有「加入商品」那條路會換車

- `src/Hosts/GreyGray.Api.Storefront/M1aEndpoints.cs` 第 985-996 行（`AddCartLineAsync`）：拿到 `checkout.cart-already-completed` 或 `checkout.cart-not-found` 時**換一顆新 cookie 再重試一次**。這是 #36 當初的修法，註解就寫在那裡。
- 第 1049-1067 行（`GetCartAsync`）：**只處理 `checkout.cart-not-found`**（第 1059 行的條件），已結案的車不在內。
- 第 585-637 行（`CompleteCheckoutAsync`）：成功之後**沒有任何換車動作**——第 632 行 `CreateFromCheckoutAsync` 之後就直接組回應了。

## 1. 必做

### 必做 A　結帳成功就換一台新車（`src/Hosts/GreyGray.Api.Storefront/M1aEndpoints.cs`）

在 `CompleteCheckoutAsync` 的成功路徑上換 cookie：訂單已經成立，那台車再也不能用了，讓瀏覽器立刻拿到一台新的空車。
放在**確定成功之後**（`CreateFromCheckoutAsync` 回成功、組回應之前），用 `SetCartCookie(context.Response, CartId.New())`。
註解要寫清楚為什麼：不換的話 `gg_cart` 會一直指著已結案的車，前台的購物車與徽章不會歸零，而再按一次送出訂單就是 422（§0.1 的 15 次）。

★ 注意 `BffHttp.ExecuteIdempotentAsync` 的兩階段：`work` 可能被重放。**換 cookie 要放在真的成功之後**，而且重放同一把鍵時再換一次也無害（都是換成新的空車）——但**不要**在 `work` 失敗時換。

### 必做 B　結帳撞到「已結案」時要能自救（同一支 `src/Hosts/GreyGray.Api.Storefront/M1aEndpoints.cs`）

`CompleteCheckoutAsync` 失敗且 `Error.Code == "checkout.cart-already-completed"` 時：換一顆新 cookie，並回一個**講得出下一步**的錯誤（例如「這台購物車已經下過單了，已經幫你換一台新的，請重新加入商品。」）。
**不要**換完就拿新車重試 checkout——新車是空的，那只會變成另一種錯誤。目的是讓使用者按下一次就脫身，而不是繼續撞牆。

### 必做 C　看購物車拿到已結案的車也要換（`src/Modules/Checkout/GreyGray.Modules.Checkout.Contracts/CheckoutContracts.cs` ＋ Checkout 的 Core ＋ `src/Hosts/GreyGray.Api.Storefront/M1aEndpoints.cs`）

1. `CartView` 加一個唯讀屬性表示「這台車已經結案」（`init` 屬性，照第 71-75 行既有三個的形狀，**不要改建構式參數**，那會動到所有呼叫端）。Checkout 服務組 `CartView` 的地方要把值帶出來。
2. `GetCartAsync`（第 1049-1067 行）：拿到的車是已結案時，比照第 1059-1064 行 `cart-not-found` 的做法——換新 cookie、回**空車**。註解要說明：這是 §0.2 的第二道破口，只修 checkout 那條路的話，購物車頁與徽章還是會顯示上一張單的東西。
3. 這是**模組契約**的純新增，不是凍結的 HTTP 契約；`docs/api/*.yaml` 一個字都不要動（`CartResponse` 不需要多這個欄位，前端不需要知道）。

### 必做 D　取消已出貨的訂單不再卡住（`StockReservationService.cs`）

`ReleaseByKeyAsync`（與 `ReleaseAsync` 若共用同一段）在讀到 reservation 之後、真的動 lot 之前，**多一支狀態判斷**：`status == ConsumedStatus`（2）就**安靜成功**並留一行 log 說明「已出庫，不釋放」。
理由寫進註解：貨在交運時就離開倉庫了，取消訂單不能把它變回可賣庫存；那是退貨流程（`ReturnReceived` → 開新批號入庫，`docs/02` §4「拒收退回」）的事，不是釋放。
**不要**改釋放路徑的一致性守衛（`allocation 與 lot 保留量不一致` 那條）——它做對了，是它把這個缺口叫出來的。

## 5. 可能寫錯的地方（撞到就停下來問，不要自己換做法）

- **`ExecuteIdempotentAsync` 的重放**：同一把 Idempotency-Key 重放時，`work` 不一定會再跑一次。如果換 cookie 寫在 `work` 裡面，重放就不會換。想清楚要放哪一層——必要時放在方法回傳之前、以 `Result` 是否成功決定。撞到就停下來問。
- **`SetCartCookie` 的選項要跟 `ClearCartCookie` 一致**（`HttpOnly`／`Secure`／`SameSite`／`Path`），否則瀏覽器當成兩顆 cookie。第 1073-1080 行有現成的註解講這件事。
- **`CartView` 加欄位會影響所有建構點**：用 `init` 屬性（有預設值）而不是建構式參數，否則每個 `new CartView(...)` 都要改。
- **必做 C-1 要讓服務端真的帶值**：只加屬性不填，永遠是 `false`，測試會綠但線上沒修到——這正是 #43 那種「型別有了沒人填」的形狀。測試要斷言「結案的車讀回來時該屬性是 true」。
- **`ReleaseByKeyAsync` 可能有兩個呼叫端**（`OrderCancelled` 與別處）。改在 service 裡而不是 handler 裡，兩邊都受惠；但要確認沒有哪個呼叫端**期待**已出庫時失敗。
