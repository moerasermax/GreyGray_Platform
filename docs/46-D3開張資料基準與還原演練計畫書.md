## 二、為什麼「全新重建」是對的，而且要趁現在

**挑著清會出錯，而且錯了看不出來。** 現在正式庫裡一張訂單牽著五個地方：`ordering.order`／`order_line`、
`inventory.reservation` ＋ `reservation_allocation`、`inventory.lot` 的結餘、`ledger` 的分錄、`platform.outbox_message`。
分錄是**只增不減**的帳：刪掉單據不等於帳回到起點；只把庫存數字改回去，也不等於對應的銷貨成本被處理過。
更麻煩的是漏刪 `outbox_message` 的話，Worker 之後可能重放一則指向已經不存在的訂單的事件。

**全新重建順便買到一件現在還沒有人驗過的事**：從 `0001` 到最新一支 migration **在乾淨資料庫上真的跑得完**。
`install-dev-environment.ps1` 的清單漏過一次（BE-31 起停在 `0014`，`0015` 沒補），`yc-deploy.ps1` 的 migration 清單也要人手動加到最新一支
（09-04 那次就差點漏掉 `0018`）。**開張前重建一次，是唯一一次便宜驗證這條路的機會**——上線之後就再也不能重來。

⚠ **驗證一律走正式 migrations**，不准用 EF 的 `EnsureCreated`：那會建出一個「跟正式 schema 很像但不是同一份」的資料庫，
check constraint 與索引都可能不一樣（EF model 與 `db/migrations` 目前已知還有兩組 constraint 漂移沒補）。

## 三、開張前要有的三個東西

### 3.1 重建（reset）

一支腳本，把正式資料庫**丟掉重建**：drop 所有 schema → 依序套用 `db/migrations/` 全部 → 驗證版本。
必須冪等、必須印出「套用了哪幾支、最後停在哪一支」，而且**必須有一道刻意的確認**（不能手滑就把正式庫清掉）。

### 3.2 種子（seed）——**走真實端點，不直寫資料庫**

沿用使用者 2026-09-01 立過的原則（那次拒絕了「幫正式機種一個 SKU」的提議）：
員工帳號走 `GreyGray.Tools.StaffBootstrap`；商品、SKU、批號進貨走 `POST /v1/products`／`/skus`／`/lots`。
好處是「種子跑得完」本身就等於「這些端點真的能用」——直寫資料庫種出來的資料，只證明得了 INSERT 沒被 constraint 擋。

種子的**內容**（要賣什麼、幾個 SKU、期初批號多少）是營運資料，**要使用者給**，腳本只吃一份清單檔。

### 3.3 還原演練——**「備份沒還原過就不算備份」**

在**隔離環境**把現有備份真的還原一次。這一項不是 `pg_restore` 回 0 就算過，成立條件見下一節。

## 四、還原演練的成立條件（逐項要有證據）

1. **schema 版本對得上**：還原出來的資料庫，migration 停在的那一支要與正式機相同（現在是 `0018`）。
2. **應用真的起得來**，不只是資料庫還原成功。要一起還原／重建的東西：
   - 13 個模組角色的資料庫密碼
   - `Identity:DataProtectionKey`（**少了它，登入與註冊全部 500**——BE-25 踩過）
   - `secrets\ecpay.json`（少了它 Worker 與 Storefront **拒絕開機**，這是 BE-46 刻意的設計）
3. **對外副作用全部隔離**：還原出來的環境裡有舊的 `platform.outbox_message`，一起來就會投遞。
   演練環境**不准**打到真綠界、不准發任何對外通知。
4. **資料抽樣核對**：至少一張訂單，逐項對「訂單狀態 ↔ 出貨單 ↔ 批號結餘 ↔ 保留單 ↔ 分錄」五處是否一致。
5. **量出還原要多久**：這個數字就是將來真的出事時的停機時間下限。
