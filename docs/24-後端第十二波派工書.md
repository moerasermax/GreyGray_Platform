## 0. 這一波要解的問題：admin BFF 三組端點永久掛住，根因是 Ordering ↔ Fulfillment 的循環相依

**這一波不是「查」，是「查完＋確診＋知道怎麼修」之後才派工的**——Leader 這一輪
親自用 `dotnet-dump` 對 `D:\GreyGray` 的 admin Host 抓了三次記憶體傾印，逐步排除
資料庫、Redis／Garnet、認證、並行競態，最後鎖定確切根因。以下是完整的診斷鏈，
你不需要重查一次，直接跳到 §5 動手；如果要複查，指令都在下面。

### 症狀（FE-12 第九波回報，這一波實測重現）

`GET /v1/orders`、`GET /v1/orders/{id}`、`GET /v1/campaigns`、`GET /v1/shipments`
在 admin Host（5001 埠）永久掛住不回應——不是慢，是完全沒有 HTTP 回應，client 端
等到自己的 timeout 才斷線。後端 log 只印「Executing endpoint」沒有「Executed endpoint」。
storefront Host（5000 埠）同名端點正常回 401。**這一波實測證實：即使完全不帶
cookie（未認證）、即使只送一個請求（不是併發競態），一樣永久掛住**——`curl -m 60`
對 admin `/v1/orders`送出後，60 秒內沒有任何回應（`exit code 28`，client timeout）。

### 排除過程（逐項，都是這一波實測，不是猜測）

| 排除項 | 怎麼查的 | 結論 |
|---|---|---|
| 資料庫（Postgres）卡住 | 對 `iam.staff_account`／`ordering.*` 等 schema 查 `pg_stat_activity`，在請求卡住期間查 | **零筆**——`ordering`／`campaign` 相關的資料庫連線完全沒被開啟過，代表卡住的地方在 DB 呼叫**之前** |
| Redis／Garnet（session store）卡住 | `GET /v1/me`（跟 `/v1/orders` 用**完全同一個** `StaffRoleFilter(StaffRole.ReadOnly)` endpoint filter，也會查 session）——結果 `/v1/me` 在 3ms 內回 401，`/v1/orders` 同時掛住 | **不是** session／Redis 問題，同一段驗證邏輯在別的端點上完全正常 |
| 認證／session cookie | 完全不帶 cookie 送請求，一樣掛住 | **跟認證無關**，掛住點在 `StaffRoleFilter` 執行之前 |
| 併發競態 | 全新啟動 admin Host，只送**一個**請求（沒有任何其他併發請求），一樣永久掛住 | **不是併發問題**，單一請求就會觸發 |
| .NET 執行緒集區耗盡 | 掛住期間 `/health` 仍然正常回 200（3-5ms） | 不是全域執行緒耗盡，問題侷限在特定請求的 DI 解析路徑 |

### 根因（`dotnet-dump` 直接證實，不是推論）

用 `dotnet-dump collect` 對卡住中的 admin process 抓傾印，`parallelstacks -a` 看到
**三個執行緒同時卡在 `Monitor.Enter_Slowpath`，而且都在
`Microsoft.Extensions.DependencyInjection.ServiceLookup.CallSiteVisitor.VisitCallSite`
內部**——這是 .NET DI 容器自己的內部鎖，不是應用程式的鎖。`dumpheap -stat -type
OrderingRepository` 在同一次卡住期間查到 **346～714 個** `OrderingRepository` 執行個體
（正常情況下一個請求最多 1 個）——代表同一個工廠委派被**重複呼叫**，而不是單純卡住等待。

**確切的循環是這樣**（兩邊都用工廠委派手動呼叫 `GetRequiredService`／`GetService`，
不是建構式自動注入，所以 .NET DI 內建的循環偵測（只看建構式參數型別）完全看不到）：

```
OrderingApplicationService 的工廠（Ordering.Infra/ModuleRegistration.cs:80）
  → serviceProvider.GetService<IFulfillmentQuery>()
    → 解析到 FulfillmentApplicationService
      → 它的工廠（Fulfillment.Infra/ModuleRegistration.cs:63）
        → serviceProvider.GetRequiredService<IOrderQuery>()
          → 解析到 OrderingApplicationService  ←── 繞回起點
```

**為什麼只有 admin Host 中獎，storefront／Worker 都沒事**：
`Ordering.Infra/ModuleRegistration.cs:76-79` 的既有註解寫得很清楚——
「Storefront／Worker 目前不掛 Fulfillment 模組」，所以那兩個 Host 上
`serviceProvider.GetService<IFulfillmentQuery>()` 永遠解析到 `null`（`GetService`
是可選的，沒註冊就回 null，不會炸），迴圈的另一半根本不存在。**只有 admin Host
同時掛了 Ordering 與 Fulfillment 兩個模組**（`src/Hosts/GreyGray.Api.Admin/Program.cs`
的 `.AddOrderingModule(...)` 與 `.AddFulfillmentModule(...)` 都在同一份 `builder.Services`
鏈上），而且只有 admin 的 `/v1/orders`／`/v1/campaigns`／`/v1/shipments` 會真的觸發
解析 `IOrderingApplication`／`ICampaignAdministration`（透過 `ICampaignOrderQuery`
→ `CampaignOrderQueryAdapter` → `IOrderQuery` 一樣會繞進同一個迴圈）／`IFulfillmentQuery`。
`/v1/me`、`/auth/login` 完全不碰 Ordering 或 Fulfillment，所以沒事。

**為什麼 175 條測試全過卻沒抓到**：全 repo 沒有任何一個測試同時呼叫
`AddOrderingModule` 與 `AddFulfillmentModule` 組成同一個真的 DI 容器
（`grep -rn "AddOrderingModule\|AddFulfillmentModule" tests/*.cs` 只有
`GreyGray.M1a.CheckoutOrdering.Tests` 呼叫 `AddOrderingModule`，`GreyGray.M1b.Fulfillment.Tests`
兩個都沒呼叫，用手動建構＋假物件測 `FulfillmentApplicationService`）。這個循環
**只有兩個模組的真實 DI 容器同時存在時才會出現**，這正是 admin Host 獨有的組合，
沒有任何測試涵蓋到。

### 兩邊的用途都是真的業務需求，不是可以刪掉的死碼

- `OrderingApplicationService.RecordShipmentDeliveredAsync`
  （`Ordering.Core/OrderingApplicationService.cs:490-519`）：出貨單簽收後呼叫，
  因為一張訂單可能對應多個出貨單（N:M），要重新問 Fulfillment「這張訂單掛的
  全部出貨單是不是都簽收了」才能起算鑑賞期 Saga Timer（ADR-025）。**這個查詢是
  必要的**，不能只靠事件payload（事件只帶一張出貨單的資訊，判斷不出「全部」）。
- `FulfillmentApplicationService`（建構式參數 `IOrderQuery orders`，
  `Fulfillment.Core/FulfillmentApplicationService.cs:13`，用在
  `CreateShipmentAsync` 裡查訂單明細來建出貨單，`:27` 的
  `orders.GetAsync(orderId, cancellationToken)`）：**這個查詢也是必要的**，
  出貨單本來就需要訂單資料。

**所以這不是「刪掉一邊的依賴」能解的**，兩邊都要留著，但**建構時機**要改。

#### 必做 3　新增一條「Ordering ＋ Fulfillment 同時掛真實 DI 容器」的迴歸測試

全 repo 現在沒有任何測試涵蓋這個組合（見 §0 診斷）。新增一條測試（放在
`tests/GreyGray.M1b.Fulfillment.Tests/` 或 `tests/GreyGray.M1a.CheckoutOrdering.Tests/`，
你自己判斷哪個位置更合理），至少要做到：

1. 用真的 `ServiceCollection` 呼叫 `AddOrderingModule(configuration)` **與**
   `AddFulfillmentModule(configuration)`（跟 admin Host 完全一樣的組合）；
2. 建一個 scope，解析 `IOrderingApplication` 與 `IFulfillmentQuery`；
3. **用有上限的 timeout 包住解析呼叫**（例如 `Task.Run(...).WaitAsync(TimeSpan.FromSeconds(5))`
   或等效寫法），超時要讓測試明確失敗並印出清楚的錯誤訊息——**不能讓這條測試本身
   卡死整個測試套件**，那樣會比沒有這條測試更糟（下一個踩到這裡的人會看到
   `ops/test.ps1` 卡住不知道為什麼）；
4. 如果需要真的 PostgreSQL（`OrderingDbContext`／`FulfillmentDbContext` 的
   `AddDbContext` 在真正建立 DbContext 實體之前不需要能連線，只有真的執行查詢
   才需要——參考 `Ordering.Infra/ModuleRegistration.cs:41`「options factory 在真正
   解析 IdentityDbContext 時才執行」那種模式，你可能根本不需要真的資料庫，
   只是要證明「解析這兩個介面不會卡住」，不是要執行查詢）。

這條測試在你修好 bug 之前應該會**逐字重現**「掛住」這個症狀（在 timeout 內失敗），
改完之後轉綠——跟這個專案一貫的「先紅後綠」規矩一致。
