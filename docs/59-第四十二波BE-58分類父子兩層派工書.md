## 1. 要做的事

### 1.1 migration `0023_category_parent.sql`（新檔）

1. `catalog.category` 加 `parent_id uuid NULL`。
2. 複合外鍵 `category_parent_same_tenant_fk`：`(tenant_id, parent_id) REFERENCES catalog.category (tenant_id, id) ON DELETE RESTRICT`。
3. `CHECK (parent_id IS NULL OR parent_id <> id)`，名稱 `category_parent_not_self`。
4. 索引 `ix_category_tenant_parent ON catalog.category (tenant_id, parent_id)`。
5. **兩層守衛 trigger**（ADR-041「資料庫也守這條規則」）：
   - 函式 `catalog.category_two_level_guard()`，`BEFORE INSERT OR UPDATE OF parent_id ON catalog.category FOR EACH ROW`。
   - 第一步：`PERFORM pg_advisory_xact_lock(...)`，key 由租戶決定（例如 `hashtextextended('catalog.category-tree:' || NEW.tenant_id::text, 0)`）——同一個租戶的階層寫入排成一列。
   - `NEW.parent_id` 不是 null 時：
     - 查上層：`WHERE tenant_id = NEW.tenant_id AND id = NEW.parent_id`。**查不到就不在 trigger 裡擋**，交給外鍵回 `23503`（M3 靠這一點）。
     - 查得到、而且上層的 `parent_id` 不是 null → 擋。
     - 有任何分類的 `parent_id = NEW.id`（同租戶）→ 擋。
     - 擋的方式：`RAISE EXCEPTION ... USING ERRCODE = 'check_violation', CONSTRAINT = 'category_two_level'`（測試斷言 SqlState `23514` 與 constraint 名稱）。
   - 函式**保持預設的 `VOLATILE`**（**不准標 `STABLE`／`IMMUTABLE`**——那兩種會沿用呼叫端語句的 snapshot，下面的排隊就失效了）；
     預設的 `SECURITY INVOKER`，**不要用 `SECURITY DEFINER`**；函式內一律寫 `catalog.category`（schema 限定）。模組 role 本來就有這張表的 SELECT。
   - ⚠ 為什麼要拿鎖：兩條交易同時把 A 設成 B 的子、把 B 設成 A 的子，沒有鎖的話兩邊讀到的對方都還是根分類。
     拿了鎖之後，後到的那條會等先到的 commit，而 VOLATILE 的 PL/pgSQL 在 READ COMMITTED 下每一條查詢都會取新的 snapshot，所以後到的那條看得到先到的結果。**M7 要把這件事證明出來。**
   - 死結前提：`BEFORE ROW` trigger 執行時，目標列的列鎖已經拿到，接著才拿 advisory lock。**應用一次只寫一筆分類**，所以不會出現「A 交易拿著列 X 等鎖、B 交易拿著鎖等列 X」。
     **不要寫一次更新多筆分類的程式**；萬一真的死結（`40P01`），被中止的那筆整筆回滾、規則不會被破壞，走例外即可。
   - 只改 `tenant_id` **不需要**觸發檢查：`id` 是全域主鍵，換租戶的分類一定對不上同租戶複合外鍵，會先被外鍵擋下（在報告用一句話確認你同意這個推論，或指出反例）。
6. **函式、trigger 都要建在 `SET ROLE greygray_owner` 與 `RESET ROLE` 之間**；owner 斷言照 `0019` 保留 `pg_tables` 那段，**再加一段 `pg_proc`**
   （`pronamespace = 'catalog'::regnamespace AND proowner <> 'greygray_owner'::regrole` 就 `RAISE`）。整份要能重放（見 §0.1）。

### 3.4 `docs/45` 邊界六類
