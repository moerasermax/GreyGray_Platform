## 0. #27　收藏心點了會跳到商品頁

### 現象（Leader 2026-09-01 在真 Chrome 裡實測）

在 `/products` 或 `/categories/{id}` 的商品卡上點愛心，
**不會切換收藏，而是導航到該商品的詳情頁**。

### 根因（三條獨立證據）

1. `apps/storefront/app/(shop)/_components/ProductCardLink.tsx:39`
   用 `<Link href={/products/${product.id}}>` **把整張卡包起來**
2. `packages/ui/src/components/ProductCard.tsx:97` 的收藏心外面只包了
   `<span onClick={(event) => event.stopPropagation()}>`
3. Leader 用 JS 查證：收藏鈕的 `closest('a')` **非 null**

**`stopPropagation()` 擋得住 React 的 `onClick` 冒泡，
擋不住 `<a>` 的預設導航行為**——要擋導航必須 `preventDefault()`。

### 修法

`ProductCard.tsx:97` 那個 `onClick` 同時呼叫 `preventDefault()` 與 `stopPropagation()`。

**★ 不要把整個 `ProductCard` 搬出 `<Link>`**，也不要改 `ProductCardLink` 的結構
——那會動到整個列表的導航行為，風險遠大於這個 bug。

### 已知限制（Leader 已查證，不用再查）

**這個 workspace 沒有 jsdom／`@testing-library`，也沒有安裝**，
所以**寫不出「模擬點擊愛心、斷言沒有導航」的測試**。
**不要為此加相依套件**（會動 `pnpm-lock.yaml` ＋ 需要連網，不在這一包範圍）。

**替代的迴歸保證**：把那個 handler 抽成一個**可單元測試的小函式**
（例如 `packages/ui/src/components/ProductCard.tsx` 裡 export 一個
`suppressCardNavigation(event)`），用假的 event 物件測它
**確實呼叫了 `preventDefault` 與 `stopPropagation` 兩者**。
這條測試擋得住「有人日後把 `preventDefault` 拿掉」，那正是這個 bug 的形狀。

## 1. #28　前台必填欄位只有視覺上的 `*`

### 現象（Leader 用 JS 逐欄查證）

| 表單 | input 的 `required` | `aria-required` | 畫面上的 `*` |
|---|---|---|---|
| 後台 `/login` | ✅ `true` | — | ✅ |
| 前台 `/login`（`login-phone`／`login-password`） | ❌ `false` | ❌ `null` | ✅ |
| 前台 `/register`（五個欄位，三個標 `*`） | ❌ 全 `false` | ❌ 全 `null` | ✅ |

用讀螢幕軟體的人**不會知道哪些欄位必填**。

### 根因

`Field` 元件（`packages/ui/src/components/Field.tsx`）的 `required` **只負責畫那顆星號**，
不會傳給裡面的 input——**呼叫端必須自己也在 `<Input>` 上寫 `required`**。

**後台 `apps/admin/app/login/page.tsx` 就是正確寫法**：
`<Field ... required>`（第 80、91 行）**而且** `<Input ... required>`（第 85、96 行）。
前台只寫了前者。

### 修法

照後台既有寫法，把 `required` 補到前台這兩頁**標了 `*` 的** `<Input>` 上：

- `apps/storefront/app/(account)/login/page.tsx`：`login-phone`、`login-password`
- `apps/storefront/app/(account)/register/page.tsx`：`register-phone`、
  `register-password`、`register-display-name`

**★ 只補標了 `*` 的欄位。** `register-email` 與 `register-referral-code`
的畫面上寫著「選填」，**不要給它們 `required`**。

**★ 不要順手改表單的送出行為。** 目前兩個表單都是「空白也送出、由伺服器回 401
並顯示錯誤訊息」，那是既有行為（後台的表單甚至刻意 `noValidate`）。
這一包只補無障礙屬性，**不改互動**——若補上 `required` 之後瀏覽器開始擋送出、
使得既有錯誤訊息路徑走不到，**停下來寫進報告問**，不要自己決定要不要加 `noValidate`。
