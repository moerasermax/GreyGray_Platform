## 0. 這一波要解的問題：admin 正式機導向永遠指向 `localhost`

FE-12（第九波）發現：admin standalone `server.js` 內嵌的設定
`"trustHostHeader": false`（Next.js 15.5 的內建預設值，不是誰手動設的）
讓 middleware 裡 `new URL('/login', request.url)` 算出來的 origin 永遠退回
`localhost:PORT`，不會用反向代理實際收到的 `Host` header。正式機用
`HOSTNAME=127.0.0.1` ＋ cloudflared 反向代理（`ops/deploy.ps1:215` `:222`），
所以**任何未登入的人打後台任何頁面，都會被導到 `https://localhost:5003/login`
——那是使用者自己的電腦，後台整個登入不能**。

**這一波之前 Leader 做過的查證**（你不需要重查，直接看結論）：

1. **確認 `trustHostHeader` 是真的、會生效的 flag，不是猜的**：`.next/standalone/apps/admin/server.js`
   裡實際烘進去的 `nextConfig` JSON，`experimental` 區塊裡明寫
   `"trustHostHeader":false`——這是 `next build` 自己產生的，代表就算
   `apps/admin/next.config.ts` 完全沒設這個值，Next 也會用 `false` 當預設。追查
   `node_modules/next/dist/build/define-env.js:157`：
   `'process.env.__NEXT_TRUST_HOST_HEADER': config.experimental.trustHostHeader ?? false`——
   證實這個值真的來自 `apps/admin/next.config.ts` 的 `experimental.trustHostHeader`，
   會被編譯進 `__NEXT_TRUST_HOST_HEADER` 環境變數，在 server 端真的用得到。
2. **這個 flag 沒有在官方 TypeScript 型別裡**：`frontend/apps/admin/node_modules/next/dist/server/config-shared.d.ts`
   的 `ExperimentalConfig` interface 沒有 `trustHostHeader` 這個欄位（已經
   grep 過整個型別定義檔確認）。這代表**直接寫
   `experimental: { trustHostHeader: true }` 會被 `pnpm typecheck` 擋下來**
   （excess property check：「物件字面值只能指定已知屬性」），你需要一個
   型別繞過寫法（見 §5 必做 1）。
3. **嘗試親自重跑 FE-12 當時的即時驗證，撞到一個環境層級的既知問題，沒有跑完**：
   Windows ＋ pnpm 的 `.next/standalone` 產物裡有真的 symlink（例如
   `node_modules/.pnpm/next@.../node_modules/styled-jsx` 指到 pnpm 的
   virtual store），Node.js 的 `fs.realpathSync` 對這個 symlink 丟
   `EPERM: operation not permitted`，導致 standalone `server.js` 完全
   啟動不起來（`HasExited: True`，立即崩潰）——這是**這個 repo 已知的
   獨立問題**（見知識庫「Windows + pnpm 的 Next standalone 必須實體化
   symlink 與 virtual dependency context」），不是這一波要解的範圍，但
   **你交付時的即時驗證可能也會撞到同一個坑**，見 §5 必做 2 的因應方式。

**這一波不用管**（不在範圍內，已經有獨立追蹤）：
- Windows/pnpm standalone symlink 的一般性修法——那是另一個系統性問題，
  這一波只需要「想辦法讓一次 standalone server 跑起來驗證這個特定修法」，
  不用解決整個 symlink materialize 的問題。
- storefront Host 完全沒有 CORS——那是**後端 worktree**的修法（storefront
  Host 的組合根加 `AddCors`），不在前端這棵樹，Leader 另外在後端樹開一包
  （BE-28）處理。

## 5. 工作包

### FE-18　修 admin 正式機導向永遠指向 localhost　🔴

**相依**：無　**獨佔**：見 §3

#### 必做 1　`apps/admin/next.config.ts` 加上 `experimental.trustHostHeader: true`

```typescript
const config: NextConfig = {
  reactStrictMode: true,
  // ...既有內容不動...

  /*
   * Next.js 內建設定，預設 false（見 node_modules/next/dist/server/config-shared.d.ts
   * 的 ExperimentalConfig，這個欄位不在官方型別裡，是刻意繞過型別檢查啟用的）。
   * false 時 middleware 裡 request.url 的 origin 會退回 HOSTNAME:PORT
   * （正式機是 127.0.0.1:5003），不會用 cloudflared 轉發過來的實際 Host header，
   * 導致未登入導向永遠指向使用者自己的電腦。true 之後才會信任反向代理送來的
   * Host header——正式機 cloudflared 預設會原樣轉發 Host（沒有另外設定
   * httpHostHeader override），所以這個修法對得上目前的部署拓樸。
   */
  experimental: {
    trustHostHeader: true,
  } as NextConfig['experimental'],

  // ...既有內容不動...
};
```

（上面是形狀示意，實際位置放在既有 `images`／`output` 那些欄位附近即可，
不用照抄註解逐字，但**型別繞過的方式**與**「為什麼要繞過」的理由**要留著，
不然下一個人看到 `as NextConfig['experimental']` 會以為是隨手亂寫。）

#### 必做 2　即時驗證：讓一次 standalone server 跑起來，送 spoofed Host header

**步驟**：

1. `cd frontend/apps/admin && pnpm build`（確認 standalone 產物是最新的）。
2. 啟動 `node .next/standalone/apps/admin/server.js`，環境變數
   `HOSTNAME=127.0.0.1 PORT=<你選一個空的埠>`。
3. **如果撞到 §0 第 3 點提到的 `EPERM: ... styled-jsx` 崩潰**：這是已知的
   Windows/pnpm symlink 問題，不是你這一波的程式碼有問題。先確認 process
   真的立刻崩潰（`HasExited: True`／log 有那個 EPERM），不要把恰好還在監聽
   同一個埠的舊行程誤認成「這次啟動成功了」——**啟動前先確認目標埠沒有
   任何行程在聽**（`netstat -ano` 或等效指令），避免像 Leader 這一輪一開始
   誤判的狀況。如果你的環境剛好沒有這個 symlink 問題（跟 Leader 的環境不同、
   或你有辦法繞過），直接繼續下一步；如果一樣撞到、而且沒辦法在合理時間內
   解決，**如實記錄在自驗報告的「我發現但沒做的事」**，改用退而求其次的
   驗證方式（見下面「備援驗證」），不要假裝驗證過。
4. 成功啟動後，送這幾個請求（換成你實際用的埠）：
   ```
   curl -s -D - -o /dev/null http://127.0.0.1:<port>/orders -H "Host: admin.greygray.tw"
   curl -s -D - -o /dev/null http://127.0.0.1:<port>/orders -H "Host: example.invalid"
   ```
   **修好之前**（如果你想先驗證症狀重現，可以在改動前先跑一次）：`Location`
   header 應該是 `http://localhost:<port>/login?from=%2Forders` 這種絕對網址、
   host 是 `localhost`，跟你送的 `Host` header 對不上。
   **修好之後**：`Location` header 應該用你送的 `Host` header（例如
   `http://admin.greygray.tw/login?from=%2Forders`），不再是 `localhost`。
5. 跑完記得停掉這個測試用的 server 行程，不要留著佔用埠。

**備援驗證**（如果 §5 必做 2 步驟 3 的 symlink 問題無法在合理時間內解決）：
retrieve 一份 `next build` 產出的 `nextConfig`（`.next/standalone/apps/*/server.js`
裡烘進去的那段 JSON）， `grep` 確認 `"trustHostHeader":true` 已經確實出現在
建置產物裡（跟 §0 第 1 點 Leader 查證的方法一樣）。這只能證明「設定值有正確
傳遞到建置產物」，**不能**證明「Next 的路由層真的照這個設定改變行為」——
如果只能做到這一步，在自驗報告誠實標註這是**部分驗證**，不要寫得像已經
端對端驗證過。

**自驗（寫進 `.dispatch/reports/FE-18.md`）**

1. `pnpm typecheck` 全過（含 `apps/admin/next.config.ts` 本身，證明型別
   繞過寫法真的編譯得過）
2. `pnpm build` exit 0（admin 與 storefront 都跑，storefront 不該有任何變化）
3. `git diff --name-only` —— 只有 `frontend/apps/admin/next.config.ts`
4. §5 必做 2 的即時驗證結果——貼出實際 `curl` 指令與 `Location` header 的
   實際內容，不是「應該會這樣」的推測。如果撞到 symlink 問題改用備援驗證，
   誠實標註驗證深度打了折扣
