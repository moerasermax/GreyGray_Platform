# 第四十三波計畫書：綠界非即時付款（路線 B）與付款通知安全修補

> **狀態**：2026-09-30 深夜使用者拍板**路線 B**（正式支援 ATM／超商代碼／條碼），以及第二節四項規則。第四十三波派第 1 輪：BE-61（#64 修補＋過渡期只收信用卡）＋FE-55（分類樹接線，原計畫）。
> **依據**：`.dispatch/reports/BE-59.md`（綠界非即時付款查證，commit `998643f`）；2026-09-30 五個唯讀查證代理對 HEAD `e4b152d`（後端）／`ba3450a`（前端）逐行核對（行號已更正 BE-59 報告在 `7096a27` 之後的漂移）。
> **編號**：本檔 docs `66`；ADR-042、ADR-043 已預留給社群登入與多語系（`docs/58-第四十二波計畫書.md` 第 256～257 行），本計畫的 ADR 用 **ADR-044**；包名後端從 BE-61、前端從 FE-55 起算。`docs/58-第四十二波計畫書.md` 原排的社群登入與多語系各包**整批往後排**（第六節）。

## 一、一句話

先修「綠界付款通知被偽造一次就永遠收不到」的安全漏洞（#64，BE-59 評 High），同一包把正式站**暫時限縮成只收信用卡**；接著分四波把 ATM／超商代碼／條碼做成完整能力（取號資訊、3 天繳費期限、逾期自動取消、人工退款），最後一包才重新打開這三種付款方式。BE-59 粗估 5～6 包，逐行核對後是 **7 包＋Leader 先改契約**：BE-59 漏了非信用卡的退款路徑，以及 Order 沒有併發控制。

## 二、使用者已拍板的規則（2026-09-30）

| # | 題目 | 拍板 | 設計含意 |
|---|---|---|---|
| 1 | 非即時付款的繳費期限 | **統一 3 天，主動送給綠界** | ATM 送 `ExpireDate=3`（天）、超商代碼送 `StoreExpireDate=4320`（分鐘）、條碼送 `StoreExpireDate=3`（天）——三者單位不同（BE-59 §1.5），派工書要逐一寫明並以官方文件複核。取號後訂單的 `PaymentDueAt` 以綠界回傳的到期時間為準，綠界期限＝訂單期限，兩邊不會不一致 |
| 2 | 信用卡未付款訂單 | **建單後 24 小時未付自動取消** | 所有訂單建單時都設 `PaymentDueAt = 建單＋24h`；取號成功後改成綠界到期時間（3 天）。逾期取消釋放庫存。沿用鑑賞期那套 saga 計時器 |
| 3 | 非信用卡付款的退款 | **人工匯款，後台登記** | 需要退款時訂單標成「待人工退款」，客服向客人要帳戶後自行匯款，再到後台登記已退金額。**系統不存客人銀行帳號** |
| 4 | B 做完之前的正式站 | **暫時只收信用卡** | BE-61 把 `ChoosePayment` 改成 `Credit`；最後一包（BE-66）才重新開放 ATM／超商代碼／條碼 |

## 三、第四十三波（本波）

### 3.1 BE-61 付款通知安全修補＋過渡期只收信用卡（後端，Codex high；派工書 `docs/67`）

**#64 修法**——webhook 端點在寫任何冪等資料之前先驗簽：

- 現況（已觀察）：`src/Hosts/GreyGray.Api.Storefront/M1aEndpoints.cs` 第 1084 行的 `POST /webhooks/ecpay` 是 inline lambda；第 1092～1096 行只檢查有沒有 `MerchantTradeNo`，第 1105 行就 `TryBeginAsync` 佔鍵，驗簽要到第 1124 行呼叫服務層、在 `src/Modules/Payment/GreyGray.Modules.Payment.Core/PaymentApplicationService.cs` 第 154 行才做。`src/Platform/Idempotency/IdempotencyStore.cs` 第 131～134 行對「同鍵不同內容」永遠回 `KeyReusedWithDifferentPayload`，hash 不同時過期也搶不回（第 81～83 行）。
- 修法：
  1. `Payment.Contracts` 新增「只驗不寫」的入口（例如 `IEcpayCallbackVerifier.Verify`：驗 CheckMacValue、MerchantID 與必要欄位，不讀資料庫、不寫狀態），實作重用 `PaymentApplicationService.cs` 第 154～169 行抽成的私有方法。**不准在 Host 抄第二份 CheckMacValue 演算法**；**不改 `IIdempotencyStore` 介面**（改了要動 6 個測試替身）。
  2. 端點改成「讀表單 → Verify → 失敗直接回 422、**冪等表零寫入** → 用驗過的欄位算 hash → TryBegin → Handle → Complete／Abandon」；服務層原本的驗簽保留作第二道防線。
  3. scope 由 `webhook:ecpay` 改為 `webhook:ecpay:payment-result`，key 改為 `MerchantTradeNo:TradeNo:RtnCode`、hash 只算這三個已驗欄位——對齊 `docs/05-API契約.md` 第 169 行本來就寫的「`MerchantTradeNo`＋交易編號」，加 `RtnCode` 讓同一交易編號的失敗與成功各自一把鍵（Codex 覆驗提出），也替 BE-63 的取號通知（另一個 scope）預留位置。換 scope 讓舊的污染列全部失效，**不需要 migration**。
  4. 把 lambda 抽成可直接呼叫的 `internal static` 處理函式，才寫得了端點層測試（目前 tests 底下沒有任何打 `/v1/webhooks/ecpay` 的測試）。端點測試放 `tests/GreyGray.M1a.CheckoutOrdering.Tests/` 的**新檔**，沿用同目錄 `TestDoubles.cs` 第 117 行的 `InspectableIdempotencyStore`。
  5. 改掉 `M1aEndpoints.cs` 第 1073～1083 行「維持現狀是對的」那段註解。
- 驗收要證明：① 偽造 payload 先到、真通知後到，真通知仍回 `1|OK` 且 Payment 變 Captured；② 驗簽失敗時冪等表**零寫入**（斷言列數）；③ 同一份真通知重送回 AlreadyCompleted、不重複入帳。
- 已知代價（推論，要用測試釘住）：換 scope 後，部署前已完成的通知若被綠界重送會重新進服務層；服務層對「已 Captured 且同 TradeNo」回成功（`PaymentApplicationService.cs` 第 180～186 行），對 Failed 回 false 不丟例外（`src/Modules/Payment/GreyGray.Modules.Payment.Core/Payment.cs` 第 189～196 行）。

**過渡期只收信用卡**（同包：與 #64 同在 Payment 模組、同一個測試目錄 `tests/GreyGray.M1a.PaymentLedger.Tests/`，分兩包會觸發稽核 ③）：

- `src/Modules/Payment/GreyGray.Modules.Payment.Infra/EcpayGateway.cs` 第 42 行 `ChoosePayment = "ALL"` 改為具名常數 `"Credit"`，註解指回 ADR-044／BE-66（重新開放的那一包）。**寫死、不做設定開關**。
- 補一條測試斷言送出的 `ChoosePayment == "Credit"`。**不准改** `tests/GreyGray.M1a.PaymentLedger.Tests/EcpayGatewayTests.cs` 第 24、65 行的 `"ALL"`——那是綠界官方 CheckMacValue 範例向量。
- 回呼**不**加「PaymentType 不是信用卡就拒收」：錢已經收了還拒收，會重演 BE-59 的 C5。
- dev 綠界模擬器不用改。

**部署前後（Leader）**：部署前在正式機跑**唯讀**盤點（`BEGIN TRANSACTION READ ONLY`）：`platform.idempotency_key` 裡 `scope='webhook:ecpay'` 各狀態筆數、key 不符 `^GG[0-9a-f]{18}$` 的筆數；另一條查詢列 `payment.payment` 的 Pending／Failed（**分開查、離線比對，不跨 schema JOIN**）。對得上的 Pending 要人工到綠界後台對帳。
