# M0 工作包

**這份是給接手實作的人（或 AI agent）看的。** 骨架、契約與架構測試已經完成並可編譯，
下面是 M0 剩下的部分，拆成八個可獨立完成的工作包。

M0 的定義（藍圖 §11）：地基。做完的驗收是——
**一個 hello-world 模組能發事件、被另一模組消費、trace 完整、架構測試會擋下違規參考、服務重開機後自動起來。**

## 開工前必讀

1. `README.md` 的四條硬規則
2. `docs/00-decisions.md` —— **已決定的不要重新討論**
3. `docs/01-系統結構.md` 的組件參考規則與 Contracts DAG

## 通用規範

- **語言**：註解與 XML doc 用繁體中文。命名用英文。
- **金額**：一律 `GreyGray.Shared.Kernel.Money`（`long` 最小單位）。
  **任何地方出現 `decimal price` 或 `double amount` 都是 bug**，不管看起來多方便。
- **時間**：一律經 `IClock`，不要直接 `DateTimeOffset.UtcNow`——
  否則截團、逾期未付、詢價逾時放行這三條規則測不起來。
- **錯誤**：可預期的業務失敗回 `Result` / `Result<T>`；例外留給「不該發生」的狀況。
- **測試**：純函式（策略計算、狀態機轉移、分帳）不需要資料庫也不需要 mock，直接單元測試。
  需要資料庫的用 Testcontainers.PostgreSql，**不要用 InMemory provider**——
  它不會執行 CHECK constraint，而帳務的不變式正是靠 constraint 守的。
- **完成一個工作包就跑** `.\ops\test.ps1`，架構測試必須全綠。

## M0-1　Platform：Outbox 實作
**相依**：無　**檔案**：`src/Platform/Outbox/`, `src/Platform/PlatformDbContext.cs`

`platform.outbox_message` 的 EF 對應、`IEventPublisher` 的實作、`IOutboxDispatcher` 的實作。

**做法要點**

- `PublishAsync` **只寫入 outbox，不派送**。它必須參與呼叫端的交易——
  用同一個 `DbContext`／同一條連線，`SaveChanges` 一次寫掉業務資料與 outbox。
- Dispatcher 取批次用 `SELECT ... FOR UPDATE SKIP LOCKED`，讓多實例可安全並行。
- 派送前 `SET LOCAL app.tenant_id = ...`（**LOCAL，不是 SET**）。
  pgBouncer 的 transaction pooling 會讓 session 變數跨交易洩漏，
  這條不注意會造成隨機的跨租戶讀取，在測試環境幾乎不可能重現。
- 失敗：`attempts + 1`、`next_attempt_at` 指數退避（建議 2^n 秒，上限 1 小時）；
  超過 10 次進死信並發告警。
- 事件的 JSON 序列化用 `System.Text.Json` source generator，不要走反射。

**驗收**
- 整合測試：在一個交易裡寫業務資料 ＋ 發事件，交易 rollback 後 outbox 也沒有那筆。
- 整合測試：兩個 dispatcher 同時跑 100 則訊息，每則只被派送一次（用 `processed_message` 驗）。
- 整合測試：handler 丟例外 → attempts 遞增、`next_attempt_at` 往後推、訊息沒被標 processed。

**不要做**：不要為了「即時」而在 `PublishAsync` 裡直接呼叫 handler。那會破壞交易邊界。

## M0-2　Platform：消費端冪等
**相依**：M0-1　**檔案**：`src/Platform/Messaging/`

`platform.processed_message` 的實作，包成一個 dispatcher 呼叫 handler 前後會自動套用的包裝。

**做法要點**
- 「冪等」不該是叫每個 handler 自己想辦法，而是給它一張表。
  handler 開頭 `INSERT ... ON CONFLICT DO NOTHING`，插不進去代表處理過了，直接 ACK。
- 去重的 key 是 `(event_id, handler_name)`，不是只有 `event_id`——
  同一個事件會有多個 handler，各自獨立。

**驗收**：同一則訊息派送兩次，handler 的副作用只發生一次。

## M0-3　Platform：Idempotency 與 Saga Timer
**相依**：M0-1　**檔案**：`src/Platform/Idempotency/`, `src/Platform/Saga/`

**做法要點**
- `IIdempotencyStore.TryBeginAsync` 的四種回傳都要能被 BFF 正確對應到 HTTP：
  `Proceed` → 往下做；`AlreadyCompleted` → 直接回傳快取的 response；
  `InFlight` → 409；`KeyReusedWithDifferentPayload` → 422。
- Saga Timer 掃描器用 `pg_advisory_lock(1002)` 互斥。
  Outbox dispatcher 用 `1001`，每日對帳用 `1003`。**用固定常數，不要用字串 hash**——
  hash 碰撞的除錯成本高得離譜。
- Timer 到期的 handler 必須冪等：timer 可能被重複觸發。

**驗收**
- 同一個 `Idempotency-Key` 連送兩次相同 request → 第二次回傳第一次的結果，副作用只有一次。
- 同一個 key 但 body 不同 → 422。
- 兩個 Worker 實例同時跑，同一個 timer 只觸發一次。

## M0-4　Platform：OpenTelemetry 接線
**相依**：無　**檔案**：`src/Platform/Observability/`, 三個 Host 的 `Program.cs`

`trace_id` 要貫穿 API → 模組 → outbox → worker → 外部整合。
客服拿到客人的訂單編號就能查到整條鏈——這是這一項存在的唯一理由。

**做法要點**
- outbox 訊息存 `correlation_id` 與 `causation_id`，dispatcher 派送時用它們**還原 Activity 上下文**。
  沒有這一步，trace 會在 outbox 斷掉，那 M0 的驗收就過不了。
- exporter 走 OTLP。M0 階段輸出到 console 也可以，Grafana stack 是 M3。

**驗收**：`Api.Storefront` 打一個會發事件的端點，Worker 消費後，
在 trace 上看得到 API span → outbox span → handler span 是同一條 trace。

## M0-5　模組組合根樣板
**相依**：M0-1..M0-4　**檔案**：每個模組的 `*.Infra/ModuleRegistration.cs`

每個模組的 `Infra` 對外**只**公開一個 `public static IServiceCollection Add<模組>Module(...)`。
其餘型別全部 `internal`。

**做法要點**
- 每個模組一個 `DbContext`，`OnModelCreating` 裡 `HasDefaultSchema("<自己的 schema>")`。
  **不要**在任何一個 DbContext 裡 map 別的模組的表。
- 連線字串每個模組一條（各自的 DB role），從設定讀 `ConnectionStrings:GreyGray_<schema>`。
- 先做 `Identity` 與 `Catalog` 兩個當樣板，確定形狀對了再複製到其餘 12 個。

**驗收**：`Architecture.Tests` 的 `Hosts_must_not_reference_core` 仍然綠；
三個 Host 都能啟動並回 `/health`。

## M0-8　CI 與部署腳本
**相依**：M0-6

**做法要點**
- CI：`dotnet build` ＋ `ops/test.ps1`。
  NuGetAudit 已在 `Directory.Build.props` 升成 error——有已知弱點的套件會讓 build 直接失敗，
  這是刻意的。升級靠 Renovate 開 PR，不靠人記得。
- 部署：`dotnet publish -r win-x64 --self-contained` → NSSM 註冊 → 沿用既有 12 個服務的
  S4U ＋ BootTrigger ＋ 每 5 分鐘 watchdog ＋ RestartOnFailure 999 慣例。
- **部署腳本必須先確認舊 process 已終止再啟動。**
  這是 baby-tracker 踩過的坑：`Stop-ScheduledTask` 沒帶走 node 子行程，
  孤兒占著埠、健康檢查由舊行程回答 → 回報成功但跑的是舊碼。
  這裡要用同樣的防呆：**要求接手的行程啟動時間晚於本次重啟，否則直接 throw。**
- Migration 由獨立高權限帳號在部署階段執行，執行後即撤回。線上服務帳號永遠沒有 DDL 權限。

**驗收**：一鍵部署後三個服務都在跑，`/health` 回 200，且新行程的啟動時間確實晚於部署時間。

## 明確不在 M0 範圍

不要順手做掉，做了會拖慢 M0 且不會更早驗證任何風險：

- 任何業務邏輯（訂單、開團、採購、出貨、記帳）—— 那是 M1a 以後
- 運費規則引擎 —— M3。M1a 是一口價，超商 60 / 宅配 120（ADR-010）
- 藍新與 LINE Pay —— M3。M1a 只有綠界（ADR-011）
- RLS 多租戶隔離 —— 只留欄位（ADR-006）
- Channel 模組 —— M4
- 前端 —— 已定 Soft Seoul（ADR-009），但那是另一條線，後端不受影響

## 停損線

如果 M0 做超過三個月還沒能讓 M0-6 通過，**那不是你慢，是硬邊界那整套儀式對現階段太重了**。
屆時請把 assembly 分離與 DB role 分離降級成 namespace 邊界，保留意圖、砍掉儀式（ADR-004）。
