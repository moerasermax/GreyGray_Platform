## 1. 要做的事

1. **取號通知路由** `POST /v1/webhooks/ecpay/payment-info`（Storefront，`MapPayment` 裡，緊接付款結果路由）：
   - 新 scope 常數 `webhook:ecpay:payment-info`；新的 `internal static HandleEcpayPaymentInfoWebhookAsync(...)`，注入 `IEcpayCallbackVerifier`、`IEcpayPaymentInfoHandler`、`IIdempotencyStore`。

   - 永久性錯誤（金額不符、方式不符、找不到付款）照付款結果路由一樣 Abandon＋Problem（綠界會重送）——這是既有行為，本包不改，報告寫明。
2. **訂單詳情帶取號資訊**（只改 `GET /v1/orders/{orderId}`，**不動 `ToOrderAsync` 的簽章與結帳／取消兩條 render 路徑**）：
   - 把這個 inline lambda 抽成 `internal static`（照 BE-35 的前例），以便測試。
   - 訂單狀態是 `AwaitingPayment` 才呼叫 `IPaymentInstructionsQuery.GetOutstandingInstructionsAsync`；**其他狀態一律 `null`、不呼叫查詢**（已取消的訂單即使 Payment 還在狀態 5 也要是 `null`）。責任切分（ADR-044 已補）：Payment 判斷取號狀態與期限，Host 依訂單狀態決定訂單層看不看得到。
   - 查詢回 Failure → `BffHttp.Problem(query.Error)`（不准取 `.Value` 丟例外，也不准吞成 `null`）。
   - `OrderResponse` 最後加 `PaymentInstructions`（有預設值 `null`，Host 自己的 response record，欄位名與契約一致：`method`、`bankCode`、`virtualAccount`、`paymentNo`、`barcodes`、`expiresAt`、`issuedAt`）。**注意**：`GreyGrayJson` 是 `DefaultIgnoreCondition.Never`，結帳與取消的回應也會多出 `"paymentInstructions": null`——這是契約允許的純新增；報告要核對既有精確 JSON 與冪等重播快照測試，不要宣稱回應位元級不變。
   - `paymentInstructions.expiresAt` 與 `paymentDueAt` 相等是契約要求，但 `PaymentDueAt` 要到 BE-64 才會被賦值——**本包不驗這條**，由 BE-64／BE-68 驗。
3. **409**：`src/Platform/Http/BffHttp.cs` 的 `StatusFor` 加**精確比對**（`string.Equals`，不是 `Contains`）三個碼 → 409：`payment.instructions-already-issued`、`payment.concurrent-update`、`ordering.concurrent-update`（ADR-044 補記「同時更新一律 409」），放在既有規則之前；既有規則一個都不改。付款端點本身不用改程式。注意：取號通知與付款結果路由遇到 `payment.concurrent-update` 時，回應因此從 422 變成 409（綠界照樣重送）——報告寫明。
4. **後台付款摘要**：`AdminPaymentSummaryResponse` 最後加 `Method`（`PaymentMethod?`）與 `Instructions`（Admin Host 自己的 response record，欄位同上），在第 1158～1167 行的對應處從 Contracts 的 `PaymentSummary` 帶過來。`manualRefund` 不是本包。
5. 不改 `docs/`、不改 Payment／Ordering 模組、不改 `PaymentInitiationRequest` 的建構。
