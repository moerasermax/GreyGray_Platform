## 2. M1b-1 範圍

### 2.1 必做

1. `Procurement` 建立自己的 aggregate、repository、DbContext 與唯一公開組合根。
2. 消費 `campaign.CampaignClosed.v1`，從 `IOrderQuery` 取得該團訂單：
   - 只接受 `PaidAwaitingClose`／`ClosedAwaitingDeparture`，且 line 仍為 `Pending` 的訂單。
   - 只為該團的 `Preorder` line 建立一筆 `PurchaseItem`。
   - 目標採購價只可由 line 的 `CampaignOfferId` 查 `ICampaignQuery`，不可拿售價代替。
   - 同一 tenant、同一 `OrderLineId` 永遠只有一筆；事件重送不得重複建立。
3. Admin 實作 frozen API：
   - `GET /v1/campaigns/{campaignId}/purchase-items?status=`
   - `POST /v1/purchase-items/{purchaseItemId}/purchased`
4. 標記買到時驗證數量與金額，保存原幣／記帳幣，且記帳幣必須是 TWD。
   - M1b-1 只接受全數買到；部分買到會回 422，直到 M1b-2 定義短缺數量的退款去向。
5. 業務資料與 `procurement.ItemPurchased.v1` 必須由同一個 DbContext transaction 寫入。
6. Ordering 消費 `ItemPurchased`，把對應 line 設為 `Purchased`；訂單進入 `Purchasing`。重送相同事件不得破壞狀態。
7. Worker 載入 Procurement handler；Admin 載入 Procurement query/command。
8. 新增 `0007_m1b_procurement.sql`，維持 tenant composite key、schema owner 與最小權限慣例。

### 2.2 明確不做

- `/purchase-items/{id}/unavailable`
- `/purchase-items/{id}/price-changed`
- `/inquiries/{id}/reply` 與詢問 timeout
- `GoodsReceived`、旅程成本、Inventory/Ledger 後續處理
- Fulfillment 與 shipment 端點

未完成的 M1b frozen 端點仍維持不存在，不回假成功，也不以空殼寫入掩蓋缺少的補償流程。

## 3. 已確認的契約缺口

`procurement.ItemUnavailable.v1` 與 Admin 的 unavailable request 只有 `reason`，但補償規則要求客人可選 `OriginalPaymentMethod` 或 `StoredValue`。事件消費者無法從現有 payload 判斷退款去向。

同一缺口也影響 `quantityPurchased < quantityRequested`：現有狀態只有 `Purchased`／`Unavailable`，Ordering 也沒有短缺數量欄位，若先接受部分買到會讓未買到的數量沒有可追蹤的退款事實。因此 M1b-1 明確拒絕部分買到，不把它誤記成完整 `Purchased`。

在 M1b-2 開工前必須先做其中一個明確決策並凍結：

1. unavailable request 增加 `refundTo`，並把選擇帶入可可靠處理的契約；或
2. 另建「待客戶選退款方式」流程，選定後才發 `RefundRequested`。

在此之前不得默認原路退款、默認儲值金，也不得讓 unavailable API 回 200 卻沒有真的完成補償。

## 4. M1b-1 可重跑驗收

1. 同一個 `CampaignClosed` 執行兩次，PurchaseItem 數量不增加。
2. 未付款、現貨、其他團的 line 均不進採購清單。
3. 缺 `CampaignOfferId` 或 offer 查詢失敗時整批失敗，不產生半套清單。
4. 正常標記買到後：
   - `quantityPurchased`、兩種實付金額、`decidedAt` 正確保存；
   - 只產生一個 `procurement.ItemPurchased.v1`；
   - Ordering line 轉 `Purchased`，Order 轉 `Purchasing`。
5. 同內容重送回原結果；不同內容重送回衝突，不覆寫第一筆事實。
6. tenant A 無法讀寫 tenant B 的 PurchaseItem。
7. Admin 回應只包含 frozen schema 欄位；名稱與訂單編號由 BFF 組裝，不把內部 DTO 直接洩漏成 HTTP wire。
8. Procurement EF model 同時包含 `procurement.purchase_item` 與 `platform.outbox_message`。
9. focused tests、全方案 tests、Release build、架構測試與事件契約測試全綠。
