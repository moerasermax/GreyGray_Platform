## 0. 事實（Leader 2026-09-19 查證，每一條都自己看過）

### 0.1 為什麼要做

使用者 2026-09-19 拍板：超商取貨與宅配都要收件人真實姓名與手機，**而且所有後台員工都看得到明文，不遮罩、不加解鎖按鈕**。

現況有三個洞：

1. **後台什麼都看不到**。`src/Hosts/GreyGray.Api.Admin/M1aEndpoints.cs` 第 1170 行
   把 `CustomerContactMasked` **寫死成 `null`**，`AdminOrderResponse`（第 1327-1346 行）
   連 `ShippingAddressId` 都沒有。出貨的人不知道要寄給誰。
2. **#56：宅配收件資訊沒有凍結快照**。訂單只存 `ShippingAddressId`，
   前台訂單詳情是**即時**回查地址簿（`src/Hosts/GreyGray.Api.Storefront/M1aEndpoints.cs` 第 1482-1507 行）。
   於是客人事後在 `IdentityServices.cs` 第 304-333 行**改地址** → 舊訂單的收件資訊跟著變；
   第 346 行**刪地址** → 舊訂單的 `shippingAddress` 直接變 `null`（第 1498-1506 行只記一筆 log）。
   ADR-038 已經替超商門市做了凍結，宅配這半沒人做。
3. **超商取貨根本沒有收件人欄位**。`CompleteCheckoutInput`（`src/Hosts/GreyGray.Api.Storefront/M1aEndpoints.cs` 第 1696-1701 行）
   與 `CompleteCheckoutRequest`（`src/Modules/Checkout/GreyGray.Modules.Checkout.Contracts/CheckoutContracts.cs` 第 122-135 行）都沒有姓名手機。

### 0.2 個資已經在系統裡，只是放錯地方

- Identity 地址簿**已經**存了收件人姓名與手機，AES-256-GCM 加密
  （欄位 `recipient_name_ciphertext`、`phone_ciphertext` 在 `IdentityDbContext.cs` 第 125-126 行，
  加解密在 `IdentityDataProtector.cs` 第 33-74 行）。**這一份維持加密，不要動它。**
- `IAuditWriter`（`src/Platform.Abstractions/Audit/IAuditWriter.cs` 第 41-62 行）
  **沒有任何實作、三個 Host 都沒註冊、`db/migrations` 裡沒有 `audit.` 資料表**。
  BE-50 還沒生效。**這一包不做稽核，也不要試著補 `IAuditWriter`**——使用者明確不要解鎖閘門。

### 0.3 #57：outbox 永不清理

`src/Platform/Outbox/OutboxDispatcher.cs` 第 89 行投遞成功後只寫
`message.ProcessedAt = clock.UtcNow`，**全 `src/Platform/Outbox/` 沒有任何 `Remove`／`Delete`／保存期限**。

這一包會把收件人真實姓名與手機放進 `CheckoutCompleted` 的 payload，
**所以保存期限是這一包的前提條件，不是順手加的功能**。沒有它，ADR-039 的取捨不成立。

## 1. 要做的事

### 1.1 migration `0021_order_recipient_snapshot.sql`（新檔）

`checkout.cart` 與 `ordering.orders` 各加：

```
recipient_name  varchar(50)
recipient_phone varchar(20)
```

nullable、`ADD COLUMN IF NOT EXISTS`、形狀與註解風格照抄 `0020_convenience_store_snapshot.sql`。
**整套 migration 可以重放是硬性要求**（見 `install-dev-environment.ps1` 第 320-333 行那段註解）。

### 1.2 契約型別

- `CheckoutContracts.cs` 第 122-135 行 `CompleteCheckoutRequest`：加 `RecipientName`、`RecipientPhone`
  （跟既有的 `ConvenienceStoreName`／`ConvenienceStoreAddress` 一樣用 init 屬性）
- 同檔的 `CheckoutCompleted`（第 207-216 行）：加同樣兩個 init 屬性
- `OrderingContracts.cs` 第 157-165 行 `OrderView`：加兩個欄位

### 1.3 應用服務：宅配抄、超商驗

`CheckoutApplicationService.cs` 第 493-517 行 `ValidateDeliveryAsync`：

- **宅配分支**（第 504 行已經取到地址）：把地址的 `RecipientName` 與 `PhoneNumber` **抄一份**進快照。
  ⚠ **不要**要求客人在請求裡填，也**不要**用請求裡的值覆蓋地址簿的值——宅配的收件人以地址簿為準。
- **超商取貨分支**：請求裡的 `RecipientName`／`RecipientPhone` 缺或空白 → 回業務失敗
  `checkout.recipient-required`（**回 `Result` 失敗，不是丟例外，不是 500**）。
- 兩個分支都要 `Trim()`，並檢查 trim 後的長度（50／20）。

### 1.4 凍結與落地

照 0.5 的五段把值傳到底。**`Cart.Complete` 那一段不要漏**——漏了事件重放時快照會變 null。

### 1.5 兩個 Host

**`src/Hosts/GreyGray.Api.Storefront/M1aEndpoints.cs`**

- `CompleteCheckoutInput`（第 1696-1701 行）加兩個欄位
- 組請求處（第 743-751 行）帶進去
- ⚠ **冪等指紋**（第 1704-1711 行 `CompleteCheckoutFingerprint`）**一定要加這兩個欄位**。
  指紋在 `src/Platform/Http/BffHttp.cs` 第 412-414 行序列化後算 SHA256 比對。
  加了之後行為會變：**同一把 `Idempotency-Key` 換掉收件人會回 422 `platform.idempotency-key-reused`**，
  而現況是直接回快取的舊回應、把新收件人靜靜吞掉。**這個改變是我們要的**，要為它補一條測試。
- `OrderResponse` 加兩個欄位，值**從訂單快照取**，不是回查地址簿。
  ⚠ 第 1482-1507 行那段即時回查地址簿的程式**留著**（`shippingAddress` 的其他欄位還要用它），
  但 `recipientName`／`recipientPhone` **不准**從那裡取。

**`src/Hosts/GreyGray.Api.Admin/M1aEndpoints.cs`**

- `AdminOrderResponse`（第 1327-1346 行）加兩個欄位
- `ToAdminOrderAsync`（第 1060-1171 行）填值
- 第 1170 行 `CustomerContactMasked: null` **維持不動**（契約保留該欄位相容用）

### 1.6 outbox 保存期限（#57）

在 `src/Platform/Outbox/` 加一道清理：**已投遞（`ProcessedAt` 非 null）且超過保存期限的訊息刪除**。

- 天數做成組態，不寫死（比照 ADR-025 鑑賞期天數的做法）
- ⚠ **`IsDeadLettered` 為 true 的不刪**——那是還沒處理完的問題，刪掉就查不出來了
- 掛在 Worker 的既有排程機制上（`SagaTimerDispatcher` 那一層的慣例），不要自己開新的計時器型別
- 要有測試證明：已投遞且過期的會刪、已投遞但沒過期的不刪、死信不刪、未投遞不刪

## 3. 驗證要求（自述不算，要能被 Leader 重跑）

必須有的測試：

1. **#56 回歸**：宅配下單後**修改地址簿**，舊訂單讀出來的收件人**不變**

8. outbox 清理四條（見 1.6）
9. 後台訂單詳情回得出明文
