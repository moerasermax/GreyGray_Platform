## 0. 開工前必須知道：稽核已經改過這些東西

2026-08-28 做過一輪邊界稽核，修掉六類問題。**這些是既成事實，不要「順手改回去」，
也不要重做。** 完整理由在 ADR-016 / 017 / 018。

| 改了什麼 | 你會遇到的地方 |
|---|---|
| `IIntegrationEvent` 多了 `AggregateType` / `AggregateId` 兩個**抽象**成員 | 44 個事件都已經填好。新增事件時編譯器會逼你填——那是刻意的，`outbox_message` 那兩欄是 NOT NULL |
| 新增 `IIntegrationEventTypeRegistry` 介面 | **實作是你的第一包**。dispatcher 從 DB 讀回 `event_type` 字串，沒有它反查不回 CLR 型別 |
| `platform` schema 定為共用例外（ADR-016）| outbox / processed_message / saga_timer 要 map 進**每個模組的 DbContext**，否則發事件與業務寫入不同交易 |
| `IAuditWriter` 與 `AuditCategory` 移到 `Platform.Abstractions.Audit`（ADR-017）| 參數改用 `Guid?`。`Audit.Contracts` 只剩查詢面 |
| `GreyGrayJson.Options` 定為 JSON 唯一來源（ADR-018）| **不要另建 `JsonSerializerOptions`**。outbox 的 payload 一旦有正式資料就改不動了 |
| `0002_platform.sql` 加了 `SET ROLE greygray_owner` 與 owner 斷言 | **你寫的每一份 migration 都要照做**。少了它 `ALTER DEFAULT PRIVILEGES` 不會生效，15 個模組 role 對表的權限會是零 |
| 補了 5 條缺的 `ProjectReference` | Ledger→Procurement、Notification→Ledger/Reporting、Audit→Notification、Checkout→Payment |
| 架構測試從 10 條變 12 條 | 新增「業務模組不得依賴支撐模組」與「Contracts 不得宣告基礎設施套件」。兩條都注入違規驗證過會紅 |
| Storefront 不再參考 Notification.Infra 與 Reporting.Infra | 公開行程持有的 DB 登入減少兩個 |
| 新增 `tests/GreyGray.Contracts.Tests`（16 條）| 守 ADR-018 的線上格式與事件目錄。**你實作 outbox 序列化時，這組就是你的回歸網** |
| `ops/test.ps1` 改成跑 `tests/` 底下**所有**測試專案 | 原本寫死只跑 Architecture.Tests，新增測試專案會靜默地永遠不執行 |

基準線：`dotnet build` 0 error 0 warning，`ops\test.ps1` **2 個測試專案 28 條全綠**（架構 12 ＋ 契約 16）。**從這個狀態開始。**

## 4. 工作包

每一包的產出、做法要點、驗收，主體在 `docs/03-M0工作包.md`。
下面只寫**那份文件之外、這次新增或修正的部分**，以及每包的自驗要求。

### BE-1　Outbox ＋ 事件型別登錄
對應 M0-1。**這一包做錯，後面全部會壞。**

三個必須做對的地方：

1. `PublishAsync` 只寫 outbox 不派送，**且必須參與呼叫端的交易**。
   實作方式是 ADR-016：Platform 提供 `modelBuilder.AddPlatformTables()`，
   每個模組的 DbContext 都套用，`SaveChanges` 一次寫掉業務資料與 outbox。
2. Dispatcher 取批次用 `SELECT ... FOR UPDATE SKIP LOCKED`。
3. 派送前 `SET LOCAL app.tenant_id`（**LOCAL 不是 SET**——pgBouncer 的
   transaction pooling 會讓 session 變數跨交易洩漏，症狀是隨機的跨租戶讀取，
   在測試環境幾乎不可能重現）。

新增的第四件：`IIntegrationEventTypeRegistry` 的實作。
啟動時掃描各模組的 `*.Contracts` 組件建表，**發現重複的 `EventType` 直接拋例外**。
序列化一律用 `GreyGrayJson.Options`（ADR-018），不要另建。

**自驗（要把輸出貼出來）**
- 交易 rollback 後 outbox 沒有那筆
- 兩個 dispatcher 同時跑 100 則訊息，每則只被派送一次
- handler 丟例外 → `attempts` 遞增、`next_attempt_at` 往後推、訊息**沒被標 processed**
- 登錄表的 `KnownEventTypes` 數量 = 44，且與 `docs/02-事件與狀態機.md` 的目錄逐條對得上
- 故意讓兩個事件用同一個 `EventType` → 啟動時拋例外（**這條要真的注入驗一次**）

### BE-2　消費端冪等
對應 M0-2。去重的 key 是 `(event_id, handler_name)`，**不是只有 `event_id`**——
同一個事件會有多個 handler，各自獨立。

`processed_message` 的寫入必須與 handler 的副作用**在同一個交易裡**，
所以它也要 map 進模組的 DbContext（同 ADR-016）。

**自驗**：同一則訊息派送兩次，handler 的副作用只發生一次。

### BE-3　Idempotency 與 Saga Timer
對應 M0-3。四種 `IdempotencyOutcome` 對應到的 HTTP 狀態碼**以 `docs/05-API契約.md` §4 為準**
（`AlreadyCompleted` 要回傳第一次的結果含當時的狀態碼，不是固定 200）。

advisory lock 用固定常數：1001 outbox · 1002 saga timer · 1003 每日對帳。
**不要用字串 hash**——hash 碰撞的除錯成本高得離譜。

**自驗**
- 同一把 key 連送兩次相同 request → 第二次回傳第一次的結果，副作用只有一次
- 同一把 key 但 body 不同 → 422
- 兩個 Worker 實例同時跑，同一個 timer 只觸發一次

### BE-4　OTel ＋ IClock ＋ ICorrelationContext
對應 M0-4。**注意這一包還要交出 `IClock` 與 `ICorrelationContext` 的實作**——
它們定義在 `Shared.Kernel` 但目前沒有任何實作，而每個模組都會注入。

`IClock.TodayInTaipei` 用 `TimeZoneInfo.FindSystemTimeZoneById("Asia/Taipei")`。
測試用的 `FakeClock` 放測試組件，不要放進 Platform。

`ICorrelationContext` 在 API 走 request header／`Activity.Current`，
在 Worker 走 outbox 訊息帶的 `correlation_id`——**dispatcher 必須能覆寫它**，
否則背景派送的每一則訊息都會共用同一個 correlation id。

**自驗**：`Api.Storefront` 打一個會發事件的端點，Worker 消費後，
trace 上看得到 API span → outbox span → handler span 是**同一條 trace**。

### BE-5　模組組合根樣板（Identity ＋ Catalog）
對應 M0-5。每個模組一個 DbContext，`HasDefaultSchema("<自己的 schema>")`，
並呼叫 `modelBuilder.AddPlatformTables()`。

**先只做 Identity 與 Catalog 兩個**，形狀對了再複製到其餘 12 個。
兩個做完就停下來給總驗收，不要一口氣做完 14 個——形狀錯了要改 14 遍。

### BE-6　hello-world 端對端
對應 M0-6。**這一包通過就是 M0 完成。** 五條驗收一條都不能少，
特別是第 4 條（把 `Notification.Core` 加進 `Identity.Core` 的參考 → build 失敗）
與第 5 條（三個服務重開機後自動起來）。

### BE-7　五個通路接縫進 schema
對應 M0-7。**每一份 migration 開頭都要 `SET ROLE greygray_owner`，
結尾都要抄 `0002_platform.sql` 末段的 owner 斷言。**
少了它 `ALTER DEFAULT PRIVILEGES` 不會生效，而錯誤要等到執行期才浮出來。

### BE-8　CI 與部署腳本
對應 M0-8。額外一條：**CI 要把 `AddOpenApi()` 產出的 schema 與
`docs/api/openapi.*.yaml` 做差異比對**，不一致就 fail。
契約是凍結的，實作漂移了要在 CI 就看到，不是等前端整合那天才發現。

部署腳本要防「假綠燈」：**要求接手行程的啟動時間晚於本次重啟，否則直接 throw。**
這是 baby-tracker 踩過的坑——舊 process 沒死乾淨，健康檢查由舊行程回答，
回報成功但跑的是舊碼。

## 5. 自驗與總驗收

### 每一包交付時，子代理自己要跑並貼出輸出

```powershell
dotnet build .\GreyGray.slnx      # 必須 0 error 0 warning
.\ops\test.ps1                    # 現有 28 條必須全綠，你自己新增的另計
```

外加該包「自驗」段落列的每一條，**逐條貼出實際輸出**，不是「已完成」四個字。

**特別要求**：任何斷言「某件事不存在／不會發生」的測試，
都要**注入一次違規、看它變紅、再改回來**。上一輪就是在這裡踩過坑——
第一版架構測試用組件參考寫，故意注入 `Ordering.Core → Ledger.Core` 之後
8/8 仍然全綠，因為編譯器把沒用到的參考裁掉了。

### 總驗收（由我做，不是由 Codex 自己說了算）

```powershell
dotnet build .\GreyGray.slnx
.\ops\test.ps1
```

加上這九條逐項檢查：

1. `git diff --stat` 是否有越出所有權表的檔案
2. 全 repo 搜 `decimal` 與 `double`，確認沒有出現在金額位置
3. 全 repo 搜 `DateTimeOffset.UtcNow`，確認只出現在 `IClock` 的實作裡
4. 全 repo 搜 `new JsonSerializerOptions`，確認只出現在 `GreyGrayJson` 裡
5. 每一份新 migration 都有 `SET ROLE greygray_owner` 與 owner 斷言
6. `SET LOCAL`（不是 `SET`）確實出現在 dispatcher 的租戶設定上
7. 註入一次架構違規，確認 12 條測試會紅
8. `KnownEventTypes` 數量與 `docs/02-事件與狀態機.md` 的事件目錄逐條比對
9. `AddOpenApi()` 的產出與 `docs/api/openapi.*.yaml` 的差異

**任何一條不過就退回，不做部分接受。** 地基階段的部分接受，代價是後面每一包都建在歪的東西上。
