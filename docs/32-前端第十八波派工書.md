## 0. 事實（Leader 查證過）

### 0.1 使用者撞到什麼

2026-09-04 00:51 使用者在正式站回報「如果使用宅配到府那邊也不會更新，交運還是已送達都不會」。
Leader 查正式機資料庫，**不是配送方式的問題**：訂單 `GG2609036EC92E5` 底下有**三張出貨單**——

| 出貨單 | 狀態 | 交運 | 簽收 |
|---|---|---|---|
| `01a0682d…` | 建立後就沒動 | 無（`carrier_cost` 是 NULL） | 無 |
| `01a0682e…`（宅配到府） | 已送達 | 00:50:52 | 00:51:02 |
| `01a0682e…`（超商取貨） | 已交運 | 00:51:29 | 無 |

`RecordShipmentDeliveredAsync` 要求該訂單掛的出貨單**全部** Delivered 才把訂單轉 `Shipped`（N:M，ADR-025：一張訂單可以拆進多張出貨單，全部簽收才起算鑑賞期）。
所以訂單留在 `ReadyToShip`（待出貨）是**正確**的。**問題純粹是畫面沒講。**

### 0.2 為什麼會長出三張

`frontend/apps/admin/app/(dash)/shipments/_components/CreateShipmentDialog.tsx` 第 51 行：
```ts
void listOrders(browserApi(), { ...(trimmedQ ? { q: trimmedQ } : {}), limit: 50 })
```
**沒有任何狀態過濾**，已經出完貨、甚至已取消的訂單照樣被列出來讓人再勾一次；也沒有顯示「這張訂單已經有幾張出貨單」。
使用者按了「已送達」看訂單沒反應，很自然會以為出貨單沒建成功，於是再建一張——越補越多。

### 0.3 訂單頁完全沒有出貨單的資訊

`frontend/apps/admin/app/(dash)/orders/[orderId]/page.tsx` 只渲染訂單本身、品項、付款與退款（第 282 行「出貨政策」、第 319 行品項表）。**沒有任何地方列出這張訂單掛了哪些出貨單。**
所以操作的人看到「待出貨」時，無從知道是「還沒建出貨單」還是「建了三張、兩張沒簽收」。

### 0.4 資料拿得到，不用改契約

- `GET /v1/orders` 已經支援 `status` query（`docs/api/openapi.admin.yaml:537`），api-client 的 `listOrders` 也有對應參數。
- `GET /v1/shipments` **沒有** `orderId` 篩選（同檔第 774-777 行只有 `status`／`cursor`／`limit`），但 `AdminShipment` 有 `orderIds` 陣列——**在前端過濾**即可。
  同一支頁面已經在用這個模式：`frontend/apps/admin/app/(dash)/shipments/[shipmentId]/page.tsx` 第 46-49 行就是 `listShipments({ limit: 100 })` 之後用 `find` 挑出要的那張；第 70-73 行也是 `listOrders({ limit: 100 })` 之後在前端組 map。
- **所以這一包不新增任何端點、不動 `docs/api/*.yaml`、不動 `packages/api-client`。**

## 1. 必做

### 必做 A　訂單頁加「出貨單」區塊（`frontend/apps/admin/app/(dash)/orders/[orderId]/page.tsx` ＋ 同目錄的 `_components/`）

在品項表底下加一個區塊，列出掛在這張訂單上的出貨單：出貨單編號（可點進 `/shipments/{id}`）、狀態徽章（用 `frontend/apps/admin/app/(dash)/shipments/_lib/labels.ts` 現成的標籤與 tone，不要重寫一份）、配送方式、追蹤單號、交運與送達時間。
資料來源：`listShipments(browserApi(), { limit: 100 })` 之後用 `orderIds.includes(orderId)` 過濾（§0.4）。讀失敗**不要擋整頁**，比照第 70-78 行 `listOrders` 那段的做法，區塊自己顯示讀取失敗即可。

★ **這個區塊要回答使用者的問題**：當訂單還是「待出貨」而底下已經有出貨單時，要有一句話說明還差什麼。例如「這張訂單掛了 3 張出貨單，還有 2 張沒有簽收；**全部簽收後訂單才會轉為已出貨**」。沒有任何出貨單時也要講「還沒有建立出貨單」，不要只是一片空白。
數字要從資料算出來，不要寫死。

### 必做 B　建立出貨單時不要列出不能再出的訂單（`frontend/apps/admin/app/(dash)/shipments/_components/CreateShipmentDialog.tsx`）

1. **過濾掉不能再出貨的**：已出貨（`Shipped`）、已完成（`Completed`）、已取消（`Cancelled`）。用 `listOrders` 的 `status` 參數或在前端過濾都可以，但**清單為空時要講原因**（「目前沒有可以出貨的訂單」而不是一片空白）。
2. **已經有出貨單的訂單仍然可以勾，但要標示**：拆單是合法的（一張訂單拆進多張出貨單，ADR-025），所以不能直接拿掉；要在那一列標出「已有 N 張出貨單」，讓人自己判斷這次是不是真的要再拆一張。資料同樣用 `listShipments({ limit: 100 })` 前端比對。
3. 對話框頂端加一行說明：一張出貨單可以合併多張訂單，一張訂單也可以拆進多張出貨單，**訂單要等全部出貨單都簽收才會變已出貨**。

### 必做 C　測試

沒有 jsdom（前端四條之四），照既有做法：**把判斷抽成純函式再測**。至少要有：

- 「這張訂單掛了幾張出貨單、還差幾張沒簽收」的計算：0 張、全部簽收、部分簽收、有一張建了沒交運，四種情況各一條。
- 「哪些訂單可以出貨」的過濾：已出貨／已完成／已取消要被排除，待出貨要留下。
- 純呈現元件用 `renderToStaticMarkup` 驗文案（照 FE-28 在 storefront 商品頁那支 `__tests__/priceDisplay.test.tsx` 的做法）：部分簽收時要出現「全部簽收後訂單才會轉為已出貨」那句、沒有出貨單時要出現「還沒有建立出貨單」。

### 必做 D　驗證與報告

- `pnpm --recursive typecheck` 全綠。
- `pnpm --recursive test`：基準 **461** ＋ 你新增的，逐專案條數貼進報告。
- build 由 Leader 跑，你不跑；**不要起或停任何 dev server**。

## 5. 可能寫錯的地方（撞到就停下來問，不要自己換做法）

- **`listShipments({ limit: 100 })` 只拿第一頁**：M1b 資料量吃得下，但要在註解寫明這是刻意的取捨，並且**不要**假裝它是完整清單（例如不要寫「共 N 張」這種會騙人的總數，除非確定沒有下一頁）。
- **狀態值用 enum 字串不要用數字**：api-client 產生的型別是 `'Shipped' | 'Completed' | …`，不要自己對照數字。
- **標籤與 tone 用 `frontend/apps/admin/app/(dash)/shipments/_lib/labels.ts` 現成的**，不要在訂單頁重寫一份——兩份會漂移。
- **訂單頁本來就有讀取失敗的處理**：新區塊失敗不能把整頁變成錯誤頁（第 70-78 行那段的註解講過這個原則）。
- 一張出貨單可能同時掛好幾張訂單，`orderIds.includes(orderId)` 要用陣列比對，不要假設只有一個。
