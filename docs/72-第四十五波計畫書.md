## 五、BE-64 的關鍵設計（給派工書）

1. **自動取消時點另存**（`orders.payment_auto_cancel_at`，內部、不進契約）。只記 `PaymentDueAt` 不夠：舊的 24h timer 觸發時分不出要不要加寬限，會把已取號的訂單提早取消。timer handler 只在 `Status==AwaitingPayment && now >= AutoCancelAt` 時取消，其他一律 no-op（孤兒 timer、重複 timer、舊 timer 都靠這條）。
2. **不在 handler 或取消端點呼叫 `CancelAllForSagaAsync`**：dispatcher 用另一條連線 `FOR UPDATE` 鎖住正在觸發的 timer 列，同一列再 UPDATE 會互等（Postgres 偵測不到）；Storefront 的建單／取消路徑沒有明確交易，取消 timer 會先 commit。重新排期一律「只排新的、舊的觸發時 no-op」。
3. **timer handler 業務失敗不准丟例外**（dispatcher 依 `fire_at` 排序，丟例外會讓後面所有 timer——含鑑賞期與詢價逾時——一起卡住）；**樂觀鎖衝突必須往上拋**（吞掉的話 dispatcher 照寫 `fired_at`，訂單永遠不會取消）。
4. **`0025` 回填**：單一敘述 `WITH b AS (UPDATE ordering.orders SET payment_due_at = …, payment_auto_cancel_at = … WHERE status = 0 AND payment_due_at IS NULL RETURNING …) INSERT INTO platform.saga_timer … SELECT … FROM b`——沒有 JOIN，形狀同 ADR-016 的「一個交易寫兩張表」；冪等靠 `payment_auto_cancel_at IS NULL`（與取消守衛同一個欄位；重放時 UPDATE 0 列）。`saga_id` 用 `replace(id::text, '-', '')`（C# 的 `OrderId.ToString()` 是 `N` 格式）；`fire_at` 至少是 **migration 執行時間＋1 小時**（migration 在停服前執行，舊 Worker 不認得新 saga type，撈到到期 timer 會丟例外卡住整條佇列；部署若在 migration 之後失敗、舊版繼續跑，一小時內要重新部署，或把 `saga_type='ordering.payment-due' AND fired_at IS NULL` 的列設 `cancelled_at`——寫進部署步驟）。
5. **取消後才入帳**：`CapturePayment` 在 Cancelled 時不失敗——記 `PaidAmount`、維持 Cancelled、回傳「取消後入帳」，服務層發 `RefundRequested(OriginalPaymentMethod)`；由 Payment 依付款方式決定退刷或人工（BE-65）。BE-66 之前非信用卡不開放，所以本波不會出現「非信用卡被打去退刷」。
6. **寬限期間仍可自助取消**（訂單還是待付款）；付款端點先檢查逾期（422）再檢查已取號（409）——BE-68 實作。
7. 設定 `Ordering:PaymentDueHours`（預設 24）、`Ordering:NonCardPaymentGraceDays`（預設 2）；預設值放 Core 具名常數；**不要再加 `TimeSpan x = default` 的選填參數**（沒傳的測試會得到 0、訂單一建立就逾期）。

## 七、尚待確認（不擋本波）

- 人工退款的會計分錄貸方科目（`1100` 現金／銀行存款，或 `1151` 綠界在途）——BE-65 派工前問使用者（會計）。
- 跨訂單的「待人工退款」清單——BE-65 時決定。
- 完整站內通知（收件匣、未讀數）與實際發送管道——另排。
- `docs/02` 第 31 行把 Payment、Notification、Audit 列為 `OrderCancelled` 的訂閱者，程式只有 Inventory 訂閱——既有落差，本波不處理，記錄在案。
- **取消後才入帳的退刷可能被綠界默默拒絕**（BE-64 驗收審查）：剛入帳的信用卡交易還沒關帳，`Action=R` 會被拒，Payment 只寫稽核——**BE-65 必修**（未關帳走 `Action=N`，或被拒時轉待人工退款）；之前以唯讀查詢人工追蹤。
- **開放 ATM／超商（BE-66）之前要先解決**（BE-64 驗收審查）：① 待付款期間後台取消品項會調低 `GrandTotal`，但已開給客人的繳費代碼金額不變——之後入帳會因金額不符變成死信（要嘛禁止有進行中付款時取消品項，要嘛金額不符時記實收並退款，**業務規則待使用者拍板**）；② Worker 停機後恢復時，24 小時計時器可能比取號事件先被處理，把已取號的訂單提早取消（逾期 handler 在期限未延長過時先查 Payment 有沒有未繳的取號）。
- **計時器佇列的隊頭阻塞**（BE-64 覆驗提出）：`SagaTimerDispatcher` 依 `fire_at` 取最早一筆，handler 丟例外就整批 rollback、2 秒後重試同一筆。暫時性的樂觀鎖衝突會自然解開，但**非業務的永久例外會卡住整條佇列**（含鑑賞期、詢價逾時）——Platform 既有行為，需要「每筆退避／重試上限／死信」，另開包。
- **部署 `0025` 之後失敗的處置**（Leader 部署清單）：migration 在停服前執行；若之後的步驟失敗、舊版繼續跑，**一小時內要重新部署成功**；做不到就把未觸發的 `ordering.payment-due` 計時器**延後**（`UPDATE platform.saga_timer SET fire_at = now() + interval 'N hours' WHERE saga_type = 'ordering.payment-due' AND fired_at IS NULL AND cancelled_at IS NULL`）——**不要取消**（取消後 0025 重放不會再排，那批訂單會永遠不被取消）。**回滾到舊版前同樣先延後**。**新版上線後再跑一次 0025 的回填**（冪等），補上 migration 到停服之間舊版建的訂單；部署後唯讀確認「`status=0` 且 `payment_auto_cancel_at IS NULL`」為 0 筆、「`status=0` 且沒有未觸發 `ordering.payment-due` 計時器」為 0 筆。
