### FE-9　admin 契約同步與缺貨退款金額

**相依**：無　**獨佔**：見 §3

**為什麼這一包存在**：`docs/06` FE-8 要求「缺貨退款的 line 要看得出來」，現在看不出來。
後端在 `e1a30a3` 給 `AdminOrderLine` 加了 `refundedAmount`，但前端分支的 YAML 還是舊的。

**已經查證過的事實（不要重查，也不要懷疑）**

- **只跑 `pnpm api:generate` 沒有用**——codegen 讀的是前端自己那份舊 YAML，

**產出**

1. 從後端 worktree 複製 `docs/api/openapi.admin.yaml` 覆蓋前端同名檔（整份複製，不手改）

  訂單不整張作廢」。訂單詳情要撐得住「已出貨 ＋ 缺貨退款 ＋ 待採購」三種 line 同時存在。

### FE-10　後台登入接上真 API

**相依**：無　**獨佔**：見 §3

**為什麼這一包存在**：`apps/admin/app/login/_lib/session.ts` 現在是四組 hardcode 帳號、
密碼都是 `greygray123`、狀態存 localStorage。**沒有 session 就沒有真實測試**——
M1a 獨立驗收的第 5 條就是卡在這裡無法執行。

**產出**

- `session.ts` 改成打 `POST /v1/auth/login`、`GET /v1/me`、`POST /v1/auth/logout`
- 角色來自 `GET /v1/me`，不再來自前端的假資料
- 未登入時導向 `/login`，登入後導回原本要去的頁面
- MSW 補上這三個端點的 mock（新檔），讓這一包在沒有真後端時也能自驗

**做法要點**

- **session 是 `gg_admin_session` 這個 HttpOnly cookie，前端 JS 讀不到，這是刻意的。**
  不要嘗試 `document.cookie`，也不要把 token 存進 localStorage 或 sessionStorage——
  藍圖的規則是「access token 永不進瀏覽器」。
- 判斷「有沒有登入」的唯一方法是打 `GET /v1/me`：200 就是有、401 就是沒有。
  不要自己維護一份「已登入」的布林值當真相。
- `endpoints/admin.ts` **已經有** `login`／`logout`／`getMe` 三個函式，直接用。
  需要它們改簽章就停下來回報，不要自己改（那個檔案不是你的）。
- 角色高低（`Owner > Accountant ≈ Operator > ReadOnly`）現有的排序邏輯可以留，
  但**它只是選單顯示用**。註解要寫清楚後端的 Policy 才是最終防線，不要讓後人誤會。
- 401 要能區分「沒登入」與「session 過期」：過期要提示重新登入，不要靜默跳走。
- 現有四個角色的測試帳號**只准留在 mock 裡**，不要留在正式碼路徑上。

**自驗（逐條貼出實際指令與輸出）**

1. `git diff --stat` —— 只有 §3 列的獨佔路徑，加上 `handlers.admin.ts` 的**那一行**
2. `grep -rn "localStorage\|sessionStorage" apps/admin/app/login apps/admin/app/_lib` —— **必須 0 筆**
3. `grep -rn "greygray123" apps/admin --include=*.ts --include=*.tsx` ——
   只准出現在 mock 檔裡，正式碼路徑必須 0 筆
4. `pnpm --filter admin typecheck` 與 `pnpm --filter admin build`
5. `pnpm --filter admin test`
6. 四個角色各登入一次的截圖，側邊選單項目數量隨角色不同
7. **注入一次違規再改回來**：把 mock 的 `GET /v1/me` 改成回 401，
   確認畫面導向 `/login` 而不是白畫面或無限轉圈，再改回來
8. 登出後再打一次受保護頁面，確認被導回 `/login`

**這一包的邊界**：你只需要對 **mock** 驗到綠。
對真後端的驗證是整合驗收的事（後端環境尚未備妥，見 §6）。

開團→收錢→出國採購→帶回→出貨→結團」，採購那一段沒有畫面就跑不完。

**契約（已凍結，照著做，不要自己加欄位）**

- `GET /v1/campaigns/{campaignId}/purchase-items?status=`
- `POST /v1/purchase-items/{purchaseItemId}/purchased`

**產出**

- `/(dash)/procurement` 進入點：選一個已截團的團 → 看該團的採購清單

**做法要點**

- **M1b-1 只接受全數買到。** 數量少於需求會被後端回 422——
  UI 要在送出前就講清楚「這一版只能全數回報」，不要讓人填了一半才被打回。

- 「買到」是寫入型操作，要帶 `Idempotency-Key`。走 `api-client` 既有的冪等模組，

- 目標採購價來自後端（由 line 的 `CampaignOfferId` 查來的），**不是售價**。
  UI 不要把售價擺在「目標價」的位置——那會讓現場的人買錯價位。
- 現場的人是站在店裡用手機操作的。**這一頁的手機版比桌機版重要**：
  觸控目標 44×44、數字鍵盤用 `inputMode`、不要做需要精準點擊的小圖示。
