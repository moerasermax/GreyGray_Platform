# 前端第四波派工書

**給平行執行的多個 agent 用。一個 agent 一包，包與包之間的檔案所有權互斥。**

接在第三波（FE-9／10／11，`bbce5e1` → 整合驗收通過）之後。基準：前端 `4730cb0`。

**這一波補的是 M1b 的最後兩塊畫面。** 前三波把 M1a 的路徑做完了，
但契約裡的**出貨（`/v1/shipments` 三個端點）**與**缺貨補償（`unavailable`／`price-changed`）**
到現在一個畫面都沒有——後台走到「買到回報」就斷了，客人也看不到自己的品項缺貨。

## 0. 為什麼前端可以跑在後端前面（這件事要講清楚）

BE-9 當初停下來拒絕開工，理由是「我要消費的三個事件沒有人發」——**它拒絕得對**。
你可能會問：那前端為什麼可以做後端還沒實作的端點？

**因為兩者缺的東西不一樣。**

| | BE-9 缺的 | 前端缺的 |
|---|---|---|
| 缺什麼 | **執行期的事件生產者** | **執行期的 API 實作** |
| mock 能不能替代 | **不能**——沒有人發事件，就沒有東西可消費 | **能**——契約凍結了，MSW 照契約回應就是合法的替身 |
| 做下去會怎樣 | 只能自己去別的模組代發，破壞模組所有權 | 照凍結契約做，後端補上時形狀本來就該一致 |

FE-3 ～ FE-8 六包**完全沒有後端**就做完並通過驗收，靠的就是這件事：
**凍結的契約是雙向斷言**，前端照它 codegen、後端 CI 照它比對 live OpenAPI。

**但有一個條件**：你只准做契約裡**已經存在**的端點。
契約沒有的東西不要發明——那就變成前端自己造了一個後端永遠不會實作的介面。

## 6. 工作包

### FE-13　後台：出貨、交運與簽收

**相依**：無（契約已凍結且完整）　**獨佔**：`apps/admin/app/(dash)/shipments/**`

**為什麼這一包存在**：後台目前走到「買到回報」就斷了。
契約裡的四個 fulfillment 端點**一個畫面都沒有**，所以「東西買回來之後怎麼出貨」
在系統裡是空的——而那是 M1b 的最後一段。

**契約給你的四個端點**

| 端點 | 做什麼 |
|---|---|
| `GET /v1/shipments` | 列表，可依 `ShipmentStatus` 過濾，游標分頁 |
| `POST /v1/shipments` | 建立，`orderIds`（**陣列**）＋ `method` |
| `POST /v1/shipments/{id}/dispatch` | 交運，`trackingNumber` ＋ `carrierCost` |
| `POST /v1/shipments/{id}/deliver` | 簽收 |

**★ 契約明文寫的、不要做錯的兩件事**

1. **Order 與 Shipment 是 N:M。** 一張訂單可拆多個包裹；
   一個包裹也可含同一客人的多張訂單（合併出貨省運費）。
   契約 description 明寫「**這是日常，不是邊緣案例**」。
   所以建立出貨單的 UI **必須能一次勾選多張訂單**，不是「在訂單頁按出貨」。
2. **`carrierCost` 是付給物流商的成本，不是向客人收的運費。**
   後者是訂單的 `shippingFee`。**畫面上這兩個數字不可以混在一起、不可以相加**，
   而且 label 要讓營運看得懂差別。這是鐵則 2「不做金額運算」的直接應用。

**必做**

1. `(dash)/shipments/page.tsx` 出貨單列表：狀態過濾、游標分頁（照既有列表頁的做法）。
2. 建立出貨單的流程：**多選訂單** → 選 `DeliveryMethod` → 送出。
3. `(dash)/shipments/[shipmentId]/page.tsx` 詳情：交運（填單號與成本）與簽收兩個動作。
4. MSW fixtures 與 handlers，涵蓋 N:M 的兩種形狀（一單多包、一包多單）。
5. 測試：至少涵蓋「多選建立」「交運帶 Idempotency-Key」「簽收後狀態變化」。

**做法要點**

- `ShipmentStatus` 的 switch **要有 default**，顯示原始字串（鐵則 5）。
- 金額一律 `formatMoney()`，不要自己組字串。
- 側邊選單加一項「出貨」（預先授權例外 2）。

**自驗（逐條貼出實際指令與實際輸出）**

1. `pnpm --filter admin typecheck` ／ `build` ／ `test`
2. `git diff --name-only` —— 只有你擁有的路徑（＋兩個預先授權例外）
3. `grep -rn "#[0-9a-fA-F]\{3,6\}" apps/admin/app/\(dash\)/shipments/` 應為 0 筆（鐵則 1）
4. N:M 兩種形狀各截一張圖
5. 送出時 DevTools 看得到 `Idempotency-Key` header 的截圖

### FE-14　後台：缺貨補償、漲價詢問，以及退款去向回工

**相依**：無　**獨佔**：`orders/_components/**` · `procurement/**`

**這一包有兩件事，第二件是回工。**

#### 第一件：缺貨與漲價的操作畫面

契約裡這兩個端點目前沒有 UI：

| 端點 | 做什麼 |
|---|---|
| `POST /v1/purchase-items/{id}/unavailable` | 現場缺貨，`reason` ＋ `refundTo` |
| `POST /v1/purchase-items/{id}/price-changed` | 現場漲價，會發詢問給客人 |

漲價詢問的契約有一個 `到這個時間還沒回覆就自動視為照買` 的欄位——
**畫面要把那個時間顯示出來**，而且要讓營運看得懂「不回覆＝照買」。
藍圖強調**系統不會因為等客人而卡住**，所以這不是阻塞狀態，UI 不要做成「等待中」的樣子。

#### 第二件：退款去向回工（ADR-023）★

**現況是錯的。** `CancelOrderDialog.tsx` 與 `CancelOrderLineDialog.tsx` 目前是：

```tsx
const [refundTo, setRefundTo] = useState<S['RefundDestination']>('StoredValue');
```

**ADR-023 定了兩件事，這行違反了兩件：**

1. **去向由客人選，不是營運代選。** 現在的 UI 是營運在後台挑一個。
2. **M1b 只開原路退款。** `StoredValue` 在 M1b 會被後端**明確拒絕**
   （回可預期的業務失敗，訊息說「儲值金要到 M3 才開放」），
   而現在它是**預設值**——營運不改就會送出一個必定失敗的請求。

**要改成**

- **不得有預設值。** 沒選就不能送出（`required`，契約本來就是 `required`）。
- `StoredValue` 這個選項在 M1b **要顯示但停用**，旁邊寫清楚「M3 才開放」。
  不要直接從選單移除——移除會讓營運以為這個功能不存在，
  而契約與 ADR 都說它存在、只是還沒開。
- 文案要反映「**這是客人的選擇**」，不是營運的判斷。
  現在的成功 toast 寫「退款已依選擇的去處處理」，語意上還可以，但要確認上下文對得起來。
- 後端回 `StoredValue` 不開放的業務失敗時，**要把後端的訊息原樣顯示給營運**，
  不要吞掉換成通用錯誤——那個訊息就是在解釋為什麼不能選。

**共用元件**：`RefundDestinationFields.tsx` 兩個對話框都在用，改一次兩邊都會動。
**先讀它再動手**，不要各改各的。

**自驗（逐條貼出實際指令與實際輸出）**

1. `pnpm --filter admin typecheck` ／ `build` ／ `test`
2. `git diff --name-only` —— 只有你擁有的路徑（＋預先授權例外 1、3）
3. **`grep -rn "useState.*StoredValue" apps/admin/` 必須是 0 筆**——這條就是回工的驗收
4. 沒選 `refundTo` 時送不出去的截圖
5. 選 `StoredValue` 時看得到「M3 才開放」的截圖
6. 漲價詢問畫面顯示自動視為照買的時間

### FE-15　前台：客人看得到自己的品項缺貨與退款

**相依**：無　**獨佔**：`apps/storefront/app/(account)/orders/**`

**為什麼這一包存在**：後台可以把品項標成缺貨了（M1a-6 已上），
但**客人在前台看不到這件事**。訂單詳情頁不知道 `Unavailable` 這個狀態，
`refundedAmount` 也沒有呈現。客人只會看到金額對不上而不知道為什麼。

**契約已經有的東西**

- `OrderLineStatus` 的 enum 含 `Unavailable`，契約 description 明寫：
  「`Unavailable` = 現場缺貨，該 line 取消並退款，**其餘 line 續行，訂單不整張作廢**」
- `AdminOrderLine.refundedAmount` 已在契約裡（前台對應欄位照 `openapi.storefront.yaml` 為準）
- `/v1/wallet` 儲值金餘額端點存在，契約寫「退款走儲值金……這個數字在退款流程裡會被看到」

**必做**

1. **先讀既有的訂單詳情頁**，確認它現在怎麼處理未知的 line 狀態。
   **先找，不要重寫**——這一包是補呈現，不是重做頁面。
2. `Unavailable` 的 line 要清楚標示：這個品項缺貨、已退款、**其餘品項照常出貨**。
   最容易做錯的是讓客人以為整張單被取消了。
3. 退款金額用 `formatMoney()` 呈現，**不要自己算**「原價減退款」——
   總額後端會回，鐵則 2。
4. MSW fixture 要有一張「部分品項缺貨」的訂單，這是這一包的主要測試資料。
5. 狀態的 switch 要有 default（鐵則 5）。

**明確不做**

- **不要做「客人選退款去向」的畫面。** 前台契約沒有那個端點，
  而且 M1b 只開原路。做了就是發明凍結契約之外的介面。

**自驗（逐條貼出實際指令與實際輸出）**

1. `pnpm --filter storefront typecheck` ／ `build` ／ `test`
2. `git diff --name-only` —— 只有你擁有的路徑（＋預先授權例外 1）
3. 部分品項缺貨的訂單詳情截圖，看得出「其餘品項照常」
4. `grep -rn "#[0-9a-fA-F]\{3,6\}" apps/storefront/app/\(account\)/orders/` 應為 0 筆

### FE-12　關掉 mock，對真後端跑一遍　⏸ **等後端 BE-13 通過才能開**

**這一包從第三波移過來，內容不變**（原文見 `docs/12` FE-12）。
它一直沒開的原因只有一個：**沒有可以連的後端環境**。

**解除條件**：後端 BE-13（M-1 環境收尾）通過整合驗收，也就是
`ops/verify-environment.ps1` 全 PASS、兩個服務重開機後自動起得來。

**在那之前不要開。** 硬開的話你會花整包的時間在裝環境上，
而那是後端 BE-13 的工作、而且他們有 `docs/14` 的 runbook 與四個 SSH 坑的紀錄。

**這一包的定位要記住**：它不是寫功能，是**驗證**。預期產出多半是
「發現了什麼」而不是新程式碼。FE-1 ～ FE-15 全部通過了，
但**沒有一行前端程式對真後端跑過**——「在 mock 下是對的」已經證明很多次，
「接上真後端是對的」一次都沒證明過。

## 7. 自驗與交付

### 你交付時要附的東西

1. `pnpm --filter <你的套件> typecheck` ／ `build` ／ `test` 的**實際輸出**
2. `git diff --name-only` —— 逐一對照 §4 的所有權表
3. 該包 §6 各自列的自驗項目（含截圖）
4. **你發現但沒做的事**：任何「我覺得這裡怪怪的但不在我範圍」都要寫出來。
   這一項不是形式——第三波就是靠它發現了契約與 UI 不一致

### 然後停下來

**你不可以自己宣告通過。** 貼出實際指令與實際輸出，不是「已完成」四個字。
然後停下來等整合驗收。不要接著做下一包。

### 整合驗收（由整合者做，不是你）

1. 越界檢查，**區分同波越界與跨波接線**
2. 自己重跑 typecheck／build／test，**不採信交付方的自述**
3. 八條鐵則掃描：raw hex、金額運算、直接 fetch、`<img>`、觸控目標
4. **每個 mutation 真的帶了 `Idempotency-Key`**——這條要看實際送出的 header，
   不是看程式碼有沒有寫
5. 交付方**沒有提到**的問題
