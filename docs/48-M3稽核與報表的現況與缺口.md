### 三之二　#55：撥款到帳（`PayoutSettled`）**有人收、沒有人發**

**更正**：本文初稿寫「金流手續費沒有任何地方記」——**那是錯的，我沒查完就寫**。實際上：

- 科目有：`AccountCodes.PaymentProcessingFee = "5400"`（`LedgerContracts.cs:113`-114）
- 分錄有：`LedgerEventHandlers.cs:42`-55 的 `PayoutSettledLedgerHandler`，DR 現金 ＋ 手續費 / CR 綠界在途
- 註冊有：`Ledger.Infra/ModuleRegistration.cs:79`
- **發布者：`src/` 裡一個都沒有。** `PayoutSettled` 只出現在契約定義、Ledger 的訂閱端、
  以及兩支測試裡；**沒有任何程式建立並發布它**。

後果：**「現金」科目永遠是 0，錢在帳上永遠停在「綠界在途」；月損益的手續費永遠是 0。**
這不是回歸，是一塊「設計好、還沒做」的區域（事件登錄表裡還有 `ReconciliationDiscrepancyFound`，
可見對帳功能本來就規劃過），但**開張前會計那一角要用到**。

★ **這裡有一個更值得記的教訓**：BE-47 為了 #43 加的 `LedgerCoverageTests`，
類別註解寫的是「鎖住分錄對照表的每個階段**都有人發、有人收**」，
但它實際斷言的是——`Every_ledger_table_event_has_a_ledger_handler`——**只有「有人收」那一半**
（而且做得很紮實，連負向對照都寫了：`ShipmentDispatched` 有非 Ledger 的訂閱者，證明第二個斷言不是裝飾）。
**「有人發」那一半從來沒有被斷言過**，所以 `PayoutSettled` 一直是綠的。
要補的話，形狀是：掃 `src/` 裡有沒有任何地方建構該事件型別，或在 outbox 層斷言事件型別出現過。

要做月損益之前，得先決定撥款資料從哪來（綠界對帳單匯入？API 拉？人工輸入？）——
**這是業務決策，不是實作細節。**

## 四之二、報表要拍板的兩件事（2026-09-06 查證過，含建議）

包二（報表）現在卡的不是工，是兩個決策。兩個都查過資料才寫，不是憑印象。

### 決策一：撥款資料從哪來（**這一個比較重要**）

`MonthlyPnLReport` 的第六個數字「金流手續費」來自 `PayoutSettled`，而**現在沒有任何地方發這個事件**（#55）。
查綠界官方文件，他們有現成的東西：

**「下載撥款對帳檔」API**（[官方文件](https://developers.ecpay.com.tw/?p=16415)）

| 項目 | 內容 |
|---|---|
| 端點 | 正式 `https://ecpayment.ecpay.com.tw/1.0.0/Cashier/QueryTradeMedia`／測試 `https://ecpayment-stage.ecpay.com.tw/1.0.0/Cashier/QueryTradeMedia` |
| 方式 | HTTPS POST、JSON、`Data` 要加密 |
| 參數 | `MerchantID`、`DateType`（1 結算日／**2 撥款日**）、`BeginDate`／`EndDate`（**最長一個月**）、`PaymentType`（可選） |
| 回傳 | CSV，欄位含 **特店交易編號、綠界交易編號、交易金額、金流手續費、平台手續費、退款金額、應收款項(淨額)、撥款日期** |
| 前置 | **要在廠商後台「系統開發管理 → 系統介接設定」設定白名單 IP**；每分鐘只能下載一個檔；timestamp 10 分鐘內有效 |

**這份 CSV 的欄位跟 `PayoutSettled` 幾乎是一對一**：

| `PayoutSettled` 欄位 | 對帳檔欄位 |
|---|---|
| `GrossAmount` | 交易金額（合計） |
| `FeeAmount` | 金流手續費 ＋ 平台手續費 |
| `NetAmount` | **應收款項(淨額)** |
| `PaymentIds` | 特店交易編號 → 我們的訂單／付款 |
| `SettlementBatchRef` | 撥款日期或批次識別 |

**建議**：用這支 API，按**撥款日期**（`DateType=2`）一天抓一次，一個撥款日一批，發一則 `PayoutSettled`。
好處是不用人工輸入、也不會漏；壞處是要先在後台設白名單 IP（**正式機 YC 的對外 IP**）。

★ **但這裡有一個會影響會計語意的坑，必須使用者拍板**：
綠界的「撥款」是**兩階段**——① 撥入**綠界帳戶**（一般賣家每週二、特約每日）
② 廠商自己按「提領」才轉進**銀行帳戶**（約 2–3 個工作日）。
**對帳檔的「撥款日期」是第 ① 階段。**

所以問題是：我們帳上的「現金」要指哪一個？

| 選項 | 意思 | 代價 |
|---|---|---|
| **A** | 撥入綠界帳戶就記「現金」 | 簡單，一則事件搞定；但「現金」裡含著還沒進銀行的錢，**對不上銀行對帳單** |
| **B** | 多一個「綠界帳戶」科目，提領時才轉進「現金」 | 帳準、對得上銀行；多一個科目 ＋ 提領那一步目前沒有資料來源（可能要人工輸入或另一支 API） |

**Leader 建議 B**——理由是這個專案的帳已經很講究（在途科目本來就分家了，`LedgerContracts.cs:59` 註解明寫「現金／銀行存款**只有撥款到帳後才進這裡**」），
用 A 會讓「現金」這個科目失去它註解宣稱的意義。但 B 要多做一步，**這是使用者的取捨，不是技術細節**。

### 決策二：報表的端點與畫面長什麼樣

`docs/05-API契約.md` 明寫「不要照著這幾行做 UI」，所以形狀要重新設計。
**建議**：比照 ADR-032 的做法（**只准純新增、既有的一個字不動**）加四條唯讀 operation，
後台開一頁分四個區塊（每團毛利、月損益、批號成本、訂單漏斗）。
這一項比較沒有爭議，**真正該先定的是決策一**——沒有撥款資料，月損益就會少一個數字或永遠是 0。
