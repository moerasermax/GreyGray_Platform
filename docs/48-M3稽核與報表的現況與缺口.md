### 三之二　#55：撥款到帳（`PayoutSettled`）**有人收、沒有人發**

**更正**：本文初稿寫「金流手續費沒有任何地方記」——**那是錯的，我沒查完就寫**。實際上：

- 科目有：`AccountCodes.PaymentProcessingFee = "5400"`（`LedgerContracts.cs:113`-114）
- 分錄有：`LedgerEventHandlers.cs:42`-55 的 `PayoutSettledLedgerHandler`，DR 現金 ＋ 手續費 / CR 綠界在途
- 註冊有：`Ledger.Infra/ModuleRegistration.cs:79`
- **發布者：`src/` 裡一個都沒有。** `PayoutSettled` 只出現在契約定義、Ledger 的訂閱端、
  以及兩支測試裡；**沒有任何程式建立並發布它**。

後果：**「現金」科目永遠是 0，錢在帳上永遠停在「綠界在途」；月損益的手續費永遠是 0。**
這不是回歸，是一塊「設計好、還沒做」的區域（事件登錄表裡還有 `ReconciliationDiscrepancyFound`，
可見對帳功能本來就規劃過），但**開張前會計那一角要用到**。

★ **這裡有一個更值得記的教訓**：BE-47 為了 #43 加的 `LedgerCoverageTests`，
類別註解寫的是「鎖住分錄對照表的每個階段**都有人發、有人收**」，
但它實際斷言的是——`Every_ledger_table_event_has_a_ledger_handler`——**只有「有人收」那一半**
（而且做得很紮實，連負向對照都寫了：`ShipmentDispatched` 有非 Ledger 的訂閱者，證明第二個斷言不是裝飾）。
**「有人發」那一半從來沒有被斷言過**，所以 `PayoutSettled` 一直是綠的。
要補的話，形狀是：掃 `src/` 裡有沒有任何地方建構該事件型別，或在 outbox 層斷言事件型別出現過。

要做月損益之前，得先決定撥款資料從哪來（綠界對帳單匯入？API 拉？人工輸入？）——
**這是業務決策，不是實作細節。**

### ⚠ 更正（同一天稍後，讀了程式碼之後）

初稿寫「兩個呼叫點都拿到 `null` 就靜靜地什麼都不做」——**錯了，兩個行為不一樣**：

| 呼叫點 | 沒有 writer 時 | 現在走得到嗎 |
|---|---|---|
| `Identity.Core/CustomerDirectoryService.cs:39`-44 | **fail-closed**：回 `audit.writer-unavailable`「稽核寫入服務未啟用，拒絕讀取個資明文」 | **走不到**——`GetContactAsync` 沒有任何 HTTP 端點呼叫，`openapi.admin.yaml` 也沒有這條 operation |
| `Payment.Infra/OrderingEventHandlers.cs:162`-165 | `if (auditWriter is null) { return; }`——**真的靜默略過** | 會，退款有在走 |

所以實際狀態是：**退款打給綠界的請求／回應沒有被留存**（`ExternalIntegration`），沒有任何徵兆；
個資那條的 fail-closed 守衛目前睡著（沒人叫得到它），**但誰要做客戶個資查詢功能，會發現整條被擋**，
而那時的錯誤訊息很明確、不會白花時間。

**「多人存取個資查不出是誰」這個風險現在不成立**——現在沒有任何方法經由 API 讀到客戶明文。
與 BE-49 同族的只有 Payment 那一條（不會報錯的錯）；Identity 那一條反而是這個專案少見的、做對了的 fail-closed。

`AuditContracts.cs:10`-13 的註解把設計意圖寫得很清楚：「個資存取留痕是**同步**的——
Identity 讀客戶明文時就要寫一筆，不能事後補事件」。意圖在，實作不在。

## 四、建議切成兩包，稽核先做

### 包一（建議先做）：稽核真的會寫

- migration：`audit.audit_record` 表（欄位照 `AuditRecord` 契約），沿用 `0001` 已經設好的
  「只給 INSERT／SELECT」權限，**不要**在這裡改權限設計。
- `Audit.Infra`：`IAuditWriter` 實作 ＋ `AddAuditModule`，三個 Host 與 Worker 都要註冊。
- `IAuditQuery.SearchAsync` 實作（游標分頁比照既有做法）。
- **一條架構測試**：把三個 Host／Worker 的容器建起來，斷言 `GetService<IAuditWriter>()` **不是 null**。
  沒有這一條，下次有人漏註冊，整個稽核又會靜靜地退回空的——這正是這一包要防的形狀
  （比照 BE-46 的 `WorkerCompositionTests`）。
- ★ **要先決定：除了現有兩個呼叫點，還要記哪些動作？** 出貨、改價、取消訂單、庫存調整、
  員工登入失敗——每一個都是候選，但每加一個就多一個呼叫點要維護。**這是使用者要拍板的。**

### 包二（等包一之後）：報表

- `Reporting.Infra` 的 read model ＋ 四個查詢實作。
- HTTP 契約：`docs/05` 明寫「不要照著這幾行做 UI」，所以**要先設計端點形狀**（修訂凍結契約，比照 ADR-032 的做法：只准純新增）。
- 後台頁面（前端樹另一包）。
- **`PaymentProcessingFee` 的來源要先拍板**，否則月損益會少一個數字或填一個假的。
