# 開發工作流與設計準則

**狀態時間**：2026-09-06。使用者拍板新增（原始要求六條，見文末「來源」）。
**這一份是兩棵樹共用文件**，列在 `.dispatch/audit-dispatch.sh` 第 ⑦ 項的清單裡——
兩棵樹逐位元相同，改一邊沒改另一邊，稽核會擋。

**這份不取代六條鐵則，也不擴大任何人的權限。**
六條鐵則的價值在於**每一條都能一眼判定違反**（金額不是 `Money` 就是 bug、
模組參考到 `*.Core` 就是 bug）。底下這些是**審查準則**與**流程規約**，
判定要靠人，所以它們不進鐵則區，也不會有 hook 幫你擋。

---

## 一、設計準則（SOLID 與設計模式）

**以 SOLID 作為設計與審查的準則，優先沿用專案既有模式。**

這個專案已經在用、而且要當共同語彙的模式：

| 模式 | 在哪裡 | 意思 |
|---|---|---|
| `Result` / `Result<T>` | 全部模組的 application service | 可預期的業務失敗回值，不丟例外（鐵則 5） |
| Outbox | `platform.outbox_message` ＋ Worker | 業務交易與事件發布同一個交易落地，事後投遞 |
| Saga timer | 鑑賞期（ADR-025） | 用排程狀態機處理「時間到了才發生」的規則 |
| Aggregate | `ShipmentAggregate`、`OrderAggregate` 等 | 不變式的守門人；跨聚合一律走事件 |
| Contracts-only 跨模組 | `*.Contracts` | 模組之間只看得到契約（鐵則 3，架構測試會擋） |
| `IClock` 注入 | 全部 | 時間是相依，不是環境（鐵則 2） |

**新增抽象或套用一個新模式時，派工書（或自驗報告）要寫得出三件事**：

1. 它解決的**具體問題**是什麼（要指得出現在哪一段程式因此變難改或測不動）
2. **更簡單的做法**是什麼，為什麼不夠
3. **維護代價**：多出幾層間接、下一個人要多讀哪幾個檔才看得懂

寫不出這三件，就不要加。**不得為了符合名詞而擴大派工範圍**——
「這裡應該用 Strategy」不是理由，「這三個分支已經各自被改過兩次而且每次都漏掉一個」才是。

## 二、架構界線（Clean Architecture）

**見 `docs/00-decisions.md` ADR-034。** 一句話版本：

現在的架構是**模組化單體 ＋ 每模組 `Core`／`Infra`／`Contracts` 三層**，
依賴方向朝核心（`Infra` → `Core`，`Core` 不認識 `Infra`），跨模組只經 `Contracts`，
而且**有架構測試在擋**。這與 Clean Architecture 的核心關切（業務政策與外部技術的依賴方向）相容。

**但本專案不承諾任何特定的 Clean Architecture 樣板**（四層命名、Domain／Application 專案拆法、
Ports & Adapters 的目錄形狀）。**這一條不構成重構授權**：
不得以「改成 Clean Architecture」為理由提出搬移型別、拆分專案、新增轉換層的重構案。
架構或契約要變，另走決策（ADR）與派工。

## 三、跨平台／手機

**見 `docs/00-decisions.md` ADR-035。** 一句話版本：

保留可能性，**現在不動工**。後端已是契約凍結的 REST（`docs/05-API契約.md` ＋ `docs/api/*.yaml`），
前端經 BFF，這已經是最低成本的保留方式。

**現在就要守的**：業務規則留在後端；不要新增「只有 Next.js 頁面才成立」的業務流程；
錯誤語意與契約相容性要維持（前端四條之三「不猜業務規則」正是為此）。

**現在不要做**：選框架、開 App 專案、拆微服務、重寫登入、為了「將來手機要用」而放寬 API 暴露或 CORS。

⚠ **已知的具體衝突，不要在派工書裡當成小事帶過**：現行契約明文
「access token 永遠不進瀏覽器、前端只拿 HttpOnly cookie、**任何要求前端存 token 的設計都是錯的**」
（`docs/05-API契約.md` §2 認證）。原生 App 不是瀏覽器——
要嘛把 App 當成另一個 BFF 客戶端、自己管 cookie jar，要嘛發 token，
而後者直接牴觸現行決策。**這是要拍板的事，不是實作細節。**

## 四、平行派工的條件

**平行以「工作包」為單位，每一包只有一個原始碼實作者。**

多包平行要同時滿足：

1. **`allow` 前綴互不涵蓋**（`audit-dispatch.sh` ③ 會機械檢查；注意它比的是前綴涵蓋，不是字串相等）
2. 包與包之間的**依賴可滿足**（B 包要用 A 包新增的介面，就不能同時開；先做共同前置包）
3. **共用檔案有唯一負責者**：migration 編號、`ModuleRegistration`／`WorkerModules` 這類註冊檔、
   契約 YAML、共用測試基底——同一波裡只能有一包能改
4. **共享驗證資源要排序**：build 輸出、三個 Host、測試資料庫與連接埠是全樹共用的。
   `ops\test.ps1` 與 `start-dev-hosts.ps1` 互斥（跑測試前要先收 Host，否則檔案鎖）——
   兩包同時跑測試會互相打斷，Leader 要指定順序
5. **子代理不各自 commit**。驗收通過到提交之間，受驗的內容不能再被別包改動

**不具備條件就序列派工。** 慢一輪，比兩包互相蓋掉重來便宜。

### ✗ 不要做的事：同一個包給多個 agent

現有授權模型是「包 → `allow` 路徑 → 一個責任 agent → 一份自驗報告」。
同一個 `GG_PACKAGE` 交給多個 agent，即使口頭分配不同檔案，**每一個都握有整包的寫入權限**：
稽核 ③ 只看包與包之間、看不到包內互撞，兩個 agent 又共用同一個 git index，會互相蓋掉，
出事時也分不出責任落在哪一份報告。

**要多工就把一波切成更多包**，用 ③ 保證不重疊——你要的併行完全成立，閘門也還在。

### 唯一 Leader

規劃者、覆驗者、派工書作者、實作者可以是不同的人或不同模型，**但**
**啟用派工、調整授權、裁決邊界、批准整合這四件事必須唯一歸屬於 Leader。**
多個規劃模型不等於多個 Leader。

## 五、驗證分層：自驗是必要不充分

| 誰 | 做什麼 | 效力 |
|---|---|---|
| 子代理 | **自我驗證**：跑完派工書列出的每一條，把**實際輸出**貼進 `.dispatch/reports/<包名>.md` | **必要不充分**。只代表「可以交付了」，**不代表通過** |
| Leader | **整合驗證**：自己重跑 build／test／端對端，逐行看 `git diff`，跑 `audit-dispatch.sh` | **唯一的通過條件** |

**子代理不能自己宣告通過**（兩棵樹的 `CLAUDE.md` 早有這一條，這裡只是講清楚兩層的關係）。
Leader 不採信自述——不是不信任，是因為自述抓不到「他以為在驗、其實量錯了」那一類錯，
而這個專案已經有四次「沒反應」的結論後來被證明是量法壞掉。

## 六、邊界測試（派工書必列）

派工書的每一條驗收要寫出：**前置條件 → 操作 → 預期結果 → 怎麼驗**。
依變更風險涵蓋正常、邊界、失敗三類。**「加了三條測試」不等於邊界測試做完。**

交易類（訂單／庫存／帳務／出貨）的包，至少要考慮這六種：

1. **重複與併發**：同一個請求送兩次、兩個請求同時搶同一批貨（冪等鍵、樂觀鎖）
2. **金額與數量的上下限**：0、負數、超過庫存、超過 `long` 能表達的範圍
3. **非法狀態轉移**：已出貨再取消、已取消再出貨、跳過中間狀態
4. **權限**：換一個角色打同一個端點
5. **事件重放**：同一則事件被投遞兩次（outbox 至少一次投遞，重放必須是 no-op）
6. **部分失敗**：三張出貨單只簽收一張、部分買到、外部服務逾時

**不適用的類別要在派工書裡註明理由**，不要靜靜跳過。
資料庫層的規則（constraint、trigger）**一律用正式 migrations 驗**，
`EnsureCreated` 成功不代表正式 schema 正確。

## 七、Planner 上稿

**`git` 裡的 `docs/*.md` 是正本，Planner 是跨機器可讀的副本。**
理由：hook 與 `audit-dispatch.sh` 實際讀的是檔案系統；`ACTIVE.md` 仍是派工授權的唯一輸入。
Planner 拿不到那個角色，硬把它寫成正本，會生出一個「看起來是正本、實際上不生效」的來源。

| 什麼 | 什麼時候上傳 | kind |
|---|---|---|
| 波次計畫書 | 拍板之後、寫派工書之前 | `plan` |
| 派工書 | **派工前先 commit 閘門檔之後、真的派出去之前** | `dispatch` |
| 驗收／執行紀錄 | 撤包之後 | `exec` |

上傳一律帶 `commitSha`（寫派工書時的樹 HEAD），這樣文件版本才對得回程式狀態。

- **回填範圍**：只補最近一波，之後每一波都傳。歷史 47 份不回填。
- **Planner 掛掉時**：**不擋派工**（git 才是正本）。Leader 在該波派工書留一行
  「Planner 上稿待補」，可用時補上。這一條刻意寫死，免得子代理自己發明例外。

## 八、角色分工（可調，不是鐵則）

一波的計畫可以指定：**規劃者 → 覆驗者 → 派工書作者 → 實作者**，Leader 唯一。
預設配置（使用者 2026-09-06 提的，可依包的大小調整）：

| 角色 | 預設 | 為什麼 |
|---|---|---|
| 整體規劃設計 | Fable／Opus | 要跨兩棵樹看全局 |
| 規劃覆驗、派工書撰寫 | Codex（Astra） | **這一道是新增的**：派工書寫錯前提發生過三次，子代理否決派工書四次、四次都對 |
| 實作 | Sonnet（Claude）／Astra（Codex） | 依包的性質挑 |
| 其他 | Gemini 等由 Leader 調度 | |

**模型配置寫在波次計畫與啟動 prompt 裡，不是永久架構決定。**
小包（半天以內、單檔、無契約變更）不必走完整條鏈——覆驗的成本要對得起包的風險。

**覆驗要產出的是缺口與反例**（「這個前提我查了，第 N 行不是這樣寫的」），
不是「看起來可以」。驗收依據永遠是實際證據。
