- 計畫：`docs/72-第四十五波計畫書.md`；這是 **BE-68 驗收走查時發現的缺陷**（不是新功能），修正包、無契約變更、無 migration。
- **只動 Ordering 模組與它的測試**。不准改 `src/Hosts/`、`src/Platform/`、其他模組、`docs/`、`db/`。

## 0. 事實（後端 HEAD 為準；對不上就停下來回報）

### 0.1 實測到的現象（2026-10-02，dev Release＋綠界模擬器）

- 兩次畫面走查各下一張單：**兩次都相撞**。第一次 Host 先寫入、Worker 撞 23505（`worker.out.log`，`CheckoutCompletedHandler.HandleAsync` → `CreateFromCheckoutAsync`），outbox `checkout.CheckoutCompleted.v1` 留下 `attempts=1` 後成功——客人看不到；第二次 Worker 先寫入、Host 撞 23505（`storefront.out.log`，`CompleteCheckoutAsync` 的 work → `CreateFromCheckoutAsync` → `OrderingDbContext.SaveChangesAsync`），冪等鍵 `storefront:cart:checkout` 變 `ABANDONED`、前台顯示「系統發生問題，請稍後再試。」，但訂單其實已由 Worker 建好。
- 撞到的是 `ux_orders_tenant_checkout_cart`（`db/migrations/0006_m1a_core.sql` 第 630～631 行，`(tenant_id, checkout_cart_id)`）。**同一張表還有 `ux_orders_checkout_event`（第 632～633 行，`checkout_event_id`）**——兩條路徑用的是同一個 `CheckoutCompleted` 事件，所以先撞到哪一個都可能，兩個都要認。
- 正式機 BE-64 之前的 storefront log 全部查過：約 48 次結帳請求，撞到這個索引 **0 次**；dev 的 outbox 有 4 筆 `CheckoutCompleted` 是「失敗 1 次後成功」——**競態本來就存在**，BE-64 在查詢與 INSERT 之間多了一次計時器寫入（`OrderingApplicationService.cs` 第 99 行 `timerScheduler.ScheduleAsync`），把時間窗拉大了，Host 開始會輸。

## 1. 要做的事

1. **Core 新例外**：`src/Modules/Ordering/GreyGray.Modules.Ordering.Core/` 新增 `OrderingCheckoutAlreadyPlacedException`（`sealed`，比照同目錄 `OrderingConcurrencyException.cs` 的形狀）。
2. **Infra 翻譯**：`OrderingDbContext.SaveChangesAsync` 另接 `DbUpdateException`，**只在** `InnerException is PostgresException { SqlState: UniqueViolation }` **且** `ConstraintName` 是 `ux_orders_tenant_checkout_cart` 或 `ux_orders_checkout_event` 時：`ChangeTracker.Clear()` → 丟 `OrderingCheckoutAlreadyPlacedException`。其他任何 `DbUpdateException` **原樣往上拋**（不准吞、不准改型別）。既有的併發分支不動。
3. **Core 回既有訂單**：`CreateFromCheckoutAsync` 第 108 行的 `SaveChangesAsync` 接住 `OrderingCheckoutAlreadyPlacedException` → 重新 `GetByCheckoutAsync(tenantId, cartId)` → **走跟第 53 行完全相同的判斷**（同鍵回既有 `ToView()`、異鍵回 `ordering.checkout-already-processed`；把那段抽成一個私有方法兩處共用，不准複製一份）。重讀仍是 `null`（理論上不會）→ 重拋原例外。
4. **不准**改成「先排計時器以外的順序」、不准在這裡加 advisory lock 或改 Host、不准改 `IOrderingApplication` 的方法清單、不准改冪等包裝器。
5. 輸家那一邊已排的計時器（saga_id 是沒寫進資料庫的 OrderId）會變成孤兒；觸發時 `GetAsync` 回 `null` → no-op（BE-64 已有此行為）。**本包不清它**，但 R1 要斷言它存在且觸發 handler 時不丟例外、不動任何訂單。
