### ★ Leader 已經靜態推翻的一件事（交接書與 00-進度總表寫錯了）

`00-進度總表.md`「現在卡在哪」#22 與 `04-交接書.md` 第四節都宣稱：

> (A) 客戶端拿**同一把** `Idempotency-Key` 重試，會被當成全新請求 → **建出第二張訂單**

**Leader 2026-09-01 讀程式碼認為這個結論是錯的**，因為**兩個模組各自都有冪等，
而且都綁在同一把 checkout 冪等鍵上**：

| 模組 | 冪等做法 | 位置 |
|---|---|---|
| Checkout | `cart.IsCompleted` 且 `cart.CheckoutIdempotencyKey` 相同 → `cart.ReplayCompletedEvent()`，**重播同一個 `CheckoutCompleted`**；key 不同 → `CartAlreadyCompleted` 失敗 | `src/Modules/Checkout/GreyGray.Modules.Checkout.Core/CheckoutApplicationService.cs:210-215` |
| Ordering | `orders.GetByCheckoutAsync(TenantId, CartId)` 找得到既有訂單，且 `CheckoutIdempotencyKey` 相同 → **直接回既有訂單**；key 不同 → `ordering.checkout-already-processed` 失敗 | `src/Modules/Ordering/GreyGray.Modules.Ordering.Core/OrderingApplicationService.cs:40-53` |

所以**同一把 key 重試，推論上會一路重播到原本那張訂單，不會建出第二張**——
BFF 層的 key 被 abandon 掉，只是讓請求「重跑一次業務邏輯」，而業務邏輯本身
是可重入的。**「客人重複下單／重複付款」這個結論站不住。**

**但這是推論，不是證據。這一包最重要的一條，就是用測試把它釘死或推翻。**
如果測出來真的會建第二張訂單，那 Leader 這個推論就是錯的，嚴重性要往上調——
**如實記錄你測到的，不要為了配合任何一方的說法調整結論。**

### 於是還剩下什麼真的是缺口

推翻 (A) 之後，仍然成立的不一致有三條，**這一包要逐條產出證據**：

- **(A′) 幽靈訂單**：訂單已經 commit，但第 ③ 步失敗 → 客人拿到錯誤、永遠看不到 201。
  訂單其實存在（`PaymentRequested` 也已經發出去了）。**這正好解釋 BE-32 的觀察。**
- **(A″) 換一把 key 就卡死**：客人（或前端）在收到錯誤後改用**新的**
  `Idempotency-Key` 重試 → Checkout 回 `CartAlreadyCompleted` → **永遠回不了 201**，
  訂單卻在資料庫裡。這是「不會重複下單，但客人自己救不回來」。
- **(B) 購物車結案了但沒有訂單**：第 ② 步失敗（業務失敗，非例外）時，
  第 ① 步的購物車結案**已經 commit** → 購物車沒了、訂單也沒建立。

### 還有一塊完全沒人審過的

`BffHttp.ExecuteIdempotentAsync` **不是 checkout 專用**——全 repo 有 **33 個呼叫點**
（Admin Host 21 個、Storefront Host 12 個）。「副作用已 commit 卻把冪等鍵 abandon」
這個形狀，在 checkout 這一條之所以沒釀成重複下單，**純粹是因為 Checkout 與
Ordering 兩個模組剛好自己有冪等**。**其他 32 個呼叫點有沒有這個運氣，沒有任何人查過。**
如果某個呼叫點包的是「模組本身沒有冪等的寫入操作」，那裡才是真正的重複副作用風險。

**這一塊是這一包價值最高的部分。**
