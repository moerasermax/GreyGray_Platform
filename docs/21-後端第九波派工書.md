### BE-23　`CapturePayment` 誤設 `RefundedCurrency` ＋ EF model 補三條約束　🔴

**相依**：無　**獨佔**：見 §3

**這是這一波的重點。** FE-12 對真後端跑的第一個「結帳付款」流程，
現在**必定**在真的資料庫上炸 `23514`——不是邊角案例，是主流程的第一步。

**必做**

1. **刪掉 `Order.cs:206`**（`RefundedCurrency = amount.Currency;`）。
   `CapturePayment` 只是記錄付款，沒有任何退款發生，不該碰 `RefundedCurrency`。
   對照同一檔案 `299-300` 行（`Refund`）與 `627-628` 行（缺貨補償退款）——
   兩處都是 `RefundedAmountMinor` 與 `RefundedCurrency` **一起**設，
   那才是這兩個欄位該被寫入的地方。
   ★ 只刪這一行。`PaidAmountMinor` 與 `PaidCurrency` 那兩行是對的，不要動。

2. **把缺的三條 check constraint 補進 `OrderingDbContext.cs` 的 `ConfigureOrder`**，
   跟 `db/migrations/0006_m1a_core.sql:598-615` 的定義**逐字一致**（欄位名要用
   snake_case 資料庫欄名，不是 C# 屬性名）：
   - `orders_currency_consistent`
   - `orders_paid_consistent`
   - `orders_refunded_consistent`

   目的：往後任何用 `EnsureCreatedAsync()` 建 schema 的整合測試，
   也會受這三條約束保護，不會再重演「172 條測試沒有一條抓到」。

   ★ 這一波**不**要求把其餘幾條 migration 裡有、EF model 也沒有的約束
   （`orders_id_not_empty`／`orders_status_known`／`orders_shipping_policy_known`／
   `orders_delivery_method_known`／`orders_quote_explain_array`）一起補齊——
   那幾條是列舉範圍檢查，C# enum 已經在型別層擋住多數情況，風險與這次不同等級。
   **如果你評估後認為應該一起補，先在自驗報告寫清楚理由，不要不聲不響多做。**

3. **加一條會失敗在修之前的迴歸測試**，證明修的是真的：
   在 `tests/GreyGray.M1a.CheckoutOrdering.Tests/`（或你判斷更合適的既有檔案）

   `EnsureCreatedAsync()` 建的 schema 在你補完第 2 點之後就會真的擋下這個 bug，
   所以這條測試在「先補約束、後刪那行」的順序下會先紅再綠，能證明它真的測到重點）。

4. **至少一條測試要在「真的套過 migration 的 schema」上完成付款**，

### BE-24　`0003_channel_seams.sql` 對 `ledger.account` 的 seed 非冪等　🔴

**相依**：無　**獨佔**：見 §3

**這個 bug 只在「重放已經跑過的 migration」時才會發生**——`ops/test.ps1` 每次都是
全新容器，永遠踩不到；BE-22 是因為要讓本機開發環境腳本可以安全重跑才撞見的。
但 `ops/invoke-migrations.ps1` 沒有任何「已套用就跳過」的追蹤，
**每次重新部署都會把全套檔案再套一次**，所以這不是邊角案例。

**必做**

1. **把 `db/migrations/0003_channel_seams.sql` 裡 `ledger.account` 的 seed
   INSERT（約 64-71 行）改成 `WHERE NOT EXISTS` 導引的 `INSERT ... SELECT`**，
   不要再用 `ON CONFLICT (tenant_id, code) DO NOTHING`：

   ```sql
   INSERT INTO ledger.account (tenant_id, code, name, category, is_active)
   SELECT '00000000-0000-0000-0000-000000000001'::uuid, '1200', '通路應收帳款', 'ASSET', false
   WHERE NOT EXISTS (
       SELECT 1 FROM ledger.account
       WHERE tenant_id = '00000000-0000-0000-0000-000000000001'::uuid
         AND code = '1200'
   );
   ```

   **為什麼這樣就對了**：`WHERE NOT EXISTS` 在建構候選列**之前**先判斷要不要插入；
   資料列已存在時整條 `INSERT` 不會被觸發，`id` 是不是 `NOT NULL`
   （那是 `0005` 才加的欄位）根本不會被檢查到。在全新資料庫上（`id` 欄位還不存在）
   `NOT EXISTS` 一樣成立，行為跟原本的 `ON CONFLICT DO NOTHING` 沒有差別。
   ★ 只改這一段 seed INSERT，`0003` 檔案其他部分不要動。

2. **加一條迴歸測試**：在 `tests/GreyGray.M1a.Migrations.Tests/M1aCoreMigrationTests.cs`
   新增一個 `[Fact]`，套用完整鏈 `0001`～`0014`（可以直接呼叫既有的
   private helper `ExecuteMigrationChainAsync(connectionString, migrations, 14, ct)`，
   看它現在的簽章能不能直接吃 14，不行就照同樣寫法擴充，不要另開一支平行的 helper），
   然後**單獨重放一次 `0003_channel_seams.sql`**，斷言不噴 `PostgresException`。

   這條測試在你修之前跑起來必須是紅的（重現 `null value in column "id"`），
   修完之後轉綠——兩次的實際輸出都要出現在自驗報告裡。

**做法要點**

- **不要去動 `0005` 或任何更後面的 migration。** 問題出在 `0003` 自己的 INSERT
  沒有為「重放」做防護，不是 `0005` 加欄位加錯了——欄位加 `NOT NULL` 對正式資料
  是對的，`0005` 自己的 seed（`121-141` 行）已經用 `ON CONFLICT ... DO UPDATE`
  處理好重放，不用管它。
- 這個 bug 目前**沒有留下髒資料**（整份檔案包在 `BEGIN...COMMIT`，失敗會整份
  rollback）——BE-22 已經查過，不用重查，但你的迴歸測試斷言的是「不噴錯」，
  不是「資料庫沒壞掉」。

**自驗（寫進 `.dispatch/reports/BE-24.md`）**

1. 修之前重放 `0003`（在已套過 `0001`～`0014` 的資料庫上）的實際錯誤輸出
   （`ERROR: null value in column "id"` 那個訊息）
2. 修之後同樣操作，實際輸出證明不再噴錯
3. `dotnet build .\GreyGray.slnx` 0 error 0 warning
4. `.\ops\test.ps1` 全綠，說明新增幾條（**前景跑，不准丟背景**）
5. `git diff --name-only` —— 只有你擁有的路徑
6. 在一個**全新**資料庫上从頭套 `0001`～`0014` 一次，確認 `ledger.account`
   仍然有 **15** 筆，沒有因為改法而漏插或重複
   （★ 2026-08-30 BE-24 執行後更正：原本寫的「16 筆」算錯了——`0003` 插入的
   `1200` 本來就在 `0005` seed 的 15 筆裡面，對它走的是 `ON CONFLICT ... DO UPDATE`
   補 `id`／`type`，不是再插一列，所以不能「`0003` 的 1 筆 ＋ `0005` 的 15 筆」相加）
