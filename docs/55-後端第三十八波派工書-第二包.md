## 0. 事實（Leader 2026-09-19 查證）

### 0.1 為什麼要做

FAQ 有三處寫「請聯絡客服」，但**站上沒有任何客服管道**。
使用者 2026-09-19 拍板：前台右下角做展開式客服小視窗，**引導式選單、不接 AI**，
客人選不到答案就留言，**留言進後台自己的客服工單列表**（不是 GitHub issue、不是寄 Email）。

前端那半是 FE-35（前端樹 `docs/37`）。**你只做後端**。

### 0.2 為什麼是新模組，以及為什麼不叫 `Support`

現有 14 個模組沒有一個適合：
- `Notification` 是**只訂閱事件**的支撐模組，而且**沒掛在 Storefront Host**
  （`src/Hosts/GreyGray.Api.Storefront/GreyGray.Api.Storefront.csproj` 第 17 行的註解明講）
- `Audit`、`Reporting` 幾乎是空殼

客服工單要被 Storefront 與 Admin **兩個 Host 直接呼叫**，不是純訂閱事件，所以是業務模組。

⚠ **模組叫 `CustomerService`，不叫 `Support`。**
架構測試的 `SupportModules`（`tests/GreyGray.Architecture.Tests/ModuleBoundaryTests.cs` 第 22-33 行）
指的是「**支撐模組**：不被任何業務模組依賴——它們只訂閱事件」。
取名 `Support` 會跟那個概念撞在一起，以後每個讀架構測試的人都要重新判斷一次。

**所以**：
- 模組名 `CustomerService`，schema `customer_service`，role `greygray_customer_service`
- 進 `ModuleBoundaryTests.cs` 第 16-20 行的 `Modules` 陣列
- **不要**進第 30-33 行的 `SupportModules`

**但對外的端點路徑用 `/v1/support/tickets`**（對客人來說「support」比「customer-service」短而自然）。
模組名與路徑不同是刻意的，不要「順手統一」。

### 0.3 契約 Leader 已經寫好——**一個字都不要改**

`docs/api/openapi.storefront.yaml`、`docs/api/openapi.admin.yaml`、`docs/05-API契約.md`
Leader 已經改好並提交。**`docs/api/` 與 `docs/05` 不在你的 `allow` 裡。**

| 端點 | 身分 | 成功 | 失敗 |
|---|---|---|---|
| `POST /v1/support/tickets` | **匿名可打** | `201 SupportTicket` | `422 support.contact-required`、`429 support.too-many-requests` |
| `GET /v1/support/tickets`（Admin） | `StaffRole.ReadOnly` | `200 SupportTicketPage` | — |
| `GET /v1/support/tickets/{id}`（Admin） | `ReadOnly` | `200 SupportTicket` | `404` |
| `POST /v1/support/tickets/{id}/resolve`（Admin） | `StaffRole.Operator` | `200 SupportTicket` | `404`、`409 support.already-resolved` |

**建立工單的 request**

| 欄位 | 型別 | 必填 |
|---|---|---|
| `message` | `string`，1-2000 字 | ✅ |
| `contactEmail` | `string \| null` | email 與 phone **至少一個** |
| `contactPhone` | `string \| null` | 同上 |
| `menuPath` | `string[]`，最多 5 層、每層 ≤ 100 字 | ❌ |
| `orderId` | `uuid \| null` | ❌ |

`menuPath` 是客人在小幫手裡走過的選單路徑——**要知道他是卡在哪一題才問的**，
不然客服看到一句「不能用」完全沒有上下文。

**`SupportTicket` 回應**：`id`、`status`（`open` / `resolved`）、`message`、`contactEmail`、`contactPhone`、
`menuPath`、`orderId`、`customerId`、`createdAt`、`resolvedAt`、`resolvedBy`、`staffNote`。

⚠ **前台的 201 回應不要回 `customerId` 以外的任何別人的資料**；工單建立後前台不提供查詢端點
（匿名工單沒有安全的查詢方式——這是刻意的，不是漏做）。

### 1.6 防灌 —— ⚠ fail-open 要自己寫，不會自動發生

全 repo **沒有 rate limit、沒有 antiforgery**（`docs/00-decisions.md` 第 457 行明寫「還沒接」，
設計上交給 Cloudflare）。這是**第一個真正需要防灌的匿名寫入端點**。

做法：用既有的 `IDistributedCache`（Garnet）做「同一 IP ／同一 `gg_cart` cookie 每小時上限」，
範本是選店票（`src/Hosts/GreyGray.Api.Storefront/Logistics/CvsLogisticsEndpoints.cs`
第 350-365 行：`SetAsync` 帶 TTL、`GetAsync` 取回）。超過回 `429 support.too-many-requests`。

⚠ **底層是 `AddStackExchangeRedisCache`，Garnet 斷線時 `IDistributedCache` 會拋例外**
（`RedisConnectionException` 之類）。**計數的讀寫一定要包 try-catch，捕捉到就放行並記 error log。**
照抄而不包，端點會變成 fail-closed——Garnet 一掛，連正常客人的留言都收不了（直接 500）。

**判斷依據**：客服留言不是安全邊界。KV 掛掉時寧可收到灌水，也不要讓真客人問不了問題
（何況 session 也靠 Garnet，它掛掉時整站登入已經先壞了）。

## 3. 驗證要求

必須有的測試：

1. 匿名留言成功建立工單
2. 登入客人留言，工單帶得出 `CustomerId`
3. email 與 phone 都沒填 → 422 `support.contact-required`
4. `message` 超過 2000 字 → 擋下
5. `menuPath` 超過 5 層 → 擋下
6. 超過每小時上限 → 429 `support.too-many-requests`
7. **★ `IDistributedCache` 丟例外時 fail-open**：留言仍然收得下來（不是 500）
8. 後台列表游標分頁（`limit+1` 判斷、游標壞掉回 Problem）
9. `ReadOnly` 角色不能結案、`Operator` 可以
10. 重複結案 → 409 `support.already-resolved`
11. 架構測試：新模組沒有被任何業務模組依賴

**★ 跑完之後一定要自己起一次 dev 環境確認沒把它弄壞**
（新 schema 漏投遞的話 Host 會直接 crash，這是 1.3 那張表的重點）：

```

```
