## 0. 要修的是什麼

### 機制（BE-34 已證實，直接當前提）

`src/Modules/Fulfillment/GreyGray.Modules.Fulfillment.Core/FulfillmentApplicationService.cs:18`
的 `CreateAsync`：

- 每次都 `ShipmentId.New()`
- **不發任何事件、不改訂單狀態**——建完之後訂單仍是 `ReadyToShip`
- 唯一的守衛是 `order.Value.Status != OrderStatus.ReadyToShip`，而它自己不改狀態，
  所以**重試會通過同一個守衛**
- 資料庫唯一鍵 `ux_shipment_order_tenant_shipment_order` 是
  `(tenant_id, shipment_id, order_id)`——**擋不到「同一批訂單被建成兩張出貨單」**
- **一層冪等都沒有。** checkout 那邊有 Checkout ＋ Ordering 兩層模組冪等接住，這裡沒有

### 觸發路徑（Leader 已重新逐行確認過，全部成立）

`POST /v1/shipments`（`src/Hosts/GreyGray.Api.Admin/M1bFulfillmentEndpoints.cs:72`）
用的是 `BffHttp.ExecuteIdempotentAsync` 的**舊多載**
（`src/Platform/Http/BffHttp.cs:174`）：

1. `CreateAsync` 已經 `SaveChangesAsync`（出貨單已經在資料庫裡）
2. 之後在收尾階段出錯——`JsonSerializer.Serialize` 丟例外，或
   `idempotency.CompleteAsync` 在 `affected != 1` 時 `throw`，DB 連線瞬斷也算
3. 舊多載的 `catch { AbandonAsync; throw; }` 把冪等保護解除，回 500
4. 店員用**同一把 key** 重送
5. `IdempotencyStore.TryBeginAsync` 的 `ON CONFLICT ... WHERE` 條件
   （`src/Platform/Idempotency/IdempotencyStore.cs:82`）對
   `ABANDONED` ＋ 相同 request hash 回 `Proceed`
6. → **第二張出貨單**

**第 4 步不是假設。** 前端的 `createPayloadIdempotencyScope`
（`packages/api-client/src/idempotency.ts`，**在前端 worktree**）
只有在**成功之後**才 `complete()` 換新 key；失敗後同一份 payload 重送，
送的就是**同一把 key**。所以這條路是真的走得到的，不是理論。

### 為什麼比 #22 嚴重

重複那張出貨單**會被撿貨、會被 `dispatch`**（寫入 `carrier_cost` 物流成本），
所以**同一批貨可能出兩次、物流成本重複入帳**。
觸發條件比 checkout 窄（要基礎設施故障，不是每天都會走的業務失敗路徑），
但後果嚴重得多——這是 33 個呼叫點裡唯一會**直接賠錢**的。

## 1. 修法：**已經定死，不要重新設計**

### ★ 先講一個 Leader 已經否決的方向，不要走回去

`04-交接書.md`、`00-進度總表.md` #23 與 `.dispatch/PROMPTS.md` 都寫過
「以 `(tenant_id, 排序後的 orderIds, method)` 查既有出貨單」這個選項。

**Leader 查證後否決。那個做法會破壞已凍結的契約。**

`docs/api/openapi.admin.yaml:768` 的 `POST /v1/shipments` 描述明文寫著：

> **Order 與 Shipment 是 N:M。** 一張訂單可拆多個包裹；
> 一個包裹也可含同一客人的多張訂單（合併出貨省運費）。這是日常，不是邊緣案例。

同一句話在三個地方各寫了一次（`FulfillmentContracts.cs` 的 `ShipmentSummary`
XML doc、`ShipmentAggregate.cs` 的 `Create` XML doc、
`db/migrations/0012_m1b_fulfillment.sql` 的 `COMMENT ON TABLE`）。
**「同一批訂單、同一個配送方式、建成兩張出貨單」就是「一張訂單拆兩個包裹」
這個日常情境本身**，用它當自然鍵等於把這個能力關掉。

**而且既有測試蓋不到這個回歸**：
`tests/GreyGray.M1b.Fulfillment.Tests/FulfillmentPostgresTests.cs:95` 的
`Orders_and_shipments_are_many_to_many` 拆兩個包裹時**刻意用了兩個不同的
`DeliveryMethod`**（`HomeDelivery` 與 `ConvenienceStore`），
`tests/GreyGray.M1b.Fulfillment.Tests/ShipmentAggregateTests.cs:33` 也一樣。
所以自然鍵修法**跑完全套測試會全綠**，然後在正式環境擋掉「同一個宅配拆兩箱」。
這正是要在派工書裡先講死的原因。

### 定案：**呼叫端把冪等鍵傳進來**，比照 Checkout 與 Ordering 既有做法

這個 repo 已經有一模一樣的前例，照抄它，不要自創：

| 既有前例 | 位置 |
|---|---|
| `Cart.CheckoutIdempotencyKey`（可為 null ＋ 過濾式唯一索引） | `src/Modules/Checkout/GreyGray.Modules.Checkout.Infra/CheckoutDbContext.cs:98` |
| 「已完成就比對鍵、相同就重播」 | `src/Modules/Checkout/GreyGray.Modules.Checkout.Core/CheckoutApplicationService.cs:210` |
| `Order.CheckoutIdempotencyKey`（必填 ＋ 唯一索引） | `src/Modules/Ordering/GreyGray.Modules.Ordering.Infra/OrderingDbContext.cs:219` |

**為什麼這個做法不會破壞 N:M**：店員刻意要建第二張出貨單時，是一次**新的
使用者動作**，前端的 `complete()` 已經換過 key，所以鍵不同 → 照樣建得出來。
只有「同一次動作的重試」鍵才會相同 → 回原本那一張。**語意完全對得上。**

### ★ 第二個 Leader 裁決：**繼續用舊多載，不要改成 BE-35 的兩階段多載**

`PROMPTS.md` 寫「`POST /v1/shipments` 還在用舊多載」，容易被讀成「所以要改成新的」。
**不要改。** 理由是推導過的，不是省事：

新多載刻意**不接手 `CompleteAsync` 自己的失敗**，冪等鍵會留在 `IN_FLIGHT`。
`IdempotencyStore` 的 retention 是 **24 小時**，而 `TryBeginAsync` 對
`IN_FLIGHT` 且未過期的鍵回 `InFlight`，BFF 於是回 **409**。
結果是店員在那 24 小時內**用同一把 key 重送一律 409**，唯一的出路是換一把新 key
——而換新 key 正好繞過這一波要加的模組冪等，**建出第二張出貨單**。

反過來，底層有了模組冪等之後，舊多載的「abandon 之後同一把 key 重試」
變成**最好的路徑**：重試會走進新的冪等分支、回原本那一張、回 201。

**所以這一波 `src/Platform/Http/BffHttp.cs` 一個位元組都不准動。**
（這也正是 `04-交接書.md` 說的「不需要動 `BffHttp`，也不動契約」。）

### 落地形狀

**① 契約**（`FulfillmentContracts.cs` 的 `IFulfillmentApplication.CreateAsync`）
加一個 `string idempotencyKey` 參數，放在 `method` 與 `cancellationToken` 之間。
**這是模組內部的 C# 契約，不是 HTTP 契約**——`docs/api/openapi.admin.yaml`
一個字都不改（`Idempotency-Key` header 本來就已經在那條端點上了）。

**② 聚合**（`ShipmentAggregate.cs`）
新增 `public string? CreationIdempotencyKey { get; private set; }`，
由 `Create(...)` 帶進來。
**用 `string?` 而不是 `string`，比照 `Cart` 不是比照 `Order`**——
`fulfillment.shipment` 已經有既有資料列，它們沒有鍵。

`Create` 要驗鍵：空白或長度大於 255 就回
`Result.Failure("platform.idempotency-key-required", "建立出貨單必須提供 1 到 255 字元的 Idempotency-Key。")`
（錯誤碼與 `CheckoutApplicationService` 用的同一個，不要自創新碼）。

**③ Repository**（`IShipmentRepository` 與 `FulfillmentRepository.cs`）
新增 `GetByCreationKeyAsync(TenantId tenantId, string idempotencyKey, CancellationToken)`，
**要 `Include(shipment => shipment.OrderLinks)`**（回應要帶 `orderIds`）。

**④ 應用服務**（`FulfillmentApplicationService.cs` 的 `CreateAsync`）
順序**必須**是：

```
① 驗 idempotencyKey（空白或超長 → platform.idempotency-key-required）
② GetByCreationKeyAsync 查既有出貨單
     找到 → 比對 (orderIds 集合, method)
              相同 → 直接回既有那一張的 ToContract()   ← 重播
              不同 → Result.Failure("fulfillment.idempotency-key-reused", …)
     沒找到 → 往下
③ 既有的「每張訂單都要是 ReadyToShip」守衛      ← 原封不動
④ ShipmentAggregate.Create → shipments.Add → SaveChangesAsync
```

**★ ② 一定要排在 ③ 前面，這是重點不是風格。** 出貨單建好之後訂單狀態可能已經
被下游（`ShipmentDispatched` 讓 Ordering 轉狀態）推走，此時若先跑 ③，
重播會被 `fulfillment.order-not-ready-to-ship` 擋掉，等於「重試永遠回不了成功」
——那正是 BE-34 在 #22 (A″) 找到的同一種死路，不要在這裡複製一個。

比對 `orderIds` 用**集合相等**（順序無關），不要用 `SequenceEqual`。

**⑤ EF 對映**（`FulfillmentDbContext.cs`）
`creation_idempotency_key`、`varchar(255)`，加過濾式唯一索引
`ux_shipment_tenant_creation_key`，**逐字對齊 migration**：

```csharp
entity.HasIndex(shipment => new { shipment.TenantId, shipment.CreationIdempotencyKey })
    .IsUnique()
    .HasFilter("creation_idempotency_key IS NOT NULL")
    .HasDatabaseName("ux_shipment_tenant_creation_key");
```

**⑥ Migration**（`db/migrations/0016_fulfillment_shipment_idempotency.sql`，**新檔**）
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 加
`CREATE UNIQUE INDEX IF NOT EXISTS ... WHERE ...` 加 `COMMENT ON COLUMN`。
開頭 `SET ROLE greygray_owner`、結尾那段 owner 檢查的匿名區塊，
**照 `db/migrations/0015_ordering_partial_purchase_shortfall.sql` 抄**
（`schemaname IN (...)` 那一串要改成 `'fulfillment', 'platform'`）。
可重跑是硬要求。

**⑦ 端點**（`M1bFulfillmentEndpoints.cs` 的 `POST /v1/shipments`）
比照 `CompleteCheckoutAsync` 的做法，**自己讀 header** 再傳進去：

```csharp
if (!context.Request.Headers.TryGetValue("Idempotency-Key", out var key))
{
    return BffHttp.Problem(
        new Error("request.idempotency-key-required", "缺少 Idempotency-Key header。"),
        StatusCodes.Status400BadRequest);
}
```

錯誤碼與訊息**逐字**照 `BffHttp` 既有的那一份（在 `BffHttp.cs:384` 附近），
不要寫成別的字串——前端在比對它。
然後把 `key.ToString().Trim()` 傳給 `CreateAsync`。

`api.MapPost("/shipments", ...)` 的 lambda 因為多了一個 early return，
會從運算式主體變成區塊主體，**這是預期中的形狀改變**。
`StaffRoleFilter` 那一行不要動。
