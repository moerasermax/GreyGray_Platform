## 0. 這一波要解的問題：storefront Host 完全沒有 CORS

FE-12（第九波）發現：`src/Hosts/GreyGray.Api.Storefront/Program.cs` 沒有任何
`AddCors`／`UseCors`（Leader 這一輪重新查證：`grep -n "Cors" Program.cs` 確實
是空的）。前台開發環境是 `:5002`（`frontend/apps/storefront/package.json` 的
`dev`／`start` script）對 storefront BFF `:5000` 是跨源，前端的
`browserApi()` 直接呼叫 BFF、不經 Next route handler 代理。**購物車、結帳、
登入、註冊這些 client 端呼叫在真瀏覽器裡會全部被瀏覽器的 CORS 檢查擋下**——
curl 測不出這個問題（curl 不執行瀏覽器的 CORS 規則），只有真瀏覽器才會踩到。

**admin Host 早就有同一類問題，已經解決過**（ADR-021，M1a-6 串接補漏）：
`src/Hosts/GreyGray.Api.Admin/Program.cs:31-53` 讀 `Cors:AllowedOrigins`
設定，Development 沒有值時預設 `http://localhost:5003`／`http://127.0.0.1:5003`，
Production 沒有預設、必須明確設定，不用 `AllowAnyOrigin`，允許 credentials。
**這一波是把同一個已經拍板、已經在跑的模式套用到 storefront，不是重新設計
一套 CORS 策略**——不需要新的 ADR 討論，`Cors:AllowedOrigins` 這個設定鍵、
「白名單、不用萬用字元、允許 credentials」這些決定都已經是既定政策。

## 5. 工作包

### BE-28　storefront Host 補上 CORS（比照 admin Host 的 ADR-021 模式）　🔴

**相依**：無　**獨佔**：見 §3

#### 必做 1　`src/Hosts/GreyGray.Api.Storefront/Program.cs` 複製 admin Host 的 CORS 模式，埠號換成 5002

參考 `src/Hosts/GreyGray.Api.Admin/Program.cs:31-53`／`:88-90` 的完整寫法，
在 `src/Hosts/GreyGray.Api.Storefront/Program.cs` 對應位置加上同樣形狀的
程式碼：讀 `Cors:AllowedOrigins`、Development 沒有值時預設
`http://localhost:5002`／`http://127.0.0.1:5002`、`AddCors` 一個具名 policy
（`AllowAnyHeader`／`AllowAnyMethod`／`AllowCredentials`）、`app.UseCors(...)`
放在 `MapM1aStorefrontEndpoints()` 之前。policy 名稱不要跟 admin 的
`"AdminFrontend"` 撞名（這是兩個獨立的 Host process，其實撞名也不會真的
出錯，但取一個對得上語意的名字，例如 `"StorefrontFrontend"`）。

#### 必做 2　驗證：真的送一次帶 `Origin` 的 preflight 請求

**這個問題本質上是瀏覽器層級的行為，curl 不會自動附加或檢查 CORS 相關
header，但可以手動組出等效的請求來驗證伺服器端的回應是否正確**：

```
curl -i -X OPTIONS http://127.0.0.1:5000/v1/cart \
  -H "Origin: http://127.0.0.1:5002" \
  -H "Access-Control-Request-Method: GET"
```

**改之前**：這個 preflight 請求應該回 `405 Method Not Allowed`（沒有
`OPTIONS` handler，也沒有 CORS middleware 幫忙處理 preflight）——這是 FE-12
第九波實測過的既有症狀，你可以先跑一次確認症狀還在，再動手。

**改之後**：應該回 `204 No Content`（或 `200`，視 ASP.NET Core CORS
middleware 版本行為），並且回應 header 裡有
`Access-Control-Allow-Origin: http://127.0.0.1:5002`、
`Access-Control-Allow-Credentials: true`。**同時要驗證白名單真的生效**：
換一個不在白名單裡的 `Origin`（例如 `http://evil.invalid`）送同樣的請求，
確認**不會**回帶 `Access-Control-Allow-Origin` 對到那個來源（不是允許
任何來源）。

查一下 repo 裡有沒有既有的 CORS 相關測試可以參考格式（`grep -rn "AddCors"
tests/`），如果找不到合適的既有模式、且你判斷值得新增一條自動化測試
（例如用 `WebApplicationFactory` 起一個 test host 送 preflight 請求），
可以加；如果評估後認為手動 curl 驗證已經足夠清楚、新增測試的建置成本
不成比例，也可以只做手動驗證、在自驗報告寫清楚你的判斷理由——這個決定
留給你，不是必做項目。

**自驗（寫進 `.dispatch/reports/BE-28.md`）**

1. `dotnet build .\GreyGray.slnx` 0 error 0 warning
2. `.\ops\test.ps1` 全綠，176 條（這一包不該讓既有測試數字變少；如果你
   新增了測試，數字應該增加，並在報告說明增加了幾條）。**前景跑，
   分批跑完，不准丟背景**
3. `git diff --name-only` —— 只有你擁有的路徑（見 §3）
4. **開發環境端對端驗證**：啟動 `D:\GreyGray` 的三個 Host（`ops\start-dev-hosts.ps1`），
   對 storefront BFF（`:5000`）送 §5 必做 2 的 preflight 請求，貼出白名單
   內／白名單外兩種 `Origin` 的實際回應 header
5. 確認 admin Host 的 CORS 設定沒有被你改動（`git diff` 不該碰到
   `src/Hosts/GreyGray.Api.Admin/Program.cs`）
