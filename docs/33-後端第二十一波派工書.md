## 0. 事實（Leader 已逐條查證，直接當前提）

### 契約怎麼寫的

`docs/05-API契約.md` 的冪等章節（§4）明文規定四件事裡的三件：

| 情況 | 契約規定的 HTTP 與 code |
|---|---|
| 沒帶 `Idempotency-Key` | `400`，`platform.idempotency-key-required` |
| `InFlight` | `409`，`platform.request-in-flight` |
| `KeyReusedWithDifferentPayload` | `422`，`platform.idempotency-key-reused` |

### 程式實際回什麼

| 位置 | 實際的 code | 對不對 |
|---|---|---|
| `src/Platform/Http/BffHttp.cs:384` | `request.idempotency-key-required` | ✗ 前綴錯 |
| `src/Platform/Http/BffHttp.cs:392` | `request.idempotency-key-too-long` | ✗ 前綴錯（契約沒列這一個，見下） |
| `src/Platform/Http/BffHttp.cs:411` | `request.idempotency-in-flight` | ✗ 前綴**與名字**都錯 |
| `src/Platform/Http/BffHttp.cs:414` | `request.idempotency-key-reused` | ✗ 前綴錯 |
| `src/Hosts/GreyGray.Api.Storefront/M1aEndpoints.cs:578` | `request.idempotency-key-required` | ✗ 同上（`CompleteCheckoutAsync` 自己抄了一份） |
| `src/Hosts/GreyGray.Api.Admin/M1bFulfillmentEndpoints.cs:79` | `request.idempotency-key-required` | ✗ 同上（BE-36 照既有形狀抄的，見 §3） |

**而且同一個條件在這個 repo 裡有兩種碼**：
`src/Modules/Checkout/GreyGray.Modules.Checkout.Core/CheckoutApplicationService.cs:197`
用的是**契約正確的** `platform.idempotency-key-required`，BffHttp 用的是 `request.` 那個。

### 真正的後果（不是潔癖問題）

前端 `packages/api-client/src/problem.ts`（**在前端 worktree**）的
`isInFlight` 判斷的是 `problem.code === 'platform.request-in-flight'`，
`http.ts` 拿它決定「409 要不要用同一把 key 自動重試」，預設重試 2 次。

**後端從來沒有回過那個字串，所以那段自動重試是死的。**
使用者遇到「同一個操作還在處理中」時，看到的是一個生的 409 錯誤，
而不是被透明地重試掉。

### 為什麼是改程式、不是改契約

- `docs/05-API契約.md` 是**已凍結的契約**（ADR·B6），契約凍結後只允許
  正規化格式、不得改語意。改契約去遷就實作是反過來的。
- **改這些字串不會動到 `docs/api/*.yaml`**——那兩份 OpenAPI 只引用
  `#/components/parameters/IdempotencyKey`（header 參數），**完全沒有列舉錯誤碼**。
  所以前端 codegen 的輸出一個位元組都不會變，`check-openapi.ps1` 也不受影響。
- 全 repo（含 `tests/`）**沒有任何測試斷言那四個 `request.` 字串**（Leader 已 grep 確認），
  所以不存在「測試在幫錯的行為背書」的問題。

## 1. 修法：**四個字串，加一份測試**

### 改哪些字串

| 現在 | 改成 |
|---|---|
| `request.idempotency-key-required` | `platform.idempotency-key-required` |
| `request.idempotency-in-flight` | `platform.request-in-flight` |
| `request.idempotency-key-reused` | `platform.idempotency-key-reused` |
| `request.idempotency-key-too-long` | `platform.idempotency-key-too-long` |

**三個檔案共六處**（位置見 §0 的表）。訊息文字不要改，只改 code。

### `too-long` 那一個是 Leader 裁決，講清楚

契約表裡**沒有** `key 太長` 這一列——契約只說 key 是「1..255 chars」。
程式多做了一個更精確的 400 子類，那是好事，不要為了對齊表格把它併掉。

**裁決：保留這個碼，但前綴跟著改成 `platform.`，並在 `docs/05-API契約.md`
補一行說明它是 400 的子類。** 這是**補文件記錄既有行為**，不是改契約語意——
線上格式、HTTP 狀態碼、既有三個碼全部沒動。

### 明確不要做的事

- **不要改 `docs/api/openapi.admin.yaml` 或 `openapi.storefront.yaml`。** 一個字都不要動。
- **不要改前端。** 前端本來就照契約寫，是後端對不上它。這一包不碰前端樹。
- **不要順手統一其他不相干的錯誤碼。** 只動冪等這四個。
- **不要動 `BffHttp` 的兩階段多載邏輯**（BE-35 蓋的）與
  `FulfillmentApplicationService` 的模組層冪等（BE-36 蓋的）。這一包只換字串。
- **★ 不要動 `BffHttp.StatusFor`。** 你會注意到一件事：模組層
  （`CheckoutApplicationService`、`FulfillmentApplicationService`）也會回
  `platform.idempotency-key-required`，而那條路徑走的是 `BffHttp.Problem(error)`
  **沒有帶明確狀態碼**，`StatusFor` 比對不到任何關鍵字 → 回 **422**，跟契約說的 400 不一樣。
  **這是 Leader 已經查過、刻意不動的**：`BeginAsync` 在 `work` 執行**之前**就把
  缺鍵／空白鍵擋成 400，所以模組層那個失敗**經由 HTTP 走不到**。
  在 `StatusFor` 加分支會影響到所有走 `Problem(error)` 的呼叫點，
  風險遠大於一條走不到的路徑。**發現了就寫進報告，不要動手。**

#### 必做 3　迴歸測試（`tests/GreyGray.Platform.Tests/`）

四個情況各一條，斷言 **code 字串逐字**與 HTTP 狀態碼：

| 情況 | 期望 |
|---|---|
| 沒帶 header | `400` ＋ `platform.idempotency-key-required` |
| key 超過 255 字元 | `400` ＋ `platform.idempotency-key-too-long` |
| 同一把 key 仍在處理中 | `409` ＋ `platform.request-in-flight` |
| 同一把 key 換了 payload | `422` ＋ `platform.idempotency-key-reused` |

**這四條測試存在的理由就是「下次有人改字串會立刻紅」**——
這個缺陷之所以活到現在，正是因為沒有任何測試斷言過這些字串。
測試裡要寫一行註解指回 `docs/05-API契約.md`，說明權威在那裡。

#### 必做 4　順帶根治「migration 上界寫死」這一類漂移

BE-36 的自驗報告「我發現但沒做的事 ①」找到第三個同型的過期字串
（前兩個是 `ops/` 那兩支，BE-36 已修）：

`tests/GreyGray.M1a.Migrations.Tests/M1aCoreMigrationTests.cs:296`

```
[Fact(DisplayName = "0001→0014 之後單獨重放 0003，ledger.account 的 seed 不會炸")]
```

底下是 `await ExecuteMigrationChainAsync(connectionString, migrations, 14, cancellationToken);`
——**上界寫死 14**。這條測試的意圖是「套完**全套** migration 之後再重放 0003」，
所以每加一份 migration，這個 14 就多過期一次。
（`0015`／`0016` 都沒動 `ledger.account`，所以它現在**不會紅**，
只是測到的東西比它宣稱的少——這比紅還危險，因為沒有人會發現。）

**Leader 裁決：把上界改成從 `db/migrations/*.sql` 的實際檔案數推導，
不要再寫死一個數字**，DisplayName 同步改成「全套 migration 之後」這種
不帶編號的說法。這一類「寫死上界」在這個 repo 已經出現三次
（`install-dev-environment.ps1`、`verify-environment.ps1`、這一支），
前兩支因為要「刻意列死才看得出基準線變了」而保留清單，
**但測試不一樣：測試要的是「跟上現況」，寫死只會讓它悄悄少測。**

`ExecuteMigrationChainAsync` 怎麼枚舉檔案你自己讀，
如果推導會讓這條測試的語意改變（例如它其實刻意只要跑到 14），
**停下來寫進報告問，不要自己改語意。**
