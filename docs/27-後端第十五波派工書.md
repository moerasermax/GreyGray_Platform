## 0. 這一波要做的事：ADR-026 支援部分買到

契約已拍板（`docs/00-decisions.md` ADR-026）：**買到的數量照常出貨，短缺的
數量退款。** 相依的 ADR-024（綠界退款 API）已由 BE-17 完成。

現在 `PurchaseItemAggregate.MarkPurchased`（`quantityPurchased != QuantityRequested`
一律回 `procurement.partial-purchase-not-supported`）與
`Order.RecordItemPurchased`（`quantityPurchased != line.Quantity` 一律回
`ordering.partial-purchase-not-supported`）都刻意拒絕部分買到——那是 M1b-1
當時正確的 fail-closed，現在退款去向已經拍板，要放寬。

### 0.1　設計方向（Leader 已查過現有程式碼，照這個方向做，不要重新設計）

**核心洞察：Fulfillment／Shipment 完全不記錄數量**（`grep -rn "Quantity"
src/Modules/Fulfillment/` 是 0 筆）——一張出貨單只記錄「哪些 OrderLine
在這一趟」，不記錄「幾件」。所以放寬部分買到**不會影響出貨模組**，
範圍只在 Procurement 與 Ordering 兩邊，比 ADR-026 原本估計的「一整包，
影響 Procurement／Ordering／Ledger 三個模組」還再窄一點——**Ledger 這一側
不用新增任何程式碼**，短缺的退款直接重用 BE-17／BE-18 已經蓋好、測完的
`RefundRequested` 事件與下游 Payment／Ledger 消費者，不是新的退款機制。

**沿用 M1b-2 已經拍板的「決策延後」模式**（`M1bCompensationEndpoints.cs`
開頭的註解）：標記缺貨當下不承載、不預設退款去向，退款去向由客人事後選、
另外呼叫一個獨立端點。部分買到比照辦理——**標記「買到 3／5」的當下不問
退款去向，短缺的 2 件掛著，之後另一個端點問客人要退到哪裡才真的退款**。

**Procurement 這一側幾乎不用改資料形狀**：`PurchaseItemAggregate` 已經有
`QuantityRequested`／`QuantityPurchased` 兩個欄位，短缺數量本來就是兩者的
差，不需要新欄位。只需要放寬 `MarkPurchased` 的驗證。

**Ordering 這一側需要一個新欄位**：`OrderLine` 現在只有 `Quantity`
（客人訂購的數量），標記買到之後如果是部分買到，短缺的數量要暫存起來
（因為退款去向要之後才知道），所以新增 `QuantityShortfall`（int，預設 0）。
**`RefundedAmountMinor`／`RefundedCurrency` 這兩個既有欄位可以直接重用**
（現在只有 `MarkUnavailable` 會設），退款真的完成時把短缺退款金額寫進去，
不需要再新增一個「已解決」旗標——`RefundedAmountMinor is not null` 本身
就是「短缺已經有退款決定」的判準。

**退款完成時才把 `Quantity` 減下去**：`Quantity` 從「客人原本訂購」語意
改成「現在這條 line 實際要出貨／已出貨的數量」——退款決定做出來之前，
`Quantity` 維持原值（尚未出貨，不影響任何下游），退款一旦完成，
`Quantity -= QuantityShortfall`（連帶 `LineTotal`／`GoodsTotalAmountMinor`
自動跟著變小，不用另外算）。**這個決定刻意不在 `RecordItemPurchased` 當下
就調整 `Quantity`**——出貨模組不看數量，調整早一點或晚一點對出貨沒有影響，
但退款去向還沒決定前就調整訂單金額，會讓客人看到的訂單總額在退款真的發生
之前就先變了，時序上說不通。

### 0.2　新增的東西，逐一列清楚

1. **Migration `0015_ordering_partial_purchase_shortfall.sql`**：
   `ordering.order_line` 加一欄 `quantity_shortfall integer NOT NULL DEFAULT 0`。
   照既有 migration 慣例：`SET ROLE`、owner 斷言、可重跑（`ADD COLUMN IF NOT EXISTS`
   或等效寫法）。
2. **`OrderLine`（`Order.cs` 裡的 internal class）**：
   - 新增 `public int QuantityShortfall { get; private set; }`
   - `MarkPurchased()` 改簽章成 `MarkPurchased(int quantityPurchased)`，
     內容變成 `Status = OrderLineStatus.Purchased; QuantityShortfall = Quantity - quantityPurchased;`
   - 新增 `RecordShortfallRefund(Money refundAmount)`：驗證
     `refundAmount == UnitPrice.MultiplyByQuantity(QuantityShortfall)`
     （驗證方式比照既有 `MarkUnavailable` 對 `LineTotal` 的驗證），
     設定 `RefundedAmountMinor`／`RefundedCurrency`，`Quantity -= QuantityShortfall`。
   - `ToView()` 要把 `QuantityShortfall` 帶進 `OrderLineView`（見下方契約異動）。
3. **`Order.RecordItemPurchased`**：拿掉 `quantityPurchased != line.Quantity`
   那個硬擋（`ordering.partial-purchase-not-supported`），改呼叫
   `line.MarkPurchased(quantityPurchased)`（原本呼叫 `line.MarkPurchased()`
   沒有參數，要跟著改）。**冪等檢查要跟著更新**：現在的冪等只看
   `line.Status == Purchased` 就回 `AlreadyRecorded`，沒有比對這次的
   `quantityPurchased` 是否跟上次記錄的一致——**這是既有的小缺口，
   趁這次一起補**：如果 `line.Status == Purchased` 但
   `line.Quantity - line.QuantityShortfall != quantityPurchased`
   （已經解決過的情況另外處理，見下一點），回一個新的業務失敗
   （例如 `ordering.purchase-already-recorded`，訊息比照 Procurement
   那一側同名情境的寫法），不要靜默接受不一致的重送。
4. **新的 domain 方法 `Order.RefundLineShortfallByAdmin(OrderLineId orderLineId)`**：
   回傳 `Result<Money>`（比照既有 `CancelLineByAdmin` 的形狀）。驗證：
   - line 存在、`line.Status == OrderLineStatus.Purchased`
   - `line.QuantityShortfall > 0`（沒有短缺就沒什麼好退）
   - `line.RefundedAmountMinor is null`（還沒退過；已經退過要回
     `AlreadyRecorded` 語意，冪等，不要重複退，比照這個檔案其他地方
     "AlreadyRecorded" 的寫法）
   計算 `refundAmount = line.UnitPrice.MultiplyByQuantity(line.QuantityShortfall)`，
   呼叫 `line.RecordShortfallRefund(refundAmount)`，`GoodsTotalAmountMinor`／
   `GrandTotalAmountMinor` 各減掉 `refundAmount.AmountMinor`（比照
   `CancelLineByAdmin` 對這兩個欄位的調整方式），回傳 `refundAmount`。
5. **`IOrderingApplication` 新增介面方法 `RefundLineShortfallAsync`**（比照
   `CancelLineAsync` 的簽章：`orderId, lineId, reason, refundTo, cancellationToken`，
   回傳 `Result<OrderView>`），`OrderingApplicationService` 實作：驗證 reason、
   `GuardStoredValueRefund(refundTo)`（**這個既有守衛直接重用，不要重寫**——
   代表 `StoredValue` 一樣要擋到 M3），載入訂單、呼叫
   `order.RefundLineShortfallByAdmin(lineId)`，成功的話發布
   `RefundRequested` 事件（**重用既有事件型別，不要新增事件**，欄位比照
   `CancelLineAsync` 裡發布 `RefundRequested` 的寫法：`orderId`、`lineId`、
   退款金額、`refundTo`、`reason`），`SaveChanges`。
6. **新的 Admin HTTP 端點**：**開一個新檔案**
   `src/Hosts/GreyGray.Api.Admin/M1bShortfallRefundEndpoints.cs`
   （**不要改 `M1aEndpoints.cs`**——那個檔案已經很大，而且這個端點的形狀
   跟 `M1bCompensationEndpoints.cs` 更像：獨立小檔、獨立 `MapXxxEndpoints`
   擴充方法，在 `Program.cs` 掛一行），比照 `M1bCompensationEndpoints.cs`
   的寫法：
   - `POST /v1/orders/{orderId}/lines/{lineId}/refund-shortfall`
   - request body：`{ reason: string, refundTo: RefundDestination }`
     （跟現有 cancel 端點的 `CancelOrderInput` 同形狀，可以直接重用
     那個型別，不用新建一個一模一樣的 record）
   - `StaffRoleFilter(StaffRole.Operator)`（跟 cancel 端點同權限）
   - 呼叫 `ordering.RefundLineShortfallAsync(...)`，回應組裝比照
     `CancelOrderLineAsync` 呼叫 `ToAdminOrderAsync` 那一段
   - 用 `BffHttp.ExecuteIdempotentAsync`，idempotency scope 比照既有寫法：
     `orders:{orderId}:lines:{lineId}:refund-shortfall`
7. **`Program.cs` 掛新端點**：`src/Hosts/GreyGray.Api.Admin/Program.cs`
   加一行 `app.MapM1bShortfallRefundEndpoints();`（比照現有
   `MapM1bCompensationEndpoints()` 那一行的位置與寫法）。
8. **契約異動**（`docs/api/openapi.admin.yaml`，新增不改既有語意）：
   - `AdminOrderLine` schema 加一個欄位
     `quantityShortfall: { type: integer, description: 短缺、等待退款決定的數量；0 表示沒有短缺或已經處理完畢。 }`
     （比照 `refundedAmount` 那個欄位旁邊插入，不放進 `required` 清單）
   - 新增 operation：`/v1/orders/{orderId}/lines/{lineId}/refund-shortfall`，
     完全比照 `/v1/orders/{orderId}/lines/{lineId}/cancel`
     （`docs/api/openapi.admin.yaml:569-597`）的形狀抄一份，`summary`／
     `description` 換成描述短缺退款這件事，`x-required-role: Operator`，
     一樣要 `IdempotencyKey` 參數、一樣的 `reason`／`refundTo` request body、
     一樣回 `AdminOrder`、一樣有 `422`。
   - `src/Hosts/GreyGray.Api.Admin/OpenApiComponents.cs` 的 `IdempotentEndpoints`
     集合加一行 `(HttpMethod.Post, "/v1/orders/{orderId}/lines/{lineId}/refund-shortfall")`。
   - `AdminOrderLineResponse`（`M1aEndpoints.cs` 裡的 internal record，
     這個檔案這一波**只准新增這個 DTO 要多帶的一個欄位與對應的映射那一行，
     不准動其他任何地方**——BE-30 剛動過這個檔案，你要先看過 BE-30 提交後
