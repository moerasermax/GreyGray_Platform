## 0. 缺陷（已確認）

### 0.1 trigger 在「上層查不到」時提早放行，連帶跳過「自己已有子分類」檢查

`db/migrations/0023_category_parent.sql:55`～57 的 `IF NOT FOUND THEN RETURN NEW; END IF;` 寫在第 59-64 行兩項檢查**之前**。
BEFORE ROW trigger 只看得到同一語句裡先處理過的列，而自我外鍵的檢查延到語句結束才做，所以**單一語句依「孫、子、根」的順序寫入三列，可以建出三層**。
驗證代理已在 dev PostgreSQL 17.11 用暫存表＋ROLLBACK 實測：孫→子→根的列序 `INSERT 0 3` 成功、查得到三層；對照組（根→子→孫）被 `category_two_level` 擋下。

後果：前台清單「對父分類封閉」的保證會破（只有孫有商品時，子會列出、根不會）；中間那層在後台改不動（永遠 `category-depth-exceeded`）。ADR-041 明寫資料庫守衛要擋「直接寫資料庫的種資料」，所以在範圍內。

**修法**：只要 `NEW.parent_id` 不是 null，**「有任何同租戶分類的 `parent_id = NEW.id`」這項檢查一律要做**，不受「上層查不到」影響；「上層的上層不是 null」這項才依賴查得到上層。
推論（請在報告確認或反駁）：三層鏈 G→C→R 只要有一條邊是在這個語句寫入的，不是 C 的子分類檢查擋下，就是 G 查 C 的上層時擋下，所以這樣改就完整了。

### 0.2 「競態被資料庫擋下也回 422」這條路徑沒有任何測試走到

- ADR-041 與 `docs/59` §1.2 第 5 點要求：trigger 丟 23514 時，Infra 把 `PostgresException` 包成 `CatalogPersistenceConflictException`，服務層 catch 後回 `Result`（`src/Modules/Catalog/GreyGray.Modules.Catalog.Core/CatalogServices.cs:231`～236、277～282）。
- 現有測試：S13（`tests/GreyGray.M1a.IdentityCatalog.Tests/CategoryHierarchyTests.cs`）只測純函式 `MapCategoryHierarchyError`；S14（`tests/GreyGray.M1a.IdentityCatalog.Tests/CategoryHierarchyMigrationServiceTests.cs:29`）證明的是**應用層先擋**。**EF 丟 `DbUpdateException` → `when` 篩選 → 服務層 catch → `Result` 這整條，沒有一條測試真的走過**；EF／Npgsql 升版讓 `InnerException` 對不上時，客人會拿到 500，而現有測試全綠。
