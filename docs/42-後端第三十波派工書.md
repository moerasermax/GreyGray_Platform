## 0. 事實（Leader 查證過，逐行）

### 0.1 正式機上發生了什麼（2026-09-03 13:51-13:59）

使用者在正式站後台走出貨：建立出貨單（13:51:59）→ 交運（13:52:49，`fulfillment.shipment.status=2 Dispatched`）→ 標記已送達（13:53:46，`status=5 Delivered`，`delivered_at` 有值），`fulfillment.shipment_order` 正確掛到訂單 `GG2609031CADB04`。後台這一段沒有問題。

但訂單 `ordering.orders.status` 仍是 **5（ReadyToShip）**、`appraisal_due_at` 是 null，前台「我的訂單」因此顯示「準備出貨」。原因在 `platform.outbox_message`：

```
fulfillment.ShipmentDispatched.v1  processed_at 13:52:50（沒有 handler，正常）
fulfillment.ShipmentDelivered.v1   processed_at NULL，attempts 8，
  last_error: System.ArgumentNullException: Value cannot be null. (Parameter 'resolvedFulfillmentQuery')
```

Worker log 每次都是同一句：`Outbox 訊息 …（fulfillment.ShipmentDelivered.v1）第 N 次派送失敗`。`OutboxDispatcher.cs:27` `MaxDeliveryAttempts = 10`、`:194-199` 退避 2^n 秒（上限 1 小時）——第 10 次就進死信。**Leader 在 13:59:58 先把正式機的 `GreyGray-Worker` 停掉（並停用 watchdog 排程），訊息停在 attempts=8、沒進死信**；這一包部署上去、Worker 一起來就會接著處理它。你不用管正式機。

### 0.4 一個不用資料庫就能重現炸點的方法

`RecordShipmentDeliveredAsync(orderIds, ct)` 第 551-558 行的三個 null 檢查都在碰資料庫**之前**；傳 **空的 `orderIds`** 進去，第 561 行的 foreach 一次都不跑、`scheduled` 是 false、不 `SaveChanges`，直接回 `Result.Success()`。所以：

## 5. 可能寫錯的地方（撞到就停下來問，不要自己換做法）

- `InternalsVisibleTo` 用 csproj 的 `<InternalsVisibleTo Include="…"/>` 項目（SDK 會生成 attribute），不要另外手寫組件屬性的 .cs 檔。
- 必做 B-1 收集 handler 型別要在 `Build()` **之前**（`builder.Services` 是 `IServiceCollection`，建完就不該再碰）；解析要在 **scope** 裡（handler 是 scoped）。
- 必做 C 的 configuration：`AddFulfillmentModule` 與其他模組都是延後讀連線字串，但 Payment 模組在**註冊時**就讀綠界設定（`ModuleRegistration.cs:108-135`），所以 in-memory 設定要先給；`validateScopes: true` 下 singleton 不能吃 scoped，若有模組因此紅燈，那是既有問題——停下來寫進報告，不要把 `validateScopes` 拿掉。
- 負向對照那條**不要**呼叫 `AddWorkerModules` 再移除 descriptor（DI 註冊互相牽連，移不乾淨）；直接列 11 個 `Add*Module` 呼叫一遍就好，並在註解說明「這串要跟 `WorkerModules` 少一個 Fulfillment 一致」。
- `RecordShipmentDeliveredAsync` 傳空清單就不碰資料庫（§0.4），但 `OrderingApplicationService` 的建構會 `GetRequiredService<OrderingDbContext>()`——EF 建 DbContext 不會連線，假連線字串沒關係；真的有東西在建構時連線（例外訊息會是 Npgsql 的），停下來問。
