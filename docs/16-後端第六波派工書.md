**必做**

2. **診斷 `sc start` 錯誤 5。** 已知的事實，不要重查：

4. **重開機驗證**：兩個服務都是 Automatic，重開機後要自動起來。

### BE-14　M1b-4　出貨、交運與簽收

**相依**：無（契約已凍結且完整）　**獨佔**：`src/Modules/Fulfillment/**` · `db/migrations/0012_*.sql`

**契約已經在那裡了**，四個端點都凍結好：

| 端點 | 做什麼 |
|---|---|
| `GET /v1/shipments` | 出貨單列表，可依 `ShipmentStatus` 過濾 |
| `POST /v1/shipments` | 建立出貨單，`orderIds`（陣列）＋ `method` |
| `POST /v1/shipments/{id}/dispatch` | 交運，`trackingNumber` ＋ `carrierCost` |
| `POST /v1/shipments/{id}/deliver` | 簽收 |

**★ 契約明文寫的、不要做錯的兩件事**

1. **Order 與 Shipment 是 N:M。**
   一張訂單可拆多個包裹；一個包裹也可含同一客人的多張訂單（合併出貨省運費）。
   契約的 description 明寫「**這是日常，不是邊緣案例**」。
   不要做成 1:N，之後改不動。
2. **`carrierCost` 是你付給物流商的成本，不是向客人收的運費。**
   後者在訂單的 `shippingFee` 裡（ADR-010：超商 60／宅配 120 一口價）。
   **兩個是獨立的數字**，月結時運費是賺是賠自己會浮出來。
   把它們混在一起就永遠算不出物流的真實損益。

**必做**

1. Fulfillment 模組：Contracts／Core／Infra 三層，照 BE-5 的組合根樣板。
2. `0012_m1b_fulfillment.sql`：`fulfillment` schema、shipment 與 shipment_order 兩張表
   （N:M 的連接表），`SET ROLE greygray_owner` ＋ `RESET ROLE` ＋ owner 斷言。
   子表用 `tenant_id + parent_id` 複合 FK。
3. 簽收後把 Order 轉 `Completed`——**透過 Ordering 的 input port，不要跨 schema 改狀態**。
4. `carrierCost` 進 Ledger 的分錄（物流成本），照 `docs/02` 的分錄表。
5. 業務寫入與 outbox 必須是**同一個 DbContext 的同一次 `SaveChanges`**，
   而且要有「強制拒絕 outbox insert 時業務欄位也回滾」的故障注入測試——
   BE-12 就是這樣驗的，照抄那個做法。

**自驗（逐條貼出實際指令與實際輸出）**

1. `dotnet build .\GreyGray.slnx` 0 error 0 warning
2. `.\ops\test.ps1` 全綠，貼出新增了幾條
3. `git diff --name-only` —— 只有你擁有的路徑（＋預先授權的兩個例外）
4. `grep -rn "decimal \|double " src/Modules/Fulfillment/` 應為 0 筆
5. `grep -rn "DateTimeOffset.UtcNow" src/Modules/Fulfillment/` 應為 0 筆
6. N:M 的實測：一張訂單拆兩個包裹、一個包裹含兩張訂單，各跑一次
7. `0012_` 連續執行兩次（可重跑性）

而且進度表寫著「**從沒有人完整走過一遍**」。手動走一次會有人走，
但**不會有人每次改完都走一次**——所以要有一支可重跑的腳本。

**必做**：一支腳本走完整條路徑，每一步斷言狀態與分錄：

```
開團 → 下單 → 付款（綠界測試憑證）→ 截團 → 採購清單
→ 買到回報 → 帶回入庫 → 建出貨單 → 交運 → 簽收 → 訂單 Completed
→ 對帳：借貸相等、每團毛利算得出來
```

**做法要點**

- 用 Testcontainers 起真的 PostgreSQL，**不要用 InMemory**——
  帳務的不變式是靠 CHECK constraint 與 `journal_line_balanced` trigger 守的，
  InMemory 不執行它們，用它測等於把要驗的東西關掉再說「通過」。
- 每一步都要**斷言**，不是「跑完沒噴錯」。特別是分錄：借貸相等要用查詢驗。
- 腳本要能重跑（測試資料自己清乾淨），否則第二次跑就會撞既有資料。

**自驗**：完整跑一次的輸出，每一步的斷言結果都要看得到。

## 6. 遇到契約缺口或平台缺口時怎麼辦

**這個專案已經發生過六次，六次的處理都是對的。** 照著做，不要自己補預設值。

| 缺口 | 錯的做法 | 對的做法 |
|---|---|---|
| request 少一個必要欄位 | 猜一個預設值 | 回明確的業務失敗（例如 422），endpoint 不映射 |
| 凍結契約沒有你需要的路由 | 自己加一個 HTTP route | 走模組的 input port，Host 不新增未凍結路由 |
| 事件的欄位不夠建立聚合 | 用 `0` 或空值先建起來 | 註冊冪等 subscriber 但 no-op，等帶完整資料的入口 |
| 平台上沒有指定的元件 | 偷偷換一個相容的 | 停下來回報，讓整合者決定並留下 ADR |
| 兩份已採納的文件互相矛盾 | 挑一個看起來合理的 | 停下來，這需要人拍板 |
| 上游沒有人發你要消費的事件 | 在別的模組裡代發 | 停下來回報——這正是 BE-9 做對的事 |

**共同的理由**：填掉的那一刻，缺口就從「還沒決定」變成「已經決定了，只是沒人知道」。
代價不對稱——顯性化的成本是一次回報，填掉的成本是**幾個月後在錢上發現**。

## 7. 自驗與總驗收

### 每一包交付時，子代理自己要跑並貼出輸出

1. `dotnet build .\GreyGray.slnx` —— 0 error 0 warning（不寫 C# 的包免）
2. `.\ops\test.ps1` —— 全綠，說明新增幾條（不寫 C# 的包免）
3. `git diff --name-only` —— 逐一對照 §3 的所有權表
4. 該包 §5 各自列的自驗項目
5. **你發現但沒做的事**：任何「我覺得這裡怪怪的但不在我範圍」都要寫出來

### 交付完就停

**你不可以自己宣告通過。** 貼出實際指令與實際輸出，不是「已完成」四個字。
然後停下來等整合驗收。不要接著做下一包。

### 總驗收（由整合者做）

1. 越界檢查：`git diff --name-only` 對照所有權表，**區分同波越界與跨波接線**
2. 重跑 build 與測試，**自己跑，不採信交付方的自述**
3. 鐵則掃描：`decimal`／`double`／`DateTimeOffset.UtcNow`／跨 schema JOIN
4. migration：`SET ROLE` ＋ owner 斷言 ＋ 可重跑 ＋ **一號一檔**
5. 契約：`ops/check-openapi.ps1`（里程碑模式只驗 operation coverage，
   **不要把它報告成 schema 完全一致**）
6. 交付方**沒有提到**的問題——BE-12 的 migration 撞號就是複驗才看到的
