# FE-50 後台角色判斷對齊後端規則

## 證據與範圍
Leader 2026-09-24 以 Playwright＋本機 Chrome，用 dev 的營運／會計種子帳號與 AI 唯讀帳號逐頁實測（只讀、不送出）：

| 角色 | 前端顯示了、但後端會拒絕（403）的東西 |
|---|---|
| 營運（Operator） | 側邊欄「帳務」；儀表板帳務兩區；帳務頁（`/v1/ledger/*` 403） |
| 會計（Accountant） | 側邊欄「出貨」「現場採購」；出貨頁（`/v1/shipments` 403）；「新增商品」「新增開團」「提前截團」「新增開團商品」等寫入按鈕 |
| 唯讀、會計 | **訂單列表**為「出貨進度」欄呼叫 `/v1/shipments` → 403 |
| 唯讀、會計 | 訂單詳情顯示「取消整張訂單」「取消此品項」（後端要求 Operator） |

根因：`frontend/apps/admin/app/login/_lib/session.ts` 的 `hasRequiredRole` 用等級大小比較（`ROLE_RANK`：ReadOnly 0、Operator 1、Accountant 1、Owner 2），把營運與會計當同級互通；但後端 `IStaffRolePolicy.Allows`（後端樹 Identity 模組 Core 專案的 IdentityServices.cs）是：
`actual == Owner || actual == required || required == ReadOnly`——營運與會計**互不相通**。凍結契約也寫明「權限判斷不要用 enum 大小比較」。所有頁面都呼叫同一支 `hasRequiredRole`，所以修它一處，側邊欄、開團／分類頁的寫入按鈕、FE-49 的儀表板與訂單詳情判斷會一起對齊。
只修前端顯示與請求時機；後端權限不動（它是最後防線）。

## 要求
1. `hasRequiredRole(current, required)` 改為與後端 `Allows` 完全相同的三條規則；拿掉等級比較（`ROLE_RANK` 若無其他用途就刪除）。函式簽章不變，所有呼叫端不必改。
2. 在 `login/_lib/` 補測試：4×4 角色組合逐一列出期望值（16 條），其中至少明確斷言「Operator 不可進 Accountant」「Accountant 不可進 Operator」「任何角色可進 ReadOnly」「Owner 全通」。既有 `session.auth-mock.test.ts` 的期望不改。
3. 訂單列表：角色不符合 Operator 時不呼叫 `listShipments`，「出貨進度」欄顯示中性的「—」（不顯示錯誤、不顯示「載入失敗」）；Operator 以上行為不變。
4. 訂單詳情：「取消整張訂單」「取消此品項」只在符合 Operator 時渲染（後端 `/orders/{orderId}/cancel` 與 `/orders/{orderId}/lines/{lineId}/cancel` 都掛 `StaffRoleFilter(StaffRole.Operator)`，見後端樹 Admin Host 的 M1aEndpoints.cs 第 177–222 行，只讀參考）。同頁其他寫入按鈕（如退短缺款）若存在，查後端對應端點的 `StaffRoleFilter` 後同樣處理，並在報告列出對照表。
5. 不改 API、後端、側邊欄設定表（`requiredRole` 值不動）、主題、FE-48 的登入還原邏輯。
