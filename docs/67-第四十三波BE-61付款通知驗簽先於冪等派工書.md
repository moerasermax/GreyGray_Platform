## 1. 要做的事

### 1.1 `Payment.Contracts`：只驗不寫的入口

新增一個公開介面（名稱可調整，形狀照這個）：

```csharp
public sealed record EcpayCallbackEnvelope(string MerchantTradeNo, string TradeNo, int RtnCode);

public interface IEcpayCallbackVerifier
{
    /// 只驗 CheckMacValue、MerchantID 與必要欄位；不讀資料庫、不寫任何狀態、不發事件。
    Result<EcpayCallbackEnvelope> Verify(IReadOnlyDictionary<string, string> fields);
}
```

- 實作**重用** `PaymentApplicationService.cs` 第 154～169 行：抽成共用的私有方法，回傳一個**內部**型別（含解析好的 TradeAmt，給 Handle 後段做金額比對用），`Verify` 只回它的投影 `EcpayCallbackEnvelope`、`HandleEcpayCallbackAsync` 用完整的內部型別；錯誤碼維持 `payment.invalid-signature`／`payment.invalid-callback`。**金額不進公開契約**（鐵則：金額用 `Money`；envelope 不需要金額）。
- **不准**在 Host 或任何其他地方寫第二份 CheckMacValue 演算法；**不准**把 `IEcpayGateway` 公開；**不改** `IPaymentCommand` 既有兩個方法的簽章；**不改** `IIdempotencyStore`；**不改 `PaymentApplicationService` 的建構子**（§0.5 那幾個測試用位置參數 new 它）。
- DI：在 `Payment.Infra/ModuleRegistration.cs` 把 `IEcpayCallbackVerifier` 也指到同一個 scoped `PaymentApplicationService`（照第 74～77 行的寫法）。

### 1.2 端點：先驗簽、再去重

把第 1084～1139 行 lambda 的主體抽成 `M1aEndpoints` 裡一個 `internal static` 方法（例如 `HandleEcpayWebhookAsync(IReadOnlyDictionary<string,string> fields, IEcpayCallbackVerifier verifier, IPaymentCommand payments, IIdempotencyStore idempotency, CancellationToken ct)`）。
`MapPost` 仍是 lambda：讀表單成 dictionary 後呼叫它；lambda 的服務參數一律標 `[FromServices]`（漏註冊時才會是明確的例外，而不是被靜默推斷成 JSON body）。**不准把抽出來的 static 方法直接當 `MapPost` 的 handler**——它的 dictionary 參數會被推斷成 JSON body，綠界的 form POST 會得到 415。順序：

1. 讀表單 → `verifier.Verify(fields)`。**失敗直接回 `BffHttp.Problem(error)`（422），不呼叫 `IIdempotencyStore` 的任何方法。**
2. `scope = "webhook:ecpay:payment-result"`（具名常數）；`key = $"{MerchantTradeNo}:{TradeNo}:{RtnCode}"`（三者取自 `EcpayCallbackEnvelope`，照驗過的值、不另外 Trim）。
   **RtnCode 要進 key**：同一個交易編號先收到失敗通知、再收到成功通知（或 BE-66 之後先取號 `RtnCode=2` 再付款 `RtnCode=1`）時，各自一把鍵，不會互相擋。
3. hash **只算這三個已驗欄位**（例如 `MerchantTradeNo=…&TradeNo=…&RtnCode=…` 的 SHA-256），**不再算整份表單**：驗簽通過之後，綠界對同一事件的重送若多一個欄位或欄位值略有不同，用整份表單會變成「同鍵不同內容」而被永久 422。改成只算身分欄位後，同一把鍵的 hash 必然相同，`KeyReusedWithDifferentPayload` 對驗過簽的通知不會再發生（分支保留，不要刪）。
4. `TryBeginAsync` 之後的 AlreadyCompleted／InFlight／KeyReused／Handle／Complete／Abandon／catch 形狀**維持原樣**。
5. 服務層 `HandleEcpayCallbackAsync` 裡原本的驗簽**保留**（第二道防線），不要因為 Host 驗過就拿掉。
6. **已知限制、本包不修**（寫進報告「我發現但沒做的事」）：行程在 `TryBeginAsync` 之後、Complete／Abandon 之前被殺掉，會留下最長 24 小時的 InFlight 列，期間綠界重送都回 409——這是所有冪等端點共通的既有行為。

- 換 scope 的效果：舊 scope `webhook:ecpay` 的列再也不會被讀到，被偽造請求佔住的列自然失效。**不寫 migration、不刪任何資料。**
- 改寫第 1073～1083 行的註解：說明 #64（驗簽前佔鍵會被偽造請求永久封鎖）、ADR-044、以及為什麼服務層仍保留驗簽。
