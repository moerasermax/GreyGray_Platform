## 盤點結果（2026-09-30）

方法：6 個唯讀代理（五項各一，加一個交叉檢查）。交叉檢查員抽查 12 條關鍵主張，**11 條成立、1 條不成立**（社群登入前端包寫的 `(auth)/login` 路徑不存在，實際是 `(account)/login`，已更正）。Leader 另外親自複驗三點：登入欄位、#60 在 PM 有無前例、波次編號。

### 跟前提不符、要更正的三件事

1. **前台會員是用手機號碼加密碼登入，不是 email。** `docs/api/openapi.storefront.yaml` 第 92 行登入的 `required: [phoneNumber, password]`；`0006_m1a_core.sql` 第 32-53 行的 `customer_credential` 中，`phone_lookup` 與 `password_hash` 都是 NOT NULL，唯一索引是 `(tenant_id, phone_lookup)`。email 是選填、加密存放（第 55-66 行）、**沒有 lookup、沒有唯一性、也沒有驗證流程**。所以社群登入**不能靠 email 自動合併帳號**（會有帳號接管風險），這就是帳號模型要使用者拍板的原因。
2. **IG 做不了一般消費者登入。** Meta 官方文件寫明，Instagram API with Instagram Login 只給「Instagram professionals — businesses and creators」管理自己的帳號（https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login ）。Basic Display API 停用日 2024-12-04 目前只有 Meta for Developers 的 X 貼文當來源，**日期本身尚待確認**，但結論不受影響。
   **「我們有創作者帳號」不會改變結論**（使用者 2026-09-30 提問，Leader 當天回官方總覽頁查證）：
   https://developers.facebook.com/docs/instagram-platform/overview 原文 *"To use the APIs, your **app users** must have an Instagram professional account."*——
   要求的是**登入的那個人**（我們的客人）是專業帳號，不是網站經營者；客人的個人帳號一律不支援。
   而且要服務「不是我們自己擁有的」專業帳號，官方要求 *Advanced Access*，必須通過 *Meta App Review* 加 *Business Verification*（後者要營業登記，目前還沒辦）。
   **創作者帳號能用在自己身上的**（只服務自己的帳號，不需要 Advanced Access）：「追蹤我們」連結、在前台展示自己的 IG 貼文、IG 私訊當客服管道。**使用者 2026-09-30 拍板：IG 相關全部先捨棄**，這三項都不做。
3. **商品描述的程式早就有。** 前台詳情頁會渲染 `shortDescription`／`description`（前端樹 `(shop)/products/[productId]/page.tsx` 第 86-93 行），商品卡顯示 `shortDescription`，後台 `ProductForm` 有兩個欄位。**正式站兩個商品的描述一個是「111」、一個是 null**（2026-09-30 公開 GET）。團隊看到「沒有描述」，主因是**資料沒填**；程式只差一個小缺口：詳情頁用 `<p>` 沒加 `whitespace-pre-line`，換行會被吞掉。

### 新發現的既有風險 #60（PM 過去沒有任何紀錄）

- `Payment.Infra/EcpayGateway.cs` 第 42 行是 `ChoosePayment = "ALL"`，只設了 `ReturnURL`／`ClientBackURL`，**沒有 `PaymentInfoURL`**；`PaymentApplicationService.cs` 約第 208 行只有 `RtnCode == 1` 走收款，其餘一律 `payment.Fail`。（已觀察）
- `Ordering.Core/Order.cs` 的 `PaymentDueAt` 只有第 139 行的宣告與第 590 行的讀取，**從來沒被賦值**，付款期限與逾期提示實際上永遠不會出現。（已觀察）

- 正式站目前用的是綠界測試商店（3002607），沒有真實金流，**不急但開張前一定要結案**。

## 第四十二波各包

### BE-58　分類父子兩層（契約包，高 effort）

**要做的事**

1. **`0023_category_parent.sql`**：`catalog.category` 加 `parent_id uuid null`；複合外鍵 `(tenant_id, parent_id) → category(tenant_id, id)`；`CHECK (parent_id <> id)`；索引 `(tenant_id, parent_id)`；
   **兩層守衛 trigger（先拿每租戶 advisory lock）**；競態被資料庫擋下時 Infra 轉成同樣的 422 碼（覆驗後加，細節見 `docs/59` §1.1、§1.2）。`0023` 原本是 `docs/53` 為 BE-50 預留的號，BE-50 改成開包時取下一號。
2. **Domain 規則（Catalog Core）**：**固定兩層**——`parent_id` 只能指向根分類；已經有子分類的分類不能再被設成別人的子分類。違反時走 `Result` 錯誤（鐵則），錯誤 code 新增。**商品可以直接掛在父分類上**（Leader 代決，理由：營運初期不必為了一兩個商品硬開子分類）。
3. **契約（純新增）**：admin 的 `Category`、`CategoryInput` 與 storefront 的 `Category` 加選填 `parentId`（`Id | null`）；`GET /v1/products` 加選填 `includeDescendants`（boolean，預設 false，保留舊行為）。
4. **一條要在 ADR-041 明文寫下的例外**：`GET /v1/categories` 的「已發布」條件改成「**自己或任一子分類有可售商品**」，否則只有子分類有商品的父分類會消失、前台組不出樹。這改的是既有 operation 的語意，**與 ADR-032「既有 operation 零改動」衝突**，ADR-041 要寫明例外理由：正式站這個清單目前是 `[]`、沒有依賴它的消費者；平面分類（沒有子分類的）行為完全不變。**這一點列為覆驗爭點第 1 條。**
5. `docs/api` 與 `docs/05` **由 Leader 在派工前寫好**、與閘門檔同一個 commit；`check-openapi` 維持綠（operation 集合沒變）。

## 要請覆驗的爭點（派工書寫完後給外部模型逐行覆驗）

1. **ADR-041 的例外**：`GET /v1/categories` 發布條件改語意，還是改成新增參數（例如 `includeAncestors`）維持純新增？Leader 傾向例外，理由是正式站清單為空、平面分類行為不變；覆驗要找反例：**有沒有任何現有呼叫端依賴「只列直接有商品的分類」**。
2. **`password_hash` 可空 vs 佔位雜湊**：可空要保證每一條讀它的路徑都 fail closed；覆驗要列出所有讀取點。
3. **OAuth 回呼與 FB 資料刪除端點**：state cookie 在頂層 GET 導向下的 SameSite=Lax 行為、資料刪除端點免 Origin 的範圍與 rate limit 現況（盤點未查 Storefront Host 的 Origin 允許清單實作位置）。
4. **dev 回呼網址**：Google Web client 是否接受 `http://127.0.0.1`、LINE 是否接受 http 的 localhost；記憶記載登入態走查必須用 `127.0.0.1:5002`。
5. **FE-52 漢堡鈕位置**：結帳與付款頁不放，會不會違反「每頁都要有出口」（#30／#32 的教訓）？結帳頁本來就有 `PageTopBar` 返回鍵，Leader 判斷不違反。
6. **多語系的 cookie 方案對靜態／ISR 頁的影響**。

**免外部覆驗**：FE-51、FE-53。它們**不符合** `docs/45`「小包」的單檔條件，不送外部模型是 Leader 依風險（無契約、無後端、純 UI、可逆）的明文裁量，改由唯讀查證代理逐行核對。BE-59 是查證包，產出本身就是證據，也免。
