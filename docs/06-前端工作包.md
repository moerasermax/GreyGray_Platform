## 工作區：前端有自己的 worktree

前端與後端**共用同一個 repo，但不共用工作目錄**。

| | 路徑 | 分支 | 誰在動 |
|---|---|---|---|
| 後端 | `GreyGray_Platform\` | `feat/contract-freeze-and-frontend-scaffold` | Codex（BE-1 / BE-4 / BE-8 進行中） |
| 前端 | `GreyGray_Platform-fe\` | `feat/frontend-wave-1` | FE-1 ～ FE-8 |

**為什麼不是各自一個 repo**：`docs/api/*.yaml` 同時是前端 codegen 的輸入，
也是後端 CI（`ops/check-openapi.ps1`）拿來斷言 `AddOpenApi()` 實際產物的目標。
兩邊看同一個檔案，「後端偷偷偏離契約」才會在 CI 就被抓到。
拆成兩個 repo 就得複製這份 YAML，而複製品會漂移——那正是凍結契約要防的事。

**對你的實際影響只有兩條**：

1. 你的工作目錄是 `GreyGray_Platform-fe\`。**不要跑去沒有 `-fe` 的那個目錄**改東西，
   那是後端的工作區——在那裡改的東西會混進別人做到一半的變更裡。
2. commit 前先 `git status`，確認清單裡**只有 `frontend/` 底下的檔案**。
   看到 `src/`、`ops/`、`.github/` 出現在你的變更清單裡，代表你走錯樹了，停下來回報。

## FE-1　型別產生、mock server 與端點層
**相依**：無　**獨佔**：`packages/api-client/src/types.*.ts`, `src/mock/**`, `src/endpoints/**`
**已預先授權**：`packages/api-client/package.json` 的 `devDependencies` 可加 `msw`（僅此一處）

**產出**

1. `pnpm api:generate` **已經跑得通、型別也已經產出來了**（storefront 1,776 行／
   admin 2,106 行）。你要做的是確認它們是最新的（契約若有動就重跑），不是重新設定它。
2. `src/endpoints/storefront.ts` 與 `src/endpoints/admin.ts`：
   把每個端點包成具名函式，簽章用產生出來的型別。例如
   `getCampaign(client, campaignId): Promise<CampaignDetail>`。
   **這一層不做任何轉換**——只負責把路徑、query、body 組對，型別接對。
3. `src/mock/**`：用 MSW 攔截，覆蓋**兩份 YAML 裡所有 M1a 端點**。
4. `src/mock/fixtures.ts`：固定的假資料。

**做法要點**

- 假資料要**像真的**：中文商品名（藥妝品項）、真實的台幣金額（`amountMinor` 是分，
  `NT$780` 就是 `78000`）、合理的截團時間、混合現貨與預購的購物車。
  用 `Lorem ipsum` 或 `商品1 商品2` 做出來的畫面看不出版面問題。
- **每個端點都要有錯誤 fixture**：至少一個 422（帶 `errors` 欄位驗證）、
  一個 409、一個 500。前端最常漏的就是錯誤狀態的畫面，沒有 fixture 就不會做。
- mock 要能用環境變數開關（`NEXT_PUBLIC_USE_MOCK=1`），
  後端好了之後**不改任何頁面程式碼**就能切過去。
- 分頁 mock 要真的分頁：`nextCursor` 要能走到第二頁，最後一頁回 `null`。
  只回一頁的 mock 會讓無限捲動的 bug 到上線才出現。

**驗收**
- `pnpm --filter @greygray/api-client typecheck` 綠
- 一個最小 smoke test：對每個 M1a 端點各打一次 mock，回應能通過型別檢查
- 故意打一個會回 422 的 mock，接到的是 `ApiError` 且 `fieldErrors` 有值

| `Avatar` | |

- 每個元件都是 `'use client'` 或純展示的 server component，自己判斷；

- 一頁 `app/_kitchen-sink/page.tsx`（暫時的，交付後由 FE-3 刪掉）展示全部元件的所有狀態

- 鍵盤可以走完整個 kitchen sink，每一步都看得到焦點框
- 內文對比度 ≥ 4.5:1（token 已經幫你選好，用錯的話是你自己換了顏色）

## FE-3　前台：逛與找
**相依**：FE-1, FE-2　**獨佔**：`apps/storefront/app/(shop)/**`

**產出**：首頁 · 分類頁 · 商品列表 · 商品詳情 · 開團列表 · 開團詳情

**做法要點**

- 首頁結構照 ADR-009 的切版：圓角搜尋列 ＋ 頭像 → 柔粉漸層 banner ＋ 圓形產品 →
  橫捲圓形分類標 → 商品卡牆（帶 NEW／人氣標籤與收藏愛心）。
- **商品頁走 SSR**（server component 直接呼叫 BFF），因為 SEO 與 LINE 分享的 OG 標籤靠它。
  互動的部分（收藏、加購）才切 client component。
- 列表用游標式分頁，`nextCursor` 為 `null` 時停止。**不要顯示總筆數**，後端不給。
- 預購商品的 `available` **恆為 0，但仍然可以下單**——
  預購是訂單驅動，下單只登記需求。拿 `available` 擋預購是最容易犯的錯。
- 每個商品配 1–2 句描述、顯示單位價格、統一 1:1 裁切（前台 UX 規則）。

**驗收**
- 商品詳情頁 `view-source` 看得到商品名與描述（證明是 SSR 不是 CSR）
- 列表滾到底會載入第二頁，最後一頁不再打 API
- 一個已截團的團：商品還看得到，但加購鈕是 disabled 並說明原因

## FE-4　前台：買
**相依**：FE-1, FE-2　**獨佔**：`apps/storefront/app/(checkout)/**`

**產出**：購物車 · 配送方式選擇與詢價 · 結帳 · 付款導轉 · 付款結果頁

**做法要點**

- 購物袋一律顯示**含運總額**（`quote.grandTotal`），不是商品小計。
  沒選配送方式前顯示「運費另計」，不要顯示 0。
- 切換配送方式就重新 `POST /v1/cart/quote`。那個端點是純函式、不寫入，可以放心多打。
- **混合訂單**（`hasMixedModes = true`）必須讓客人選 `shippingPolicy`，
  並且說清楚「現貨先出會付兩次運費／等回國一起出省一次」。這是下單時就要問的，不是出貨時。
- **冪等鍵**：結帳表單載入時用 `createIdempotencyScope()` 建一把，
  整個送出流程（含重試）共用，成功後才 `reset()`。
  按鈕連點兩下必須是同一把 key——換 key 重試會變成第二張訂單。
- 付款：拿 `PaymentInitiation` 建 hidden form，把 `fields` **原封不動** POST 到 `action`。
  不要自己組簽章、不要改任何欄位的值、不要少送欄位。
- `explain` 陣列要顯示出來（可摺疊），客服要能直接回答「為什麼收這麼多」。

**驗收**
- 連點結帳鈕五次，只產生一張訂單（mock 要能驗證 `Idempotency-Key` 相同）
- 切換超商／宅配／自取，含運總額跟著變，且都是後端回的數字
- 購物車有一項 `availabilityWarning` 時，結帳鈕被擋下並說明原因
- 網路中斷模擬：顯示 `NetworkError` 的訊息，不是白畫面

## FE-5　前台：我的
**相依**：FE-1, FE-2　**獨佔**：`apps/storefront/app/(account)/**`

**產出**：註冊 · 登入 · 我的訂單 · 訂單詳情 · 收件地址 CRUD · 儲值金餘額

**做法要點**

- **註冊表單的欄位集中在一處**（一個 schema 檔），不要散在多個元件裡。
  欄位本身已經定案（ADR-019，不遷移歷史會員），**不會再變**；
  集中的理由改成：Google 帳號串接排在 M1a 之後，屆時要在同一個註冊流程裡
  插入 OAuth 的入口，散在多個元件會很難改。
- **老客人會發現自己要重新註冊、看不到舊訂單**（歷史資料不遷移）。
  註冊頁要有一句話說明「舊訂單請到原平台查詢」，不要讓人以為資料弄丟了。
  文案的實際期限等舊平台租約到期日確認後補上。
- 登入失敗一律顯示「手機號碼或密碼錯誤」，**不要區分帳號不存在與密碼錯**——
  區分了等於送對方一份帳號列舉工具。這條後端也守著，前端不要自作聰明還原細節。
- 訂單狀態有九個，畫一條時間軸。**`Cancelled` 不在主線上**，要另外處理。
  `switch` 一定要有 `default`（後端新增狀態不算破壞性變更）。
- 訂單詳情要顯示 `paymentDueAt` 倒數（逾期未付會自動取消），
  但**倒數歸零不要自己把畫面改成已取消**——重新 `GET` 拿後端的狀態。
- 缺貨退款的 line 要看得出來：`status = Unavailable` ＋ `refundedAmount`，
  並說明「其餘品項照常出貨」。客人最怕的是以為整張單沒了。
- 儲值金餘額旁要說明「退款選儲值金零手續費、下次可直接折抵」。

**驗收**
- 九個訂單狀態各有一組 fixture，時間軸都畫得出來
- 塞一個 mock 回未知的 `status` 值，畫面顯示原始字串而不是崩掉
- 表單驗證錯誤（422）的 `errors` 對應到正確的欄位下方

## FE-6　後台：殼、登入與營運儀表板
**相依**：FE-1　**獨佔**：`packages/ui/src/admin/**`, `apps/admin/app/(dash)/{layout,page}.tsx`, `apps/admin/app/login/**`

**產出**：AppShell（側邊欄 ＋ 頂列）· 登入頁 · 首頁儀表板 · 後台元件庫

後台元件庫（**就這些**）：
`DataTable`（密、可排序、空狀態、載入骨架）· `StatusPill`（訂單／團／付款狀態共用）·
`MoneyCell`（tabular-nums、右對齊）· `DirectionCell`（借／貸，**顏色之外一定要有文字**）·
`FilterBar` · `KpiTile` · `Drawer` · `Dialog` · `Toast` · `EmptyState` · `ErrorState` ·
`Field` / `Input` / `Select` / `DateRangePicker`

**做法要點**

- **首頁最重要的一塊是「負債 vs 現金」**（`GET /v1/ledger/liability-vs-cash`）。
  `isBreached = true` 代表正在用還沒交貨的錢過日子——這是代購生意最典型的崩壞前兆，
  要放在進來第一眼就看得到的位置，不要塞進第三個分頁。
- 角色檢查：每個端點的 `x-required-role` 決定選單顯不顯示。
  **但前端隱藏只是體驗，不是安全**——真正的檢查在後端，不要因為前端擋了就假設安全。
- 深色模式要做（對帳常常是晚上的事）。token 已經備好，`data-theme` 切換。
- 金額欄位一律 `MoneyCell`，禁止直接印字串。位數對不齊時掃一整欄要逐格重新對焦。

**驗收**
- 淺色與深色兩套都跑過對比度，正文 ≥ 4.5:1
- `DataTable` 在 20 列與 0 列都正常（0 列是 `EmptyState` 不是空白）
- 首頁在 `isBreached = true` 的 fixture 下有明顯的警示

## FE-7　後台：商品與開團
**相依**：FE-6　**獨佔**：`apps/admin/app/(dash)/catalog/**`, `apps/admin/app/(dash)/campaigns/**`

**產出**：分類 · 商品列表／建檔／編輯（含 SKU）· 開團列表／建檔／編輯 · 開團商品 · 狀態操作

**做法要點**

- 商品建檔的 `weightGram` 與 `size` **設成必填**。M1a 運費一口價用不到，
  但 M3 啟用材積重計費時資料就已經在那裡——回頭補幾百筆商品尺寸是純粹的浪費。
  表單上要寫一句話說明為什麼現在要填，否則使用者會覺得多此一舉而亂填。
- 開團的四個狀態操作（publish / close / cancel / settle）各有前置條件，
  **不要在前端判斷**——照後端回的 `status` 決定按鈕能不能按，422 的訊息直接顯示。
- `cancel` 要二次確認，且確認文案要說明「該團全部訂單會取消退款，
  但已登錄的旅程成本仍然留在帳上」。
- `sellingPrice` 發布後不可改，UI 要反映這件事（發布後欄位變唯讀）。

**驗收**
- 建一個團 → 加商品 → 發布 → 截團，四步都走得通（mock）
- 對已發布的團嘗試改售價，欄位是唯讀的
- `settle` 在訂單未全部出貨時回 422，訊息完整顯示

## FE-8　後台：訂單與帳務
**相依**：FE-6　**獨佔**：`apps/admin/app/(dash)/orders/**`, `apps/admin/app/(dash)/ledger/**`

**產出**：訂單列表（搜尋／狀態／團篩選）· 訂單詳情 · 整張取消 · 單品項取消 ·
分錄查詢 · 每團毛利 · 負債 vs 現金

**做法要點**

- 訂單詳情要能一眼看出**每個 line 的狀態不同**——缺貨的、已出貨的、待採購的會同時存在。
- 取消時 `refundTo` 兩個選項要說明差別：
  原路退回有手續費、**退成儲值金完全不動金流零手續費**。預設選儲值金。
- **客戶聯絡方式預設遮罩。** 要看明文得另外操作並填寫存取理由，
  每一次讀取都會寫進 audit。UI 要讓人知道這件事，不要偷偷記。
- 分錄畫面：**沒有編輯也沒有刪除**。分錄一經 posted 即不可修改，更正只能開反向分錄。
  這不是遺漏，UI 上要說明。
- 每團毛利的 `grossMargin` 是後端算好的，**不要自己加減六個欄位再對答案**。

**驗收**
- 一張含「已出貨 ＋ 缺貨退款 ＋ 待採購」三種 line 的訂單顯示正確
- 分錄列表的借貸兩欄合計相等（fixture 就要是平的）
- 聯絡方式預設是遮罩的，且畫面上寫明「查看明文會被記錄」

## 衝突處理

1. 需要改共用檔 → **停下來回報**，不要自己改。
2. `packages/ui` 缺元件 → 先確認不是命名不同；真的缺就做在自己的路由資料夾，回報時列出來。
3. 契約與畫面對不上（缺欄位、型別不對）→ **不要自己在前端補**，
   回報清楚缺什麼、哪一頁要用。契約是凍結的，改它要走 `docs/05-API契約.md` 的流程。
4. 兩包都想做同一個元件 → 依所有權表；不在表上的一律回報。

## 交付時要附的東西

- `pnpm typecheck` 與 `pnpm build` 的輸出
- 你動過的檔案清單（用來驗證沒有越界）
- 375 / 768 / 1440 三個寬度的截圖
- **你認為契約有問題的地方**——不要默默繞過，那是最貴的技術債
