## 0. 這一波要解的問題：訂單編號截斷範圍剛好落在 GUID v7 的時戳位元上

**背景**：`Order.cs:567`

```csharp
private static string BuildOrderNumber(OrderId id, DateTimeOffset placedAt) =>
    $"GG{placedAt.UtcDateTime:yyMMdd}{id.Value:N}"[..15].ToUpperInvariant();
```

`id.Value:N` 是 GUID 的 32 字元 hex（無破折號）表示法。`"GG" + yyMMdd(6碼)
+ id.Value:N` 這個字串總長是 2+6+32=40，`[..15]` 取前 15 碼，扣掉 "GG"（2碼）
與日期（6碼），**只留下 `id.Value:N` 的前 7 碼**。

`OrderId.New()`（`OrderingContracts.cs`）呼叫 `Guid.CreateVersion7()`。GUID
v7（RFC 9562）的位元配置是**時戳在前、隨機亂數在後**——這是 v7 GUID
「可依字串／二進位排序反映建立時間」這個設計目的本身要求的：

| 位元範圍 | 內容 | 對應 hex 字元位置 |
|---|---|---|
| bit 0～47（48 bit） | Unix 毫秒時戳 | 第 1～12 碼 |
| bit 48～51（4 bit） | 版本號（固定是 `7`） | 第 13 碼 |
| bit 52～63（12 bit） | 亂數 A | 第 14～16 碼 |
| bit 64～65（2 bit） | 變異位元 | 第 17 碼前半 |
| bit 66～127（62 bit） | 亂數 B | 第 17～32 碼 |

**現在的寫法只取前 7 碼，完全落在「時戳」那個區段裡**（時戳佔前 12 碼，
7 < 12）。48 bit 時戳裡，前 7 碼 hex 只反映高 28 bit（`timestamp >> 20`），
這個值大約每 **2^20 毫秒（≈17.5 分鐘）才會變一次**——同一個視窗內不管
建立幾筆訂單，前 7 碼幾乎必然相同，撞上 `ux_orders_tenant_number`
（`tenant_id, order_number` 唯一鍵）就 500。BE-32 活體驗證時實測：連續／
間隔重試超過 20 次、跨度超過 10 分鐘，全部撞同一個編號。

**修法（已經定死，不要重新設計）**：**改取 hex 字串的「尾端」而不是
「開頭」**——GUID v7 的最後 7 碼（第 26～32 碼）完全落在「亂數 B」那個
62 bit 純亂數區段裡，跟時戳完全無關。改成：

```csharp
private static string BuildOrderNumber(OrderId id, DateTimeOffset placedAt)
{
    var randomSuffix = id.Value.ToString("N")[^7..];
    return $"GG{placedAt.UtcDateTime:yyMMdd}{randomSuffix}".ToUpperInvariant();
}
```

**這個修法刻意維持跟原本完全相同的長度與格式**（`order_number` 欄位是
`varchar(32)`，這個改法連欄位長度都不用動）——只是換了「取 hex 字串的
哪一段」，不改變整體形狀，也不需要動 `db/migrations/`。7 碼純亂數
（28 bit）的碰撞機率是 1/2^28（約 2.7 億分之一），比現在「同一視窗內
幾乎必然撞號」好上天文數字等級，而且不需要引入序號產生器或額外的資料庫
往返（維持現有「不查資料庫就能算出編號」的簡單性）。

**這一波不用管**：BE-32 自驗報告「我發現但沒做的事②」記錄的「HTTP 500
但訂單其實已經寫進資料庫」這個**未查證的觀察**——那份報告自己講得很清楚
這只是觀察到的現象、不是確診的結論，可能是這個撞號 bug造成的表面症狀
（收到 constraint violation 之後某個重試或錯誤處理路徑的副作用），也可能
是完全獨立的另一個問題。**這一波先只修訂單編號本身**，如果動手驗證這一波
的修法時仍然重現那個「500 但資料庫有資料」的現象，代表它是獨立問題，
在自驗報告裡如實記錄、不要在這一包裡動手查（除非五分鐘內就能確認是不是
同一個根因，那種情況才附帶記錄，仍然不需要修）。

## 5. 工作包

### BE-33　修訂單編號 GUID v7 撞號　🔴

**相依**：無　**獨佔**：見 §3

#### 必做 1　`Order.cs:567 BuildOrderNumber` 改取 hex 字串尾端

```diff
- private static string BuildOrderNumber(OrderId id, DateTimeOffset placedAt) =>
-     $"GG{placedAt.UtcDateTime:yyMMdd}{id.Value:N}"[..15].ToUpperInvariant();
+ private static string BuildOrderNumber(OrderId id, DateTimeOffset placedAt)
+ {
+     var randomSuffix = id.Value.ToString("N")[^7..];
+     return $"GG{placedAt.UtcDateTime:yyMMdd}{randomSuffix}".ToUpperInvariant();
+ }
```

長度與格式跟原本完全一樣（`GG` + 6 碼日期 + 7 碼 hex = 15 碼），只是那
7 碼 hex 換成從 GUID 尾端取，不是開頭。

#### 必做 2　補一條迴歸測試：同一視窗內連續建兩張訂單，編號不能一樣

在 `OrderingTests.cs` 新增一個測試（照抄既有 `Checkout_creates_order_idempotently`
的 fixture 建立方式），背靠背用**兩個不同的 `Checkout`**（不同 `CartId`／
`EventId`，其餘欄位可以相同）建立兩筆訂單，斷言：

- 兩次呼叫都成功（`IsSuccess`）
- 兩筆訂單的 `Id` 不同（確認真的是兩筆不同訂單，不是冪等命中同一筆）
- **兩筆訂單的 `OrderNumber` 不同**——這是這一波要保證的核心不變量

寫測試的時候心裡要清楚：這條測試**修好之前應該紅**（因為兩次 `OrderId.New()`
呼叫執行時間差通常遠小於 1 毫秒，一定會撞號），**修好之後應該綠**。
你可以（但不是必須）先在修法之前跑一次這條新測試，貼出紅的證據，再修
`Order.cs`，再貼出轉綠的證據——這是最有說服力的驗證方式，比只寫「我覺得
修好了」有力。

**自驗（寫進 `.dispatch/reports/BE-33.md`）**

1. `dotnet build GreyGray.slnx` 0 警告 0 錯誤
2. 新測試**修法前**跑起來是紅的（貼出實際失敗訊息，證明 bug 真實存在
   且用單元測試就能穩定重現）
3. 修法後：新測試變綠；`ops/test.ps1` 全綠，跟基準 186 比對（這一波
