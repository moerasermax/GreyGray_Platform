## 1. ★★ 雙重入帳的陷阱——這一包最容易做錯的地方

**先讀完這一節再寫程式。**

### 事實

1. 帳務的進貨成本分錄掛在 **`GoodsReceived`** 上，不是掛在 `LotCreated` 上：
   `Ledger.Infra/LedgerEventHandlers.cs:227` 的 `GoodsReceivedLedgerHandler`，
   `DR 存貨(1300) / CR 現金(1100)`。
2. **`LotCreated` 目前零消費者。** 全 repo 沒有任何 `IIntegrationEventHandler<LotCreated>`。
3. 但 `GoodsReceivedInventoryHandler` 建完批號之後**會發 `LotCreated`**
   （`Inventory.Infra/ModuleRegistration.cs:160-172`）。

### 陷阱

「批發進貨也要入帳，所以加一個 `LotCreatedLedgerHandler`」——**這樣寫，代購那條線
會對同一批貨記兩次帳**：`GoodsReceived` 記一次，它引發的 `LotCreated` 再記一次。
存貨與現金雙雙翻倍，而且**現有測試一條都不會紅**，因為現在根本沒有人訂閱 `LotCreated`。

### 要求

新的 `LotCreated` 帳務 handler **必須只在 `Source == LotSource.LocalWholesale` 時入帳**，
`OverseasPurchase` 直接 return（那筆已經由 `GoodsReceivedLedgerHandler` 記過）。
**而且要有一條專屬迴歸測試**：走完整的代購路徑（發 `GoodsReceived`），
斷言 ledger **只有一筆**存貨分錄，不是兩筆。

科目用哪一組不用你決定，`Ledger.Contracts/LedgerContracts.cs:52` 的註解已經定了：
「**兩種模式（出國採購團／本地批發現貨）用的是同一組科目**——唯一的差別是存貨怎麼進來，
那個差別體現在 Saga 的狀態機上，不體現在帳上」。所以批發進貨也是
`DR 存貨(1300) / CR 現金(1100)`，`campaignId` 傳 `null`。

## 2. 冪等：照 BE-36 的形狀抄，不要自己發明

`POST /v1/lots` 是**建立型端點**，副作用會 commit，而且重複建立的後果是
**幽靈庫存 ＋ 一筆多出來的存貨分錄**——跟 #23 重複出貨單同一個形狀，只是這次是錢。

BE-34 審完 33 個 `BffHttp.ExecuteIdempotentAsync` 呼叫點的結論是：
**BFF 那一層的冪等擋不住「key 被 abandon 之後同鍵重試」**，
底層一定要有自己的冪等。BE-36 已經把樣板做出來了，直接抄：

`M1bFulfillmentEndpoints.cs:69-101`（`POST /shipments`）：

1. 沒帶 `Idempotency-Key` → `BffHttp.Problem(new Error("platform.idempotency-key-required", …), StatusCodes.Status400BadRequest)`
   ——**`platform.` 前綴，不是 `request.`**。BE-37 剛把全 repo 對齊，不要走回去。
2. `BffHttp.ExecuteIdempotentAsync(context, idempotency, M1aEndpoints.Scope(context, "lots:create"), input, …)`
3. **把那把 key 傳進模組**，模組存在批號上，同一把鍵重送回**原本那一張**。
4. `.AddEndpointFilter(new M1aEndpoints.StaffRoleFilter(StaffRole.Operator))`

**★ 明確禁止的方向（Leader 已判斷，不要走）**：

- **不要用 `(tenant_id, sku_id, quantity, unit_cost)` 之類的自然鍵。**
  同一個 SKU 一週進三次貨、每次數量成本都一樣，是**日常**。
  這跟 BE-36 否決自然鍵是同一個理由，只是這次更明顯。
- **不要用 BE-35 的兩階段多載。** 失敗的鍵會留在 `IN_FLIGHT`（retention 24 小時），
  店員同鍵重送一律 409，唯一出路是換新 key——而換新 key 正好繞過你要加的模組冪等。
