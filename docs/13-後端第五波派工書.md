### BE-9　M1b-3　帶回入庫與旅程成本

**相依**：M1b-1（已交付）　**獨佔**：見 §2

**範圍**（依 `docs/10` §1：輸入 `GoodsReceived`、`TripCostRecorded`；
輸出 批號成本、Ledger 分錄、訂單待出貨）

**必做**

1. `Inventory` 建立自己的 aggregate、repository、DbContext 與唯一公開組合根。
2. 消費 `procurement.ItemPurchased.v1`，帶回入庫時建立批號並結轉實際成本。
3. 旅程成本登錄：機票、住宿、交通等實際發生的成本要能記進該團。
   **藍圖講得很清楚：旅程取消時「已發生的旅程成本仍要入帳（那是實際損失，不能假裝沒發生）」**——
   所以旅程成本不是訂單的附屬，它有自己的生命週期。
4. Ledger 分錄：照 `docs/02-事件與狀態機.md` 的帳務分錄，**不要自己發明科目**。
5. 訂單所有 line 都入庫後轉「待出貨」。
6. 業務資料與整合事件必須由**同一個 DbContext transaction** 寫入。
7. `0008_m1b_inventory.sql`，維持 tenant composite key、schema owner 與最小權限慣例。
   **每一份 migration 都要有 `SET ROLE greygray_owner` 與 owner 斷言**，少了它權限會是零。

**明確不做**

- **M2 的 `lots` 兩個端點**。契約已定但實作刻意延後（CLAUDE.md「已經定了」那節）。
  你只做 M1b-3 需要的最小批號面，不要把 M2 拉進來。
- `Ordering` 的 STOCK 分支（那是 M2）。
- 出貨、物流、運費成本（那是 M1b-4）。
- 匯率換算的規則引擎。原幣與記帳幣**都由呼叫端傳進來**，你只存不算。

**做法要點**

- 成本一律 `Money`。**看到 `decimal` 或 `double` 出現在成本位置就是 bug**，不管多方便。
- 「帶回入庫」是 at-least-once 的事件消費，**必須冪等**：同一個 `ItemPurchased` 重送
  不得建立兩個批號。這是硬性契約（藍圖：所有 consumer 必須冪等）。
- 旅程成本要能分攤到團，但**分攤規則不要自己發明**——
  `docs/02` 沒寫的就停下來回報，不要挑一個「看起來合理」的。
- 禁止跨 schema JOIN。要 Procurement 的資料就走它的 `*.Contracts` 查詢介面。

**自驗（逐條貼出實際指令與實際輸出，不是「已完成」四個字）**

1. `dotnet build .\GreyGray.slnx` —— 0 error **0 warning**
2. `.\ops\test.ps1` —— 既有 125 條全過，你新增的另計
3. 全 repo 搜 `decimal` 與 `double`，確認沒有出現在金額或成本位置
4. 全 repo 搜 `DateTimeOffset.UtcNow`，確認只出現在 `IClock` 的實作裡
5. `0008_*.sql` 有 `SET ROLE greygray_owner` 與 owner 斷言（貼出那幾行）
6. **冪等測試**：同一個 `ItemPurchased` 送兩次，斷言只有一個批號。
   跑真 PostgreSQL 17 Testcontainers，**不要用 EF InMemory**——
   它不執行 CHECK constraint，而帳務的不變式正是靠 constraint 守的
7. **注入一次違規再改回來**：讓 `Inventory.Core` 參考 `Ledger.Core`，
   確認架構測試**變紅**，再改回來。貼出紅的那次輸出。
   （上一輪在這裡踩過坑：編譯器會把沒用到的參考裁掉，所以要真的用到它才算數）
8. 分錄的借貸兩欄合計相等（貼出斷言）

## 5. BE-11 卡住的兩個決策（要老闆拍板，不是子代理能決定的）

`docs/10` §3 已經指出退款去向的契約缺口。查過藍圖之後，
**這個缺口其實是兩個問題，而且第二個比第一個嚴重。**

### 問題一：缺貨退款的去向，由誰選？

| 證據 | 說的是什麼 |
|---|---|
| 藍圖 · 補償路徑 | 「該 OrderLine 取消並退款（**客人自選**原路或儲值金）」 |
| `docs/06` FE-8 | 後台取消對話框有 `refundTo` 兩個選項，**預設儲值金**（營運選） |
| `docs/10` §3 | 兩條路：unavailable request 增加 `refundTo`；或另建「待客戶選退款方式」流程 |

**藍圖說客人選，現有的後台契約是營運選。這兩個不是同一件事。**
若採「客人選」，要新增一個等待客戶回覆的流程；
但藍圖同時強調系統**不應該**因為等客人而卡住——兩者要怎麼並存，需要決定。

### 問題二：M1b 的時候，「退成儲值金」這個選項到底存不存在？

**這題是我查藍圖時發現的，`docs/10` §3 沒有提到，但它可能讓問題一的答案失效。**

| 證據 | 說的是什麼 |
|---|---|
| 藍圖 · 落地里程碑 | **儲值金排在 M3**（「運費規則引擎 ＋ 藍新與 LINE Pay ＋ **儲值金** ＋ Reporting ＋ Audit ＋ 退貨入庫」） |
| 藍圖 · 補償路徑 | 退款走儲值金 → `RefundRequested(to=CREDIT)` → DR 預收貨款 / CR 客戶儲值金，零手續費 |
| `docs/06` FE-8 | 後台預設就是選儲值金 |
| ADR-019 更正（`0add0dc`） | 舊平台儲值金餘額為 0 |

也就是說：**M1b-2 需要一個退款去向，而預設的那個去向排在 M3 才做。**
三種可能，要選一種：

1. **把儲值金的最小面從 M3 拉到 M1b**——只做「餘額 ＋ 兩個分錄方向」，
   到期規則、儲值、查詢等等仍留在 M3
2. **M1b-2 只做原路退款**，`refundTo` 這一版只有一個合法值；
   FE-8 現有的「預設儲值金」UI 要跟著改（前端要回工）
3. **M1b-2 先不做缺貨補償**，整包延到 M3 之後

**我的建議是第 1 條。** 理由：藍圖把零手續費寫成儲值金的主要價值，
每一筆缺貨退款都走原路等於每筆都付手續費；而「餘額 ＋ 兩個分錄方向」
本來就是 Ledger 既有科目的用法，不需要新的帳務路徑（ADR-008：Payment 不記帳）。
**但這是錢的決定，不是我的決定。**

> 附帶一提，這題跟 CLAUDE.md 那節「沒有系統會提醒你的那一件」是同一筆帳：
> 舊平台儲值金餘額雖然確認為 0，但只要系統開始發儲值金，那就是你欠客人的負債，
> 要在 Ledger 開期初分錄留痕。決定第 1 條的話，這件事要一起做。

## 6. 自驗與總驗收

### 每一包交付時，子代理自己要跑並貼出輸出

```powershell
dotnet build .\GreyGray.slnx      # 必須 0 error 0 warning
.\ops\test.ps1                    # 現有 125 條必須全綠，你自己新增的另計
```

外加該包 §4「自驗」段落列的每一條，**逐條貼出實際輸出**。

**特別要求**：任何斷言「某件事不存在／不會發生」的測試，
都要**注入一次違規、看它變紅、再改回來**。這條踩過坑——
第一版架構測試用組件參考寫，故意注入違規之後仍然全綠，
因為編譯器把沒用到的參考裁掉了。

### 交付完就停

**自驗全過之後，你的工作就結束了。** 不要往下做下一包，不要「順手」修別的東西。
這條踩過坑：Codex 曾經越波次——交付後不停手、自己往下做，
結果驗收得先把兩件事的變更拆開才驗得動。

### 總驗收（由整合者做，不是由子代理自己說了算）

```powershell
dotnet build .\GreyGray.slnx
.\ops\test.ps1
```

加上這十條逐項檢查：

1. `git diff --stat` 是否有越出所有權表的檔案（**要區分越界與正常的跨波修改**）
2. 全 repo 搜 `decimal` 與 `double`，確認沒有出現在金額位置
3. 全 repo 搜 `DateTimeOffset.UtcNow`，確認只出現在 `IClock` 的實作裡
4. 全 repo 搜 `new JsonSerializerOptions`，確認只出現在 `GreyGrayJson` 裡
5. 每一份新 migration 都有 `SET ROLE greygray_owner` 與 owner 斷言
6. `SET LOCAL`（不是 `SET`）確實出現在 dispatcher 的租戶設定上
7. 注入一次架構違規，確認架構測試會紅
8. `KnownEventTypes` 數量與 `docs/02-事件與狀態機.md` 的事件目錄逐條比對
9. `AddOpenApi()` 的產出與 `docs/api/openapi.*.yaml` 的差異
   （**用修好里程碑過濾之後的 `ops/check-openapi.ps1`**，不要再把 M2 的缺漏算進來）
10. 服務清單有沒有 `GreyGray-Web-Storefront` 與 `GreyGray-Web-Admin`（5002／5003），
    且找不到 node 時是明確 FAIL 而不是 silently skip

**任何一條不過就退回，不做部分接受。**

驗收結論寫進 `GreyGray_PM/03-驗收紀錄.md`，再更新 `00-進度總表.md` 與 `web/dashboard.html`。
**交付方不能自己標 ✅**（`GreyGray_PM/README.md`）。
