|---|---|---|---|---|

### 1.3 服務

- `InitiateAsync`（順序很重要）：
  1. 有效付款是 5：未逾期（`now < ProviderExpiresAt + 1 秒`）→ 回 **`payment.instructions-already-issued`**（不開新單、不動資料；HTTP 409 由 BE-63 明給，`BffHttp.StatusFor` 不會自動對到 409）；已逾期 → `ExpireInstructions`、**先 SaveChanges**、照常開新單。
  2. Pending 沿用時，**`request.Method` 與 `payment.Method` 不同** → `Supersede`、先 SaveChanges、開新單（同一個 `MerchantTradeNo` 不能送不同的 `ChoosePayment`）；相同 → 照現況沿用。
  3. 非信用卡且 `PaymentInfoUrl` 為 null → `payment.payment-info-url-required`。
- `HandleEcpayPaymentInfoAsync`（取號通知）：共用 BE-61 的驗簽私有方法；找付款；拒 SimulatePaid；金額照舊；**不套時間窗**；`PaymentType` 前綴的方式必須等於 `payment.Method`（不同 → `payment.payment-method-mismatch`）；取號成功 RtnCode（依方式：ATM 2；超商代碼／條碼 10100073）→ 解析並 `IssueInstructions`，**狀態真的改變才**發一次 `PaymentInstructionsIssued`。
  - ATM `ExpireDate`（`yyyy/MM/dd`）→ 當天 **23:59:59** 台北；超商代碼／條碼照字面台北時間；都用 `TaipeiTime.Zone` 取偏移後 `ToUniversalTime()`。`InstructionsIssuedAt` 用 `IClock`，**不用** `TradeDate`。
  - 其他 RtnCode（取號失敗）→ 照 1.2 的 `Fail` 規則（Pending → Failed＋`PaymentFailed`，讓客人能重新發動）。
- `HandleEcpayCallbackAsync`（付款結果）：
  - **時間窗依通知的 `PaymentType` 前綴決定**：`ATM_`／`CVS_`／`BARCODE_` 不套；其他（含 `Credit_`、缺欄位）照套。`payment.Method` 不為 null 時，前綴的方式必須一致（不同 → `payment.payment-method-mismatch`）。這樣 `Method` 為 null 的舊付款（舊流程送過 `ALL`，可能是 ATM）也不會被誤擋。
  - 取號成功的 RtnCode（2／10100073）送到**付款結果**路由 → 回業務失敗 `payment.unexpected-payment-info`、不改資料（ADR-044：事件類型由路由決定，不靠 RtnCode 猜）。
- **併發**：取號與付款結果、或任兩個通知同時改同一筆時，`Status` 是 concurrency token——兩個處理方法的 SaveChanges 若遇 `DbUpdateConcurrencyException`，回業務失敗 **`payment.concurrent-update`**（Host 會 Abandon，綠界重送時以最新狀態重新判斷）。事件必須和狀態在**同一次** SaveChanges 落地（確認 `eventPublisher` 是交易式 outbox；不是的話停下來回報）。
- **不改**建構子、`EcpaySettings`。
