## 1. 要做的事

1. **設定**：Core 新增具名的期限設定（例如 `OrderingPaymentDeadlines`：`PaymentDue` 預設 24 小時、`NonCardGrace` 預設 2 天，提供 `Default`）；`ModuleRegistration` 讀 `Ordering:PaymentDueHours`、`Ordering:NonCardPaymentGraceDays`（必須 > 0，否則啟動丟例外）。傳進 `OrderingApplicationService` 用**選填參數、`null` 代表 `Default`**——**不准**用 `TimeSpan x = default`（沒傳的測試會拿到 0、訂單一建立就逾期）。
2. **Order 聚合**：
   - 新欄位 `PaymentAutoCancelAt`（內部、不進契約）、`CancellationSource`（`OrderCancellationSource`：`Customer`、`Staff`、`PaymentExpired`；放 Ordering.Contracts，值給明確數字）。
   - 建單：`PaymentDueAt = PaymentAutoCancelAt = PlacedAt + PaymentDue`。
   - 收到取號：只在 `AwaitingPayment` 且方式不是信用卡時套用——`PaymentDueAt = ExpiresAt`、`PaymentAutoCancelAt = ExpiresAt + NonCardGrace`；其他情況 no-op（不丟例外）。
   - 逾期：只在 `Status == AwaitingPayment && PaymentAutoCancelAt != null && now >= PaymentAutoCancelAt` 時取消（來源 `PaymentExpired`、固定原因「逾期未付款，系統自動取消」）；其他一律 no-op。
   - 客人取消 → 來源 `Customer`；後台取消 → `Staff`。**寬限期間客人仍可自助取消**（訂單還是待付款）。
   - **取消之後才入帳**：`CapturePayment` 在 `Cancelled` 時不失敗——**金額仍必須等於 `GrandTotal`**（不准為了放行而繞過第 221～225 行的檢查）、記 `PaidAmount`、維持 `Cancelled`、回傳「取消後入帳」；`Completed` 維持原本的失敗。
   - 自助取消被拒時的訊息改成同時涵蓋「已付款」與「已取消」（例如「這筆訂單目前不能自助取消，如有問題請聯絡客服。」）；**錯誤碼不變**。
3. **服務層**：
   - 建單排 `ordering.payment-due` 計時器（`saga_id` 用 `order.Id.ToString()`、`fire_at = PaymentAutoCancelAt`、payload `"{}"`），比照鑑賞期「先排、再 SaveChanges」；`timerScheduler` 為 `null` 時跳過（既有測試的建構方式不必改）。
   - 收到 `PaymentInstructionsIssued`：handler **必須用 `AddIdempotentIntegrationEventHandler<PaymentInstructionsIssued, …, OrderingDbContext>` 登記**（它開的交易讓 `ScheduleAsync` 的 raw SQL 與訂單更新一起 commit 或一起 rollback；直接登記的話計時器會先自動提交，訂單存檔失敗就留下孤兒）；套用期限後**再排一個新計時器**到新的 `PaymentAutoCancelAt`。**不准呼叫 `CancelAllForSagaAsync`／`CancelAsync`**（dispatcher 用另一條連線鎖住正在觸發的那一列，同一列再更新會互等、Postgres 偵測不到；建單／取消路徑沒有明確交易）——舊計時器觸發時由「`now < PaymentAutoCancelAt` → no-op」擋掉。找不到訂單 → 記 log、no-op。
   - 逾期計時器 handler（Infra，比照 `AppraisalPeriodTimeoutHandler`，注入 internal 服務）：取消時走既有的 `PublishCancellationAsync`（發 `OrderCancelled`，未付款所以不發退款），庫存由 Inventory 照常釋放。**業務上不需要取消（孤兒、已付款、已取消、還沒到期）一律 no-op、不准丟例外**（會卡住整條計時器佇列，含鑑賞期與詢價逾時）；**樂觀鎖衝突必須往上拋**（吞掉的話 dispatcher 照寫 `fired_at`，訂單永遠不會取消）。
   - `PaymentCaptured` 遇到「取消後入帳」：**只**發一筆 `RefundRequested`（金額＝這次入帳的 `PaidAmount`，不要重新取 `GrandTotal`；`OriginalPaymentMethod`；原因寫明「取消後才入帳，原路退款」），**不准發 `OrderPaid`、`OrderReadyToShip`**、不重新保留庫存，不丟例外。
   - `OrderCancelled` 加選填 init 屬性 `Source`（`OrderCancellationSource?`，舊事件為 `null`），`PublishCancellationAsync` 帶入。**事件型別名與事件數不變**（docs/02 已補記）。
   - `OrderView` 補 `CancellationSource`（與 `CancelledAt`，若還沒有），供 BE-68 交給 API。**不要動 `IOrderingApplication` 的方法清單。**
4. **樂觀鎖**：Order 加 `xmin` row version（比照 Campaign）。**只改品項的操作也必須讓父 Order 參與版本檢查**（例如 `SaveChangesAsync` 時把有子項變更的 Order 標成 Modified，讓 UPDATE 帶 `xmin` 條件；或另一種你能用測試證明等效的做法）——否則取消先提交後，舊快照的出貨仍能把已取消的品項改成已出貨。`OrderingDbContext` 覆寫 `SaveChangesAsync`，把 `DbUpdateConcurrencyException` 轉成 Ordering.Core 新的併發例外。給 HTTP 用的取消類方法（客人取消、後台取消、取消品項、短缺退款）接住它回 `Result.Failure("ordering.concurrent-update", …)`；**事件 handler 與計時器 handler 不接**（讓 outbox／dispatcher 重試）。
5. **migration `db/migrations/0025_ordering_payment_due.sql`（新檔）**（`SET ROLE greygray_owner`；可重放）：
   - `ordering.orders` 加 `payment_auto_cancel_at timestamptz`、`cancellation_source smallint`（＋`CHECK (cancellation_source IS NULL OR cancellation_source IN (…))`，值與 enum 一致；用 `DROP CONSTRAINT IF EXISTS` 再 `ADD`）。
   - **回填**：單一敘述 `WITH b AS (UPDATE ordering.orders SET payment_due_at = placed_at + interval '24 hours', payment_auto_cancel_at = placed_at + interval '24 hours' WHERE status = 0 AND payment_due_at IS NULL RETURNING id, tenant_id, payment_auto_cancel_at) INSERT INTO platform.saga_timer (id, tenant_id, saga_type, saga_id, fire_at, payload, created_at) SELECT gen_random_uuid(), tenant_id, 'ordering.payment-due', replace(id::text, '-', ''), GREATEST(payment_auto_cancel_at, now() + interval '1 hour'), '{}'::jsonb, now() FROM b;`——**沒有 JOIN**（形狀同 ADR-016「一個交易寫兩張表」）；冪等靠 `payment_due_at IS NULL`（重放時 UPDATE 0 列、不會再排）；`fire_at` 至少 migration 執行時間＋1 小時（migration 在停服前執行，舊 Worker 不認得新的 saga type）。欄位與型別以 `0002` 的 `saga_timer` 定義為準，對不上就停下來回報。
   - `ops/install-dev-environment.ps1` 清單補 `0025`；`ops/verify-environment.ps1` 期望數量 24 → 25。
6. EF 對應新欄位；`OrderingDbContext` 的 `xmin`。
